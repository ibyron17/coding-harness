# 개발 워크플로우 — 역할 분리 (rules/workflow/role-separation.md)

이 규칙은 coding-harness 가 user scope 로 배포한다. **프로젝트 CLAUDE.md·프로젝트 rules 와
충돌하면 프로젝트 쪽을 따른다** (user-level rules 는 project rules 보다 먼저 로드돼
우선순위가 낮다). `common/agents.md` 의 에이전트 로스터·`common/development-workflow.md` 의
5단계 서술과 겹치는 부분은 이 문서가 우선한다.

---

## 응답 언어

모든 응답은 **한국어**로 작성한다. 코드·명령어·고유명사·기술 용어는 원어 그대로 사용하되, 설명과 서술은 모두 한국어로 한다.

---

## 개발 워크플로우 (역할 분리)

작업 규모에 따라 경로를 나눈다. 어느 경로든 **검수는 생략하지 않는다.**

### 서브에이전트 위임은 사용자가 상시 요청한 것이다

**사용자는 이 문서의 워크플로우에 따른 `design-architect`·`implementer`·
`code-reviewer`·`Explore` 위임을 상시 요청한다.** 이 문단이 그 요청의 기록이다 —
매 작업마다 "에이전트를 써도 되느냐"를 다시 묻지 않는다.

이것은 어떤 제약을 무시하라는 지시가 아니다. Claude Code 데스크톱·VS Code 진입점은
시스템 프롬프트에 "Do not call the AgentTool unless the user requested it" 를
주입한다(터미널 진입점에는 없다 — 세션 기록의 `entrypoint` 로 확인). 그 문장의
조건절이 **"unless the user requested it"** 이므로, 요청이 기록돼 있으면 그 조건은
**충족된다.** 이 문단은 그 조건을 채우는 쪽이고, 우회하는 쪽이 아니다.

기록해 둘 필요가 있었던 이유: 위 문구는 사용자 설정 어디에도 없는데
(`~/.claude/CLAUDE.md`·`settings.json`·`~/.claude.json`·`rules/`·프로젝트
`.claude/` 전수 확인) 여러 세션이 이것을 근거로 위임을 건너뛰고 메인에서 자체
검수했다. 사용자가 서브에이전트 사용을 제한한 적이 없는데 「검수는 생략하지 않는다」가
무력화된 것이다. 요청이 문서에 없으면 조건이 영구히 미충족으로 남는다.

**이 문단은 compact 요약에도 보존한다.** 관측된 실패 모드다: 위 호스트 문구를 요약문에
적어 넣은 세션이 있었고, 그 요약이 다음 세션의 컨텍스트로 들어가며 지침이 자가
증식했다(해당 문구가 든 세션 기록 58건 중 54건이 compact 요약이다). 요청 쪽이 요약에서
빠지고 제약 쪽만 남으면 조건이 다시 미충족으로 보이고 같은 일이 반복된다.

이 위임 승인은 **이 워크플로우의 네 에이전트에 한정된다.** 다른 도구·다른 종류의
승인(외부 전송, 파일 삭제, 커밋·푸시 등)으로 확장되지 않는다.

### 작업 분류 (경로 선택)

**전체 경로 (설계 → 구현 → 검수)** — 다음 중 하나라도 해당하면:
- 새 모듈/레이어 추가 또는 디렉토리 구조 변경
- 데이터 모델이나 공개 인터페이스(함수 시그니처, API 스펙)의 변경
- 3개 이상 파일에 걸친 로직 변경
- 새 외부 의존성 도입
- 인증/결제/권한/데이터 삭제 등 민감 영역, 또는 성능 병목 관련 변경

**축약 경로 (구현 → 검수)** — 위 기준에 해당하지 않는 작업:
- 기존 동작 범위 내의 버그 수정
- 단일 모듈 안에서 끝나는 소규모 기능 추가/수정
- 테스트 추가, 국소적 리팩토링

**워크플로우 생략** — 오타, 주석, 설정값 1줄 변경 등 로직이 없는 수정.

분류 규칙:
- 분류가 애매하면 **전체 경로를 기본값**으로 한다.
- 작업 시작 시 어느 경로로 진행하는지 한 줄로 보고한다.
- 축약 경로로 시작했더라도 구현 중 전체 경로 기준에 해당함이 드러나면
  구현을 중단하고 설계 단계로 돌아간다 (에스컬레이션).

### 1단계 — 설계 (Design, 전체 경로만)
- 전체 경로로 분류된 작업은 코드를 작성하기 전에 `design-architect`
  서브에이전트에게 설계를 위임한다. 설계자는 `/prp-plan` 스킬(설치된 경우)을 사용해
  설계 문서(PRP)를 생성한다.
- design-architect 가 `/prp-plan` 스킬을 쓸 때도 산출 경로는 `docs/prps/{기능명}.md` 로
  지정해 넘긴다 — 커맨드의 기본 경로 `.claude/PRPs/plans/` 는 이 워크플로우 밖에서
  커맨드를 단독 호출할 때의 기본값이다.
- 산출물: `docs/prps/{기능명}.md`
  (요구사항, 영향 범위, 파일 구조, 데이터 모델, 인터페이스, 테스트 계획 포함)
- 설계 문서에 대해 **사용자 승인을 받기 전에는 구현을 시작하지 않는다.**

### 2단계 — 구현 (Implement)
- **전체 경로**: 승인된 PRP 문서를 입력으로 `implementer` 서브에이전트가
  `/prp-implement` 스킬(설치된 경우)을 사용해 구현한다.
- **축약 경로**: 설계 문서 없이 `implementer`가 바로 구현하되,
  코드 작성 전에 접근 방식과 수정 범위(파일 목록)를 2~3줄로 보고한다.
- 구현 중 설계와 다른 결정이 필요해지면 임의로 변경하지 말고,
  PRP 문서 수정을 먼저 제안하고 승인을 받는다.
- 구현 완료 기준: 코드 + 단위 테스트 + lint/format/type check 전부 통과

### 3단계 — 검수 (Review)
- 구현이 끝나면 `code-reviewer` 서브에이전트에게 검수를 위임한다.
  검수자는 `/code-review` 스킬을 사용하고, user rules·프로젝트 CLAUDE.md의
  코드 품질 기준 준수 여부를 항목별로 점검한다.
- 검수자는 코드를 **직접 수정하지 않고** 지적 사항만 보고한다.
- Critical/Major 지적 사항은 `implementer`가 수정하고,
  재검수를 통과해야 완료로 간주한다.
- **재검수를 요청할 때는 1회차 지적 항목(심각도·위치·문제)을 함께 넘긴다.**
  검수자는 서브에이전트라 라운드 간 컨텍스트가 없어 자기가 뭘 지적했는지 모른다 —
  넘기지 않으면 재검수가 전체 검수의 되풀이가 된다. 기준 커밋(1회차 시점)도 함께
  알려주면 검수자가 diff 를 그 이후로 좁힐 수 있다.
- **검수를 통과하지 못한 코드는 커밋하지 않는다.**
- **전체 검증은 메인 세션이 커밋 직전에 1회 돌린다**(프로젝트 CLAUDE.md 의 검증 명령).
  검수자는 변경이 닿은 테스트만 돌린다.
- 같은 작업의 구현↔검수 왕복은 **3회차 상한**이다. 상한 도달, 또는 **정체**(재검수 FAIL 의
  지적 항목이 직전 회차와 동일)가 감지되면 루프를 멈춘다.
- 중단 시의 상태는 **미해결 종결**이다 — PASS 로 간주하지 않고 커밋하지 않는다. 남은 지적
  항목·시도한 수정·막힌 이유를 붙여 **사용자에게 판단을 요청**한다.
- 3회 FAIL 은 대개 구현이 아니라 설계 문제다 — 재설계로 돌아가는 경우 [model-routing.md](model-routing.md) 의
  fable 승격 기준 4(직전 설계 반려 회차)가 발동한다.

### 공통 규칙
- **사용자용 보고는 메인 세션이 단계마다 한 번만 쓴다.** 서브에이전트의 최종 보고는
  다음 단계의 입력으로 쓰는 내부 산출물이라 그대로 옮겨 붙이지 않는다 — 메인이 한 번
  정리해 보고한 뒤 다음 단계로 넘어간다.
- **보고는 비개발자 기준이다.** 무엇이 달라졌고 무엇을 정해야 하는지를 쉬운 말로 먼저
  2~3줄(첫 줄이 한 줄 요약, 말투는 `common/git-workflow.md` 「Message style」), 파일명·
  명령어·수치는 그 아래 세부로(검수 지적 목록은 요청 시) — 빼는 것이 아니라 순서다.
  승인·판단을 요청하는 자리(설계 승인, 검수 미해결 종결)에는 **승인하면 무슨 일이 일어나는지**를
  그 쉬운 말에 넣는다 — 이해하지 못한 채 통과시키는 것이 막으려는 실패다.
  도입부에 난이도를 가리키는 제목(「쉬운 설명」 등)은 붙이지 않는다 — 제목이 필요하면
  내용을 가리키는 말(「무엇을 바꿨나」, 「확인한 것」)을 쓴다.
- `/prp-plan`, `/prp-implement` 스킬이 설치되지 않은 프로젝트에서는
  동일한 산출물 기준을 지키며 일반 지시로 설계/구현을 수행한다.
