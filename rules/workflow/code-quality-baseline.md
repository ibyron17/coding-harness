# 코드 품질 가이드라인 (rules/workflow/code-quality-baseline.md)

## 코드 품질 가이드라인

### 구조와 모듈화
- 관심사를 레이어로 분리하고, 레이어 간에는 명시적인 데이터 모델
  (dataclass/TypedDict/interface 등 언어에 맞는 타입)로만 통신한다.
  구체적인 레이어 구성은 프로젝트 CLAUDE.md의 아키텍처 섹션을 따른다.
- 외부 세계(네트워크, DB, 파일시스템)에 닿는 코드와 순수 로직을 분리한다.
  순수 로직은 입력→출력만 있는 함수로 작성해 단위 테스트가 가능해야 한다.
- 함수는 한 가지 책임만 갖고 50줄을 넘지 않는다. 넘으면 분리한다.
- 순환 의존이 생기면 구현을 멈추고 구조를 먼저 재검토한다.

### 가독성
- 이름은 축약하지 않는다 (`grp` ✕ → `feature_group` ○).
  이름만 읽고 역할을 알 수 있어야 한다.
- 중첩은 최대 3단계. 그 이상이면 early return이나 함수 추출로 평탄화한다.
- 주석은 "무엇을"이 아니라 "왜"를 설명할 때만 쓴다.
  코드로 표현 가능한 것은 코드로 표현한다.
- 매직 넘버/문자열은 이름 있는 상수로 선언한다.
- 모든 공개 함수에 타입 명시와 한 줄 docstring(또는 언어 관례의 문서 주석)을 붙인다.

### 설계 원칙
- 기본은 가장 단순한 구조다. 디자인 패턴은 구체적인 문제가 있을 때만 도입하고,
  도입 시 어떤 문제 때문인지 그 이유를 모듈 상단 주석으로 남긴다.
- 지금 필요 없는 확장성을 미리 만들지 않는다(YAGNI). 추측성 추상화 금지.
- 상속보다 조합을 우선한다. Singleton, 전역 가변 상태는 사용하지 않는다.
- 새 의존성 추가는 표준 라이브러리로 불가능할 때만, 이유와 함께 제안한다.

### 성능
- 프로젝트의 실제 병목을 기준으로 최적화한다.
  병목이 무엇인지는 프로젝트 CLAUDE.md의 성능 섹션에 정의한다.
  (예: 외부 API 호출, DB 쿼리, 대용량 파일 I/O, 렌더링)
- 정의된 병목이 없으면: 알고리즘 복잡도가 명백히 나쁜 경우
  (불필요한 중첩 루프, N+1 쿼리 패턴)만 바로잡고 그 외 최적화는 하지 않는다.
- 측정 없는 마이크로 최적화는 하지 않는다.
  성능 개선은 병목을 측정한 근거가 있을 때만 수행한다.
- 외부 API를 호출하는 코드는 호출 횟수 최소화, 실패 시 재시도,
  rate limit 대응을 기본으로 갖춘다.

### 강제 수단
- 프로젝트 언어에 맞는 linter/formatter/type checker를 설정하고
  모든 커밋 전에 통과시킨다. 실제 사용하는 도구와 명령은
  프로젝트 CLAUDE.md의 빌드/검증 섹션을 따른다.
- 경고를 무시하는 주석(`# noqa`, `eslint-disable` 등)은 사유 없이 추가하지 않는다.
- 핵심 순수 로직은 단위 테스트를 함께 작성한다.
- 기능 구현 전에 파일 구조와 데이터 모델을 먼저 제안하고 승인을 받는다.
