# 모델 운용 원칙 (rules/workflow/model-routing.md)

### 모델 운용 원칙
- **설계 (design-architect): opus 기본 + 조건부 fable 승격** — 판단 오류의 파급이 가장 큰 단계다.
  승격은 **디스패치 시점의 `model` 인자**로 지정한다 — 에이전트 frontmatter 의 `model: opus` 는
  기본값이고 디스패치 인자가 그보다 우선한다(frontmatter 를 `fable` 로 고쳐 상시 승격하지 않는다).
  아래 중 하나에 해당하면 fable 로 올린다:
  1. 사용자가 프롬프트에 **「심층 설계」** 또는 **「fable 로」** 를 명시했다
  2. 데이터 모델 전면 개편, 또는 3개 이상 서브시스템을 가로지르는 구조 변경
  3. 동시성·분산·상태 동기화처럼 설계 오류의 복구 비용이 특히 큰 영역
  4. **직전 설계가 검수·구현 단계에서 반려돼 다시 설계하는 회차** — opus 가 한 번 실패한 문제다

  **애매하면 승격하지 않는다.** fable 은 토큰당 단가가 2배다($10/$50 vs $5/$25). 이 저장소에서
  같은 설계 과제를 두 모델 × 두 프롬프트(절차 스캐폴딩 유/무)로 돌린 A/B 2회(과제 2종 · 총 6팔 ·
  블라인드 채점)는 **일상적 설계 과제에서 fable 의 품질 우위를 보이지 못했다** — 2회차 1위는
  opus 였다. 승격의 근거는 "fable 이 더 낫다"가 아니라 "난도 상단 문제에 능력 천장이 필요하다"
  이므로, 위 4개에 걸리지 않으면 opus 를 유지한다.

  **어느 모델로 디스패치했는지 착수 보고에 한 줄 남긴다**(예: `설계 모델: fable(기준 4 — 재설계)`)
  — 사후에 회차별로 어느 모델이었는지 추적할 수 있어야 한다.
- **구현 (implementer): sonnet** — 토큰 소비가 가장 큰 단계, 품질/비용 균형
- **검수 (code-reviewer): sonnet 기본** — 인증/결제/권한/데이터 삭제 등
  민감한 변경은 검수 요청 시 opus 승격을 지시.

  **사용자가 프롬프트에 「전수 검사」를 명시하면 fable 로 승격한다.** 여기서 전수 검사는
  diff 범위 검수가 아니라 **저장소 전체를 문서화된 불변식·테스트 계약 전부에 대해 훑는
  감사**를 뜻한다 — 이때만 검수의 지평이 fable 의 측정된 우위 구간("과제가 길고 복잡할수록
  리드가 커진다")에 들어간다. 승격 범위는 **그 감사 디스패치 1회**이고, 뒤따르는 diff 범위
  재검수는 기본값(sonnet, 민감 시 opus)으로 돌아온다. 설계와 마찬가지로 디스패치 시점의
  `model` 인자로 지정한다 — frontmatter 의 `model: sonnet` 은 고치지 않는다.

  **diff 범위 검수는 fable 로 올리지 않는다.** 검수는 병렬화되고 설계는 안 되므로,
  능력을 살 첫 수단은 모델 승격이 아니라 렌즈 분할(검수자 N명 병렬)이다. 가격도
  같은 방향이다 — fable 검수자 1명 = opus 검수자 2명 = sonnet 검수자 5명.
  `docs/prps/model-scaffolding-ab-experiments.md` §6 은 코드 검수가 아니라 **설계
  단계 A/B 실험**의 기록이다 — 있는 것은 독립 심판(opus)이 메인 세션의 접지 판단
  2건을 사후 교정했다는 관찰(n=1)뿐, "검출이 겹치지 않았다"는 재현율 주장이나
  메인 세션의 모델 특정은 원문에 없다. 렌즈 분할의 근거는 그 실측이 아니라 위
  병렬화 가능성·가격 비교다.

  **어느 모델로 디스패치했는지 착수 보고에 한 줄 남긴다**(설계와 동일).
- **탐색 (Explore): haiku** — 수집·요약 전용
- **haiku는 소극적으로 사용한다**: 판단이 필요한 작업(설계, 구현, 검수 판정)에는
  사용하지 않는다. 각 에이전트는 직접 읽기를 기본값으로 하고,
  넓은 범위 탐색이 필요할 때만 Explore에 위임하며,
  판단의 근거가 되는 파일은 요약에 의존하지 않고 직접 읽는다.
