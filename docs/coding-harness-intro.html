coding-harness와 허브

coding-harness는 Claude Code에 설계·구현·검수 절차와 팀 공통 코드 규칙을 얹는 설정 묶음입니다. 허브는 내 컴퓨터에서 돌고 있는 모든 Claude Code 프로젝트의 진행 상황을 한 화면에 모아 보여 주는 대시보드입니다.

저장소: github.com/ibyron17/coding-harness

설치하기 사용하기 좋아지는 점 사용 전후 비교 알아둘 점

설치하기

처음 한 번만 하면 됩니다. 명령은 어느 폴더에서 실행해도 됩니다.

Claude Codegit저장소 접근 권한허브를 쓸 경우 python3 3.10 이상
저장소 주소
https://github.com/ibyron17/coding-harness

방법 1. Claude에게 말로 맡기기

Claude Code 입력창에 아래 문장을 그대로 붙여 넣습니다. Claude가 저장소를 받고, 무엇이 설치될지 먼저 보여 준 뒤, 확인을 받아 설치합니다.

Claude Code 입력창
https://github.com/ibyron17/coding-harness 저장소를 ~/works/coding-harness 에 받아서 --scope user 로 설치해줘. 설치 전에 --dry-run 결과를 먼저 보여줘.

허브도 쓰려면 이어서 “허브도 설치해줘”라고 하면 됩니다.

방법 2. 터미널에서 직접 설치하기

  1. 저장소 받기

    설치할 프로젝트 안이 아니라 바깥 폴더에 받습니다.

    터미널
    git clone https://github.com/ibyron17/coding-harness.git ~/works/coding-harness

  2. coding-harness 설치

    첫 줄은 무엇이 설치될지 보여 주기만 하고, 둘째 줄이 실제 설치입니다. 규칙 46개, 에이전트 4개, 명령 8개가 ~/.claude에 들어가 내 모든 프로젝트에 적용됩니다. 원래 있던 다른 파일은 건드리지 않습니다.

    터미널
    ~/works/coding-harness/install.sh --scope user --dry-run
~/works/coding-harness/install.sh --scope user

  3. 허브 설치 선택

    터미널에서 허브 파일을 설치한 뒤, Claude Code 입력창에서 세 명령을 차례로 입력합니다. /hub install은 세션 기록을 모으는 장치(훅)를 등록하는 단계이고, /hub off로 언제든 뺄 수 있습니다.

    터미널
    ~/works/coding-harness/hub/install.sh
    Claude Code 입력창
    /hub install
/hub server start
/hub

업데이트는 한 줄입니다. Claude Code 입력창에 /harness-update를 입력하면 최신 버전을 받아 다시 설치합니다. 허브를 설치했다면 허브도 함께 갱신됩니다.

한 프로젝트에만 쓰고 싶으면 그 프로젝트 폴더에서 --scope user 대신 --scope project로 설치합니다. 이때 프로젝트의 .claude/ 폴더에 파일이 생기므로, 팀 저장소에 커밋할지 미리 정해 두세요.

사용하기

평소처럼 Claude Code에 일을 시키면 됩니다. 절차는 Claude가 알아서 밟습니다.

요청을 받으면 Claude가 먼저 작업 크기를 판단하고, 어느 경로로 갈지 한 줄로 알려 줍니다.

작업 크기예시진행 순서
아주 작음오타, 주석, 설정값 한 줄바로 수정
작음버그 수정, 한 모듈 안의 작은 기능, 테스트 추가구현 → 검수
큼새 모듈, 3개 이상 파일에 걸친 변경, 함수·API 모양 변경, 인증·결제·권한·데이터 삭제설계 → 내 승인 → 구현 → 검수
요청→ 설계 문서→ 내가 승인→ 구현→ 검수→ 통과하면 커밋

검수에서 FAIL이 나오면 구현을 맡은 AI가 고치고 다시 검수를 받습니다. 세 번 안에 통과하지 못하면 멈추고 나에게 판단을 묻습니다. 검수를 통과하지 못한 코드는 커밋하지 않습니다.

내가 할 일은 두 가지입니다. 큰 작업의 설계 문서를 읽고 승인하는 것, 그리고 끝난 결과를 확인하는 것입니다.

직접 입력하는 명령

Claude Code 입력창하는 일
/harness-updatecoding-harness(와 허브)를 최신 버전으로 업데이트
/hub허브 화면 열기
/hub dashboard off
/hub dashboard on		이 프로젝트의 진행 기록(단계·진행률) 끄기·다시 켜기. 처음에는 켜져 있습니다.
/prp-commit“로그인 관련 변경만”처럼 말로 골라서 커밋
/prp-pr브랜치 변경을 정리해 GitHub PR 만들기
/code-review 123번호를 준 GitHub PR을 검수. 내 작업의 검수는 자동으로 돕니다.

/prp-commit·/prp-pr은 AI가 스스로 부를 수 없게 막혀 있어서, 내가 입력해야만 실행됩니다. 그냥 “커밋해줘”라고 말해도 됩니다. 반대로 설계 AI의 /prp-plan, 구현 AI의 /prp-implement, 검수 AI의 /code-review는 각 AI가 필요할 때 알아서 불러 쓰므로 따로 입력할 필요가 없습니다.

요청 문장에 「심층 설계」를 넣으면 가장 강한 모델로 설계하고, 「전수 검사」를 넣으면 저장소 전체를 규칙·테스트 기준으로 훑습니다. 프로젝트 루트의 CLAUDE.md에 개요·구조·성능 병목·빌드와 검증 명령·팀 컨벤션 다섯 가지를 적어 두면, 검수가 그 기준으로 확인합니다.

좋아지는 점

기술적인 내용은 빼고, 실제로 일할 때 달라지는 것만 적었습니다.

coding-harness

코드 품질과 작업 방식

만든 AI가 스스로 채점하지 않습니다

코드를 쓰는 AI와 검사하는 AI가 따로 있습니다. 검사하는 AI는 코드를 고칠 권한이 없고, 문제를 지적할 때마다 실패하는 테스트 같은 증거를 붙여야 합니다.

결함은 커밋 전에 막힙니다

검수를 통과해야만 커밋합니다. 실제 기록에서 첫 구현 3건 중 1건이 이 단계에서 걸려 고쳐졌습니다(아래 비교).

큰 작업은 설계부터 합니다

코드를 쓰기 전에 설계 문서를 보고 승인합니다. 방향이 엇나간 채 한참 진행되는 일이 줄고, 왜 그렇게 만들었는지 기록이 남습니다.

작업 크기에 맞는 절차

오타는 바로 고치고, 작은 수정은 구현과 검수만, 큰 변경만 전체 절차를 밟습니다. 작은 일에 무거운 절차를 씌우지 않습니다.

누가 시켜도 같은 기준

함수 길이, 중첩 깊이, 테스트 먼저 쓰기 같은 규칙 46개가 모든 세션에 똑같이 적용됩니다. 사람마다, 세션마다 코드 스타일이 달라지는 일이 줄어듭니다.

단계별로 알맞은 모델

설계처럼 판단이 중요한 단계에는 상위 모델을, 구현과 검수에는 Sonnet을, 단순 탐색에는 Haiku를 씁니다. 품질이 필요한 곳에 비용을 씁니다.

읽기 쉬운 보고와 커밋 메시지

보고는 무엇이 달라졌고 무엇을 정해야 하는지부터 쉬운 말로 씁니다. 커밋 메시지도 개발자가 아니어도 이해할 수 있게 한 줄로 남깁니다.

한 번 설치, 한 줄 업데이트

규칙이 개선되면 /harness-update 한 줄로 받습니다. 내가 따로 만든 설정 파일은 건드리지 않습니다.

허브

여러 프로젝트를 한눈에

창을 옮겨 다니지 않아도 됩니다

여러 프로젝트와 세션이 지금 무엇을 하는지 한 페이지에서 봅니다. 세션 아래에는 설계·구현·검수 에이전트가 한 줄씩 나옵니다.

멈춘 작업이 눈에 띕니다

한동안 새 기록이 없는 세션에는 「소식 없음」 표시가 붙습니다. 승인을 기다리며 방치된 작업을 놓치지 않습니다.

어느 단계인지 바로 압니다

“쿠폰 기능 추가 3/4 · 75%”처럼 작업 제목과 단계 진행률이 보입니다. 진행 기록은 처음부터 켜져 있습니다.

사용 한도를 미리 봅니다

5시간·7일 사용 한도가 얼마나 찼는지, 언제 초기화되는지 패널 하나로 확인합니다.

내 컴퓨터 밖으로 나가지 않습니다

허브는 로컬에서만 돌고 보기 전용입니다. 무엇을 모을지(프롬프트 발췌, 사용량 등)는 직접 켜고 끕니다.

어떻게 셌나
  • Claude Code 작업 기록에 남은 검수 에이전트 실행 326회 중, PASS/FAIL 판정이 남은 231회를 셌습니다. 중단·오류로 판정이 없는 95회는 뺐습니다. 기간은 2026-08-03 ~ 10-08, 프로젝트 폴더 6곳입니다.
  • 같은 세션에서 PASS가 나올 때까지 이어진 검수를 한 작업으로 묶어 144건이 나왔습니다.
  • FAIL은 커밋을 막는 결함(심각도 CRITICAL·HIGH, 테스트 실패 포함)이 하나 이상 나왔다는 뜻입니다.
  • “coding-harness 없이” 막대는 추정입니다. 검수가 없으면 첫 구현이 그대로 커밋된다고 보고 그렸습니다.
  • 근사치입니다. 사소한 지적을 반영한 뒤 받은 확인 검수도 “한 번에 통과”로 셌기 때문에, 결함 비율은 실제보다 낮게 잡혔을 수 있습니다.

알아둘 점

  • 시간이 더 걸립니다. 검수와 수정 왕복이 붙기 때문입니다. 위 기록에서도 작업 3건 중 1건은 한 번 이상 다시 고쳤습니다. 작은 일은 짧은 경로로 가서 부담을 줄입니다.
  • 사용량(토큰)이 늘어납니다. AI 여러 개가 설계·구현·검수를 나눠 맡고, 검수에서 걸리면 다시 고치기 때문입니다. 늘어나는 폭을 줄이려고 판단이 중요한 설계에만 상위 모델을 쓰고, 구현·검수는 Sonnet, 단순 탐색은 Haiku처럼 더 저렴한 모델에 맡깁니다.
  • 검수도 완벽하지 않습니다. 위 수치는 검수 AI가 찾아내 증거까지 붙인 결함만 셉니다. 검수가 놓친 결함은 어느 쪽 막대에도 들어 있지 않습니다.
