`git grep -n "rules-docs-sync"` 는 이 문서 이전에 **두 곳**을 낸다:

|---|---|
| `docs/prps/HANDOFF.md` §3-C 표 | `README.md` commands 표 줄 수 5건 · 「설계 문서 42개」 vs 실측 50 · R1 검수의 추가 절감 여지(−34B·−11B) |

**판정: 같은 문서다.** 이 파일이 그 예약을 받는 정본 `rules-docs-sync` PRP 이고, 이번 회차는
그 대기열 중 **tests-hardening §21-7 항목 1~9 에 해당하는 부분만** 처리한다. 위 표의 나머지
항목은 **이 문서의 §13 에 대기열로 이월**한다 — 지우지 않는다. 두 예약 지점의 문면은 그 시점
이관 기록(핀된 역사)이므로 고치지 않는다.

**두 예약과 이번 회차의 실제 교집합은 1건이다** — `audit-remediation` §9 의
「`rules/README.md`:5·:52(RN 누락·산술)」이 §21-7 항목 5(README 산문 수량)와 같은 자리를
가리킨다. 이번 회차가 그 자리에 파리티 검사를 붙이므로 그 이관 항목은 여기서 닫힌다.
나머지는 겹치지 않는다(대기열 항목은 링크 정책·어휘 통일·문서 분리 같은 **정책 결정**이
필요한 것들이고, §21-7 9건은 **검사 정합**이다).

**`shell-hardening` 으로 미룰 항목: 찾지 못했다.** 9건을 하나씩 그 PRP 의 대기열과
대조했다 — 9건 모두 마크다운 산문·검사 스크립트의 정합 문제로 읽히고,
`install.sh`·`hub/install.sh`·`hub_usage_fetch` 의 셸/네트워크 견고성에 걸리는 것을
이 대조에서 찾지 못했다. 이번 회차가 `tests/run.sh` 를 고치지만
셸 견고성이 아니라 **주석의 인용 형태**를 고치는 것이다.

**항목 10(검수 3회차 잔여 LOW 4건)은 이 회차 범위 밖이다** — 발주 지시대로다. 함께 넣지
않는 이유: 4건 중 2건은 §21-7 자신이 「아래에서 고쳤다」고 적었고 남은 2건(LOW-c 절차 위치
선언과 목록 밖 조회의 어긋남 · LOW-d GitHub `until` 의 배타/포함 표기)은 **`NOTICE.md` §5
재동기화 절차의 서술 정정**이라, 묶음 1 이 같은 절을 열더라도 판정 근거가 다르다 —
LOW-c·LOW-d 는 「절차가 맞는가」이고 이번 9건은 「검사가 무는가」다. 판정 축이 다른 것을
같은 검수 회차에 섞으면 검수자가 두 기준을 한 diff 에 적용해야 한다.

## 1. 요구사항 요약

`tests/run.sh` 는 이 저장소의 유일한 안전망이고, S1~S4 의 주제는 「검사가 있다 ≠ 검사가
문다」였다. §21-7 의 9건은 S3b 가 **배포 자산 25행의 로컬 패치 중 어느 것이 되돌려져도
검사가 잡지 못하는가**를 실측해 남긴 구멍 목록이다. 이 회차는 그 구멍 중 기계로 닫을 수
있는 자리에 가드를 붙이고, **각 가드를 뮤테이션 원장(`tests/mutations.tsv`)의 변조행으로
등록해 「지우거나 되돌리면 실제로 실패한다」를 T37 이 실행마다 확인하게** 만든다. 기계로
닫을 수 없는 자리는 닫지 않고 그렇게 판정한다.

성공 기준은 「검사를 추가했다」가 아니라 **「원장에 등록한 변조를 넣으면 지정한 그룹이
실패하고, 원본에서는 통과한다」**이며, 그 판정을 T37-15 가 자동으로 돌린다.

## 3. 오케스트레이터 브리핑의 정정과 내가 재도출한 정본 목록

발주 브리핑은 「결론만 믿지 말고 다시 돌려라」를 요구했다. 다시 돌려서 **브리핑 2건을
정정**하고 **§21-7 의 열거 3건이 비망라임을 확인**했다.

### 3-1. 브리핑 정정 ① — T26 의 「선언 2곳」은 `rules/README.md` 가 아니라 **루트 `README.md`** 다

브리핑은 「`rules/README.md` 안의 `실측 <n,nnn>B` 선언 2곳」이라고 적었다. 실측:

```
grep -c "실측" rules/README.md          # → 0
grep -n "실측 [0-9,]*B" README.md       # → 2건 (상시 컨텍스트 절 · rules 구성 절)
```

`test_always_on_context_budget` 은 `local readme_file="$REPO_ROOT/README.md"` 를 읽는다.
**3중 갱신의 대상은 `tests/run.sh` 의 상수 + 루트 `README.md` 의 선언 2곳**이다. 갱신
대상을 `rules/README.md` 로 착각하면 T26-2·T26-3 가 `-ne` 로 즉시 빨개진다.

한 가지 더 — T26-1 은 `-gt`(상한)지만 T26-2 가 첫 선언을 **상수와 실측 양쪽에** `-ne` 로
비교하므로, 실효적으로 `실측 == 선언1 == 선언2 == 상수` 4중 등식이다. 현재 넷 다 **55457**
(여유 0).

### 3-2. 브리핑 확인 ② — `install.sh` 상수는 잠겨 있고 `CLAUDE.md` 산문만 무방비다 (브리핑이 맞다)

```
grep -n "10개" CLAUDE.md                          # → 배포 자산 선언 줄 1건
ls -1 commands/ | wc -l                            # → 12
grep -n "^readonly COMMANDS_FILE_COUNT=" install.sh # → 12
grep -n "T22-138" tests/run.sh                     # → 상수 vs 실제 파일 수 대조가 존재
```

`CLAUDE.md` 의 배포 자산 선언은 `commands/` 를 **10개**로 적고 실측·상수는 **12** 다.
`install.sh` 쪽은 T22-138 이 잠근다. **잠기지 않은 것은 `CLAUDE.md` 산문 하나뿐이며 그
값이 지금 틀렸다.**

**바이트 중립 확인(중요):** `10개`·`12개` 는 둘 다 5바이트다(`printf | wc -c` 로 확인).
따라서 이 정정은 T26 예산을 움직이지 않고 **3중 갱신이 필요 없다**. 동시에 이것이 정확히
「길이 중립 패치는 T26 이 원리적으로 못 잡는다」(`NOTICE.md` §5 가 자백한 한계)의 실례다 —
그래서 값을 고치는 것만으로는 부족하고 파리티 검사가 필요하다.

### 3-3. 항목 5 의 두 축을 갈라 다룬다

- **지금 틀린 것**: `CLAUDE.md` 의 `commands/ 10개`(실측 12). → 값을 고친다.
- **틀려도 아무도 모르는 것**: `rules/README.md` 산문 수량은 **내가 센 10개 선언 모두
  현재 성립한다**. 실측 `11/4/5/5/8/7/5` = 45 + README = 46, 「Always loaded (16 files)」=11+4+1,
  「Conditionally loaded (30 files)」=5+5+8+7+5, 「All 46 rules」 모두 성립.
  `rules/react/patterns.md` 의 react-native 「8 files」도 정확하다. → 값은 그대로 두고
  **파리티 검사만 붙인다.**

### 5-3. 데이터 모델 — 새 가드가 쓰는 명시적 자료 구조

bash 3.2 에는 `declare -A` 가 없다. 이 저장소의 기존 관례(T31-6 의 `for token in …` ·
T22 의 `for a b; do` 짝 순회)를 따라 **위치 기반 문자열 배열**로 표를 만든다. 새 자료
구조를 도입하지 않는다.

```
# T38: (상대경로, 계약 토큰) 쌍의 평탄 배열. 짝수 인덱스=경로, 홀수=토큰.
#   readonly PATCH_CONTRACT_PAIRS=( "<경로>" "<토큰>" … )
# T38 양방향용: 상류 관례 복귀 시 나타나는 토큰(부재 단언 대상)
#   readonly UPSTREAM_PYTEST_TOKENS=( "pytest.fixture" "@pytest.mark" "import pytest" "conftest.py" )
# T39-1~T39-3: (선언 파일, 추출 정규식, 실측 명령 키) 3튜플 — 3의 배수 인덱스로 순회
```

「짝 순회」의 함정: 배열 길이가 홀수면 마지막 짝이 조용히 빠진다. **길이의 짝수성과
검사한 쌍 수를 함께 단언**한다(T38-4).

### 5-4. 인터페이스 — 공개(그룹 진입점) 시그니처

기존 관례(`test_<이름>() { … }`, 인자 없음, `local test_name="<그룹ID>"`, `finish_group`
으로 끝)를 그대로 복제한다. `verify_group_registry_parity` 가 `declare -f` 텍스트에서

## 8. 설계 결정과 근거

**D1 — 디자인 패턴을 도입하지 않는다.** 기존 관용구만 복제한다: 존재/부재 토큰 검사
(T28-2·T28-3·T31-6) · 상수 vs 실측 파리티(T22-138·T30·T25-1) · 상한 래칫
(`NOTE_FAILURE_ID_LESS_RATCHET`) · 공허 통과 방지 계수 단언(T28-1·T22-165·T37-13).
새 메커니즘·새 의존성 0. python3 인라인은 T28-1·T29-1 의 선례가 있으나 이 회차의 검사는
전부 `grep`/`awk` 로 표현 가능하므로 **쓰지 않는다**.

**D2 — 표 구동 + 계수 단언을, 서브체크 난립보다 택했다.** 11행 + 4성분에 서브체크를 하나씩
붙이면 서브체크 16개·변조행 16개가 된다. **T37 의 실측 실행시간이 127초(변조행 24)** 이므로
변조행당 약 5.3초가 붙는다 — 16행은 T37 을 +85초 만든다. 표 구동 5개로 묶으면 +27초다.
근거는 선례에도 있다: T31-6 은 토큰 3개를 한 서브체크의 루프로 돌리고 변조행 1건만 갖는다.
단 이 선택에는 대가가 있다 — **변조 1건이 무는 것은 그 루프 경로이고 표의 나머지 항목이
개별로 물린다는 증거는 아니다.** 그 자리를 T38-5(계수 단언)가 부분적으로만 막는다(§12).

**D3 — 「양방향」은 `rules/python/testing.md` 하나에만 쓴다.** §21-7 항목 2 가 제시한
「로컬값 존재 + 상류 관례 부재」 양방향은 그 파일에서만 우려가 구체적이다(상류 pytest 관례로
복귀). 실측으로 `pytest.fixture`·`@pytest.mark`·`import pytest`·`conftest.py` 가
`rules/python/` 전체에서 0건임을 확인했으므로 부재 단언이 지금 성립한다. 나머지 4파일은
「되돌아왔을 때 나타날 리터럴」을 지목할 근거가 없어 존재 단언만 둔다 — **없는 우려에 대한
방어를 만들지 않는다**(karpathy #2). 양방향을 쓰는 그 한 파일에서는 **방향마다 변조행을
따로 둔다** — 근거는 §6 묶음 3 서두에 있다.

**D4 — 「정확한 인용」도 제거한다.** §3-4 표에서 9건은 현재 정확하다. 그래도 지운다:
S3b 가 「자기 수정에 따라 움직이는 값은 인용하지 않는 것이 유일한 근본 해법」으로 판정했고,
같은 ruleset 안에 두 관례가 공존하는 것 자체가 항목 7 의 결론이다. 절반만 고치면 공존이
남는다.

**D5 — 핀된 역사는 보존하고, 살아있는 포인터만 제거한다.** 판별식: 그 인용이 **지금의
상태**를 주장하는가(살아있음 → 제거), 아니면 **그때 그 자리에 무엇이 있었는지**를
기록하는가(역사 → 보존). `rules/common/code-review.md:68` 은 「그때 위양성이 났던 자리」
이므로 지금 값으로 고치면 거짓이 된다.

**D6 — 어서션 범위를 배포 트리로 좁힌다.** 구 슬러그 어서션과 줄 번호 래칫 모두
`rules/`·`agents/`·`commands/` 만 본다. `NOTICE.md` 는 구 슬러그를 개명 근거와 함께
정당하게 담고, `docs/prps/` 는 핀된 역사다. 저장소 전체를 보면 오폭한다(실측).

**D7 — 새 그룹 2개, 기존 그룹 확장 1개.** 근거는 §5-2. 요지: T28 의 헌장이 `rules/` 로
한정돼 있고, T30 확장은 개명(→ 원장 T99-3 연쇄) 또는 이름의 거짓말 중 하나를 강제한다.

### 9-3. 각 가드의 「무는지」 확인 방법

원장이 이 확인을 기계화한다 — T37-15 가 행마다 **미러 사본에 변조를 넣고 `--only
<expect_group>` 을 두 번 돌려** 「변조하면 실패 / 원본이면 통과」 판정 쌍을 실제로 만든다.
따라서 묶음별 확인 절차는:

```
1. 가드를 넣는다            → 검증: bash tests/run.sh --only <그룹> 이 통과
2. 원장 행을 등록한다        → 검증: bash tests/run.sh --only T37 이 통과
                              (실패하면 그 행이 실제로 물지 않는다는 증거다)
3. 묶음 전체                → 검증: bash tests/run.sh 가 38/38
```

2단계가 이 설계의 성패 기준이다. T37-15 가 내는 네 가지 실패 형태를 구현자가 구분해야
한다(그 함수의 문면대로):

| 실패 문구 | 뜻 |
|---|---|
| `사전조건 불성립 — 변조 전 <그룹> 이 이미 FAIL` | 원장 무효 또는 가드 자체가 원본에서 빨갛다 |
| `사전조건 실패 — sed 적용 후 바이트 변화 없음` | `mutation_sed` 가 대상 문자열을 못 찾았다(묶음이 그 문자열을 이미 고쳤을 때 발생) |
| `가드 무력화 — 변조 후에도 <그룹> 이 PASS` | **K6 회귀** — 가드가 물지 않는다 |
| `실패 메시지에 토큰 '…' 없음` | 무관한 이유로 실패했다(가드가 아닌 다른 것이 빨개졌다) |

**성능 예산(실측 기반)**: 전체 스위트 167초 중 **T37 이 127초**를 쓴다(변조행 24).
변조행당 약 5.3초이므로 35행에서 T37 은 **약 185초**, 전체는 **약 225초**를 예상한다.
`tests/run.sh` 의 T37 헤더는 「`--only T37` 실측 8초대」라고 적지만 그것은 변조행이 훨씬
적던 시점의 값이다(§3-7 — 그 문면은 이 회차에서 고치지 않는다). 구현 중에는 원장 행을
묶음 끝에 일괄 등록해 `--only T37` 호출 횟수를 줄여도 좋다 — 단 **커밋 전에는 반드시
전체 `bash tests/run.sh`** 를 통과시킨다.

### 9-4. 순수 로직의 단위 검증

이 회차의 산출물은 셸 검사와 마크다운이고 새 파이썬 순수 함수를 만들지 않으므로

## 12. 이 설계의 한계

**기제**: 이 회차가 붙이는 가드는 두 종류다 — (a) 리터럴 문자열의 존재·부재를 보는 정적
검사(T32-10·T38-1~3), (b) 산문에서 추출한 숫자를 실측과 비교하거나 상한과 비교하는 계수
검사(T39-1~5·T38-4).

**그 기제에서 따라오는 한계**: (a) 는 같은 뜻을 다른 낱말로 되돌리는 편집을 보지 못하고,
토큰만 남기고 주변 문장의 의미를 뒤집는 편집도 보지 못한다. (b) 는 추출 정규식이 보는
표기 형태에 갇힌다 — 「N files」·「N개」 형태를 「N 개」·「스물」·표로 옮기면 추출이
0건이 되고, 그 자리는 「선언을 찾지 못함」 분기가 실패로 잡지만 **그 분기 자신이 정규식
표기에 의존한다**. 래칫은 개수만 보므로 인용 하나를 지우고 다른 인용 하나를 넣으면 총계가
유지돼 발화하지 않는다(`SOURCE_GUARD_ID_FLOOR` 헤더가 같은 한계를 자백한다).

**표 구동 선택에서 따라오는 한계**: T38 의 변조행 5건은 각 서브체크의 루프 경로 하나를
문다. 표의 다른 항목이 개별로 물린다는 증거는 이 설계가 내지 않는다 — T38-5 의 계수
단언은 「루프가 표 길이만큼 돌았다」까지이고 「각 항목의 토큰이 실제로 판정에 기여했다」는
아니다.

**비망라 예시** — 이 절이 열거하지 않은 것: 계약 토큰이 대표하지 못하는 로컬 패치의 나머지
문면(§5 표의 「패치 요지」 자체의 상류 대조는 이 회차도 하지 않는다 — 네트워크를 쓰지
않으므로) · §5 두 표의 1:1 대응(R5, 기계 강제 없음) · 「N번째 줄」·「line N of」 같은
줄 번호의 다른 표기 · `docs/prps/` 안의 줄 번호 인용(핀된 역사이므로 대상이 아니지만,
그중 어느 것이 역사가 아니라 살아있는 주장인지 이 회차가 전수 판정하지 않았다) ·
숫자 인용이 아닌 형태의 문서 표류(구조도·예시 코드).

**상류 원문을 받지 않았다.** §21-8 과 같은 한계다. 「되돌림이 어떤 리터럴을 재도입하는가」는
`NOTICE.md` §5 의 「패치 요지」와 이 저장소의 git 객체에 의존한다. 계약 토큰이 실제로
상류값과 다른지를 상류에서 확인하지 않았으므로, T38 의 토큰이 「로컬 패치의 존재」를 보는지

따라서 T39-2 가 「산문 → 상수」를 잇고 그 둘이 「상수 → 디스크」를 이어 **사슬이 세 상수
전부에 대해 닫힌다.** 구현자가 이 경계를 「의도와 다를 수 있다」며 물었고, 오케스트레이터가
두 검사의 대상 상수를 직접 세어 답했다. 설계 **D1**(「기존 관용구만 복제한다, 새 메커니즘
0」)의 결과이며, 그 목록에 「상수 vs 실측 파리티(T22-138·T30·T25-1)」가 있다.

### 15-4. 배열을 비우면 이 그룹은 조용히 통과한다 — 잡는 것은 원장이다

**오케스트레이터 실측.** 산문 렌즈가 「T39-1 에는 루프 계수 단언이 있고 T39-2 에는 없다」를
Nit(방어 깊이 비대칭)으로 올렸다. 그 지점을 파고들어 확인한 것:

```
사본에서 readonly README_PROSE_DECLARATIONS=( … ) → =() 로 치환
  bash tests/run.sh --only T39   → [OK] T39 통과 · 실패 0     (배열이 비었는데 그린이다)
  bash tests/run.sh --only T37   → [ERROR] T37-15: T39-1 가드 무력화 — 변조 후에도 T39 가 PASS(K6 회귀)
```

기제는 **기대값이 배열 자기 길이에서 계산된다**(`${#ARRAY[@]} / 2`)는 것이다 — 배열이 비면
기대값도 0 이 되어 계수 단언이 함께 침묵한다. T39-1 의 계수 단언은 **배열 비우기를 막는
장치가 아니다**(그 메시지가 적은 대로 「사전조건 실패로 건너뛴 항목」을 겨냥한다).

**그것을 잡는 것은 원장 판정 쌍이다.** 변조행이 **선언 파일**을 고치는데 배열이 비면 그
변조에 T39 가 반응하지 않으므로 「변조하면 실패」 절반이 깨진다. **신규 가드를 면제행이 아니라
변조행으로 등록한다는 설계 §7 의 의도가 정확히 이 자리에서 값을 냈다.**

**그리고 그 방어의 경계** — 구현자가 독립 실험으로 확인했다: 변조가 겨냥하는 `dir:common`
한 쌍만 남기고 **나머지 9쌍을 지우면 `--only T37` 이 통과한다.** 설계 §12 의 「표 구동
선택에서 따라오는 한계」가 같은 것을 적고 있다. **단정을 추가하지 않았다** — 원장이 배열
비우기를 막고 있고, 기대값을 리터럴 바닥값으로 바꾸면 배열이 정당하게 늘 때마다 손으로
고쳐야 하는 부채가 생긴다(§24-3 의 「추가하지 않았다」 판정과 같은 형태).

부수 관측(구현자가 코드 추적이 아니라 **실행으로** 확인): T39-1 의 계수 단언은
`note_failure` 가 이미 발화한 상태에서만 발화할 수 있다 — 사전조건 실패 분기가
`note_failure` 뒤에 `continue` 하고 그 밖에 증분을 건너뛰는 경로가 없다. 단독 검출력이 없는
이중 안전장치이고, **메시지 문면은 거짓이 아니므로 고치지 않았다.**

### 15-5. 구현자가 겪은 함정 — 한계 표기 주석의 위치

최초 배치는 한계 표기 주석을 **배열 정의 위**에 뒀다. `T37-13`
(`has_limit_annotation_for_guard`)은 **함수 정의 직전의 연속 주석 블록**만 보므로, 배열과
함수 사이의 빈 줄이 그 블록을 비워 보이게 만들어 **3개 ID 전부 「한계 표기 없음」으로
실패**했다. 주석을 함수 바로 위로 옮겨 해결했고, 두 렌즈가 각각 `extract_preceding_comment_block`
소스를 읽어 그 기제가 참임을 확인했다(산문 렌즈는 awk 로직만 떼어내 두 배치를 직접
재현했다). **다음 묶음에서 재발할 수 있는 함정**이라 배열 쪽에 안내 주석을 남겼다.

### 15-6. 검수 반영 — 진단의 숫자 자리가 비던 것 (검수 1회차 Minor)

접지 렌즈 Minor. 대상 파일 **자체가 없으면** `grep -cE` 는 표준출력에 아무것도 내지 않는다
(파일이 있고 매치가 0건일 때만 `0` 을 찍는다). 그래서 진단이 「정확히 1건이어야 하는데
**건** 발견됨」으로 찍혔다 — 숫자가 빈다. **판정 자체는 정확했다**(bash 3.2 가 빈 문자열
비교를 참으로 평가해 사전조건이 발화한다). 같은 그룹의 `dir:` 계열은 같은 상황에서
`선언=8, 실측=0` 으로 깨끗이 찍혀 비대칭이 뚜렷했다.

Minor 지만 반영한 이유: **S4-5(`b31fdff`, 「검사가 왜 실패했는지 알려주지 못하던 곳들을
고친다」)와 같은 축**이다. 세 서브체크 전부에 `${var:-0}` 을 넣었고(비대칭을 새로 만들지
않는다), 대상 파일 3종을 지운 사본에서 **15건 전부 `0건` 으로 찍히는 것**을 오케스트레이터가
확인했다.

**이 수정이 주석 하나의 전제를 무효화했고 함께 고쳤다.** 기존 주석이 「빈 문자열 비교가
참이라」를 사전조건의 근거로 적었는데, 기본값을 채우면 빈 문자열이 그 비교에 도달하지
않는다. 그대로 두면 **「적어 놓은 것이 참인가」 축의 결함을 새로 만드는 것**이다(묶음 1 의
차단 사유가 그 계열이었다). 구현자가 그 성질이 실제로 지키는 대상이 **본 단정(선언 대 실측)**
쪽임을 실측으로 확정하고 문단을 그쪽으로 좁혔다.

대조하라」**를 지시했고(설계 §12 가 「상류 원문을 받지 않았다」를 자백하므로 저장소의 git

```
git show "5f9552f:<경로>" | grep -qF -- "<토큰>"    # 매치하면 그 토큰은 로컬 패치가 아니다
```

가장 선명한 사례: `commands/prp-commit.md` 의 실제 로컬 패치는 **11줄짜리 「Message style」
절**인데 **어떤 토큰도 그것을 지키지 않았다.** 그런데 §5 표는 그 행의 「잠기지 않는 성분」을

**구분이 날카로웠다** — 구현자가 그 토큰을 고른 **근거는 맞았는데**(슬러그 정오는 이미
`T32-10` 이 잡는다는 것은 사실이다) **선택이 그 근거를 실현하지 못했다.** 접지 렌즈의 문장을
그대로 옮긴다: 「근거는 맞았는데 선택이 그 근거를 실현하지 못했다.」

### 16-4. 구현자가 4번째를 스스로 찾고, 그것이 고칠 수 없음을 밝혔다

제거하고 기존 `T28-4` 가 그 파일을 계속 잠그도록 남겼다(두 렌즈가 각각 그 잠금을 실측 확인).

것까지 구현자가 짚었다. **배열이 16쌍 → 15쌍이 됐다.**

### 16-5. 근본 문제 — 「성분」에 단위가 없었다 (상한 회차의 결론)

2·3회차의 차단 사유는 같은 형태였다: **「잠기지 않는 성분」이 `—`(없음)로 적혀 거짓**이었고,
고칠 때마다 **성분이 하나 더** 드러났다.

| 회차 | 드러난 성분 |
|---|---|
| 2 | 두 행에 겨냥되지 않은 편집이 각 1개(e2e 링크 완화 · Error Boundary 예외 조항) |
| 3 | 같은 문단 안의 **다섯 번째** 절(두 트랙 동시 로드 서술) |

**그리고 여기에 반대 방향의 오류도 있었다**(오케스트레이터 발견): 같은 행의 한 성분
(react-native 파일 수)은 **묶음 2 의 `T39-3` 이 실제로 잠그는데** 「잠기는 성분」에도
「검사」에도 없었다 — `NOTICE.md` 가 `T39` 를 **한 번도 인용하지 않았다.** 묶음 2 가 검사를
신설할 때 이 행을 갱신하지 않아 생긴 누락이다. 즉 그 행은 **과대 진술과 과소 진술을 동시에**
하고 있었다.

**진짜 문제는 표의 「성분」에 단위가 정의돼 있지 않다는 것이었다.** 그 파일의 React Native
문단은 **한 문단**이지만 **세 절**로 읽을 수 있다 — 문단으로 세면 넷, 절로 세면 다섯, 더
쪼개면 더 나온다. **「성분이 전부 회계에 올랐다」가 판정 가능한 기준이 아니었고**, 회차를 더
돌려도 같은 형태가 반복될 구조였다. **작업의 결함이 아니라 기준의 미정의다.**

사용자 승인 회차가 그것을 닫았다 — 다섯 번째 성분을 채우고, 계수 기준 문단에 **단위와 그
한계**를 규범 형식으로 더했다:

- **단위**: §5 정본 목록 표의 「패치 요지」가 파일별로 구분한 항목(재동기화 담당자가 그 열을
  체크리스트로 쓴다)
- **더 잘게 쪼개 적는 것은 무방하다**(다섯 번째를 적었으므로 문면이 그것을 허용해야 한다)
- **그 아래 단위의 전수는 보증하지 않는다** + 비망라 예시 + **전수 증명이 아니다**

**이 구절의 효과**: 전에는 문서가 「없음」이라고 **단정해 거짓**이었고, 이제는 **「보증하지
않는다」고 밝힌다.** 앞으로 더 잘게 쪼갠 성분을 지적하는 것은 **문서화된 한계를 인용하는
것**이지 거짓을 잡는 것이 아니다 — 그것이 기준을 판정 가능하게 만든다는 뜻이다.

### 16-6. 배열 비우기 방어가 세 번째로 성립했다

`UPSTREAM_PYTEST_TOKENS` 를 비우면 `--only T38` 은 조용히 통과하지만
`--only T37` 이 **`T37-15: T38-2 가드 무력화 — 변조 후에도 T38 가 PASS(K6 회귀)`** 로 잡는다

§15-4 의 같은 자리를 상호참조하고 있었다 — **없는 방어를 적은 것이 아니었다.**

**같은 구조가 이 PRP 에서 세 번 성립했다**: 묶음 2 의 선언 목록 · 묶음 3 의 쌍 삭제 · 이

**그 방어의 경계도 실측됐다**(구현자): 변조가 겨냥하는 쌍 **하나만 남기고 나머지를 지우면**
원장도 통과한다. 설계 §12 의 「표 구동 선택에서 따라오는 한계」가 같은 것을 적는다.

### 16-7. 빈 배열 전개가 스위트를 죽였고, 렌즈의 관측 하나는 반박됐다

1회차 접지 MEDIUM: `"${ARR[@]}"` 전개가 **bash 3.2 의 nounset 아래에서 배열이 비면

아니었다). 인덱스 기반 순회로 통일해 그 경로를 구조적으로 없앴다.

분리**였고 `T31-6` 에는 그 구조가 없다. **손대지 않은 판단은 옳았고 관측이 부정확했다.**

### 16-8. 오케스트레이터의 브리핑 오류 3건 (모두 같은 형태)

1. **구현자 보고의 문구를 검증 없이 옮겼다** — 「배열 항목 삭제를 막는 것은 `T38-4` 원장

   정확히 일반화돼 있었다. **코드는 맞고 내가 전달한 요약이 부정확했다**(렌즈가 잡았고
   「코드 자체는 정확하니 결함이 아니라 전달 문구의 부정확」으로 감점하지 않았다).
2. **완료 기준이 성립하지 않는 판별법을 요구했다** — 「`git diff --stat` 으로 이번 회차 변경
   여부를 확인하라」고 적었으나, **이미 바뀐 줄을 다시 고치면 삭제·추가 카운트가 그대로**라

**형태는 S4 의 다섯 건과 같다** — 결론은 맞는데 **그 결론에 이르는 세부(문면·판별법·절
번호·인용 열)를 읽지 않고 추정해 실었다.** 세 건 모두 **재현 방법을 함께 넘겼기 때문에**

**같은 형태가 이 PRP 에서 세 번 나왔다**: §21-7 항목 7 의 열거(6건으로 적고 실제 16) ·
설계 §5-1 의 건수(6 으로 적고 §3-4 표는 7) · §3-4 도입부(7 로 적고 표는 8). **세 개 다
「요약 숫자가 자기 근거 표와 어긋난다」다.** 정정은 §3-4·§5-1 에 취소선으로 남겼고,
§6 표까지 전파되지 않은 것을 **재검수 렌즈가 범위 밖에서 찾아** 이 회차에 함께 고쳤다.

### 17-4. 「8건」은 핀된 역사인가 — 자기 결론과의 정합

오케스트레이터가 재검수에 던진 질문: **「8건」도 저장소 상태에 따라 움직이는 값이 아닌가?**
그렇다면 이 회차가 자기 결론을 위반한 것이다.

**렌즈가 세 근거로 「핀된 역사」로 판정했다**: (a) 이 회차의 결론이 겨냥하는 것은
`파일명:줄번호` 형태의 살아있는 인용이고 「8건」은 순수한 개수다 (b) 두 문면 모두 **과거
시제**로 적혀 있다 (c) 주석이 「이 회차가 전부 앵커 전용으로 수렴시켰다」를 덧붙여 원래
대상이 이미 제거됐음을 밝힌다. 설계 §3-4 자신도 그 표의 성격을 「이 회차가 끝나면 역사가
된다」로 선언한다.

### 17-5. 래칫의 자기 참조 — 계수 대상에 검사기 자신이 들어간다

`T39-4`·`T39-5` 의 계수 대상에 `tests/run.sh` 자신이 포함되므로 **새 주석에 그 형태를 넣으면
그 즉시 래칫이 올라간다.** 확인된 것:

- **계수 정규식 리터럴 자신은 자기 패턴에 매치하지 않는다** — `:[0-9]+` 는 메타문자이지 실제
  숫자가 아니다(구현자·두 렌즈가 각각 실측).
- 새로 쓴 주석·메시지에 실제 `file:line` 형태가 **들어가지 않았다** — 착지 후에도 배포 트리
  1건 · `tests/run.sh` **4줄에 5개 발생** 그대로다.
- 원장 두 행이 삽입하는 문자열이 계수에 잡히는 것은 **의도**다(그것이 변조의 기제다).

**`tests/run.sh` 의 상한이 5 인 이유**: 래칫은 **발생 수**를 세고, 보존 대상 5건 중 둘이
**한 줄에 함께** 있다(`code-review.md` 인용과 `react/security.md` 인용). 줄 수로 세면 4 다.

### 17-6. 제거 5건 · 보존 5건 — 두 렌즈가 각각 독립 재판정했다

설계 §3-5 표의 판정을 구현자와 두 렌즈가 각각 다시 내렸고 **셋 다 같은 결론**이었다.
보존된 5건은 전부 **그때 그 자리를 기록하는 문장** 안에 있다 — 감사 항목 ID · 과거 위양성이
발생한 자리 · 인용 이관 계보. **고치면 거짓이 된다.**

교육용 예시 1건(`agents/implementer.md` 의 행 번호 인용 위험을 **가르치는** 문장)도 설계
§2·§7-4 대로 보존했고, `LINE_CITATION_RATCHET_DEPLOYED=1` 이 그것을 세는 것을 전제로 한다.

### 17-7. 설계에 없던 필수 연쇄 (구현자 발견)

하한 상수를 올리면 **원장 헤더의 이력 화살표**와 **그 상수 리터럴을 검색하는 `T99-6` 의
`mutation_sed`** 가 함께 움직여야 한다 — 안 고치면 `verify_ledger_header_citations` 가
**스위트 실행 자체를 막는다**(접지 렌즈가 되돌려 실증했다). 설계 §7 에 없던 연쇄다.

### 17-9. 이 절의 한계

**기제**: 이 절의 수치는 묶음 4 착지 시점(2026-09-08)의 실측이고, 판정은 두 회차 검수

**그 기제에서 따라오는 한계**: 검수 보고서는 산출물로 남지 않아 **회차별 건수의 사후 재현이
불가능하다.** 래칫은 **개수만** 보므로 **인용 하나를 지우고 다른 하나를 넣으면 총계가 유지돼
발화하지 않는다**(`SOURCE_GUARD_ID_FLOOR` 헤더가 같은 한계를 자백한다). 계수 정규식이 보는
표기에 갇히는 것도 그대로다 — `파일명:줄번호` 와 `currently line[s]/around lines N` 두 형태를
본다.

**비망라 예시** — 이 절이 열거하지 않은 것: 「N번째 줄」·「line N of」·「위에서 N번째」 같은
다른 표기 · `docs/prps/` 안의 인용(핀된 역사이므로 대상이 아니지만, 그중 어느 것이 역사가
아니라 살아있는 주장인지 이 회차가 전수 판정하지 않았다) · 앵커가 **지금은 실존하지만
나중에 개명될** 경우(앵커도 낡을 수 있다 — 줄 번호보다 느리게 낡을 뿐이다) · 숫자가 아닌
형태의 문서 표류.
