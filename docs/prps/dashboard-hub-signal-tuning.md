## 1. 요구사항 요약

프로젝트 대시보드(`commands/dashboard_template.html`)와 세션 허브(`hub/bin/hub_template.html`)의
시각 신호 3건을 사용자 피드백에 맞춰 조정한다. (1) 대시보드에서 「진행중」 단계 행을 표시하던
`--accent-soft` 밴드와 좌측 3px 바를 걷어내고, 신호를 `.chip`(「진행중」 뱃지) 하나에 모은 glow

세 건 모두 CSS 선언 변경이지만, 이 저장소는 지금의 CSS 를 회귀 검사가 **문자열로 잠그고**

### 2.2 정정 — 요구 2 의 「유력 후보 (a)」는 사실과 다르다

지시가 제시한 후보 (a)는 "bloom 반경 18px 이 gap 12px 보다 커서" 라고 적었다. **`box-shadow`
의 `blur` 값은 확산 반경이 아니다.** 명세상 blur 는 그림자 경계를 중심으로 **양쪽으로 절반씩**
번지는 전이 거리이고, 실제 바깥 확산은 `blur/2 + spread` 근처에서 시작해 가우시안 꼬리로 더
간다. 그래서 `0 0 18px -4px` 의 산술적 바깥 확산은 18px 도 아니고 (18/2 − 4)=5px 도 아니다 —
**실측 19px 이다**(§4.2). 후보 (a)의 결론("gap 보다 넓다")은 우연히 맞지만 근거가 틀렸고, 그
틀린 근거로 값을 고르면 (예: "18 → 12 로 줄이면 gap 안에 들어간다") 여전히 잘린다. 아래는
숫자를 추측하지 않고 **헤드리스 Chrome 으로 렌더해 픽셀을 세어** 정한 값이다.

지시가 제시한 후보 (b)(뷰포트 가장자리에서 끊긴다)도 **기각**한다. 1280px 뷰포트에서 좌우 끝
카드는 `.wrap` 의 `padding:0 16px` 만큼 여유가 있고, 그 16px 지점의 잔여 신호는 ΔL* 0.7 로
식별 한계(약 2) 아래다 — 사용자가 본 잘림이 여기일 수 없다.

`.tree-section{overflow-x:auto}` 에 의한 클리핑도 **기각**한다. `card-working` 클래스는 카드
모드의 `.card` 에만 붙고(`hub_template.html` 의 렌더 함수 `stateClass` 분기) 트리 모드의
`.tree-section`·`.tree-node` 에는 붙지 않는다.

### 2.3 실측 하네스 (재현 방법)

값의 출처를 검수자가 다시 밟을 수 있어야 하므로 방법을 적어 둔다. 저장소에 파일을 남기지
않았다(일회성 측정 도구다).

1. 대상 템플릿의 `<style>` 블록을 **글자 그대로** 떼어 정적 마크업(카드 6장 그리드 / 단계
   3행)과 함께 임시 HTML 로 조립한다 — CSS 를 손으로 옮겨 적지 않는 것이 핵심이다.
2. `Google Chrome --headless=new --force-device-scale-factor=1 --hide-scrollbars
   --window-size=1280,900 --screenshot=… file://…` 로 렌더한다.
3. PNG 를 PIL 로 열어 스캔라인을 뜨고, 픽셀을 CIE `L*` 로 변환해 배경 대비 **ΔL\*** 를 잰다.
   이 저장소가 이미 쓰는 지각 잣대와 같은 자다 — `tests/run.sh` T25-110 의
   `MIN_SURFACE_DELTA_LSTAR = 2.0`("넓은 면적의 명도 식별 한계") 를 그대로 문턱으로 쓴다.
4. 레이아웃 수치(`getBoundingClientRect`)는 `--dump-dom` 으로 `<title>` 에 실어 뽑는다.

측정 환경: macOS(darwin 25.6.0) · Google Chrome 헤드리스 · devicePixelRatio 1 · 뷰포트
1280×900 · 라이트/다크 양쪽. **Blink 계열 1종에서만 쟀다** — 다른 엔진의 blur 근사는 다를 수
있고, 그래서 §7 의 회귀 검사는 실측 상수가 아니라 **명세 상한**으로 부등식을 세운다.

## 3. 요구 1 — 진행중 단계 행: 밴드·바를 걷고 칩 glow 로

### 3.1 현상

`ol.steps li.active` 가 카드 안쪽에 `--accent-soft` 가로 밴드를 깔고, 그 왼쪽 끝에 3px 세로
그라데이션 바를 세운 뒤 바의 `opacity` 만 pulse 한다. 사용자 지적은 두 가지다 — 밴드 때문에
행이 "어색하게 구분되어" 보이고, 좌측 바가 "과하다".

### 3.2 원인 (CSS 기제)

밴드가 어색한 것은 색이 아니라 **상자의 경계가 어디에도 맞지 않기 때문**이다. `li` 는
`.card{padding:26px 30px}` 안의 블록이라 밴드의 좌우 끝이 카드 테두리에서 30px 안쪽에서 갑자기
끊긴다. 카드 테두리와도, 본문 텍스트 열과도 정렬되지 않는 세 번째 수직선이 두 개(좌·우) 생기는
셈이다. 실측 렌더에서 밴드는 `x=68..832`(카드는 `36..864`)에 그려진다.

좌측 바가 과한 것은 **모션의 담체가 「막대」이기 때문**이다. 이것은 이 저장소가 직전 회차에
스스로 세운 원칙과 어긋난다 — `docs/prps/dashboard-ui-polish-4.md` 결정 **D6** 은
"움직이는 것은 **빛**이어야지 **막대·링**이어서는 안 된다"고 못 박았는데, 그 결정이 실제로 남긴
것은 하드 링을 없앤 허브 쪽뿐이고 대시보드 쪽은 `width:3px` 막대를 그라데이션으로 부드럽게 하는
데 그쳤다. **요구 1 은 D6 을 뒤집는 것이 아니라 완성하는 것이다.**

### 3.3 처방

밴드와 바를 **삭제**하고, 「진행중」 칩에 정적 halo 를 얹은 뒤 그 halo 의 `opacity` 만 pulse
한다. 담체만 바뀌고 모션 문법(진폭 .6→1, 주기 4s)은 그대로다.

```css
/* 변경: L133 에 position:relative 추가(::after 의 포함 블록) */
li.active .chip{position:relative;background:var(--accent-ink);color:var(--bg)}

/* 삭제: L136~152 주석 블록 · L153 밴드 · L154~156 좌측 바 */
/* 신설(같은 자리): */
ol.steps li.active .chip::after{content:"";position:absolute;inset:0;border-radius:inherit;
  pointer-events:none;box-shadow:0 0 10px -1px var(--accent);
  animation:dz-step-active-pulse 4s ease-in-out infinite}
@keyframes dz-step-active-pulse{0%,100%{opacity:.6}50%{opacity:1}}
@media (prefers-reduced-motion:reduce){ol.steps li.active .chip::after{animation:none;opacity:1}}

/* 삭제: L245 PiP 압축뷰 밴드 규칙 전체 */
```

**왜 `.chip` 자신의 `box-shadow` 를 애니메이션하지 않는가**: `box-shadow` 보간은 매 프레임
리페인트다. 허브가 같은 문제를 만나 `::after` 오버레이의 `opacity` 만 돌리는 방식으로 해결해
뒀고(같은 파일 계열의 기존 관용구), 그것을 그대로 따른다.

**왜 배경·글자색은 건드리지 않는가**: `li.active .chip` 은 `--accent-ink` 채움에 `--bg` 글자다.
`opacity` 나 `background` 를 애니메이션하면 글자 대비가 주기적으로 내려간다(WCAG 1.4.3 위반
가능). `::after` 는 배경 없이 **바깥으로만** 그림자를 그리므로 칩 안쪽 픽셀을 한 개도 바꾸지
않는다 — 대비 계산에 영향이 0 이다.

**PiP 규칙을 함께 지우는 이유**: `body.dz-pip ol.steps li.active` 의 `border-radius:8px` 와
`padding-left/right:8px` 는 **밴드의 모양을 다듬기 위해서만** 존재한다. 밴드가 없어지면 남는
효과는 "진행중 행만 좌우로 8px 밀려난다"는 정렬 흔들림뿐이라, 규칙째 삭제가 맞다.

### 3.4 접근성 — 모션을 끈 사용자에게 남는 정적 채널

밴드는 직전 PRP 에서 `prefers-reduced-motion` 폴백의 "본체"로 지목돼 있었다. 그 서술은 과장이다
— 밴드를 지워도 정적 채널이 **다섯** 남는다.

| # | 채널 | 규칙 |
|---|---|---|
| 1 | 칩의 **텍스트** 「진행중」(vs 완료/대기) | 대시보드 계약: `.chip` 텍스트가 상태의 정본 |
| 2 | 칩 **반전 채움** `--accent-ink` 바탕 + `--bg` 글자 | `li.active .chip` |
| 3 | 번호 사각형 **반전** | `li.active .num{background:var(--accent-ink);color:var(--bg)}` |
| 4 | 행 **굵은 글씨 + `--head` 색** | `li.active{font-weight:700;color:var(--head)}` |
| 5 | 칩 **정적 halo**(모션만 꺼지고 `opacity:1` 로 남는다) | 새 `@media (prefers-reduced-motion)` 분기 |

채널 1 은 스크린리더에도 그대로 읽히는 유일한 채널이고 그것이 정본이다. **모션이 유일한 판별
채널이 되는 순간은 없다.**

### 3.5 실측 — 칩 glow 후보 비교

칩 오른쪽 가장자리 바깥으로 ΔL\*(카드 면색 `--surface` 기준). 라이트 테마, 애니메이션 최대치
프레임(`opacity:1`) 기준이며 최저점은 여기에 0.6 을 곱한 값이다.

| 시안 | `box-shadow` | d=1 | d=2 | d=4 | d=6 | 꼬리(ΔL\*≥1) |
|---|---|---|---|---|---|---|
| 현행(밴드) | `--accent-soft` 면 | 5.86 | 5.86 | 5.86 | 0.00 | 4 (밴드 폭) |
| **a (채택)** | `0 0 10px -1px` | **10.59** | 7.86 | 4.26 | 1.62 | 7 |
| b | `0 0 8px 0` | 13.38 | 10.59 | 5.50 | 2.39 | 7 |
| c | `0 0 12px -2px` | 8.51 | 6.66 | 3.59 | 1.62 | 7 |
| d | `0 0 6px 1px` | 17.63 | 13.35 | 6.31 | 1.94 | 7 |

- a 를 고른 이유: 최저점에서도 ΔL\* ≈ 6.4 로 **현행 밴드(5.86)와 같은 급**의 신호를 유지하면서
  최대점에서는 그 두 배가 된다. 꼬리 7px 는 카드의 오른쪽 패딩 30px 안에 여유롭게 들어간다.
- d 는 `spread` 가 양수(+1px)라 문자 그대로 **링**이 만들어진다 — 결정 D6 과 정면으로 어긋나
  기각.
- 다크 테마에서 a 는 d=1 에서 ΔL\* 11.86 으로 라이트와 사실상 같다(칩이 `--accent-ink` 채움,
  glow 가 `--accent` 인 관계가 두 테마에서 대칭이라 그렇다).

## 4. 요구 2 — 작업중 카드 bloom 이 잘려 보이는 문제

### 4.1 현상

`.card.card-working{box-shadow:var(--shadow),0 0 18px -4px var(--accent)}` 의 바깥 bloom 이 옆
카드에 닿는 자리에서 **그라데이션 도중에 뚝 끊긴다.** 라이트 모드에서 두드러진다.

### 4.2 원인 규명 (CSS 기제 — 실측 3단)

**(1) bloom 의 실제 확산은 19px 이다.** 이웃이 없는 단독 카드로 재서, 카드 테두리 바깥
`x+1..x+19` 까지 배경과 다른 픽셀이 이어지고 `x+19` 에서 정확히 페이지 배경값
`#EEF3F8 (238,243,248)` 으로 복귀했다. 그리드 `gap` 은 **12px** 이다 — 확산이 간격보다 **7px
길다.**

**(2) 잘리는 기제는 클리핑이 아니라 「이웃의 불투명 배경에 덮이는 것」이다.** 카드들은 전부
`position:relative` 에 `z-index` 가 없어 CSS 페인트 순서상 **문서 순서대로** 겹쳐 그려진다.
뒤 카드의 불투명 `--surface` 면이 앞 카드의 그림자 위에 칠해진다. 실측 스캔(라이트, y=250):

```
x=423  (0,113,177)   ← working 카드 오른쪽 테두리(--accent)
x=424  (159,196,219) ← bloom 최대
   …    (점진적 감쇠)
x=435  (221,231,238) ← 아직 배경(238,243,248)에 도달하지 못했다
x=436  (217,226,236) ← 이웃 카드의 --line 테두리
x=437  (255,255,255) ← 이웃 카드의 --surface (불투명 흰색)
```

**대조 실험으로 기제를 확정했다.** 동일 페이지에 `.card.card-working{z-index:1}` 만 더해
페인트 순서를 올렸더니 bloom 이 흰 카드 **위로 이어져** `x=437..441` 에서 부드럽게 사라졌다
(`250,252,253 → 253,253,254 → 255,255,255`). 즉 어떤 `overflow` 도 자르고 있지 않다 — 순전히
겹쳐 그리기다.

**(3) 라이트에서만 두드러지는 이유는 이웃 카드의 `--shadow` 알파다.** 두 테마 모두 bloom 은
비슷하게 넓지만, 잘리는 지점의 **잔여 신호**가 다르다.

| | 잘리는 지점(d=12)의 잔여 ΔL\* | 식별 한계(2.0) |
|---|---|---|
| 라이트 | **2.09** | **넘는다 → 보인다** |
| 다크 | 1.44 | 아래 → 안 보인다 |

왜 갈리는가: 라이트의 `--shadow` 는 `rgba(19,51,91,.06)` 로 사실상 아무것도 가리지 못하는데,
다크는 `rgba(0,0,0,.45)` 다. 다크에서는 **이웃 카드 자신의 검은 앰비언트 그림자가 간격을
가득 채워** bloom 의 꼬리를 덮어버린다(간격 중앙 실측: 다크 `(10,16,24)` 로 페이지 배경
`(14,22,33)` 보다 어둡다). 라이트에서는 간격이 `(231,236,242)` 로 거의 배경 그대로라 bloom 의
꼬리가 맨몸으로 드러난다.

**(4) 왜 「평범한 카드들 사이의 간격」은 잘려 보이지 않는가**(대조군): 모든 카드가 같은
`--shadow` 를 갖고 이웃끼리 서로 채워 간격이 **균일한 한 가지 색**이 된다(라이트 실측:
`x=844..855` 전 구간 `(231,236,242)` 일정). 잘려 보이려면 **한쪽에만 있는 그라데이션이 끝나기
전에 끊겨야** 한다 — 그 조건을 만족하는 것은 working 카드의 accent bloom 하나뿐이다.

> 정리: **"너무 넓다"가 문제의 본질이 맞다.** 다만 넓이의 기준은 "몇 px 인가"가 아니라
> **"간격 12px 안에서 감쇠가 끝나는가"** 이다.

### 4.3 처방

바깥 bloom 만 좁힌다. 안쪽 `::after` inset bloom·테두리·pulse·reduced-motion 분기는 **한 글자도
건드리지 않는다**(간격과 무관한 요소들이다).

```css
.card.card-working{border-color:var(--accent);box-shadow:var(--shadow),0 0 8px -2px var(--accent)}
```

### 4.4 실측 — 값 선정 근거

잣대: **"평범한 카드 대비 accent 성분이 홀로 만드는 ΔL\*"** (공통 `--shadow` 는 §4.2-(4) 대로
잘려도 안 보이므로 빼고 잰다). 라이트 테마.

| 후보 | 가장자리 ΔL\*(d=1) | d=9 | 꼬리(ΔL\*≥1) | 명세 상한 `1.5·blur+spread` |
|---|---|---|---|---|
| **현행** `18px -4px` | 15.54 | 4.22 | **13 → gap 12 초과** | 23 |
| `14px -4px` | 12.80 | 1.24 | 9 | 17 |
| `12px -4px` | 11.16 | 0.40 | 7 | 14 |
| `10px -2px` | 15.12 | 0.32 | 7 | 13 |
| **`8px -2px` (채택)** | **14.30** | **0.00** | **6** | **10 ≤ 12 ✅** |
| `8px 0` | 22.99 | 0.82 | 8 | 12 |

다크도 같은 순위다(`8px -2px` → 가장자리 15.27, 꼬리 6, 현행은 16.57/13).

**`8px -2px` 를 고른 결정적 이유는 가장자리 세기가 아니라 검사 가능성이다.**

- 가장자리 세기는 현행 15.54 → 14.30 으로 **ΔL\* 1.24 감소** — 이 저장소가 쓰는 식별 한계
  2.0 **아래**라 사람 눈에는 같은 세기다. `10px -2px`(15.12)와의 차이도 0.8 로 구분되지 않는다.
- 반면 `8px -2px` 는 명세가 보장하는 **보수적 상한** `1.5×blur + spread = 10` 이 `gap:12px`
  **이하**다. 즉 Blink 실측에 기대지 않고 **어느 엔진에서도** 간격 안에서 끝난다고 말할 수
  있다. `10px -2px` 는 실측으로는 멀쩡하지만 상한이 13 이라 그 보증이 없다.
- 이 성질 덕분에 §7 의 새 회귀 검사를 **리터럴 핀이 아니라 부등식**으로 세울 수 있다 — 이
  저장소가 T25-110 에서 이미 택한 형태("값이 아니라 **관계**를 고정한다")다.

실측 확인: `8px -2px` 의 accent 성분은 **d=9 에서 이미 0.00** 이다. 이웃 테두리는 d=13 에
있으므로 **4px 의 여유**를 두고 사라진다.

## 5. 요구 3 — `.head-row` 를 처음부터 고정

### 5.1 현상

스크롤을 시작하면 헤더가 22px 만큼 위로 따라 올라간 뒤 그 자리에 고정된다.

### 5.2 원인 (CSS 기제 — 실측으로 확정)

`position:sticky` 는 요소가 **정상 흐름 위치에 있을 때는 그대로 흐르다가**, 스크롤포트 상단에서
`top` 거리 안으로 들어오는 순간부터 고정된다. `.head-row` 는 `.wrap{margin:22px auto 32px}` 의
첫 자식이라 문서 최상단이 아니라 **y=22** 에서 시작한다. 따라서 `scrollY` 가 22 에 이를 때까지는
평범하게 함께 올라가고 그 뒤에 붙는다.

```
scrollY=0   → head.top=22    h1.top=32    app.top=80
scrollY=10  → head.top=12    h1.top=24
scrollY=22  → head.top=0     h1.top=10    (여기서부터 고정)
scrollY=300 → head.top=0
```

**이동량은 정확히 22px 이고, `.wrap` 의 `margin-top` 과 같은 값이다.** 추정이 맞았다.

### 5.3 처방 — 상단 여백 32px 을 sticky 요소 **안으로** 옮긴다

```css
.wrap{max-width:1440px;margin:0 auto 32px;padding:0 16px}
.head-row{display:flex;align-items:center;flex-wrap:wrap;gap:12px;position:sticky;top:0;
          z-index:10;background:var(--bg);padding:32px 0 10px;margin-bottom:8px}
```

실측 결과:

```
scrollY=0   → head.top=0  head.h=72  h1.top=32  app.top=80   ← 현행 최상단과 픽셀 동일
scrollY=8   → head.top=0  head.h=72  h1.top=32  app.top=72
scrollY=300 → head.top=0  head.h=72  h1.top=32
```

`h1.top=32`·`app.top=80` 이 현행 최상단 화면과 **완전히 같다.** 직전 PRP 의 결정 S3("스크롤
최상단 화면은 지금과 픽셀 단위로 동일하다")이 그대로 살아 있고, 산술도 형태만 바뀐다 —
`.wrap margin-top 22 + padding-top 10 = 32` → **`.wrap margin-top 0 + padding-top 32 = 32`.**

대가는 하나: 고정 상태의 헤더 두께가 **50px → 72px**(+22px)로 커진다. 900px 뷰포트에서 2.4%
이고, 늘어난 22px 은 `--bg` 와 같은 색이라 "제목 위 여백"으로 읽힌다.

### 5.4 GOTCHA — `padding` 이어야 하고 `margin` 이면 안 된다

`.head-row{margin-top:32px}` 로 같은 여백을 주면 **마진 상쇄(margin collapsing)** 로 그 마진이
`.wrap` 밖으로 빠져나가 결함이 그대로 되살아난다. `.wrap` 은 위쪽에 border 도 padding 도 없어
첫 자식의 top 마진이 통과한다. 실측 대조:

| | scrollY=0 | scrollY=10 | scrollY=30 |
|---|---|---|---|
| `padding-top:32px` (채택) | head.top=**0** | **0** | **0** |
| `margin-top:22px` (함정) | head.top=22 | 12 | 0 ← **이동 재발** |

### 5.5 곁가지 — 이미 낡아 있던 문서 한 줄

`hub/README.md` 의 "새로고침·테마 버튼은 … **화면에 고정되지 않고 스크롤하면 함께 올라간다**"
는 서술은 **이번 변경 전부터 이미 틀려 있다**(sticky 도입 커밋이 이 줄을 갱신하지 않았다 —
`git log -L` 로 확인). 어떤 검사도 이 줄을 물지 않는다. 요구 3 이 정확히 이 동작을 다루므로
같은 커밋에서 바로잡는다(무관한 죽은 코드 정리가 아니라 **변경 대상의 문서**다).

- **D7.** `@media (prefers-reduced-motion:reduce)` 분기를 유지하고, 대상만 `::before` →

  보고한다(bloom 을 통째로 지우고 공허 통과하는 것을 막는다). 실패 문구에 실측 대입값을 함께
  싣는다.
  - 계수 1.5 의 출처: CSS Backgrounds 3 §7.1.1 — blur 는 그림자 경계를 중심으로 blur 거리
    전체에 걸친 전이이며, 표준편차 `blur/2` 가우시안의 실효 확산은 `1.5×blur` 로 잡는 것이
    보수적 상한이다. 실측(Blink)은 이보다 짧다(`8px -2px` → 실측 6px vs 상한 10px) — **검사가
    구현보다 엄격한 방향**이라 안전하다.

## 10. 테스트 계획

### 10.1 자동 (필수 — 전부 통과해야 커밋)

```bash
bash tests/run.sh
python3 -m unittest discover -s tests/hub -t .
python3 -m py_compile hub/bin/*.py
bash -n install.sh && bash -n hub/install.sh
```

- 착수 시점 `bash tests/run.sh` 는 **exit 0 · 실패 0건**이었다(§2.1). 구현 후에도 같아야 한다.
- `tests/run.sh` 안의 T37(뮤테이션 하네스)이 **신설 3행이 실제로 발화하는지** 자체 검증한다 —
  변조행은 "고친 뒤의 규칙을 깨는 변형"이어야 하고, 아니면 T37 이 잡는다.
- **주의**: T22 그룹은 `mktemp -d` 샌드박스에서 `install.sh --scope project` 를 돌려 설치본을
  검사한다. 저장소 안에서 직접 `install.sh --scope project` 를 실행하지 않는다(프로젝트
  `CLAUDE.md` 금지 항목). 실제 `$HOME` 대상 설치도 하지 않는다.

### 10.2 순수 로직 단위 테스트

이번 변경에는 새 순수 함수가 없다(CSS 선언과 그 위의 문자열 검사뿐). 대신 **T25-189 의
부등식 계산이 곧 순수 로직**이므로 그 자체를 케이스로 검증한다 — 검사 안의 파서에 다음 4
케이스가 성립해야 한다.

| 입력 | 기대 |
|---|---|
| `gap:12px` + `0 0 8px -2px` | 통과(10 ≤ 12) |
| `gap:12px` + `0 0 18px -4px` (옛 값) | **실패** 보고 |
| bloom 선언 자체가 없음 | **실패** 보고(공허 통과 금지) |
| `gap` 을 못 찾음 | **실패** 보고 |

3·4번은 뮤테이션으로 직접 덮이지 않으므로 **구현 중 손으로 1회 확인**하고 결과를 구현

### 10.3 시각 확인 (사람이 눈으로 — 자동 검사가 못 잡는 몫)

`bash tests/run.sh` 는 문자열만 본다. **아래는 반드시 브라우저로 본다.**

**요구 1 — 대시보드**
1. 라이트/다크 양쪽에서 진행중 행에 **밴드가 없고**, 좌측 3px 바가 **없다**.
2. 「진행중」 칩 둘레에 halo 가 **숨쉰다**(약 4초 주기). 「완료」·「대기」 칩에는 없다.
3. 진행중 행이 **여전히 한눈에 구분된다** — 굵은 글씨 + 반전된 번호 + 채워진 칩.
4. `#dz-steps`(매크로 단계)와 `#dz-impl-tasks`(구현 세부) **양쪽에** 적용됐다.
5. **PiP 압축뷰**(`#dz-pip-btn`)에서 진행중 행이 좌우로 밀리지 않고 다른 행과 정렬된다.
6. **허브 상세 패널(iframe, 폭 550px)** 안에서 열었을 때 halo 가 패널 밖으로 새지 않는다.
7. OS 의 「동작 줄이기」를 켠 상태에서 halo 가 **멈추되 사라지지 않는다.**

**요구 2 — 허브**
8. 라이트 모드에서 작업중 카드의 bloom 이 옆 카드 경계에서 **끊기지 않는다**(간격 중간에서
   이미 사라져 있다). 1열·2열·3열 폭 전부에서 확인한다.
9. 같은 것을 **아래 줄 카드와의 세로 간격**에서도 확인한다.
10. 작업중 카드가 **여전히 한눈에 띈다** — 좁아졌지만 흐려지지 않았는지.
11. **작업중 + 상세 패널 열림**이 겹친 카드가 여전히 "숨쉬는" 것으로 구분된다.
12. 다크 모드에서 8~11 을 반복한다(현행에서 문제가 없던 쪽이 나빠지지 않았는지).

**요구 3 — 허브**
13. 스크롤을 아주 조금(5~20px) 굴렸을 때 헤더가 **1px 도 움직이지 않는다.**
14. 스크롤 최상단 화면이 변경 전과 **같아 보인다**(제목 위 여백 32px).
15. 카드가 헤더 뒤로 **깨끗이 사라진다**(`--bg` 가 가린다 — 반투명하게 비치지 않는다).
16. 좁은 폭(약 360px)에서 버튼 클러스터가 아랫줄로 내려가도 헤더가 고정을 유지한다.
17. 사용량 패널·상세 패널·툴팁이 **여전히 헤더 위에** 그려진다(층 역전 없음).

### 10.4 회귀 확인 (고의로 깨뜨려 보기)

새 가드가 실제로 무는지 확인한다 — 이 저장소의 관행이자 §2 의 실패 사례가 요구하는 절차다.

## 13. 구현 R2 — 검수 후속 조치 (MEDIUM 2 · LOW 1, CSS 미변경)

### 13.1 지적 1(MEDIUM) — T22-168 두 번째 서브체크가 li.active 문맥으로 좁혀지지 않았다

`grep -qF 'background:var(--accent-soft)}'` 는 파일 전체를 본다 — `.badge.impl` 같은 무관한
규칙이 배경·글자색 선언 순서만 바꿔도(예: `color` 를 먼저 쓰면 `background` 가 블록 끝 `}`

'li\.active\{[^}]*background:var\(--accent-soft\)'` 로 `li.active` 선택자 블록(다음 `}`
이전) 문맥으로 좁혔다 — 위 T22-164 reduced-motion 정규식과 같은 관례.

### 13.2 지적 2(MEDIUM) — T25-189 파이썬 정규식이 주석과 선언을 구분하지 않았다

`re.search` 는 원문 전체(주석 포함)를 본다. `hub_template.html` 의 근거 주석이 CSS 리터럴을
통째로 인용하는 관용구를 쓰는데, 그 인용이 완결된 형태면(예: "…였다 — `,0 0 18px -4px
var(--accent)}`") leftmost-match 특성상 실제 선언보다 먼저 매치돼 값을 잘못 읽는다 — 반대로
무해한 값을 먼저 인용하면 진짜 깨진 선언을 놓치는 공허 통과도 같은 구조에서 가능하다. 두
정규식(`gap_match`·`bloom_match`) 을 돌리기 전에 `source = re.sub(r"/\*.*?\*/", "", source,
flags=re.DOTALL)` 로 주석을 먼저 지워 둘 다 함께 보호했다 — `gap_match` 는 지금은 (주석에

## 14. 후속 결함 — `.head-row` 가 `.wrap` 좌우 거터를 덮지 못해 스크롤 중 세로 경계선이 보인다

> 상태: **구현 완료.** 결정 D19 하나를 추가한다. R1·R2(결정 D1~D18)와 무관한 별개 증상이고,
> `.head-row`·`.wrap` CSS 를 다시 건드리지만 D1~D18 어느 것도 되돌리지 않는다.
> 작업 경로: 축약 경로(구현 → 검수) — 설계 판단은 이 절을 쓰기 전에 이미 확정돼 전달됐다.

### 14.1 증상 (사용자 보고 + 실측 확증)

허브를 스크롤하면 sticky 헤더(`.head-row`) 띠의 좌우 끝에 세로 경계선이 보인다. 스크롤
최상단에서는 정상이다.

### 14.2 원인 (픽셀 실측)

- `.wrap{max-width:1440px;margin:0 auto 32px;padding:0 16px}`(결정 D12 로 이미 손댄 줄).
- `.head-row` 는 `.wrap` 의 첫 자식이고 `background:var(--bg)`(결정 S4)는 `.wrap` 의
  **콘텐츠 박스**만 덮는다. 뷰포트 1000px 실측: `.wrap` = `0~1000`, `.head-row` 배경 =
  `16~984`.
- 카드(`#dzh-app` 안)도 `16~984` 에 놓이지만, 카드가 **칠하는 범위**는 그 박스보다 넓다 —
  `.card{box-shadow:var(--shadow)}`(다크 `0 8px 24px rgba(0,0,0,.45)`)의 확산이 카드 바깥
  24px 까지 번진다. 즉 `0~16`·`984~1000` 두 띠(`.wrap` 의 좌우 padding)에는 카드 그림자가
  칠해지는데, 그 띠에는 헤더 배경이 닿지 않는다.
- 스크롤하면 카드가 헤더 밑을 지나가고, 헤더가 못 덮는 그 16px 띠에만 그림자가 남아 세로
  경계선으로 보인다.

**실측 A/B** — 카드 그림자를 `0 0 0 40px rgb(255,0,0)`(하드 엣지)로 바꾸고 스크롤하면
헤더 띠 좌우 끝에 빨간 세로 줄이 그대로 드러났다. `.head-row` 에 `margin-left/right:-16px`
+ `padding-left/right:16px` 을 주자 사라졌고, `h1` 의 `getBoundingClientRect().left` 는
`16`으로 불변이었다 — 콘텐츠 위치는 옮기지 않고 배경만 넓힐 수 있다는 뜻이다.

### 14.3 처방 — 결정 D19

- **D19.** `:root` 에 `--dzh-wrap-gutter:16px` 토큰을 신설한다(`--dzh-panel-width` 와 같은
  이유 — 여러 규칙이 같은 값을 쓰게 하는 단일 출처). `.wrap` 의 `padding:0 16px` 을
  `padding:0 var(--dzh-wrap-gutter)` 로, `.head-row` 의 `padding:32px 0 10px;margin-bottom:8px`
  를 `padding:32px var(--dzh-wrap-gutter) 10px;margin:0 calc(-1 * var(--dzh-wrap-gutter)) 8px`
  로 바꾼다. `margin(−G) + padding(+G) = 0` 이라 콘텐츠 위치는 불변이고, 배경만 거터까지
  넓어진다. `margin-top` 은 반드시 `0` 이다(D15 재확인 — 마진 상쇄로 스크롤 초반 헤더가
  다시 따라 올라가는 결함이 재발한다). `max-width:1440px;margin:0 auto 32px`(T25-170c 리터럴)와
  `display:flex`(T25-59/T25-170b 앵커)는 건드리지 않는다.

### 14.4 기각한 대안 — 헤더를 뷰포트 전폭으로 흘리기

`.head-row` 를 `.wrap` 밖으로 빼거나 배경에 `100vw` 폭을 주면 1440px 초과 화면의 누출까지
완전히 없어지지만, 넓은 화면에서 헤더 띠가 콘텐츠보다 넓어져 디자인이 바뀐다(§9.3 이 이미
마크업 이동을 기각한 것과 같은 이유 — 대안 C). 거터까지만 덮는 이번 처방은 그 트레이드오프를
받아들이고 아래 §14.5 로 문서화한다.

### 14.5 남은 한계 — 1440px 초과 화면의 8px 꼬리

뷰포트가 1440px 보다 넓으면 `.wrap` 이 가운데 정렬돼 헤더 배경은 `.wrap` 의 테두리
상자(1440px)까지만 덮고, 카드 그림자의 바깥 꼬리 8px(카드 모서리에서 16~24px 구간)이
`.wrap` 밖에 남는다. 그 구간의 알파는 ≤0.041(σ=12 가우시안 근사, `rgba(0,0,0,.45)` 기준)이고
`--bg`(#0E1621) 위에서 ΔL* ≈ 0.35 로 이 저장소가 쓰는 식별 한계(약 2, `.card.card-open`
주석 참고)를 크게 밑돈다 — 방치한다.
