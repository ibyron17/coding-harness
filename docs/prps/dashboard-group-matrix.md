# 대시보드 「그룹 × 단계」 통일 진행률 모델 (PRP)

## 요구사항 요약

`/dashboard` 의 진행률 시각화 데이터 모델을 **단일 선형 단계 목록**에서 **"N개의 그룹(서브피처),
각 그룹은 순서 있는 단계 리스트를 가진다"** 로 통일한다. 그룹이 1개면 지금과 완전히 동일한
선형 단계 띠(`#dz-step-{n}`)로, 2개 이상이면 매트릭스 표(행=그룹, 열=단계)로 렌더링한다.
계기는 다른 프로젝트에서 관측된 "4개 영역 × 4단계 + 게이트 2개" 형태의 세션인데, 현재 모델로는
이런 다중 트랙 세션을 표현할 방법이 아예 없어 LLM 이 매번 즉흥적으로 다른 대시보드를 그리게 된다.
즉흥 렌더링은 이 커맨드의 핵심 가치(**고정 셀렉터 치환으로 항상 기계적으로 정확한 갱신**)를
직접 파괴하므로, 다중 트랙을 **결정적 셀렉터 계약 안으로 흡수**하는 것이 이번 작업의 목표다.

### 이 설계가 전제하는 확정 사항 (재논의 대상 아님)

사용자와의 논의로 이미 확정된 방향이다. 이 PRP 는 아래를 **전제**로 그 위의 구체 설계만 담는다.

1. "그룹 × 단계" 통일 모델을 채택한다. 그룹 1개 = 기존 선형 화면(자산 유지), 그룹 N개 = 매트릭스.
2. 로그(`#dz-log`) · 세션 탭 · `on`/`off` 는 건드리지 않는다. 세션 모양과 무관하게 동작하므로 그대로 재사용한다.
3. 완전한 범용화는 목표가 아니다(YAGNI). 관측된 두 형태만 정확히 커버한다.
4. 결정성을 유지한다. `step` 갱신은 고정 셀렉터 치환이어야 하며 "어디 있는지 찾는" 판단이 개입하면 안 된다.
5. 게이트는 별도 개념을 신설하지 않고 "단계가 1개뿐인 그룹"으로 표현되는지 먼저 검토한다.
6. `#dz-current`/`#dz-next` 서술형 텍스트와 `#dz-badges` 성과 배지는 이번 스코프가 아니다.

## 데이터 모델

### 개념 모델 (문법·마크업과 무관한 정의)

```
Session
  title   : string
  groups  : Group[]          # 순서 있음. len(groups) >= 1
Group
  name    : string | null    # 선형 문법으로 만들어진 그룹 1개만 null 을 가진다
  phases  : string[]         # 순서 있음. len(phases) >= 1
Cell
  state   : "done" | "active" | "wait" | "na"
```

- **칸(Cell)** = (그룹, 단계) 쌍 중 **그 그룹이 실제로 가진 단계**. 진행률의 단위다.
- **전체 칸 수 `N` = Σ len(group.phases)**. 열 수 × 그룹 수가 **아니다**.
- `na` 는 표를 직사각형으로 유지하기 위한 **자리 채움**이며 칸이 아니다(분모에 들어가지 않는다).
- 게이트는 별도 개념이 아니라 `phases` 길이가 1인 그룹이다. (→ 「설계 결정 3」)

### 문자열 문법 (`init` 두 번째 인자)

```
선형 문법 :  "단계1|단계2|단계3"                                   ← 기존. 그대로 동작한다
그룹 문법 :  "그룹A:단계1,단계2|그룹B:단계1,단계2|그룹C:단계1"
```

**모드 판정 규칙 (결정적)** — `|` 로 나눈 세그먼트 목록을 보고:

| 조건 | 해석 |
|------|------|
| 모든 세그먼트에 `:` 가 **없다** | 선형 문법. 전체를 **이름 없는 그룹 1개**로 정규화한다 |
| 모든 세그먼트에 `:` 가 **있다** | 그룹 문법. 세그먼트마다 첫 `:` 앞=그룹명, 뒤를 `,` 로 나눈 것=단계 목록 |
| **섞여 있다** | 오타다. 한쪽으로 추측 해석하지 않고 **보고 후 중단**한다 |

- 그룹명·단계명에 `|` `:` `,` 를 쓰지 않는다(구분자와 충돌).
- 그룹 문법으로 그룹을 1개만 준 경우(`"worktree:설계,구현"`)도 유효하다. 렌더링은 **그룹 수**로
  결정되므로 선형 화면이 나오고, 잃어버릴 뻔한 그룹명은 `#dz-subtitle` 앞머리에 들어간다.

### 열(column) 확정 규칙

열 목록 = **모든 그룹의 단계명을 최초 등장 순서로 중복 없이 모은 것**(합집합).

- 모든 그룹이 같은 단계 목록을 가지는 일반적인 경우, 열 목록 = 그 목록이고 `na` 칸은 하나도 생기지 않는다.
- 어떤 그룹에 없는 단계의 자리는 `data-state="na"` 칸이 된다.
- 셀 좌표 `{p}` 는 **열 번호**(합집합 순번)이지 그룹 내 순번이 아니다. 직사각형인 경우 둘은 같다.
- 관례(강제 아님): 게이트처럼 단계가 1개인 그룹은 인자 목록 **맨 뒤**에 둔다. 그래야 그 그룹만의
  고유 열이 표의 오른쪽 끝에 생겨 `na` 칸이 한곳에 모인다.

### DOM 상 표현 — 셀렉터 계약

기존 「동적(치환 대상) — 7 셀렉터」 표를 유지하되, 진행 시각화 행이 **렌더링 분기에 따라 둘 중 하나**가
된다(셀렉터 개수는 여전히 7이며, 한 파일 안에 둘이 공존하지 않는다).

| 셀렉터 | 치환 대상 | 값 |
|--------|----------|-----|
| `#dz-title` | 텍스트 | 세션 제목 |
| `#dz-subtitle` | 텍스트 | (그룹명 ·) 단계 흐름 요약 · 작업 유형 |
| `#dz-progress-bar` | inline `style="width:N%"` | 완료 칸 / 전체 칸 |
| `#dz-progress-pct` | 텍스트 | `9/18 · 50%` |
| `#dz-step-{n}` **(그룹 1개)** | `class` 속성 + 자식 `.chip` 텍스트 | `done`\|`active`\|`wait` / `완료`\|`진행중`\|`대기` |
| `#dz-cell-{g}-{p}` **(그룹 2개 이상)** | `data-state` 속성 + 칸 텍스트 | `done`\|`active`\|`wait`\|`na` / `완료`\|`진행중`\|`대기`\|`–` |
| `#dz-log` | 자식 `<li>` prepend + `data-current-session` | (변동 없음) |
| `#dz-updated` | 텍스트 | 갱신 시각 |

**init 시점에만 생성되고 이후 치환되지 않는 구조 요소** (동적 표에 넣지 않는다):

- `#dz-matrix` — 매트릭스 `<table>` 자체
- `#dz-group-{g}` — 행 머리 `<th>`. 그룹명 텍스트를 담는다

**불변식 (이 두 가지가 깨지면 `step` 의 결정성이 무너진다)**

1. **한 파일에 `#dz-step-*` 과 `#dz-cell-*` 이 동시에 존재하지 않는다.** `init` 이 둘 중 하나만 만든다.
2. **`<li id="dz-step-…">` 와 `<td id="dz-cell-…">` 는 반드시 한 줄에 하나씩 생성한다.**
   `step` 의 완료 칸 카운트가 `grep -c`(줄 단위 계수)에 의존하기 때문이다.

## 인터페이스

### 호출 규약

```
/dashboard init "<제목>" "<단계1|단계2|...>"
/dashboard init "<제목>" "<그룹A:단계1,단계2|그룹B:단계1,단계2>"
/dashboard step <n> <done|active|wait>            # 그룹 1개 — 단계 번호
/dashboard step <g>.<p> <done|active|wait>        # 그룹 2개 이상 — 행.열
/dashboard log <impl|pass|fail|commit> "<한 줄 요약>" ["상세"] [--round N]
/dashboard on | off
```

`step` 의 첫 인자에 `.` 이 있으면 매트릭스 칸, 없으면 선형 단계다. 인덱스는 모두 1부터 시작한다.

### frontmatter

```yaml
argument-hint: "init \"<제목>\" \"<단계1|...> 또는 <그룹A:단계1,단계2|그룹B:...>\" | step <n>|<g>.<p> <done|active|wait> | log <impl|pass|fail|commit> \"<요약>\" [...] | on | off"
```

> `| on | off` 문자열은 그대로 유지해야 한다 — T23-6 이 `head -4` 에서 이 부분일치를 확인한다.

### `init` — 개정 절차

1단계(기존 파일 가드 + 세션 탭)와 8~9단계(로그·안내)는 **변경 없음**. 3~7단계를 아래로 교체한다.

```

   두 번째 인자를 `|` 로 나눠 세그먼트 목록을 만든 뒤 위 「모드 판정 규칙」을 적용한다.

         <ol class="steps" id="dz-steps">
```

### `step` — 개정 절차 (Bash 1회 + Edit 3회, 결정적)

> 기존 절차는 대상 줄의 전문을 LLM 이 "알고 있다"고 가정했다. 세션 2 가 기존 대시보드를 이어받는
> 경우(단계명을 모른다) 이 가정이 깨진다. 칸이 16개로 늘어나면 훨씬 자주 깨진다.
> 그래서 `log` 가 이미 검증한 **grep 앵커** 방식으로 두 분기를 통일한다.

```
0. **대상 줄과 진행률 줄을 한 번에 확보한다.** Bash 1회:
       grep -n -e 'id="dz-cell-{g}-{p}"' -e 'id="dz-progress-bar"' -e 'id="dz-progress-pct"' .claude/dashboard.html
   (선형 모드면 첫 패턴을 'id="dz-step-{n}"' 로 바꾼다.)
   각 요소는 한 줄에 하나씩 생성되므로 결과는 항상 3줄이다.
   - 대상 줄이 안 나온다 → 인덱스가 틀렸거나 모드를 혼동한 것이다. **다른 칸을 추측해서 고치지 말고
     보고 후 중단한다.** 인덱스를 잊었으면 grep -n 'dz-group-\|dz-cell-' 로 표 전체 지도를 한 번에 얻는다.
   - 대상 칸이 data-state="na" 다 → 그 그룹에 없는 단계다. 보고 후 중단한다.

1. **상태 치환** — 0에서 얻은 줄 전문을 old_string 으로 Edit 1회.
   - 선형: class="{state}" 와 자식 .chip 텍스트   (done/완료, active/진행중, wait/대기)
   - 그룹: data-state="{state}" 와 칸 텍스트       (같은 어휘를 쓴다)

2. **진행률 재계산** — 0에서 읽은 #dz-progress-pct 텍스트가 "M/N · P%" 이므로 M·N 을 그대로 얻는다.
   완료 칸 수는 다시 세지 않고 **전이로 계산한다**:
       이전 상태 ≠ done 이고 새 상태 = done  → M+1
       이전 상태 = done 이고 새 상태 ≠ done  → M-1
       그 외                                  → M 그대로
   (이전 상태는 0에서 읽은 줄에 그대로 적혀 있다 — 기억에 의존하지 않는다.)
   P = round(M/N × 100) 의 정수. #dz-progress-bar 의 style="width:P%" 와 #dz-progress-pct
   텍스트를 Edit 1회로 함께 치환한다(두 줄이 인접해 있다).
   M 이 바뀌지 않았으면 이 단계를 건너뛴다.

3. #dz-updated 텍스트를 현재 시각으로 치환한다. (Edit 1회)
```

**감사(audit)용 재계수** — 진행률이 어긋난 것 같으면 아래 한 줄로 다시 센다. `id` 접두어를 함께
매칭하므로 `<style>` 안의 `.matrix td.cell[data-state="done"]` 규칙 줄에 걸리지 않는다.

```bash
grep -c 'dz-cell-.*data-state="done"' .claude/dashboard.html   # 그룹 모드
grep -c 'dz-step-.*class="done"' .claude/dashboard.html        # 선형 모드
```

## 설계 결정과 근거

### 1. 문법 확장은 `:` 한 글자로, 모드 판정은 "전부 아니면 전무"로

`"그룹A:설계,구현|그룹B:설계"` 는 기존 `|` 의 의미(항목 구분)를 유지하면서 계층을 한 단계만 얹는다.
새 플래그(`--groups`)나 새 서브커맨드(`init-matrix`)를 만들지 않았다 — 그러면 `init` 절차가 두 벌이 되고,
"어느 쪽을 쓸지"라는 판단이 호출 지점마다 생긴다.

판정을 "`:` 가 하나라도 있으면 그룹 모드"가 아니라 **"모든 세그먼트에 있어야 그룹 모드, 하나도 없으면
선형, 섞이면 중단"** 으로 정한 이유: 전자는 `"설계|구현: PRP 반영"` 같은 오타를 조용히 그룹 문법으로
오해석해 이상한 대시보드를 만든다. 후자는 오타를 **즉시 실패**로 바꾼다. 추측하지 않고 멈추는 쪽이
이 커맨드의 성격(기계적 정확성)에 맞다.

하위 호환은 판정 규칙에서 저절로 나온다 — `:` 없는 기존 호출은 전부 "그룹 1개"로 정규화되고,
그룹 1개는 기존 `<ol class="steps">` 를 그대로 그린다. **README 설치 절차·CLAUDE.md·기존 예시는
한 글자도 고칠 필요가 없다.**

### 2. 렌더링 분기 기준은 "문법"이 아니라 "그룹 수"

`"worktree:설계,구현"`(그룹 문법, 그룹 1개)도 선형 화면이 된다. 문법과 렌더링을 분리해야 모델이
하나로 유지된다 — 문법은 입력 표기일 뿐이고, 화면을 결정하는 것은 정규화된 데이터(그룹 수)다.
덕분에 "선형은 특수 케이스가 아니라 그룹 1개"라는 확정 방향 1이 코드(지시문) 수준에서 실제로 성립한다.

### 3. 게이트는 신설하지 않는다 — "단계 1개 그룹 + 합집합 열 + `na` 칸"으로 충분하다

확정 방향 5 에 대한 검토 결과다. M6 대시보드의 게이트 2개를 그룹 모델로 표현하면:

```
"worktree 격리:설계,구현,테스트,검수|영속성·resume:설계,구현,테스트,검수
 |동시성 FIFO 큐:설계,구현,테스트,검수|이벤트 자동 만료:설계,구현,테스트,검수
 |G-1 PRP 승인:승인|G-2 재검수 통과:승인"
```

- 열 = {설계, 구현, 테스트, 검수, 승인} (5열), 행 = 6
- 칸 수 N = 4×4 + 2×1 = **18** — M6 이 손으로 정한 "매트릭스 16 + 게이트 2 = 18칸"과 정확히 일치한다.
  이 수치 일치가 "게이트는 사실 단계 1개짜리 트랙이었다"는 근거다.

그래서 `#dz-gate-*` 셀렉터, 게이트 전용 CSS(`.gate`, 점선 테두리), 게이트 전용 `step` 인자를
**전부 만들지 않는다**. 대신 직사각형 유지를 위한 `na` 상태 하나만 추가한다. `na` 는 진행률 분모에서
빠지므로 "게이트가 4칸짜리 트랙으로 잘못 계수되는" 문제도 생기지 않는다.

**비용**: 게이트 행은 대부분 `–` 로 채워진다(위 예에서 30칸 중 12칸). 이를 줄이려고 열 병합
(`colspan`)이나 별도 섹션을 도입하면 결정적 셀렉터 격자가 깨진다 — `#dz-cell-{g}-{p}` 가 항상 존재한다는
불변식이 사라지고 `step` 이 "이 그룹은 몇 칸짜리였지?"를 판단해야 한다. 시각적 여백이 결정성보다 싸다.

### 4. 칸 내용은 심볼(●◐○)이 아니라 낱말(완료/진행중/대기)

M6 은 심볼 + 범례(`● 완료  ◐ 진행중 …`)를 썼다. 낱말을 택한 이유는 둘이다.

- **어휘 통일**: 선형 분기의 `.chip` 이 이미 `완료/진행중/대기` 를 쓴다. 두 분기가 같은 낱말을 쓰면
  `step` 절차의 치환 규칙이 "상태 → 낱말" 하나로 합쳐진다(분기마다 다른 표를 외우지 않는다).
- **범례를 만들지 않아도 된다**: 심볼을 쓰면 범례가 필수인데, 이 저장소는 사용자 요청으로 `div.legend` 를
  이미 제거했고 T22-7 이 그 회귀를 막고 있다. 낱말은 범례 없이 자명하다.

`–`(na)만 낱말이 없는데, 이건 "해당 없음"이라 읽을 것이 없는 편이 맞다.

### 5. `step` 을 grep 앵커 방식으로 통일한다 (선형 경로 포함)

기존 `step` 은 Bash 없이 Edit 만 했다. 대상 줄 전문을 LLM 이 안다고 가정했기 때문인데,
이 가정은 **세션 2 가 기존 대시보드를 이어받을 때 이미 깨져 있었다**(`init` 가드가 재렌더를 막으므로
단계명을 알 방법이 없다). 칸이 16개로 늘면 훨씬 자주 깨진다.

`log` 절차가 같은 문제를 grep 앵커로 이미 해결했고 T22-12 로 회귀까지 막고 있다. 같은 패턴을 `step` 에
적용하면 비용은 **Bash 1회 증가**, 얻는 것은 "기억에 의존하는 old_string" 제거다. 진행률도 재계수 대신
0단계에서 읽은 `M/N` 에 전이(±1)를 적용해 산출하므로, 칸을 세는 판단이 아예 사라진다.

> 이 항목은 **기존 선형 경로의 절차도 바꾸므로** 승인 대상이다(아래 「승인이 필요한 핵심 결정」 3).

### 6. 매트릭스 CSS 는 템플릿에 상주시키고, init 이 CSS 를 주입하지 않는다

선형 세션에서는 `.matrix` 규칙 9줄이 매칭 대상 없이 놀지만, 그 대가로 `init` 이 `<style>` 을 건드릴
일이 없어진다. `<style>` 주입은 세션 탭에서만 쓰는 예외적 수단이고(마커 `/* DZ:SESSION-RULES */`
한 곳에 한정), 진행 시각화까지 같은 수단을 쓰면 마커가 늘고 실패 지점이 늘어난다. 죽은 CSS 9줄이 더 싸다.

### 7. 진행률 텍스트 형식을 두 분기에서 동일하게 둔다

M6 은 `9/18 칸 · 50%` 였지만 `M/N · P%` 를 그대로 쓴다. `#dz-progress-pct` 의 계약이 분기와 무관하게
하나로 유지되고, 문자열 형식이 갈라지면 `step` 2단계의 파싱이 분기별로 달라진다.
백분율은 **반올림 정수**로 못박는다(기존 문서는 이를 명시하지 않아 `9/18` 같은 경우 표기가 흔들릴 수 있었다).

### 8. 스코프 아웃과 그 사유

| 제외 항목 | 사유 |
|-----------|------|
| `#dz-current`/`#dz-next` 서술형 텍스트 | 확정 방향 6. 서술형 문장은 "기계적 치환"이 아니라 매번 다시 쓰는 판단이라 이 커맨드의 성격과 다르다. 같은 정보가 이미 `#dz-log` 에 시각과 함께 남는다 |
| `#dz-badges` 성과 배지 | 확정 방향 6. 진행률 밖의 성과 목록은 세션 형태와 무관한 별개 기능이며 이번 통일 모델 논의에서 다루지 않았다 |
| `fail` 칸 상태 | 현재 `step` 의 상태는 3종이고 트리거 표는 검수 FAIL 을 `step 4 wait` + `log fail` 로 처리한다. 실패는 로그의 관심사다. 관측된 형태를 커버하는 데 불필요 |
| 다중 셀 `step`(`step 1.2,2.2 done`) | 편의 기능이지 형태가 아니다. 필요가 실제로 확인되면 그때 추가한다(YAGNI) |
| 그룹 추가/삭제, 단계 추가 | `init` 가드가 이미 "진행 중인 대시보드는 재렌더하지 않는다"로 정해져 있다. 형태를 바꾸려면 파일을 지우고 다시 `init` 한다 |
| 자유형(LLM 즉흥) 렌더링 | 확정 방향 4 에서 명시적으로 기각 |

## 리스크와 대안

### 1. 구분자 충돌 — 그룹명·단계명에 `:` `,` `|` 를 쓰면 깨진다

**가능성 중 / 영향 중.** 한국어 단계명(설계·구현·검수)에는 드물지만 `"단계 1: PRP"` 같은 표기는 있을 수 있다.
완화: 규약에 금지 문자를 명시하고, 혼합 판정 시 중단해 조용한 오해석을 막는다.
**기각한 대안**: 따옴표·이스케이프 문법 도입 → LLM 이 파싱해야 할 문법이 늘고, 얻는 것은 드문 케이스뿐이다.

### 2. 칸이 늘면 `step` 호출 횟수가 는다 (4×4 = 16칸)

**가능성 상 / 영향 중.** 한 단계(예: 설계)가 끝나면 4개 그룹의 같은 열을 4번 호출해야 한다.
현실적으로 세션당 수십 회의 Bash+Edit 이 추가된다.
완화(이번 스코프 아님): `step 1.2,2.2,3.2,4.2 done` 처럼 쉼표 목록을 받으면 판단 없이 Edit 만 반복하면 되므로
결정성을 해치지 않는다. 실제 부담이 확인되면 후속 라운드에서 추가한다(승인 질문 4).

### 3. `grep -c` 계수는 "한 줄에 한 칸" 생성 규칙에 의존한다

**가능성 하 / 영향 상.** `init` 이 `<td>` 를 한 줄에 두 개 쓰면 감사용 재계수가 조용히 틀린다.
완화: 데이터 모델의 **불변식 2**로 명문화하고, 정상 경로의 진행률은 재계수가 아니라 전이(±1) 산술로
구하도록 해 계수 의존도를 감사 용도로만 남겼다. 자동 검증은 불가(런타임 산출물).

### 4. 게이트 행의 `–` 여백

**가능성 상 / 영향 하.** M6 형태에서 30칸 중 12칸이 `–` 다. 설계 결정 3 에서 의도적으로 수용했다.
완화: 단계 1개짜리 그룹을 인자 맨 뒤에 두면 고유 열이 오른쪽 끝에 모여 시각적으로 덜 거슬린다(관례).

### 5. 열이 많으면 표가 좁아진다

**가능성 중 / 영향 하.** 카드 폭 860px, 그룹명 열 34% 기준 6열까지는 낱말이 한 줄에 들어간다.
7열 이상이면 낱말이 줄바꿈된다. 가로 스크롤 컨테이너는 래퍼 `div` 를 요구해 세션 탭의 `~` 결합자 제약과
충돌하므로 도입하지 않는다(세션 탭 절의 결론과 동일한 이유). 줄바꿈으로 수용한다.

### 6. 기존 선형 대시보드가 있는 프로젝트에서는 그룹 모드로 전환되지 않는다

**가능성 중 / 영향 하.** `init` 가드가 기존 파일을 재렌더하지 않기 때문이다(의도된 동작).
완화: 형태를 바꾸려면 `.claude/dashboard.html` 을 지우고 다시 `init` 한다 — 가드 문구에 이미 있는 안내와 같다.
`.claude/dashboard.html` 은 임시 산출물이므로 마이그레이션 경로를 만들지 않는다.

### 7. LLM 이 렌더링 분기를 잘못 고를 수 있다

**가능성 중 / 영향 중.** 지시문 방식의 근본 한계로, 기존 기능들과 같은 수준의 리스크다.
완화: 분기 기준을 **"그룹 수"라는 단일 정수**로 축소했고(문법·이름·의도 등 다른 신호를 보지 않는다),
불변식 1("한 파일에 두 형태가 공존하지 않는다")을 명문화했다. T22-24 가 선형 자산의 삭제를 막는다.

### 8. 검토했으나 채택하지 않은 전체 대안

| 대안 | 기각 사유 |
|------|----------|
| **매트릭스 전용 `init-matrix` 서브커맨드** | 절차가 두 벌이 되고 호출 지점마다 "어느 쪽이냐"는 판단이 생긴다. 확정 방향 1(통일 모델)과 정면 충돌 |

## 사용자 승인이 필요한 핵심 결정

1. **인자 문법을 `"그룹명:단계,단계|그룹명:단계"` 로 확정한다.** 모드 판정은 "모든 세그먼트에 `:` 가
   있으면 그룹, 하나도 없으면 선형(=기존 호출 그대로), **섞여 있으면 중단하고 보고**". 그룹명·단계명에
   `|` `:` `,` 를 금지한다. → 기존 호출부는 수정이 전혀 필요 없다.

2. **게이트를 위한 새 개념을 만들지 않는다.** "단계 1개 그룹 + 합집합 열 + `na` 자리 채움 칸"으로
   표현한다(M6 의 18칸과 정확히 일치함을 확인). 대가로 게이트 행 대부분이 `–` 로 채워진다 —
   이 시각적 여백을 수용하는가?

3. **`step` 절차를 grep 앵커 방식으로 통일한다 — 기존 선형 경로의 절차도 바뀐다.**
   호출당 Bash 1회가 늘고, 대신 "대상 줄 전문을 기억하고 있다"는 깨지기 쉬운 가정이 사라진다.
   (이 가정은 세션 2 재개 시 이미 깨져 있던 잠재 결함이다.)

4. **다중 셀 `step`(`step 1.2,2.2 done`)은 이번에 넣지 않는다.** 4×4 세션에서 열 단위 전환이 잦아
   호출 횟수가 늘어나는 부담이 있는데, 지금 넣을지 실사용 후에 넣을지 판단이 필요하다.

5. **칸 표시는 심볼(●◐○)이 아니라 낱말(완료/진행중/대기)로 한다.** M6 대비 시각적 밀도가 낮아지지만
   선형 분기와 어휘가 통일되고 범례가 불필요해진다.
