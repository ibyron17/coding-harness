GitHub 에서 서브에이전트 구조를 가진 코딩 하네스 수십 종을 인기도·구조·벤치마크·논문 증거로 대조한 결과, **품질을 실제로 움직이는 것은 「역할을 나누는 것」이 아니라 「실행 가능한 검증 신호(테스트 실행·재현 명령)로 결과를 거르는 것」과 「컨텍스트를 작게 유지하는 것」**이었다. 같은 모델을 다른 하네스에 넣으면 Terminal-Bench 2.0 에서 최대 **23.8pp** 가 갈리지만(Claude Opus 4.6: Claude Code 58.0% vs ForgeCode 81.8%), 상위권은 bash 루프 하나와 제출 전 검증 게이트를 가진 단순 하네스이고, 설계자/구현자/검수자 식 **역할 분리 멀티에이전트가 상위권에 든 사례도, 그 효과를 분리한 ablation 도 어느 벤치마크·논문에도 없다**(유일한 위임 측정은 14.5% vs 14.8% 로 중립, Aider architect 모드는 단일 모델보다 낮다). coding-harness 는 「독립 검수 필수·설계 승인 게이트·3회차 상한·미해결 종결 ≠ PASS·상시 컨텍스트 래칫」이라는 골격이 2024~2026 증거와 맞고 경쟁군 중 가장 보수적이며, 모델 라우팅을 블라인드 A/B 로 뒷받침한 유일한 사례다. 뒤처진 것은 선행 조사가 지목한 그대로 **「규범을 확인할 기계가 없다」**는 점이고(6주간 착지한 장치는 전부 파일 정적 검사, 세션 행동 게이트는 여전히 0), 거기에 **Claude Code 가 그사이 추가한 네이티브 통제 기능(`effort`·`maxTurns`·`isolation: worktree`·에이전트 범위 `hooks`·`omitClaudeMd`·`Agent(...)` 스폰 제한)을 하나도 쓰지 않는다**는 점, 그리고 **검수자에게 「수정안 텍스트」를 요구하는 현행 방식이 정답 코드를 틀렸다고 판정하는 비율을 73~88% 까지 올린다는 2026년 측정**이 새로 드러났다. 권고는 전부 「산문 → 재료 패키징·재판정·기계 게이트」 방향이며, 즉시 적용 묶음은 대부분 에이전트 파일 1~5줄 또는 1회 측정(비용 S)이고, 상시 컨텍스트(T26)를 늘리는 항목은 조건부 묶음의 3건(렌즈 분할 규칙·깊이 신호·compact 복귀)뿐이라 각각 사유를 적었다. 외부 프레임워크가 내세우는 효과 수치(superpowers 50/60%, OMC 30~50%, ECC +2.25)는 전부 자기 보고라 도입 근거로 인용하지 말고, coding-harness 자신의 시간 기준선(과제당 가동 270분, 전체 검사 27분)으로 전후를 재야 한다.

## 1. 조사 대상 지형과 인기도 — star 가 아니라 다운로드와 push 날짜로 읽는다

어떤 도구가 유명한지 보려고 별 수만 보면 죽은 저장소를 분석하게 된다. 이번 조사는 별 수와 함께 마지막 push 날짜, archived 여부, 월간 다운로드를 2026-10-08 당일 실측했다. 그 결과 별 상위권의 상당수가 이미 멈췄거나 종료 수순이었고, 실사용 신호(npm 다운로드)로 보면 순위가 뒤집힌다.

**제품 CLI 는 star 순서(OpenCode 212k > Claude Code 150k > Codex 128k > Gemini CLI 107k)와 npm 월간 다운로드 순서(Codex 9,114만 > Claude Code 5,336만 ≫ OpenCode 1,057만 ≫ Gemini CLI 163만)가 정반대**다 ([cli_ide_coding_agents.md §1](/private/tmp/claude-501/-Users-dev-private-project-coding-harness/d6fb3cf9-f0ef-48b5-977c-96f85f9eec39/scratchpad/research_notes/서브에이전트%20코딩%20하네스%20벤치마킹/cli_ide_coding_agents.md); 원 데이터 [api.npmjs.org](https://api.npmjs.org/downloads/point/last-month/@openai/codex)). VS Code 확장 설치는 Claude Code 2,724만 > Codex 1,523만 > Cline 556만 순이다 ([Marketplace API](https://marketplace.visualstudio.com/_apis/public/gallery/extensionquery)). 반면 **Roo Code(24k★)는 2026-05-15 archived**, Aider(49k★)는 마지막 기능 릴리스가 2025-08-09 인 유지보수 모드, Continue 확장은 2026-06-19 이후 미갱신이고, Windsurf 는 2026-06 Devin Desktop 으로 리브랜드되며 Cascade 가 종료됐다(2차 출처) ([Kilo blog](https://blog.kilo.ai/thank-you-roo), [andrew.ooo](https://andrew.ooo/answers/what-is-devin-desktop-windsurf-rebrand-explained-july-2026/)). Charm Crush(28.5k★)는 README·`schema.json` 어디에도 서브에이전트 키가 없어 대조군으로만 남았다 ([Crush README](https://github.com/charmbracelet/crush)).

Claude Code 위 워크플로 프레임워크는 6주 사이 star 가 +3~13% 늘었지만 활성도는 양극화됐다. superpowers(296k★)는 08-28 이후 main 커밋 2건으로 「성숙·정체」, ECC(275k★)·spec-kit(141k★)·OpenSpec(71k★)·BMAD(54k★)·OMC(40k★)·gsd-core(10k★, +16.7%)는 100건 이상 커밋의 「고속 변동」, task-master(28k★)·contains-studio(12k★)·humanlayer(11.7k★)는 **0건으로 휴면**이다 ([claude_code_workflow_frameworks.md KQ1](/private/tmp/claude-501/-Users-dev-private-project-coding-harness/d6fb3cf9-f0ef-48b5-977c-96f85f9eec39/scratchpad/research_notes/서브에이전트%20코딩%20하네스%20벤치마킹/claude_code_workflow_frameworks.md); [gh api superpowers](https://api.github.com/repos/obra/superpowers)). 다운로드로는 **OpenSpec 월 245만**이 압도적인데 CLI 가 `npx` 로 호출되는 집계라 사용자 수와 비례하지 않는다 ([npm @fission-ai/openspec](https://api.npmjs.org/downloads/point/last-month/@fission-ai/openspec)). 선행 조사가 「아카이브됨」으로 적은 GSD 는 후속 gsd-core 가 가장 빠르게 성장했고, agent-os 는 구현·검수 커맨드가 사라져 표준 주입 5커맨드만 남아 **비교 대상으로서의 성격이 바뀌었다** ([agent-os commands](https://github.com/buildermethods/agent-os/tree/main/commands/agent-os)).

## 2. 부류·도구별 장단점 — 같은 모델에서 20pp 가 갈리지만, 이기는 쪽은 단순한 하네스다

같은 모델이라도 어떤 하네스에 넣느냐에 따라 점수가 크게 갈린다. 그런데 그 차이를 만드는 것은 복잡한 다중 에이전트 구조가 아니라 「결과를 테스트로 거르는가」와 「컨텍스트를 작게 유지하는가」였다. 역할을 설계자·구현자·검수자로 나누는 것 자체가 점수를 올렸다는 측정은 어디에도 없고, 그 분리는 비용(토큰 7~15배, 서브에이전트 1회당 고정비 1.5만~43만 토큰)만 확실하다.

### 2-1. 하네스 효과의 크기 — 보드에서는 크고, 통제하면 작아진다

Terminal-Bench 2.0 공식 리더보드(2026-10-08 브라우저 조회, 제출자 자체 실행)에서 **같은 모델의 하네스별 격차는 10~20pp** 다: Claude Opus 4.6 는 Meta-Harness 76.4% / Terminus 2 62.9% / **Claude Code 58.0%**, GPT-5.5 는 NexAU-AHE 84.7% / **Codex CLI 82.2%**, Gemini 3.1 Pro 는 TongAgents 80.2% / **Gemini CLI 61.4%**, Claude Opus 4.5 는 Droid 63.1% / Terminus 2 57.8% / Goose 54.3% / **Claude Code 52.1%** / OpenHands 51.9% / OpenCode 51.7% ([tbench.ai ?version=2.0](https://www.tbench.ai/?version=2.0)). 3자 분석은 Opus 4.6 에서 ForgeCode 81.8% 까지 올려 최대 **23.8pp** 로 집계하고, 격차의 원인으로 프롬프트 구조(도구 호출 오류 감소), 환경 스냅샷(초기 탐색 2~5턴 절약), 서브에이전트 「context firewalls」, 제출 전 리뷰어를 든다 ([D. Vaughan 2026-04-09](https://codex.danielvaughan.com/2026/04/09/harness-performance-terminal-bench/)). **Claude Code 하네스는 Opus 4.1/4.5/4.6·Sonnet 4.5·Haiku 4.5 다섯 모델 모두에서 단순 기준 하네스 Terminus 2 보다 낮다(0.8~5.7pp; Haiku 4.5 만 1pp 미만)** — 제출 주체가 표시되지 않아 「열등하다」고 단정할 수는 없지만, 두꺼운 기본 컨텍스트(CLAUDE.md·도구·권한 흐름)가 TB2 과제군에서 가점으로 작동하지 않은 것은 분명하다. 상용 CLI 중 상위권에 든 것은 Codex CLI(4위)뿐이고, Anthropic 은 자사 CLI 를 보드에 올리지 않는 비대칭이 있다(최신 Claude Code 항목은 2026-02-05 Opus 4.6; Opus 4.7·Fable 5.x 항목 없음).

그러나 ICLR 2026 논문의 통제 실험(6 agents × 16 models, 32,155 trials)은 결론을 뒤집는다: **"model selection is usually more important than agent scaffold"** — Codex CLI 는 GPT-5-Nano→GPT-5.2 로 52% 오르는데 Gemini 2.5 Pro 는 OpenHands→Terminus 2 로 17% 오를 뿐이다 ([arXiv 2601.11868 §4](https://arxiv.org/abs/2601.11868)). SWE-bench Verified 공식 데이터(`SWE-bench/experiments` 의 `metadata.yaml` 직접 열람)도 같은 패턴이다 — **프런티어 모델에서 스캐폴드 차이는 3~6pp**(Claude Opus 4.5: mini-swe-agent 74.4% *checked* → OpenHands 77.6% *unchecked* → Live-SWE-agent 79.2% *unchecked*), **약한 오픈웨이트 모델에서 14~27pp**(Kimi K2: mini 43.8% → OpenHands 65.4% *checked* → Lingxi 71.2% *unchecked*) ([SWE-bench/experiments verified](https://github.com/SWE-bench/experiments/tree/main/evaluation/verified)). 100줄짜리 bash-only 에이전트 mini-swe-agent 가 Claude 4.5 Opus(high)로 76.8% 를 낸다는 사실은 스캐폴드 공학의 한계효용이 프런티어 모델에선 낮아졌음을 뜻한다 ([20260217_mini-v2.0.0_claude-4-5-opus-high](https://github.com/SWE-bench/experiments/tree/main/evaluation/verified)). 2026년 통제 실험(4개 모델 × 176 구성)은 **컨텍스트 관리 이득의 대부분이 「컨텍스트 초과 실패 방지」에서 나오고, 계획 단계는 강한 모델에선 정확도가 아니라 비용만 바꾼다**고 보고한다 ([Fan et al., arXiv 2609.20804](https://arxiv.org/abs/2609.20804)).

벤치마크 수치를 읽을 때의 위생 두 가지: **SWE-bench Verified 상위 5개(79.2/79.2/78.8/77.6/77.4)는 전부 `checked: false`** 이고, OpenAI 는 어려운 138과제 감사에서 59.4% 에 결함을 발견하고 모델이 정답 패치를 기억한다는 이유로 Verified 보고를 중단했다([OpenAI, 2차 인용 Decrypt](https://decrypt.co/359012/openai-benchmark-measure-ai-coding-supremacy-contaminated)); Microsoft Research 는 이슈 텍스트만으로 파일 경로를 76% 맞히는 암기 증거를 제시했다([arXiv 2506.12286](https://arxiv.org/abs/2506.12286)). 벤더 수치는 하네스가 다르면 비교 불가다 — Anthropic 이 발표한 Opus 4.7 TB2 69.4%(2차 보도)는 같은 모델의 보드 최고치 WOZCODE 80.2% 보다 11pp 낮고, OpenAI 의 GPT-5.5 82.7% 는 보드의 Codex CLI 82.2% 와 0.5pp 차라 Codex 하네스 기반으로 추정된다 ([Vellum](https://www.vellum.ai/blog/claude-opus-4-7-benchmarks-explained), [Decrypt](https://decrypt.co/365333/openai-gpt-5-5-release-agentic-coding-benchmarks)).

### 2-3. 무엇이 품질을 움직이는가 — 재현되는 효과는 세 가지

반복 재현되는 효과는 **(1) 테스트 실행 기반 검증·선택**, **(2) 관찰 창 제한·컨텍스트 관리**, **(3) 독립 시도 N + 학습된 선택기**다. Agentless 는 다수결만 25.67% → 회귀 테스트 27.00% → 재현 테스트 **32.00%**(GPT-4o, Lite, 구형)로 「most significant performance improvement」가 테스트 실행에서 나왔고([arXiv 2407.01489](https://arxiv.org/html/2407.01489v2)), Trae Agent 앙상블(N=3, Claude 3.7 Sonnet 66.40%)은 프루닝을 빼면 63.60 으로 떨어지며 프롬프트 기반 LLM 선택으로 바꾸면 투표보다 1.8pp 낮다([arXiv 2507.23370](https://arxiv.org/html/2507.23370v1)). OpenHands 는 Claude 3.7 Sonnet 60.6% → 5회 시도 + 학습된 critic 으로 66.4% 를 냈고 「프롬프트 리랭킹보다 전용 critic 모델이 더 효과적」이라고 적었다([openhands.dev 2025-04](https://openhands.dev/blog/sota-on-swe-bench-verified-with-inference-time-scaling-and-critic-model)). SWE-agent ACI ablation 은 마지막 5개 관찰만 보이면 18.0%, 전체 히스토리 15.0%, 전체 파일 뷰 12.7%(GPT-4 Turbo, 구형)로 **컨텍스트를 줄일수록 낫다**([arXiv 2405.15793](https://arxiv.org/html/2405.15793v3)). Chroma 의 18모델 측정은 관련 부분만 담은 ~300 토큰 입력이 전체 ~113k 토큰 입력을 모든 계열에서 크게 앞선다고 보고한다([Chroma Context Rot](https://www.trychroma.com/research/context-rot)).

반면 **「에이전트 간 역할 분리」는 어떤 논문에서도 독립 변수로 측정되지 않았다.** 측정된 것은 「시도 분리(독립 궤적)」와 「판정 분리(critic/selector)」이고, 이 둘이 실제 효과의 출처다([autonomous_benchmark_agents.md KQ5](/private/tmp/claude-501/-Users-dev-private-project-coding-harness/d6fb3cf9-f0ef-48b5-977c-96f85f9eec39/scratchpad/research_notes/서브에이전트%20코딩%20하네스%20벤치마킹/autonomous_benchmark_agents.md)). Anthropic 의 「멀티에이전트가 90.2% 낫다」는 **연구(읽기 위주·병렬 가능) 과제 + 15배 토큰** 조건의 결과이고, 같은 글이 "most coding tasks involve fewer truly parallelizable tasks than research" 라고 못 박았다([Anthropic multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)). 2026년 프리프린트 2건은 **추론 토큰 예산을 같게 맞추면 단일 에이전트가 MAS 와 동급 이상**이고([Tran & Kiela, arXiv 2604.02460](https://arxiv.org/abs/2604.02460)), MAS 의 이득은 모델이 강해질수록 줄어든다([Gao et al., arXiv 2505.18286](https://arxiv.org/abs/2505.18286))고 보고한다. Anthropic 자신의 2026 측정도 조건부다 — 강모델 오케스트레이터 + 약모델 워커는 루틴 작업의 비용 꼬리를 절반~1/3 로 자르지만, **어려운 전체 세트에선 Fable 5 솔로가 같은 정확도를 22~30% 더 싸게** 냈고, 어드바이저(Opus 5.5 + Fable 5.1)는 +1.7점에 비용 2.1배로 「effort 상향과 등가」였으며, 실행자가 자문을 안 구하면 −7점이었다([Anthropic Optimizing for cost and intelligence](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)).

독립 검수 자체의 근거는 단단하다 — 외부 피드백 없는 자기 교정은 성능을 떨어뜨릴 수 있고(ICLR 2024, [arXiv 2310.01798](https://arxiv.org/abs/2310.01798)), 모델은 자기 출력을 알아보고 선호하며([arXiv 2404.13076](https://arxiv.org/abs/2404.13076)), **생성 능력이 올라갈수록 자기 선택과 생성의 격차는 커진다**(ICML 2026 「Self-Verification Cliff」: 더 강한 타 계열 검증자 +3.5pp, **더 약한 검증자 −2.3pp**, [ICML 2026](https://icml.cc/virtual/2026/82529)). MAST(NeurIPS 2025)에서 검증 추가(+15.6%p)는 최대 단일 개입이었다([arXiv 2503.13657](https://arxiv.org/html/2503.13657v2)). 그러나 코드 리뷰 LLM 은 **정답 코드를 틀렸다고 하는 과잉 교정**이 심하고, **「설명하고 수정안을 내라」는 상세 프롬프트가 GPT-4o 의 FNR 을 HumanEval 73.2%, MBPP 87.9% 로 급증**시켰으며, 수정안을 테스트로 실행해 반사실 검증하는 필터가 FNR 을 54.8→16.3% 로 낮췄다([Jin & Chen, arXiv 2603.00539](https://arxiv.org/abs/2603.00539)). 다중 검수자의 이득은 **다른 모델 계열의 오류 비상관**에서 나오고, 다수결은 「popularity trap」에 빠지며 불일치 기반 선택이 상한의 95% 를 회수한다([arXiv 2510.21513](https://arxiv.org/abs/2510.21513)). 같은 모델에 다른 프롬프트를 준 「렌즈 분할」이 같은 비상관을 주는지는 측정된 적이 없다.

계획 우선은 **계획의 질에 조건부**다 — 21,120 궤적에서 표준 계획은 해결률을 올리지만 「a subpar plan hurts performance even more than no plan at all」이고, 주기적 계획 리마인더가 위반을 줄였으며, 초기 단계에 절차를 더 끼우면 성능이 떨어질 수 있다([Liu et al., arXiv 2604.12147](https://arxiv.org/abs/2604.12147)). 스펙(계약)을 먼저 쓰게 하는 것은 Google 프로덕션 버그에서 검출률 +9.8pp(p=0.0352)로 유의했다([Tufano et al., arXiv 2608.17177](https://arxiv.org/abs/2608.17177)). 에이전트가 즉석에서 쓰는 테스트는 「과정과 비용은 바꾸지만 최종 해결률은 바꾸지 않는다」([Chen et al., arXiv 2602.07900](https://arxiv.org/abs/2602.07900)) — 검증 신호는 사전 존재·스펙 유도 테스트에서 와야 한다. 수리 루프는 **첫 2~4회에 이득이 집중**되고 그 뒤는 미미하다([Kiecker et al., arXiv 2607.05197](https://arxiv.org/abs/2607.05197); [Arimbur, arXiv 2604.10508](https://arxiv.org/abs/2604.10508)).

### 2-4. 속도·비용 — 분리의 비용은 확실하고 속도 이득은 병렬일 때만

비용 배수의 공개 수치는 에이전트 ≈ 채팅의 4배, 멀티에이전트 ≈ 15배(Anthropic), **Agent Teams ≈ 단일 세션의 약 7배**(plan mode), 오케스트레이터/실행자 분리 ≈ 2.9배(Blackbox, 미검증), 어드바이저 2.1~3.5배다 ([Costs](https://code.claude.com/docs/en/costs), [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). **서브에이전트 1회의 고정비는 측정자에 따라 15,746(lean scout)~38,401(general-purpose)~436,000 토큰**이며, 측정법은 `claude -p "ok" --model haiku --output-format json` 의 input+cache 토큰 합이다([practicalsystems](https://www.practicalsystems.io/blog/measure-your-subagent-token-cost), [hashnode](https://hashnode.com/posts/what-a-claude-code-subagent-actually-costs-measuring-the-436k-token-fixed-overhead/6a79f5b2da080ae395c58f90)). 비용은 「컨텍스트 창 수 × 각 창의 길이」로 거의 설명되므로 통제 수단은 서브에이전트 수, 시작 컨텍스트 적재량, 워커 모델 단가 셋이다. 어느 도구도 위임 1회의 고정 오버헤드를 공식 수치로 내지 않으며, Codex 의 380.9M 토큰 사고는 「모델 분리를 기본으로 켜지 않으면 오케스트레이터가 자기 등급을 복제한다」는 일반 교훈이다 — Claude Code 도 frontmatter 로 명시하지 않으면 메인 모델을 상속한다([Subagents](https://code.claude.com/docs/en/sub-agents)).

속도는 병렬도가 1 이상일 때만 준다. 설계→구현→검수처럼 직렬인 파이프라인은 서브에이전트화해도 빨라지지 않고 각 단계의 맥락 재수집 지연이 더해진다 — 직렬 파이프라인에서 서브에이전트의 정당화는 속도가 아니라 **격리와 독립 검수**다. 병렬 구현의 측정은 Bernstein 의 10 에이전트 사례(PR 10개까지 25분, 병합까지 70분, 병합 충돌 3건 전부 `cli/main.py`, **에이전트 3개가 워크트리 대신 메인 저장소에 씀**, 순차 대조군 없음) 하나뿐이고([docs.bernstein.run](https://docs.bernstein.run/en/latest/blog/ten-agents-one-release/)), 일화는 전부 「생성이 아니라 검수가 병목」으로 수렴한다 — Simon Willison "I can only focus on reviewing and landing one significant change at a time"([simonw.substack.com](https://simonw.substack.com/p/embracing-the-parallel-coding-agent)). 조직 텔레메트리(10,000+ 개발자)는 과제 완료 +21%·PR +98% 인데 **리뷰 시간 +91%·PR 크기 +154%·버그 +9%** 로 회사 수준 상관이 없다고 보고하고([Faros AI](https://www.faros.ai/blog/ai-software-engineering)), METR RCT 는 숙련 OSS 개발자가 AI 도구로 19% 더 느려졌고 체감(−20%)과 실제(+19%)의 40pp 인지 격차를 보였다([METR 2025](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). TB2 에서 턴 수·토큰과 성공률은 무상관(r≈0)이라 턴 상한은 품질 레버가 아니라 **비용·시간 상한**으로 쓰는 것이 벤치마크 관행과 맞다(mini `cost_limit=$3`, SWE-agent 시도당 `$1.5`·75 calls) ([arXiv 2601.11868 App. G](https://arxiv.org/abs/2601.11868)).

## 3. coding-harness 와의 비교 — 규약은 가장 보수적이고, 강제는 여전히 0

coding-harness 의 뼈대는 증거와 맞고 경쟁군보다 보수적이다. 그러나 「규칙은 있는데 지키는지 확인하는 기계가 없다」는 약점은 6주 전과 같고, Claude Code 가 그사이 내놓은 통제 기능을 하나도 쓰지 않는다. 몇 가지 설계 선택은 증거가 반대 방향을 가리키므로 라벨을 바꾸거나 보강해야 한다.

### 3-1. 앞선 점

**검수자 무쓰기 + 설계 승인 게이트 + 3회차 상한·정체·미해결 종결 규약**은 경쟁군 중 가장 보수적이다. superpowers 는 5라운드 뒤 「Rule and continue」(판정 후 계속, 정지는 예외), BMAD 는 >5회 HALT, OMC 는 QA 5회/동일 오류 3회, gsd 는 3사이클이고, coding-harness 만 상한 도달을 **「PASS 가 아니라 미해결 종결, 사용자 판단 필요」**로 못 박았다([role-separation.md](/Users/dev/private/project/coding-harness/rules/workflow/role-separation.md), [SDD SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)). superpowers 의 「계속」은 무인 운전 전제의 선택이고 coding-harness 는 사람 승인 게이트가 있으므로 현행이 맞다. 재검수에 1회차 지적 항목·기준 커밋을 넘기는 규칙은 superpowers re-review-prompt 의 `[FINDINGS]`·`[FIX_BASE_SHA]` 와 동등하다([re-review-prompt](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/re-review-prompt.md)).

**모델 라우팅의 측정 근거.** coding-harness 의 「설계 opus(조건부 fable) / 구현 sonnet / 검수 sonnet(민감 시 opus) / 탐색 haiku」는 경쟁군 중앙값(ECC sonnet 58/haiku 6/opus 4, 공식 feature-dev 전부 sonnet, OMC critic opus·executor sonnet)과 일치하지만, **라우팅 근거를 블라인드 A/B(2과제 × 6팔)로 댄 곳은 coding-harness 뿐**이고 경쟁군 전원은 비용 직관이다([model-scaffolding-ab-experiments.md](/Users/dev/private/project/coding-harness/docs/prps/model-scaffolding-ab-experiments.md), [claude_code_workflow_frameworks.md KQ5](/private/tmp/claude-501/-Users-dev-private-project-coding-harness/d6fb3cf9-f0ef-48b5-977c-96f85f9eec39/scratchpad/research_notes/서브에이전트%20코딩%20하네스%20벤치마킹/claude_code_workflow_frameworks.md)). A/B 의 「fable 비우위·애매하면 승격하지 않는다」는 Anthropic 어드바이저 측정(실행자 능력이 자문자에 가까울수록 이득 소멸)·Gao et al.(MAS 이득 감소)과 방향이 같다. 「약한 모델에는 자유도를 줄인다」(haiku 는 Explore 만)도 Live-SWE 의 GPT-5-Nano 44→14% 악화, TB2 의 OpenHands+Haiku 13.3% 와 일치한다.

**워크플로 단계 원장.** 허브의 `init/design/approve/impl/pass/fail/commit` 기록은 경쟁군의 원장(superpowers ledger·gsd STATE·OpenSpec `openspec view`)이 **작업(task) 상태**를 적는 것과 달리 **품질 게이트 단계**를 적는다 — 조사 범위의 어떤 도구에도 없고, PreToolUse 게이트의 입력으로 쓸 수 있는 유일한 자산이다([hub/README.md](/Users/dev/private/project/coding-harness/hub/README.md), [dashboard-recording.md](/Users/dev/.claude/rules/hub/dashboard-recording.md)). 「구조만 읽는」 서브에이전트 활동 표시·「N분째 새 기록 없음」·백그라운드 대기 표시는 disler(이벤트 도착만)·ccmanager 류(세션 busy/idle 만)에 없다. 프라이버시 기본값은 Claude Code OTel(기본 `<REDACTED>`)과 같은 편이고, disler(`--add-chat`·LLM 요약)·Opik 플러그인(full content)·claudecodeui(`~/.claude` 에 쓴다)와 반대편이다. 의존성 0·서버 선택·프로젝트 비침습은 비교군 전부(bun/node/rust/docker 상주)에 없다.

**설치기·자산 절제**는 선행 조사 판정 그대로다. 비교한 설정 배포판 6종 중 파일 단위 내용 비교로 충돌을 판정하는 것은 coding-harness 뿐이고, ECC 는 skills 286→293·rules 122 로 인플레이션이 계속된다.

### 3-2. 같은 수준

파일 기반 서브에이전트 정의(md + YAML frontmatter, 프로젝트 > 사용자)는 Claude Code·Gemini CLI·Qwen Code·OpenCode·Kilo·Factory·**OpenHands V1** 까지 수렴한 업계 규격이라 coding-harness 의 `agents/*.md` 배포는 호환성 면에서 중앙값이다([subagent/AGENTS.md](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/subagent/AGENTS.md)). 「탐색 → 질문 → 설계안 → 사용자 승인 → 구현 → 다중 렌즈 검수」 골격은 Anthropic 공식 feature-dev 플러그인과 가장 닮았다 — 차이는 feature-dev 가 설계·검수에 2~3개 병렬 에이전트를 띄우고 구현은 메인이 직접 한다는 점이다([feature-dev.md](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/feature-dev/commands/feature-dev.md)). 검수자 Edit/Write 부재는 공식 feature-dev 3 에이전트와 동급이고, OMC 는 같은 것을 PreToolUse 훅으로 막는다 — coding-harness 는 `tools:` 선언으로 하네스가 강제하므로 동급이다(단 Bash 로 `sed -i`·`git commit` 은 가능하다는 구멍은 §3-3).

### 3-3. 뒤처진 점

## 4. 적용 후보 — 즉시 / 조건부 / 보류·기각

권고는 세 묶음이다. 즉시 묶음은 에이전트 파일 몇 줄이나 1회 측정으로 끝나고 비용이 작다. 조건부 묶음은 효과는 기대되지만 전제를 먼저 확인해야 한다. 보류·기각 묶음은 증거가 없거나 저장소 원칙·선행 결정과 충돌한다. **상시 컨텍스트(T26, 현재 54,238B)를 늘리는 항목은 ⚠T26 으로 표시**했다 — 조건부 묶음의 B(렌즈 분할 규칙 + 미검증 라벨)·D(깊이 신호)·K(compact 복귀) 셋이고, 그 외는 디스패치 때만 로드되는 에이전트 파일·커맨드·허브 코드만 건드린다(C 는 커맨드에 두면 T26 을 피한다). 두 메모리 결정(task-router 기각·transcript_path 보류)은 §4-3 에서 명시적으로 유지한다.

근거 강도: **강** = 복수 논문/공식 데이터 같은 방향 · **중** = 단일 논문 또는 방법 공개된 벤더 보고 · **약** = 자기 보고·설계 논리. 비용: **S** = md 1~5줄 또는 1회 측정 · **M** = 에이전트/허브 모듈 추가, 테스트 동반 · **L** = 새 인프라·배포 채널.

## 5. 하지 말아야 할 것 — 인용 금지 수치와 안티패턴

외부 프레임워크가 내세우는 효과 수치는 거의 전부 자기 보고이고, 벤치마크 1위도 공식 재검증을 안 거친 것이 많다. 아래 수치는 coding-harness 문서나 설계 근거로 인용하지 않는다. 선행 조사 §8 의 안티패턴 10건은 전부 유효하고, 여기에 이번 조사에서 새로 관측된 것을 보탠다.

**인용하지 말 것(수치).** superpowers 6 의 「벽시계 50%·토큰 60% 절감」은 **v5→v6 자기 개선폭**이지 맨 Claude Code 대비가 아니고 참조된 실험 로그는 main 레포에 없다([Superpowers 6](https://blog.fsck.com/2026/06/15/Superpowers-6/)); OMC 「Smart model routing saves 30-50%」·ECC token-optimization 「~60%」·ECC GateGuard 「+2.25점」(과제 2건, 채점 절차 없음)·CE 「1주 → 1~3일」·oh-my-openagent 「7일 → 1시간」은 출처·표본이 없다. 「3.2x~3.9x(4 에이전트)」 워크트리 속도 주장은 페이지가 402 로 열리지 않아 측정인지 예시인지 확인 불가([claudedirectory.org](https://www.claudedirectory.org/blog/claude-code-worktrees-guide)). danielvaughan 의 「Codex ~$4.50 vs Claude ~$46.50」·「67% win rate」는 측정 방법 미공개의 일화다. **Anthropic 「멀티에이전트 90.2% 개선」은 연구 과제 + 15배 토큰**이며 코딩에 일반화된 적이 없다. SWE-bench Verified 상위 5개는 전부 `checked: false` 이고 Verified 자체가 오염 선언이 났으니 **스캐폴드 비교용으로만, 같은 모델·같은 시기·같은 검증 등급끼리만** 쓴다. 벤더 TB2 수치(Anthropic Opus 4.7 69.4%)는 보드 같은 모델 최고치(80.2%)와 하네스가 달라 비교 불가다. Blackbox 「+11.3점」은 독립 검증 없고 비용 2.9배를 수반하며, Kilo Swarm 「−39.2%」는 과제 1개이고 TB4 전체로는 「inconclusive」다([Kilo blog](https://blog.kilo.ai/p/kilo-swarm-a-39-cost-cut-on-the-task)). the-decoder 가 전한 「Fable 5 커맨더 + Sonnet 5 = 96% 성능 46% 비용」은 1차 문서 현재판에서 확인되지 않는다. lobsterblog 「33,000 토큰 오버헤드」는 원문 fetch 실패로 인용 보류. Reddit 집계(「서브에이전트 #1 token killer」)는 2차 요약이라 표본을 모른다. 외부 스캐폴드 수치를 인용할 때는 **(모델, 날짜, checked 여부, Verified/Pro/TB 중 무엇)** 네 가지를 함께 적는 규칙을 두는 것이 안전하다.

**따라하지 말 것(패턴).** Codex 의 `hide_spawn_agent_metadata` 기본값은 오케스트레이터가 자기 등급(Sol/high)을 자식 7개에 복제해 380.9M 토큰을 쓰게 했다 — **모델·effort 분리를 기본값으로 명시하지 않는 구조**가 사고의 원인이다(coding-harness 는 model 은 명시하나 effort 는 상속, §4-1 ⑤). 「experimental」 꼬리표가 오래 붙은 기능(Agent Teams·Cline 서브에이전트·Gemini `experimental.enableAgents`)에 설정 배포판이 의존하는 것은 위험하다 — 안정 표면(서브에이전트·훅·워크트리)에 기댄다. disler 식 `--summarize`/`--add-chat`(LLM 요약·대화 저장)은 비용·프라이버시 둘 다 역행이고 8개월 정지 상태다. 프록시형 관측(ccflare/CCR)은 트래픽 가로채기라 「호스트 기록만 읽는다」와 충돌한다. 자동 승인(`uzi auto`·claude-squad `-y`·ccmanager AI auto-approval)은 병렬 도구가 공통으로 가진 유혹이며 ccmanager 스스로 "bypasses Claude Code's built-in security confirmations" 라고 적는다 — `common/hooks.md` 「Never use dangerously-skip-permissions」와 상충. Vibe Kanban(종료)·uzi(16개월 정지)를 참고 구현으로 삼지 않는다. 「검수자가 수정안을 쓰게 하는 것」은 기능처럼 보이지만 FNR 을 73~88% 로 올린 측정이 있다(§3-4). 「둘 다 지적한 것만 채택」 식 합의 병합은 popularity trap 이다. 그리고 선행 조사 §8 그대로 — 자산 개수 인플레이션(ECC skills 293·rules 122 로 계속 증가), 문서가 구현을 앞질러 표로 포장(ECC continuous-learning-v2), 상시 주입문의 최상급 강제 어법(superpowers `using-superpowers` 에 "YOU DO NOT HAVE A CHOICE" 잔존), 페르소나 연극(BMAD), 훅 안 마케팅 퍼널(ruflo), 권한 전면 개방 settings 배포, README 를 자산 목록으로 믿기, 생성물을 배포 대상에 포함 — 전부 이번에도 관측됐다.

## 6. 한계와 미확인 사항

이 보고서가 말할 수 없는 것이 세 묶음 있다. 첫째, 가장 중요한 비교 실험 두 개가 세상에 없다. 둘째, 리더보드 수치는 제출자가 직접 돌린 것이라 통제 실험이 아니다. 셋째, 권고의 효과를 입증한 외부 데이터가 없어 도입하면 coding-harness 가 첫 측정자가 된다.

**없는 연구.** 코딩 구현 과제에서 「설계자/구현자/검수자 역할 분리」 대 「단일 강모델」을 토큰 예산을 맞춰 비교한 동료심사 연구는 없다(Tran & Kiela 는 multi-hop QA). 「같은 모델 렌즈 N 명」 대 「더 강한 모델 1명」을 코드 리뷰 결함 검출률로 비교한 연구도 없다. 리포지토리 수준 코드 리뷰에서 LLM 검수자의 정밀도/재현율 측정도 없다(Jin & Chen 은 함수 단위). 「opus 설계 → sonnet 구현」 대 「opus 설계 → opus 구현」의 공개 수치도 없다. PRP 품질이 구현 성공률에 미치는 영향은 자체 A/B 도 문헌도 재지 않았다. 「검수 라운드 수 vs 결함 검출」 데이터를 공개한 프레임워크는 없고, superpowers 5·BMAD 5·gsd 3·coding-harness 3 은 전부 설계 판단이다.

**데이터의 성격.** Terminal-Bench 2.0 보드 항목은 제출자 자체 실행이고 COST·TOKENS 열은 전부 비어 있어 하네스별 비용 비교가 불가하다; 2.0 리더보드 행 일부는 JS 렌더라 2차 집계(Snorkel)로만 확인했다. SWE-bench 어느 보드도 벽시계 시간을 기록하지 않는다. Claude Code·Codex CLI·Gemini CLI·OpenCode·Cline·Roo 는 SWE-bench 에 항목이 없다. OpenAI 의 Verified 중단 글은 403 으로 직접 열람하지 못해 2차 출처 간 모수 표현이 다르다(「27.6% of failed tasks」 vs 「138 hardest problems」). Terminal-Bench 논문의 실패 범주별 빈도(§4.4)는 PDF 추출 실패로 범주명만 확인했다. 3자 블로그(danielvaughan)의 Codex 기본값 수치(`max_threads` 6·`max_depth` 1 권장)는 공식 페이지에서 확인하지 못했다. Gemini CLI 서브에이전트 병렬 실행 여부, Cline 서브에이전트의 모델, Conductor 의 격리 방식, Codex cloud 의 동시 상한은 문서에 없다. Reddit 은 크롤러 차단으로 조회 불가였고 HN 스레드는 superpowers·spec-kit 외에 10pts 미만이었다. Amp 의 모델 배정은 조회 시점 스냅샷이고 Amp 스스로 "changes as models improve" 라 밝힌다.

**coding-harness 쪽 미확인.** 세션이 실제로 3단계를 지킨 비율(검수 생략·승인 전 구현 사례 수)은 저장소·메모리 어디에도 집계가 없다 — 「58건 중 54건」은 compact 요약에 호스트 문구가 든 세션 수이지 생략 사례 수가 아니다. 달러 비용 집계는 없다(토큰·모델 비율만). 0f111bd(증분 K6) 적용 **후** 과제당 가동 시간은 미측정이다. 승격 기준이 실제로 발동한 횟수(fable 설계 디스패치 건수)와 「정체」 판정이 실제로 발동한 사례는 기록이 없다. 허브가 `isolation: worktree` 서브에이전트의 cwd 를 어떻게 귀속시키는지는 코드 확인이 필요하다. `effort` frontmatter 가 haiku 에이전트에 무시되는지는 문서로 확인하지 못했다(performance.md 는 haiku 에 effort 레벨이 없다고 적음). README 커맨드 표의 줄 수가 실물과 어긋나는 항목(harness-update 393 vs 319 등)이 있는데 어느 쪽이 정본인지 판정이 없다. 사용자(1인) 외 팀원이 설치·사용한 기록은 0 이라 「공개 배포물」 전제의 제3자 데이터가 없다. 선행 조사의 star 수치는 이번에 재검증한 레포 외에는 그대로다.

**권고의 효과.** 렌즈 분할·확신 재판정·커밋 게이트·재현 증거 의무화·계획 리마인더가 coding-harness 에서 어떤 결과를 낼지는 외부 데이터가 없다. 그래서 §4-1 ⑫(기준선 확장)를 다른 권고와 같은 묶음에 넣었다 — 전후 비교 없이 도입하면 superpowers 의 「50/60%」와 같은 종류의 자기 보고가 된다. 측정 기준은 MEMORY 의 작업 시간 기준선(과제당 가동 270분·전체 검사 27분·재호출 라운드 25%)과 허브 원장이고, 체감 보고는 METR 의 40pp 인지 격차 때문에 근거로 쓰지 않는다.

## 결론

이번 조사가 바꾼 것은 「무엇을 배울까」가 아니라 **「무엇이 품질을 만든다고 믿고 있었나」**다. coding-harness 는 설계자·구현자·검수자 분리를 품질 장치로 전제해 왔지만, 2024~2026 의 벤치마크·논문·벤더 측정은 그 분리 자체가 점수를 올린 사례를 하나도 내놓지 못했고, 측정된 효과는 전부 「실행 가능한 검증 신호로 결과를 거르는 것」「컨텍스트를 작게 유지하는 것」「독립된 시도와 독립된 판정」에서 나왔다. 그러므로 역할 분리는 **통제·감사 장치**로 정당화하고(사람 승인 게이트·검수자 무쓰기·단계 원장 — 이것들은 경쟁군에 없는 진짜 강점이다), 품질은 검수자에게 재현 증거를 요구하고 구현자에게 RED 증거와 스펙을 요구하는 쪽에서 사는 것이 증거에 맞다. 가장 비싼 교훈은 자기 데이터에 있었다 — 검증 기계(K6)를 늘려 과제 시간이 5배가 됐는데 그 기계가 회귀를 잡은 실적은 0 이었고, 외부에서도 Anthropic 의 「평가자 하네스 22배」가 같은 말을 한다. 다음 기계를 붙일 때는 **그 기계가 무엇을 잡았는지 세는 장치**를 함께 붙여야 한다.

6주 전 선행 조사의 결론 「규범은 있는데 확인할 기계가 없다」는 외부에서도 내부에서도 재확인됐고, 그 공백을 메울 가장 싼 재료 둘이 그사이 생겼다 — Claude Code 가 추가한 디스패치 단위 통제(`effort`·`Agent(...)` 제한·`omitClaudeMd`)와 허브가 이미 적고 있는 단계 원장이다. 즉시 묶음 12건은 디스패치 때만 로드되는 에이전트 파일·커맨드·허브 코드와 1회 측정이라 상시 컨텍스트(T26)를 건드리지 않고, 조건부 묶음에서 T26 을 늘리는 세 항목(렌즈 분할 규칙과 미검증 라벨·깊이 신호·compact 복귀)은 각각 「규칙의 자기 기술 정확화와 오류 비상관 확보」「모델 판단 의존 축소」「경쟁군이 기록한 최고가 실패의 예방」이라는 사유가 붙는다. 외부 프레임워크에서 옮겨올 것은 카탈로그가 아니라 세 가지 습관 — 주장을 믿지 말고 증거를 요구하는 검수, 분리를 싸게 만드는 장치(effort 하향·스폰 제한·입력 패키지), 그리고 규범을 읽는 기계(원장 기반 커밋 게이트) — 이고, 그 효과는 coding-harness 가 자기 기준선으로 처음 재게 된다.
