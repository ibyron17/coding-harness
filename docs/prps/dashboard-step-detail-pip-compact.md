# 대시보드 단계별 상세 요약 + PiP 압축 뷰 (PRP)

## 요구사항 요약

`/dashboard` 에 사용자 피드백 두 가지를 반영한다. **(1) PiP 압축 뷰** — 플로팅(Document PiP) 창에서는
「작업 추적」 로그 카드를 감추고 세션 제목·전체 단계 목록·진행률만 보여주며, **현재 진행중인 단계가
한눈에 띄게** 강조한다. **(2) 단계별 상세 요약** — `ol.steps` 의 각 `<li>` 에 "그 단계에서 지금 무엇을
하고 있는지" 한 줄 요약을 붙일 수 있게 `step` 에 **선택적 상세 인자**를 추가한다.

두 요청은 독립적이지 않다. PiP 압축 뷰가 보여줘야 할 "현재 진행중인 단계"의 실질 정보량은 단계명
하나(예: "3 구현")로는 거의 0이고, **상세 텍스트가 붙는 순간 비로소 곁눈질할 가치가 생긴다**
(예: "3 구현 [진행중] — commands/dashboard.md 폴링 스크립트 작성 중"). 그래서 이 PRP 는 두 요청을
한 라운드로 묶고, PiP 압축 뷰에서 **활성 단계의 상세만 노출**하는 규칙으로 둘을 결합한다.

### 사용자 요청 원문

> "pip 모드에서는 간략히 보여주면 좋겠어. 작업 추적 항목은 제거해도 될거 같고, 세션 제목, 전체 진행 단계,
> 현재 진행중인 단계를 보여주면 좋겠어."
> "대시보드 진행 단계 항목에서 각 단계(ol.steps li)에 어떤 업무를 진행 중인지 상세 내용을 간략하게
> 요약해서 보여주면 좋을거 같아."

### 이 PRP 의 위치 — 선행 라운드와의 관계

| 문서 | 상태 | 이 PRP 와의 관계 |
|------|------|-----------------|
| [`session-dashboard.md`](./session-dashboard.md) | 커밋됨 | 원형. "파일의 DOM 자체가 상태" 대전제 |
| [`dashboard-group-matrix.md`](./dashboard-group-matrix.md) | 커밋됨 (c2cde88) | 그룹×단계 모델. **확정 방향 6 이 서술형 텍스트를 스코프 아웃했다 → 이번에 부분 번복한다(설계 결정 3)** |
| [`dashboard-pip-floating.md`](./dashboard-pip-floating.md) | **구현·검수 PASS, 미커밋(워킹 디렉토리)** | 직전 라운드. PiP `.wrap` 이동 방식·폴링 동기화 계약이 이번 설계의 전제 |

> **중요**: 이 PRP 의 기준선은 **커밋된 HEAD 가 아니라 현재 워킹 디렉토리**다.
> `commands/dashboard.md`(924줄) · `tests/run.sh`(1518줄, T22-1~38) · `README.md` 에는 PiP 기능이
> 이미 반영돼 있다. 구현 착수 전에 `git status` 로 그 미커밋 변경이 그대로 있는지 확인한다.

### 확정 사항 (재논의 대상 아님)

1. PiP 에서 로그 카드는 **감춘다**(사용자 요청). 무엇을 어떻게 감출지는 아래 설계 결정 1.
2. 폴링 동기화 계약(`dashboard-pip-floating.md`)을 깨지 않는다. `syncLog` 를 포함한 동기화 7종은
   **한 줄도 퇴화하지 않는다**.
3. `step` 의 기존 두 호출 형태(`<n>`, `<g>.<p>`)는 상세 인자 없이도 **오늘과 완전히 동일하게** 동작한다.
4. `init`/`log`/`serve`/`on`/`off` 절차는 건드리지 않는다.
5. 불변식 1(선형·매트릭스 비공존)과 불변식 2(`<li>`/`<td>` 는 한 줄에 하나)를 유지한다.

### 사용자 스토리

> 전체 경로 작업을 돌리는 개발자로서, 에디터를 보는 동안 화면 구석의 작은 플로팅 창만 흘깃 보고
> **"지금 어느 단계에서 무슨 파일을 만지고 있는지"**를 알고 싶다. 로그 20건을 좁은 창에 밀어 넣는 대신,
> 단계 목록 + 활성 단계의 한 줄 요약만 남기면 곁눈질 비용이 0에 가까워진다.

### 복잡도

**Medium** — 3파일. 신규 코드는 CSS 6줄 + 기존 CSS 1줄 수정 + 마크업 2곳 + `step` 절차 1단계 개정 +
테스트 8개. **새 모듈·새 레이어·새 의존성 없음. 스크립트(JS)는 한 줄도 바뀌지 않는다.**

### 외부 조사

**필요 없음 — 전부 기존 내부 패턴이다.** 새로 쓰는 CSS 기능은 두 가지뿐이고 둘 다 광범위 지원 상태다.

| 주제 | 근거 | 핵심 |
|------|------|------|
| `flex-basis:100%` 로 flex 줄바꿈 | CSS Flexbox Level 1 (CR, 전 브라우저) | `flex-wrap:wrap` 인 컨테이너에서 `flex-basis:100%` 인 아이템은 **항상 새 줄을 차지**한다. 래퍼 `div` 없이 "두 번째 줄"을 만드는 유일한 방법이라 `~` 결합자 제약과 충돌하지 않는다 |
| `:empty` 의사 클래스 | CSS Selectors Level 3 (REC, 전 브라우저) | **자식 노드와 텍스트가 하나도 없을 때만** 매칭된다. 공백 문자 하나만 있어도 매칭이 풀린다 → 상세 span 은 `<span class="step-detail"></span>` 처럼 **내부에 공백조차 넣지 않는다**(GOTCHA) |

**새 npm/pip 의존성 없음. 새 색 토큰 없음.**

## 데이터 모델

### 단계 상세(step detail) — 개념

```
Step                      # 선형 모드의 <li id="dz-step-{n}">
  index   : int           # 1부터
  name    : string        # init 이 넣고 이후 치환하지 않는다
  state   : "done" | "active" | "wait"
  detail  : string        # 신규. 빈 문자열이면 "없음". 줄바꿈 불가. 기본값 ""
```

- `detail` 은 **단계에 종속된 값**이다. 별도 `#dz-current` 요소를 만들지 않는 이유가 여기 있다 —
  분리하면 "어느 단계의 상세인가"를 잃고, 완료된 단계의 이력도 남지 않는다(설계 결정 3).
- `detail` 은 **`step` 호출자가 문자열로 준다.** 대시보드가 추론하거나 `#dz-log` 에서 끌어오지 않는다.
  이 커맨드의 대전제("기계적 치환만, 판단 개입 금지")를 지키는 유일한 방법이다.
- 매트릭스 모드의 `Cell` 에는 `detail` 이 **없다**(설계 결정 4).

### 동적(치환 대상) 셀렉터 표 — 1행 갱신, **개수는 7 그대로**

| 셀렉터 | 치환 대상 | 값 |
|--------|----------|-----|
| `#dz-step-{n}` **(그룹 1개)** | `class` 속성 + 자식 `.chip` 텍스트 + **자식 `.step-detail` 텍스트** | `done`\|`active`\|`wait` / `완료`\|`진행중`\|`대기` / **한 줄 상세(빈 문자열 허용)** |

> `.step-detail` 은 **class** 이고 `<li>` 와 같은 줄 안에 있으므로, 셀렉터 표의 행 수도 `step` 의 Edit 횟수도
> 늘지 않는다. `<li>` 줄 전문 치환 **1회에 상태와 상세가 함께 반영**된다.

## 설계 결정과 근거

### 1. 로그 카드는 **CSS 로 숨긴다**. DOM 에서 제거하지 않는다

사용자 요청은 "제거해도 될 거 같다"였지만, **DOM 제거는 세 곳을 동시에 깨뜨린다.**

| 깨지는 것 | 구체적 결과 |
|----------|------------|
| `sessionTabsChanged(fresh)` | 라이브 `wrap.querySelectorAll('input[name="dzs"]').length` 가 0 이 되고 `fresh` 는 2 이상 → **매 폴링(5초)마다 "새 세션"으로 오판** → `pipWindow.close()` + `location.reload()` 무한 루프. 플로팅이 사실상 사용 불가가 된다 |
| PiP 복귀 (`insertBefore(wrap, pipButton)`) | `.wrap` 이 통째로 돌아오지만 제거된 카드는 돌아오지 않는다 → **로그가 사라진 채 복귀**. 사용자가 지적한 바로 그 무결성 문제 |
| `syncLog(fresh)` | `wrap.querySelector('#dz-log')` 가 `null` → `if(live && next)` 가드에 걸려 조용히 no-op. 이후 로그 갱신이 **영구히 멈춘다**(실패가 눈에 보이지도 않는다) |

`display:none` 은 이 셋 중 어느 것도 건드리지 않는다. 요소는 DOM 에 그대로 있고, 폴링은 보이든 안 보이든
같은 노드를 갱신하며, 복귀는 서브트리 이동 하나로 끝난다. **비용은 CSS 1줄이고 얻는 것은 세 계약의 보존이다.**

부수 효과: 압축 뷰에서 렌더 트리가 줄어 좁은 창의 레이아웃 계산이 오히려 가벼워진다.

### 2. 로그 카드에 `id` 를 붙인다 — 구조 셀렉터(`:nth-of-type`)를 쓰지 않는다

로그 카드에는 현재 식별자가 없다(`<div class="card">` 두 개 중 두 번째). 후보는 셋이었다.

| 후보 | 판정 |
|------|------|
| `body.dz-pip .card:nth-of-type(2)` | **기각.** `nth-of-type` 은 class 가 아니라 **태그(div) 순서**로 센다 — `.wrap` 안의 `div` 는 카드 2개 + `.foot` 3개다. 지금은 맞지만 카드를 추가·재배치하는 순간 **조용히 엉뚱한 카드를 숨긴다.** 실패가 눈에 보이지 않는 종류의 결합이다 |
| `body.dz-pip .card:last-of-type` | **기각.** `.foot` 이 마지막 div 라 애초에 매칭되지 않는다. 실제로는 `.card + .card` 형태를 써야 하는데 역시 순서 의존이다 |
| `<div class="card" id="dz-log-card">` | **채택.** 의도가 마크업에 적혀 있고, CSS 규칙이 1줄로 끝나며, 순서 변경에 영향받지 않는다 |

**`id` 추가가 grep 앵커를 깨지 않는지 직접 검증했다.** `log` 절차 0-a 의 앵커는
`grep -n 'id="dz-log"'` 로 **닫는 따옴표까지 포함**한다. `id="dz-log-card"` 에서는 `dz-log` 다음이
`-` 이므로 이 패턴에 매칭되지 않는다. 즉 앵커의 줄 단위 유일성이 보존된다.
같은 이유로 `step` 0단계의 `id="dz-step-{n}"` 계열도 무관하다. **T22-41 이 이 성질을 직접
회귀 테스트로 고정한다** — "따옴표를 뺀 느슨한 패턴으로 되돌리거나 id 이름을 바꾸면 실패한다".

### 3. 상세는 **단계 안에** 넣는다 — `#dz-current` 서술형 요소를 신설하지 않는다

`dashboard-group-matrix.md` 확정 방향 6 은 `#dz-current`/`#dz-next` 서술형 텍스트를 스코프 아웃했고,
그 근거는 두 가지였다: (a) 서술형 문장은 기계적 치환이 아니라 매번 다시 쓰는 판단이다, (b) 같은 정보가
이미 `#dz-log` 에 남는다.

**이번 설계는 (a)를 우회하고 (b)의 전제를 바꾼다 — 부분 번복이며, 그 차이를 명시한다.**

- **(a) 반박**: 상세 텍스트를 **`step` 호출자가 인자로 준다.** 대시보드는 받은 문자열을 이스케이프해
  치환할 뿐이고, "무엇을 쓸지"는 이미 `log impl "…"` 에서 하던 것과 같은 종류의 입력이다.
  판단이 커맨드 안으로 들어오지 않는다 → 결정성 유지.
- **(b) 전제 변화**: PiP 압축 뷰가 **로그 카드를 감추기로 한 순간**, "같은 정보가 `#dz-log` 에 있다"가
  압축 뷰에서는 성립하지 않는다. 요청 1 이 요청 2 의 필요를 만들어낸 것이다.
- **별도 요소가 아니라 `<li>` 안에 두는 이유**: 상세가 단계와 붙어 있어야 (i) 어느 단계의 이야기인지
  자명하고, (ii) 완료 단계의 상세가 남아 **단계별 이력**이 되며, (iii) `step` 의 Edit 횟수가 늘지 않고,
  (iv) 폴링의 `#dz-steps` `outerHTML` 동기화가 상세까지 **공짜로** 실어 나른다. 별도 요소였다면
  셀렉터 표가 8행이 되고 폴링 계약에 행이 하나 더 붙는다.

### 4. 이번 스코프는 **선형 모드 한정**이다 (매트릭스 제외)

사용자 요청 원문이 `ol.steps li` 를 명시했지만, 그것만이 근거는 아니다.

1. **물리적 공간이 없다.** 카드 폭 860px, 그룹명 열 34%(≈290px)를 빼면 6열 기준 칸당 ≈95px 다.
   `dashboard-group-matrix.md` 리스크 5 는 이미 "7열 이상이면 **낱말 하나도** 줄바꿈된다"고
   기록했다. 그 칸에 한 줄 요약을 넣는 것은 설계가 아니라 파괴다.
2. **표 밖에 두면 새 컴포넌트다.** "활성 칸 목록" 같은 영역을 만들면 셀렉터·마크업·`step` 절차가
   전부 늘고, 이번 요청에 없던 UI 를 발명하게 된다(YAGNI).
3. **매트릭스 세션에서 손실이 없다.** 오늘과 동일하게 동작하고, 상세는 `#dz-log` 가 계속 담는다.
   PiP 압축 뷰에서도 표는 그대로 보이고 로그 카드만 숨는다 — 요청 1 의 이득은 그대로 받는다.
4. **무시는 조용히 하지 않는다.** `step <g>.<p> … "상세"` 를 받으면 상태는 갱신하고 **무시했음을
   한 줄 보고**한다. 중단하지 않는 이유는 상태 갱신 자체는 정상 수행 가능하기 때문이다 —
   부가 정보 손실 때문에 진행률을 멈추면 손해가 더 크다.

> 다중 트랙 세션에서 상세가 실제로 아쉬워지면 그때 별도 라운드에서 다룬다. 지금 만들지 않는다.

### 5. 상세 인자 생략 = **기존 값 유지**, `""` = 지움

세 가지 후보 중에서 골랐다.

| 규칙 | 판정 |
|------|------|
| 생략하면 상세를 **비운다** | **기각.** 하위 호환이 깨진다. 기존 `step 3 done` 호출이 방금 넣은 상세를 지워버려, 상세를 유지하려면 매번 다시 넘겨야 한다 |
| 생략하면 **유지**, 지우려면 `""` | **채택.** 기존 호출의 결과가 오늘과 완전히 동일(확정 사항 3). 지우는 의도는 빈 문자열로 명시된다 |
| 별도 `--clear` 플래그 | **기각.** `""` 로 충분한데 문법이 하나 늘어난다 |

"유지"가 절차상으로도 가장 싸다 — `<li>` 줄 전문 치환에서 **그 부분을 그냥 안 건드리면** 된다.
분기 하나도 추가되지 않는다.

대가: `done` 으로 넘어간 단계에 진행형 문장("…작성 중")이 남아 어색할 수 있다. 완화는 둘이다 —
호출자가 완료 시점의 문장을 넘기거나 `""` 로 지운다(규약에 명시), 그리고 **PiP 압축 뷰에서는
active 단계의 상세만 보이므로** 어색한 문장이 곁눈질 화면에 뜨지 않는다.

### 6. PiP 에서 "현재 단계 강조"는 **CSS 배경**으로 한다 — `scrollIntoView` 를 쓰지 않는다

| 후보 | 판정 |
|------|------|
| active 단계 배경 강조 + 활성 상세만 노출 | **채택.** CSS 2줄. JS 0줄. 폴링과 무관 |
| `scrollIntoView` 로 활성 단계에 스크롤 | **기각.** JS 가 필요하고 **폴링마다 재실행**해야 하며, 사용자가 직접 스크롤한 위치를 5초마다 뺏는다(`<details>` 펼침을 되접는 것과 같은 종류의 실수 — `dashboard-pip-floating.md` 설계 결정 3 이 이미 배운 교훈). 게다가 단계는 보통 4~6개라 420×620 창에서 **스크롤 자체가 거의 발생하지 않는다** |
| 비활성 단계를 아예 숨김 | **기각.** 사용자가 "전체 진행 단계"를 보고 싶다고 명시했다 |

**활성 단계의 상세만 노출**하는 규칙(`li:not(.active) .step-detail{display:none}`)이 요청 1("간략히")과
요청 2(상세)를 잇는 지점이다. 전체 화면에서는 모든 상세가 보여 이력이 되고, 좁은 창에서는
지금 필요한 한 줄만 남는다. **같은 DOM, 다른 스코프.**

### 7. `#dz-updated`(갱신 시각)는 PiP 에서도 **계속 보여준다**

로그 카드와 함께 숨기고 싶은 유혹이 있지만 숨기지 않는다. `dashboard-pip-floating.md` 리스크 1
(숨은 탭의 타이머 스로틀링으로 폴링이 최대 1분까지 늘어질 수 있음)의 **완화책 4개 중 하나가
"`#dz-updated` 가 항상 보여 정체가 눈에 보인다"**였다. 이걸 숨기면 "조용히 틀린 화면"이 된다.
한 줄짜리 `.foot` 이라 압축 뷰의 공간을 거의 먹지도 않는다.

### 8. 스코프 아웃과 사유

| 제외 항목 | 사유 |
|-----------|------|

## 리스크와 대안

### 1. DOM 제거 방식으로 잘못 구현하면 폴링이 무한 루프에 빠진다

**가능성 중 / 영향 상.** 사용자 요청 원문이 "제거해도 될 거 같다"여서 구현자가 문자 그대로
`card.remove()` 를 넣을 유인이 실제로 있다. 그 순간 `sessionTabsChanged` 가 매 폴링마다 참이 되어
플로팅 창이 5초마다 닫히고 페이지가 리로드된다(설계 결정 1).
**완화**: PRP 에 3중 파손을 명시했고, **T22-42 가 역방향 assertion 으로 강제**하며,
수동 확인 14 가 무한 리로드 부재를 직접 확인한다.

### 2. 상세 텍스트에 줄바꿈이 들어가면 불변식 2가 깨진다

**가능성 중 / 영향 상.** `<li>` 가 두 줄로 쪼개지면 `step` 0단계의 grep 앵커가 어긋나고 감사용
`grep -c` 가 조용히 틀린 값을 낸다. 실패가 즉시 보이지 않는 종류다.
**완화**: 절차에 "줄바꿈을 넣지 않는다"를 명문화(불변식 3), T22-46 이 그 문구를 고정, 수동 확인 6·7 로 확인.
**기각한 대안**: 절차에서 개행을 `<br>` 로 치환 → 여러 줄 상세라는 새 요구를 발명하는 것이고,
CSS 말줄임과도 충돌한다.

### 3. `flex-wrap:wrap` 추가가 기존 선형 UI 레이아웃을 바꿀 수 있다

**가능성 하 / 영향 중.** `ol.steps li` 는 오래된 규칙이고 `.chip{margin-left:auto}` 와 상호작용한다.
다만 상세가 비면 `.step-detail:empty{display:none}` 으로 아이템 자체가 사라져 **줄바꿈이 일어날 이유가
없고**, 나머지 아이템 폭 합이 컨테이너를 넘지 않으므로 현행과 동일하게 렌더된다.
**완화**: 수동 확인 1 이 "오늘과 동일"을 직접 확인한다. `row-gap:3px` 로 wrap 시 간격도 못박았다.

### 4. 완료된 단계에 진행형 상세가 남아 어색하다

**가능성 상 / 영향 하.** 설계 결정 5 에서 의도적으로 수용했다.
**완화**: `""` 로 지우는 규약, 그리고 PiP 압축 뷰에서는 active 상세만 보이므로 곁눈질 화면에 뜨지 않는다.
전체 화면에서는 오히려 "이 단계에서 무엇을 했는지" 이력으로 읽힌다.

### 5. 매트릭스 세션은 상세 기능을 못 쓴다

**가능성 중 / 영향 하.** 설계 결정 4 에서 의도적으로 수용했다. 손실은 "없던 기능이 계속 없는 것"뿐이고,
같은 정보는 `#dz-log` 에 남는다. **완화**: 무시 사실을 한 줄 보고해 사용자가 조용히 속지 않게 한다.

### 6. PiP 에서 로그가 안 보여 혼란스러울 수 있다

**가능성 하 / 영향 하.** 사용자가 직접 요청한 동작이다. 창을 닫으면 즉시 전체 화면에서 보이고,
README 에 한 줄 적는다. **기각한 대안**: PiP 안에 "로그는 전체 화면에서" 안내 문구 추가 →
마크업이 늘고, 압축하자는 요청과 정면으로 모순된다.

### 7. 직전 라운드가 미커밋 상태라 기준선이 흔들릴 수 있다

**가능성 중 / 영향 중.** 누군가 `git checkout` 이나 stash 로 워킹 디렉토리를 되돌리면 이 PRP 가
전제하는 `body.dz-pip`·`#dz-pip-btn`·T22-29~38 이 통째로 사라진다.
**완화**: 구현 착수 전 `git status --short` 로 4개 파일의 미커밋 변경을 확인하고
`bash tests/run.sh` 기준선을 기록한다(구현 순서 서두).

## 사용자 승인이 필요한 핵심 결정

1. **PiP 에서 로그 카드는 DOM 제거가 아니라 CSS `display:none` 으로 숨긴다.** 로그 카드에 `id="dz-log-card"`
   1개를 추가한다. 제거 방식은 폴링 무한 루프·복귀 시 로그 소실·`syncLog` 영구 정지를 동시에 일으킨다
   (설계 결정 1). 사용자가 말한 "제거"를 **시각적 제거**로 해석했다 — 맞는가?

2. **단계 상세는 선형(`#dz-step-{n}`) 모드 전용이다.** 매트릭스 모드는 칸 폭(≈95px)이 물리적으로
   부족해 제외하고, `step <g>.<p> … "상세"` 호출은 **상태만 갱신하고 상세를 무시했음을 한 줄 보고**한다
   (설계 결정 4). 매트릭스에서도 상세가 필요하면 별도 라운드로 미룬다.

3. **상세 인자를 생략하면 기존 상세가 유지되고, 지우려면 `""` 를 명시한다.** 기존 `step 3 done` 호출의
   결과가 오늘과 완전히 같아지는 대신, 완료 단계에 진행형 문장이 남을 수 있다(설계 결정 5).

4. **PiP 압축 뷰에서는 활성 단계의 상세만 보이고, 전체 화면에서는 모든 단계의 상세가 보인다.**
   두 요청을 잇는 규칙이다. 전체 화면의 완료 단계 상세를 "이력"으로 남기는 것에 동의하는가?
   (전부 숨기는 쪽을 원하면 CSS 1줄로 바꿀 수 있다.)

5. **`README.md` L120 의 stale 한 줄 수(913 → 실제 924+)를 이번에 함께 바로잡는다.** 직전 라운드에서
   누락된 값이며 어차피 같은 줄을 고친다. 이번 변경 범위 밖의 수정이므로 명시적으로 확인한다.
