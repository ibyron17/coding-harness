# 허브 서버 프로세스 신원 판정 교정 (hub-server-identity)

## 요구사항 요약

`hub_daemon.stop_server()` 는 죽이려는 PID 가 정말 우리 상주 서버인지 `ps -p <pid> -o args=`
출력으로 확인한 뒤에만 시그널을 보낸다. 그런데 비교 기준으로 넘기는 값이 **판정을 수행하는
모듈 자신의 경로**(`hub_daemon.HUB_PY_PATH`)라, 허브가 레포 사본과 설치본 두 벌로 존재하는
실제 환경에서 한쪽으로 기동하고 다른 쪽으로 정지하면 신원 확인이 실패한다. 실패한 자리에서
코드는 프로세스를 남겨 둔 채 **상태 파일만 삭제**하므로, 서버는 CLI 로 더 이상 찾을 수도
끌 수도 없는 고아가 된다. 이 설계는 (1) 신원의 기준을 "판정자의 경로"에서 "기동한 서버가
스스로 적어 둔 경로"로 옮기고, (2) 신원 확인 실패가 상태 파일 삭제로 이어지는 경로를 끊어
**다른 원인의 오판에서도 고아가 생기지 않게** 한다.

## 0. 실측 재현

아래 관측은 모두 이 회차에 직접 실행한 결과다. 재현은 **샌드박스 `HOME`** 에서 했다 —
실제 `~/.claude` 를 건드리지 않고, `hub/install.sh` 도 실행하지 않는다(설치본 역할은
`cp -R hub/bin/.` 로 만든 별도 사본이 대신한다).

재현 스크립트의 골자(전문은 아래 각 관측에 필요한 부분만 인용한다):

```bash
REPO=/Users/dev/private/project/coding-harness
FAKE_HOME=/tmp/hub-identity-repro          # 실제 $HOME 이 아니다
rm -rf "$FAKE_HOME"; mkdir -p "$FAKE_HOME/.claude/hub/bin"
cp -R "$REPO"/hub/bin/. "$FAKE_HOME/.claude/hub/bin/"     # "설치본" 역할
printf '{"server_port": 18794}\n' > "$FAKE_HOME/.claude/hub/config.json"

# 1) 레포 사본으로 기동
HOME="$FAKE_HOME" python3 "$REPO/hub/bin/hub.py" server-start --json
# 2) 설치본으로 정지
HOME="$FAKE_HOME" python3 "$FAKE_HOME/.claude/hub/bin/hub.py" server-stop --json
```

정리 의무: 재현에 쓴 서버는 `server-stop` 이 죽이지 못하므로 **반드시 손으로 회수한다**.
`pgrep -f server-run` 으로 PID 를 찾아, 그 `ps -p <pid> -o args=` 가 재현용 경로를 담고
있는 것만 `kill -9` 한다(사용자의 실제 서버를 같이 죽이지 않도록 경로로 걸러야 한다).

### 관측 A — 오판과 고아 (제기된 결함의 재현)

```
=== 1. 레포 사본으로 기동 ===
{"ok": true, "pid": 8369, "url": "http://localhost:18794/hub.html"}
server.json: {"pid": 8369, "port": 18794, "started_at_ms": 1788918660353}
ps -p 8369 -o args=: …/Python /Users/dev/private/project/coding-harness/hub/bin/hub.py server-run

=== 2. 설치본으로 정지 ===
{"ok": true, "was_running": false,
 "reason": "PID 가 재사용됐습니다 — 그 프로세스는 건드리지 않고 상태 파일만 정리했습니다"}

=== 3. 정지 후 ===
server.json 존재? NO      server_heartbeat 존재? NO
ps -p 8369 -o args=: …/hub.py server-run     ← 살아 있다
```

`ok: true` 로 보고하고 종료 코드 0 을 낸다. 사용자는 서버가 정리됐다고 읽는다.

### 관측 B — 고아는 어떤 CLI 경로로도 회수되지 않는다 (전해 들은 관측에 없던 것)

관측 A 직후의 상태에서 회수 경로를 전수 시도했다. **기동에 쓴 그 사본으로 정지해도
회수되지 않는다.**

| 시도 | 결과 |
|---|---|
| 설치본 `server-stop` (재시도) | `{"ok": true, "was_running": false}` — 아무것도 하지 않음 |
| **레포 사본**(기동한 쪽) `server-stop` | `{"ok": true, "was_running": false}` — 역시 아무것도 하지 않음 |
| 설치본 `server-start` | `{"ok": true, "already_running": true}` — 새로 띄우지도 않음 |
| 설치본 `server-restart` | `{"ok": false, "phase": "start", "reason": "정지 직후에도 서버가 살아 있다고 판정됐습니다 …"}` |
| 포트 점유 | `port 18794 occupied: True` — 계속 점유 |

원인은 단순하다: `stop_server()` 의 첫 분기가 `read_server_record()` 가 `None` 이면
`{"ok": True, "was_running": False}` 로 즉시 반환한다. 상태 파일이 없어졌으므로 **PID 를
아는 코드 경로가 남아 있지 않다.** 남은 회수 수단은 사람이 `pgrep`/`kill` 을 직접 쓰는
것이다.

이것이 이 설계의 초점을 정한다 — **결함의 파괴력은 오판이 아니라 오판 뒤의 삭제에서
나온다.** 신원 기준만 고치면 이 경로(관측 A)는 막히지만, 다른 원인으로 신원 확인이
실패하는 순간 같은 고아가 다시 만들어진다.

### 관측 C — `server-status` 도 어느 사본에게 묻는지에 따라 답이 달라진다

같은 살아 있는 서버 하나(레포 사본이 기동)를 두 사본에게 각각 물었다:

```
설치본에게 물음:   {"record": {"pid": 59521, …}, "process_present": false, "alive": true, "http_ok": true, …}
레포 사본에게 물음: {"record": {"pid": 59521, …}, "process_present": true,  "alive": true, "http_ok": true, …}
```

`server_status()` 도 같은 판정을 쓰므로 `process_present` 가 사본에 따라 뒤집힌다. 대조군
(기동한 사본)이 `true` 를 내므로 이것은 관측 실패가 아니라 판정 실패다.

### 관측 D — 두 사본은 "정규화가 다르게 만든 같은 파일"이 아니다

```
$ ls -li <repo>/hub/bin/hub.py ~/.claude/hub/bin/hub.py
780473897 … /Users/dev/.claude/hub/bin/hub.py
787463859 … /Users/dev/private/project/coding-harness/hub/bin/hub.py
$ shasum -a 256 <두 파일>        # 두 해시가 동일(eb4ed46b…)
$ python3 -c "from pathlib import Path; print(Path(A).resolve()==Path(B).resolve())"
False
```

내용은 같고(같은 sha256), **inode 는 다르고**, `resolve()` 결과도 다르다. 하드링크도
심볼릭 링크도 아닌 독립된 두 파일이다.

### 관측 E — `sys.argv[0]` 은 `ps` 출력의 부분문자열이고, `resolve()` 결과는 아닐 수 있다

같은 스크립트를 세 방식으로 호출하고, 자기 `ps args` 안에 어느 값이 들어 있는지 확인했다:

| 호출 방식 | `argv[0]` 이 `ps args` 에 있나 | `Path(__file__).resolve()` 가 있나 |
|---|---|---|
| 절대 경로 | True | True |
| 상대 경로 (`./probe.py`) | True | **False** |
| 심볼릭 링크 경유 | True | **False** |

### 관측 F — 지금의 파서는 미지의 필드를 무시한다 (전방 호환)

```bash
cd <repo>/hub/bin && python3 -c "
import sys; sys.path.insert(0,'.'); import hub_server_state as s
print(s.parse_server_record('{\"pid\":1,\"port\":2,\"started_at_ms\":3,\"hub_py_path\":\"/a/hub.py\"}'))"
# → ServerRecord(pid=1, port=2, started_at_ms=3)
```

새 코드가 쓴 `server.json` 을 **낡은 설치본이 읽어도** 파싱은 성공하고 오늘과 같은 동작을
한다. 필드 추가가 낡은 사본을 깨뜨리지 않는다.

### 기준선

이 회차에 직접 돌린 착수 시점 기준선:

- `python3 -m unittest discover -s tests/hub -t .` → **629 tests OK**
- `bash tests/run.sh` → **38 그룹 전부 통과 · 실패 0 · exit 0**

구현 후 이 두 값이 유지되는지(테스트 수는 늘어나는지) 대조한다.

## 1. 왜 「경로 정규화」로는 고쳐지지 않는가

2026-08-25 세션이 이 결함을 **「hub 데몬 프로세스 신원 확인의 경로 정규화」**로 명명했다.
그 명명은 문제를 틀리게 지목한다. 세 가지 이유가 있고, 셋 다 위 실측에서 따라온다.

**(1) 두 경로는 같은 파일의 다른 표기가 아니다.** 정규화(`realpath`·`Path.resolve`)가
해결하는 문제는 `~/x`·`./x`·`/a/../b/x` 처럼 **같은 파일을 가리키는 서로 다른 문자열**이다.
관측 D 는 두 사본이 inode 가 다른 독립된 두 파일임을 보인다. 어떤 정규화 함수도 서로 다른
두 파일을 같은 값으로 접지 못한다.

**(2) 비교의 한쪽이 애초에 틀린 값이다.** `is_our_server_process(ps_output, hub_py_path)`
는 순수 함수로서 결함이 없다 — 주어진 두 값을 정확히 비교한다. 결함은 호출부가 두 번째
인자로 `HUB_PY_PATH`(= 판정을 수행하는 모듈이 사는 디렉토리의 `hub.py`)를 넘긴다는 데
있다. 판정해야 하는 명제는 「PID p 의 프로세스가 **이 `server.json` 을 쓴 서버**인가」이고,
현재 코드가 판정하는 명제는 「PID p 의 프로세스가 **나와 같은 설치본에서 실행됐는가**」다.
후자는 안전 성질이 아니라 구현의 부수 효과다. 두 명제는 사본이 한 벌일 때만 우연히
일치한다.

**(3) 정규화를 걸면 오히려 새로 깨지는 경우가 생긴다.** 관측 E 는 상대 경로 호출과 심볼릭
링크 경유 호출에서 `resolve()` 결과가 `ps` 출력에 **없다**는 것을 보인다. 지금은 기동과
정지가 같은 절대 경로일 때 우연히 맞는데, 양쪽에 `resolve()` 를 걸면 `ps` 텍스트(정규화되지
않은 원래 argv)와의 대조가 그 두 경우에서 실패한다. 즉 정규화는 이 결함에 대해 무효이면서
새 실패 모드를 추가한다.

### 이 결함은 이미 「문서화된 우회」로 봉인돼 있었다

`docs/prps/hub-server-control-skill.md` 의 「확정된 전제 (재론하지 않는다)」 절 전제 2 는
이 결함을 정확히 서술해 놓고, 고치는 대신 **호출 규약**으로 회피한다: "CLI 호출은 언제나
설치 경로로 한다. 저장소 체크아웃 경로로 부르면 … `is_our_server_process()` 가 'PID
재사용'으로 오판하고 `server.json` 만 지워 고아 프로세스를 만든다."

이 설계는 그 전제를 **철회**한다. 사람이 매번 지켜야 하는 호출 규약은 안전장치가 아니다 —
규약을 어기면 조용히 `ok: true` 가 나오고 프로세스가 남는다. 관측 B 는 규약을 어긴 결과가
「그 세션에서 실패」가 아니라 「그 서버를 영구히 회수 불가」임을 보인다.

## 2. 신원의 기준을 무엇으로 바꾸는가 (후보와 실패 모드)

| 후보 | 기준 | 실패 모드 | 판정 |
|---|---|---|---|
| **(a) 기동 경로를 레코드에 적고 대조** | 서버가 기동 시 자기 `hub.py` 경로를 `server.json` 에 적고, 정지 측은 **그 값**과 `ps` 출력을 대조 | 데이터 모델 변경(필드 1개 추가) · 구버전 레코드에 그 필드가 없다(§3) · 레코드가 손상되면 판정 불가로 떨어진다(오늘과 같음) | **채택** |
| (b) 경로를 보지 않고 `server-run` 만 확인 | `ps` 출력에 `server-run` 이 있으면 우리 것 | 방어가 문자열 1개로 줄어든다. PID 가 재사용된 프로세스의 명령행에 그 토큰이 우연히 들어 있으면 `SIGKILL` 이 남의 프로세스로 간다(예: 그 토큰을 인자로 받은 스크립트·에디터·`grep`). 오늘의 기준보다 **약하다** | 기각(단, §3 의 구버전 전이에서 한정적으로 차용) |
| (c) 포트·상태 파일 기준 | 레코드의 `port` 가 HTTP 200 을 내면 그 PID 를 우리 것으로 본다 | 포트 응답은 **PID 와 묶이지 않는다.** 레코드가 낡아 PID 가 남의 것으로 바뀐 상태에서 그 포트에 (우리든 남이든) 무엇이든 응답하면, 무관한 PID 에 `SIGKILL` 을 보내는 것을 승인해 버린다. 신원 기준으로는 오늘보다 위험하다 | 기각(고아 **증거**로는 유용 — §5) |
| (d) PID + 프로세스 시작 시각 | `ps -p <pid> -o lstart=` 를 `started_at_ms` 와 대조 | 실측: `lstart` 는 **초 해상도**이고, 실제 프로세스 시작과 `started_at_ms`(bind 직후 기록) 사이에 이 머신에서 **929ms** 차가 났다(인터프리터 기동+임포트+bind). 따라서 수 초의 허용 창이 필요한데, 그 창이 곧 PID 재사용이 통과할 틈이다. 게다가 `lstart` 문자열은 `%a %b %d` 형식이라 **로케일 의존**이다 — `LC_TIME` 이 영어가 아니면 파싱이 깨져 "판정 불가"로 떨어지고, 안전 기본값과 결합하면 정지 불가가 된다 | 기각(경로와 직교하는 앵커라 훗날 보강 후보로는 남는다. 지금은 필요 없다 — YAGNI) |
| (e) `lsof` 로 포트 소유 PID 확인 | `lsof -i :<port>` 의 PID 와 대조 | 표준 라이브러리가 아닌 외부 도구 의존이 새로 생긴다(허브의 명시적 금지). 권한·속도 편차도 크다 | 기각 |

### 채택안 (a) 의 구체적 형태 — 무엇을 적는가

적는 값은 `Path(__file__).resolve()` 계열이 **아니라** 서버 프로세스의 `sys.argv[0]` 이다.
근거는 관측 E 다: `argv[0]` 은 세 호출 방식 모두에서 `ps args` 의 부분문자열이었고,
`resolve()` 결과는 상대 경로·심볼릭 링크 경유에서 부분문자열이 아니었다. 우리가 원하는
성질은 "정규 경로"가 아니라 **"그 프로세스의 `ps` 텍스트와 대조 가능한 값"** 이므로,
`ps` 가 보여주는 것과 같은 출처(argv)를 쓰는 것이 맞다.

또한 이 값은 `_spawn_server_process()` 가 `[sys.executable, HUB_PY_PATH, "server-run"]` 로
띄운 그 문자열과 동일하다 — spawn 경로에서는 절대 경로가 그대로 들어가고, 사람이 포그라운드
디버깅으로 `python3 hub/bin/hub.py server-run` 을 직접 부른 경우에는 그 상대 경로가 그대로
기록돼 역시 `ps` 와 맞는다.

빈 문자열·공백만인 `argv[0]`(임베딩 등 비정상 실행)은 **필드 부재와 같게** 취급한다 —
빈 문자열을 그대로 비교 기준으로 쓰면 오늘의 `is_our_server_process` 안전 가드(빈 경로면
`False`)에 걸려 그 서버가 영구 정지 불가가 된다.

## 3. 하위 호환 — 새 필드가 없는 `server.json` 을 만나면

이 전이는 가설이 아니다. **이 머신에서 지금 돌고 있는 서버의 레코드가 그 경우다**(읽기만
했다):

```
$ cat ~/.claude/hub/server.json
{"pid": 94393, "port": 8794, "started_at_ms": 1788917021160}
```

새 코드를 설치하는 순간 이 레코드는 "필드 없는 구버전 레코드"가 되고, 그 서버는 재기동
전까지 계속 산다.

| 전이 규칙 | 결과 | 판정 |
|---|---|---|
| 필드 부재 = 판정 불가 → 손대지 않는다 | 그 서버는 **영구 정지 불가**가 된다(관측 B 와 같은 곤경을, 설치 직후 모든 사용자에게). 회수는 손으로 `kill` | 기각 |
| 필드 부재 = 우리 것 → 무조건 kill | 신원 확인이 통째로 사라진다. 하필 구버전 레코드가 **가장 오래된** 레코드라 PID 재사용 확률이 가장 높은 쪽이다 | 기각 |
| **필드 부재 = 완화된 기준으로 강등** | `ps` 출력이 「공백으로 끊은 토큰 중 하나가 `/hub.py` 로 끝난다」 **그리고** 「`server-run` 을 담는다」를 둘 다 만족할 때만 우리 것으로 본다. 여기에 §5 의 하트비트 게이트가 겹쳐 삭제를 막는다 | **채택** |

강등 기준을 후보 (b)(=`server-run` 단독)보다 좁게 잡은 이유: kill 경로이므로 우연한 일치를
줄일 값이 남아 있으면 쓴다. `/hub.py` 를 **토큰의 접미**로 보는 것은 부분문자열
(`foo_hub.pyc`·`my-hub.python`·산문 속 언급)로 보는 것보다 좁고, 공백이 든 홈 디렉토리
(`/Users/x y/.claude/hub/bin/hub.py`)에서도 성립한다 — 공백으로 끊으면
`y/.claude/hub/bin/hub.py` 가 나오고 이것도 `/hub.py` 로 끝난다(2회차 검수 정정 — 원문은
슬래시 없는 `hub.py` 접미로 적었는데, 그 기준이면 `ps -r hub.py …` 처럼 파일명만 언급하는
토큰도 접미 조건을 만족해 §9-2 의 N6 기대치(그런 토큰은 `False`)와 모순됐다. 실제 구현
(`hub_daemon.LEGACY_RECORD_HUB_PY_TOKEN_SUFFIX`)은 처음부터 `/hub.py` 였다 — 이 문서의
서술만 뒤늦게 맞춘다).

**이 좁힘이 배제하는 경우(비망라 예시 1건, 3회차 검수 실측으로 모집단을 재정정).** 이
배제를 가르는 것은 `hub_py_path` **필드의 유무가 아니라 그 값의 경로 형태 여부**다 —
`hub_daemon._is_path_like_hub_py_path` 는 필드가 없는 값(None)과, 필드는 있지만 디렉토리
성분이 없는 값(예: `"hub.py"`)을 완화 분기에서 **똑같이** 취급한다. 그래서 이 배제는
「구버전 레코드」(필드 자체가 없던 과거 코드의 산물)에 한정되지 않는다 — **신규 코드가
쓴 레코드라도** 디렉토리 성분이 없는 호출로 뜬 서버는 같은 처지에 놓인다. 예: `hub/bin`
안에서 `python3 hub.py server-run` 을 그대로 실행하면 `argv[0]` 이 `"hub.py"` 이고,
`run_server` 는 그 값을 그대로 `server.json` 에 적는다(3회차 검수 실측 — 신규 형식
레코드다, 필드는 채워진다). 이 값의 `ps` 토큰도 `/hub.py` 로 끝나지 않으므로 완화 판정
자체가 실패하고, 신원 대조는 「불일치」로 떨어진다. 프로세스가 실제로 살아 있어 하트비트는
신선하므로, `stop_server` 는 이를 §5 판정표의 「불일치 + 하트비트 신선」행으로 분류한다
(「완화 일치 + 하트비트 없음」행이 아니다) — 도달하는 진단 문구는 다르지만 결과는 같다:
상태 파일이 보존되고 `ok:false` 가 영구히 난다.

이 잔존은 「전이 창의 크기와 닫히는 조건」 문단이 다루는 전이 창(구버전 레코드가 재기동
1회로 닫히는 창)과 다르다 — 신규 코드로 재기동해도 같은 bare 호출을 반복하면 기록값은 여전히 경로
형태가 아니어서 창이 저절로 닫히지 않는다(닫으려면 호출 자체가 디렉토리 성분을 포함해야
한다). 비망라 예시: 심볼릭 링크를 디렉토리 성분 없는 상대 경로로 참조해 기동한 호출도
같은 방식으로 배제된다. 전수 증명이 아니다.

**이 잔존을 받아들이는 근거(3회차 검수 판정, 차단 아님).** `server-run` 은
`hub/bin/hub.py` 의 모듈 docstring 과 `cmd_server_run` 이 이미 포그라운드 디버깅용
진입점으로 선언한 명령이고, 변경 전 코드는 같은 입력에서 상태 파일을 지워 고아를 만들었으므로(관측 A 와
같은 성격) 이 회차는 이 경우에서도 개선이다.

**전이 창의 크기와 닫히는 조건.** `write_server_record` 는 `run_server` 의 bind 직후에만
호출되므로(`hub_server.py` 를 읽어 확인 — 유지보수 티커는 하트비트만 touch 한다), 레코드는
**서버를 한 번 재기동하면 새 형식으로 갱신된다.** 즉 완화 기준이 적용되는 모집단은
"새 코드 설치 시점에 이미 돌고 있던 서버"이고, 그 서버를 한 번 정지·기동하면 창이 닫힌다.
영구 강등이 아니다.

**반대 방향(전방 호환)은 이미 성립한다.** 관측 F — 지금의 `parse_server_record` 는 미지의
필드를 무시하므로, 새 코드가 쓴 레코드를 낡은 설치본이 읽어도 오늘과 같이 동작한다. 따라서
"레포는 새 코드, 설치본은 낡은 코드" 상태에서도 낡은 쪽이 더 나빠지지는 않는다(더 좋아지지도
않는다 — 그 쪽은 여전히 자기 경로와 대조한다).

## 4. 안전 기본값은 유지되는가

`is_our_server_process` 의 docstring 이 선언한 성질은 **"확인할 수 없으면 손대지 않는다"**
이고, 이것이 남의 프로세스에 `SIGKILL` 을 보내지 않는 방어다. 판정 기준을 바꾼 뒤의 상태를
분기별로 적는다.

| 상황 | 오늘 | 변경 후 | 안전 성질 |
|---|---|---|---|
| `ps` 실행 자체 실패(`None`) | 아무것도 안 함, `ok:false` | 동일 | 유지 |
| `ps` 빈 출력(프로세스 없음) | 상태 파일 정리 | 동일 | 유지(부재의 적극적 관측이다 — §5) |
| 레코드에 경로 있음 · 대조 불일치 | 프로세스 안 건드림 + **상태 파일 삭제** | 프로세스 안 건드림 + 삭제는 §5 의 게이트를 통과할 때만 | **강화** |
| 레코드에 경로 없음(구버전) | 판정자 자기 경로와 대조 → 대개 불일치 → 삭제 | 완화 기준으로 판정, 삭제는 §5 게이트 통과 시만 | 부분 교환(§3) |
| 레코드에 경로 있음 · 대조 일치 | (사본이 한 벌일 때만 도달) SIGTERM→SIGKILL | 사본이 두 벌이어도 도달 | 의도된 변경 |

**어디를 의도적으로 교환하는가.** 구버전 레코드 한 경우에서만, "정확한 경로 일치"를
"어떤 `hub.py` + `server-run`"으로 낮춘다. 이 교환은 (i) 모집단이 설치 시점에 살아 있던
서버로 한정되고, (ii) 재기동 1회로 닫히고, (iii) 그 완화된 판정이 참일 때도 §5 의 하트비트
게이트를 함께 통과해야 kill 로 간다. 나머지 모든 분기에서 안전 성질은 유지되거나
강화된다.

`SIGKILL` 을 보내는 지점(`_wait_for_process_exit`)도 같은 기준을 써야 한다. 지금 이 함수는
`HUB_PY_PATH` 와 대조하므로, `stop_server` 만 고치면 SIGTERM 을 보낸 직후의 대기 루프가
"신원이 확인되지 않는다 → 죽은 것으로 간주"로 판단해 **아직 살아 있는 프로세스를 죽었다고
보고하고 상태 파일을 지운다.** 이 함수는 레코드(또는 그 경로)를 인자로 받아야 한다.

## 5. 고아를 만들지 않는 실패 처리 (핵심)

### 원칙

**상태 파일 삭제는 "부재의 적극적 관측"에만 조건부로 허용한다. "신원을 확인하지 못했다"는
부재의 관측이 아니다.**

오늘의 코드는 스스로 모순한다 — "이 프로세스가 내 것인지 확신할 수 없으니 건드리지
않겠다"고 판단한 직후에, **그 프로세스를 다시 찾을 유일한 메모(PID 가 적힌 `server.json`)를
버린다.** 관측 B 가 그 결과다.

### 하트비트가 독립 증인이다

`server.json` 과 별개로 `server_heartbeat` 가 있고, 이것은 살아 있는 서버의 유지보수 티커가
매 사이클 touch 한다(`hub_server._maintenance_loop`). 그래서 하트비트 신선도는 **`ps` 경로
대조와 완전히 독립적인** 「허브 서버가 살아 있는가」 증인이다. 관측 A 직후의 상태를 7초
기다린 뒤 다시 물었을 때 이 성질이 그대로 드러났다:

```
heartbeat 존재? YES      server.json 존재? NO
status: {"record": null, "process_present": false, "heartbeat_age_ms": 2392,
         "alive": true, "http_ok": true, …, "orphaned_evidence": true, …}
```

`server.json` 이 사라진 뒤에도 살아 있는 서버가 하트비트를 계속 되살렸다. 반대로, PID 가
정말 재사용된 경우(서버가 죽은 경우)에는 하트비트를 갱신하는 주체가 없어 TTL 이 지나면
만료된다.

### 판정표

`heartbeat_fresh` 는 새 개념이 아니다 — 이미 있는 순수 함수 `hub_server_state.is_server_alive`
를 `_server_already_running` 이 쓰는 방식과 똑같이 쓴다(새 순수 함수를 만들지 않는다).

| `ps` 결과 | 신원 대조 | 하트비트 | 해석 | 행동 |
|---|---|---|---|---|
| 실행 실패 | — | — | 관측 불가 | 아무것도 안 함 · `ok:false` (오늘과 같음) |
| 빈 출력 | — | — | 프로세스 부재를 관측했다 | 상태 파일 정리 · `ok:true` (오늘과 같음) |
| 있음 | 일치 | — | 우리 서버다 | SIGTERM → (필요 시) SIGKILL → 정리 |
| 있음 | 불일치 | **만료** | 살아 있는 허브 서버의 증거가 없다 → 레코드가 낡았다 | 상태 파일 정리 · `ok:true` · "PID 재사용" (오늘과 같음) |
| 있음 | 불일치 | **신선** | **무언가가 우리 하트비트를 갱신하고 있다 → 오판일 수 있다** | **아무것도 안 함 · 상태 파일 보존 · `ok:false` + 진단** |

**「일치」행의 숨은 분기(2회차 검수 정정 — D4·R4 와의 자기모순 해소).** 이 표는 신원 대조를
「일치 / 불일치」이분법으로만 나누지만, 구현은 「일치」안에서 한 번 더 갈린다. 레코드에
기록된 경로가 있고 그 경로로 정확히 일치했으면 이 표의 하트비트 열 그대로 `—`(보지 않음)
이고 곧장 kill 로 간다. 그런데 **레코드 값이 경로 형태가 아니어서(필드 부재를 포함한다)
완화 기준으로 일치했으면** 하트비트를 **함께** 본다(3회차 검수 정정 — 이 하위 분기를 가르는
것은 "구버전이냐"가 아니라 "기록값이 경로 형태냐"다; `hub_daemon._is_path_like_hub_py_path`
가 그 판정을 `is_our_server_process`·`stop_server` 양쪽에 같은 기준으로 공급한다) — 아래
D4·R4 가 적은 「세 조건의 동시 성립」(완화 판정의 두 토큰
조건 + 하트비트)이 가리키는 것이 이 하위 분기다. 즉 하트비트 AND 는 **완화 분기에만**
걸리고, 정확한 경로 일치 분기는 이 표의 대시 그대로 하트비트를 보지 않는다. 표에 열을 하나
더 늘리지 않은 이유는 YAGNI다 — 행 5개짜리 표에 「신원 대조 방식(정확/완화)」 열까지
더하면 표가 필요 이상으로 커지는데, 이 문단이 그 구분을 온전히 서술한다.

마지막 행이 이 설계의 실질이다. 관측 A 는 정확히 이 행에 해당하고(하트비트가 신선했다),
변경 후에는 삭제가 일어나지 않으므로 **고아가 만들어지지 않는다.** 사용자는 `ok:false` 와
종료 코드 1, 그리고 PID 가 적힌 진단을 받는다. 상태 파일이 남아 있으므로 원인을 고친 뒤
(예: 새 코드로 재기동, 또는 손으로 확인) 다시 정지할 수 있다.

### 이 게이트가 신원 기준 수정과 독립적으로 값을 갖는 이유

브리핑의 질문 4 가 지적한 그대로다. 신원 대조가 실패하는 원인은 이번에 고치는 두 벌 설치
말고도 있을 수 있다. 기제: 판정은 `ps` 텍스트와 기록된 문자열의 부분문자열 일치이므로,
그 텍스트나 그 기록을 바꾸는 어떤 변화도 대조를 깨뜨릴 수 있다. 그 기제에서 따라오는
한계는, 대조 실패를 "프로세스 부재"로 해석하는 코드가 남아 있으면 원인이 무엇이든 같은
고아가 난다는 것이다. 비망라 예시: `ps` 출력이 긴 명령행에서 잘리는 경우, `hub.py` 를
개명하는 변경, 래퍼 스크립트나 `python3 -c` 경유 실행, 레코드 필드가 부분 손상된 경우.
이 목록은 전수 증명이 아니다 — 그래서 원인별 대응이 아니라 **삭제 조건 자체**를 고친다.

### 낡은 레코드를 보존해도 다른 것이 막히지 않는가 (확인함)

`_server_already_running` 은 하트비트가 만료됐고 레코드의 PID 가 우리 것으로 확인되지
않으면 `False` 를 돌려준다 → 포트가 비어 있으면 `start_server` 가 그대로 spawn 하고, 새
서버가 bind 직후 `server.json` 을 덮어쓴다. 즉 **진짜로 낡은 레코드가 남아 있어도
`server-start` 는 막히지 않는다.** 보존이 새 교착을 만들지 않는다.

`server-restart` 는 stop 이 `ok:false` 면 start 를 시도하지 않는다(그 함수의 문서화된 결정
D4). 위 마지막 행에서 restart 가 `{"ok": false, "phase": "stop", …}` 로 멈추는 것은
의도된 동작이다 — 낡은 서버가 살아 있을 수 있는 상태에서 새로 띄우지 않는다.

### 인접해서 발견한 것 — 이 회차의 범위 밖으로 둔다

`clear_server_state` 는 `server.json` **과 하트비트를 함께** 지운다. 그래서 관측 A 직후
(하트비트가 되살아나기 전) `server-status` 는 이렇게 답했다:

```
{"record": null, "process_present": false, "heartbeat_age_ms": null, "alive": false,
 "http_ok": true, …, "orphaned_evidence": false, …}
```

고아가 실재하는데 `orphaned_evidence` 가 `false` 다 — 그 판정식이 `record is None and alive`
이고, 하트비트까지 지워져 `alive` 가 `false` 이기 때문이다. 5초 뒤 살아 있는 서버가
하트비트를 다시 touch 하자 `orphaned_evidence: true` 로 바뀌었다(§5 의 인용). 즉 고아를
표면화하도록 만들어 둔 그 필드가 **고아가 만들어진 직후 한동안 침묵한다.** 그 창에서
유일한 단서는 `record: null` 과 `http_ok: true` 의 동시 성립이고, 이 조합에는 이름이 없다.

이것을 이 회차에서 고치지 않는 이유: §5 의 게이트가 착지하면 「신원 오판으로 상태 파일이
지워지는」 경로가 막히므로 이 창에 **도달하는 주된 경로가 사라진다.** 남는 도달 경로(수동
조작, 과거에 이미 만들어진 상태)를 위해 판정식이나 상태 필드를 지금 손대는 것은 이 회차의
요청 범위를 넘는다. 다음 회차가 같은 것을 다시 발견하지 않도록 여기 적어 둔다.

### 진단에 남의 명령행을 싣지 않는다

불일치 분기의 진단에 `ps` 출력 원문을 담고 싶은 유혹이 있다. 그러나 그 출력은 **PID 가
재사용됐다면 제3자 프로세스의 명령행**이고, 명령행에는 토큰·비밀번호가 실릴 수 있다. 허브는
프라이버시 우선 설계를 고지한 도구다. 그래서 진단에는 **우리 자신의 데이터만** 싣는다:
`pid` 와 `recorded_hub_py_path`(우리가 적은 값), 그리고 "직접 확인하려면
`ps -p <pid> -o args=` 를 보십시오"라는 안내.

## 7. 데이터 모델과 인터페이스

### 데이터 모델

```python
@dataclass(frozen=True)
class ServerRecord:
    """server.json 의 내용 — 서버 자신이 bind 성공 직후 1회 쓴다."""

    pid: int
    port: int
    started_at_ms: int
    # 이 서버를 띄운 hub.py 의 경로 — `sys.argv[0]` 그대로다(정규화하지 않는다).
    # 정규화하지 않는 이유: 대조 상대가 `ps -p <pid> -o args=` 텍스트이고 그 텍스트는
    # 정규화되지 않은 argv 이다. 상대 경로·심볼릭 링크 경유 실행에서 resolve() 결과는
    # ps 출력의 부분문자열이 아니다(설계 문서 관측 E).
    # None = 이 필드가 없던 구버전 코드가 쓴 레코드(완화 판정으로 강등, 설계 문서 §3).
    hub_py_path: str | None = None
```

`server.json` 스키마(새 형식):

```json
{"pid": 94393, "port": 8794, "started_at_ms": 1788917021160,
 "hub_py_path": "/Users/x/.claude/hub/bin/hub.py"}
```

### 인터페이스

```python
# hub_server_state.py (순수, 잎 모듈 — 다른 허브 모듈을 임포트하지 않는다)
def parse_server_record(text: str) -> ServerRecord | None:
    """server.json 텍스트를 판다. 깨졌거나 필수 3필드가 없으면 None.

    `hub_py_path` 는 선택 필드다 — 없거나 null 이거나 공백만이면 None 으로 접는다.
    필수로 만들면 구버전 레코드가 통째로 None 이 되어 그 서버가 영구 정지 불가가 된다.
    """

# hub_daemon.py (순수 판정 + 그것을 쓰는 I/O — 이 모듈의 기존 형태를 유지한다)
def is_our_server_process(ps_output: str, hub_py_path: str | None) -> bool:
    """`ps -p <pid> -o args=` 출력이 `hub_py_path` 로 기동된 우리 hub.py server-run 인가.

    `hub_py_path` 가 None(구버전 레코드)이면 완화 기준으로 판정한다 — 공백으로 끊은 토큰
    중 하나가 `/hub.py` 로 끝나고 `server-run` 을 담으면 우리 것으로 본다.
    판정할 수 없으면(빈 출력 등) False — "확인할 수 없으면 손대지 않는다"가 안전한 기본값이다.
    """

def stop_server() -> dict:
    """신원 확인 → SIGTERM → (필요 시) SIGKILL → 상태 파일 정리.

    신원 확인이 실패했을 때 상태 파일을 지우는지는 하트비트가 결정한다(설계 문서 §5) —
    하트비트가 신선하면 살아 있는 서버가 있다는 뜻이므로 오판을 의심해 아무것도 하지 않고
    ok:false 로 보고한다. 지우면 그 프로세스를 다시 찾을 PID 가 사라져 고아가 된다.
    """

def _wait_for_process_exit(record: ServerRecord) -> dict:
    """SIGTERM 후 재확인하고, 안 죽으면 SIGKILL. 재확인도 record 의 경로로 대조한다 —
    자기 모듈 경로로 대조하면 살아 있는 프로세스를 죽었다고 오판해 상태 파일을 지운다."""
```

하트비트 신선도 판정에는 TTL 이 필요하고 TTL 은 config 에서 온다 —
`stop_server()` 는 지금 config 를 읽지 않으므로 `hub_collect.load_config()` 호출 1개가
새로 들어간다(`restart_server` 가 이미 같은 호출을 한다 · 테스트 베이스
`HubDaemonIoScenarioTest` 가 `CONFIG_PATH` 를 이미 격리해 준다). TTL 계산은 기존 순수 함수
`hub_server_state.server_heartbeat_ttl_ms` 를 그대로 쓴다.

`stop_server()` 의 반환 계약(추가되는 분기만):

```python
{"ok": False,
 "reason": "PID <n> 의 프로세스를 우리 서버로 확인하지 못했는데 하트비트는 살아 있습니다 — "
           "오판일 수 있어 상태 파일을 그대로 두고 아무것도 하지 않았습니다",
 "pid": <int>,
 "recorded_hub_py_path": <str | None>}   # 우리가 적은 값만 싣는다(§5 프라이버시)
```

### 함수·파일 크기

`stop_server` 는 분기 2개(하트비트 조회 + 게이트)만 늘어 50줄 아래에 머문다.
`hub_daemon.py` 는 800줄 상한(T25-100)의 절반 남짓이라 이 변경의 증분이 그 여유를
잠식하지 않는다. **줄 수를 숫자로 적지 않는다** — 이 파일을 고치는 커밋마다 움직이는 값이고,
적는 순간 그 커밋이 값을 밀어 낡는다(이 절의 초안이 실제로 그렇게 낡았다:
`rules-docs-sync.md` §17-1 이 저장소 자신에 적용한 원칙, `T39` 가 강제한다).
지금 값은 `wc -l hub/bin/hub_daemon.py` 로 센다. 새 모듈이 필요하지 않다.

## 8. 설계 결정과 근거

| # | 결정 | 근거 |
|---|---|---|
| **D1** | 신원의 기준을 **레코드에 기록된 기동 경로**로 옮긴다 | 판정해야 하는 명제가 "이 `server.json` 을 쓴 서버인가"이고, 레코드는 그 서버 자신이 쓴 자기 신고다. 판정자의 경로는 그 명제와 무관하다(§1-(2)) |
| **D2** | 기록하는 값은 `sys.argv[0]`, **정규화하지 않는다** | 대조 상대가 정규화되지 않은 `ps` 텍스트다. 관측 E — `resolve()` 결과는 상대 경로·심볼릭 링크 경유에서 `ps` 출력의 부분문자열이 아니다 |
| **D3** | 새 필드는 **선택 필드**(기본 `None`) | 필수로 하면 구버전 레코드가 파싱 실패(`None`)가 되고, 그러면 `stop_server` 첫 분기가 "서버 없음"으로 반환해 그 서버가 영구 정지 불가가 된다(관측 B 와 같은 곤경) |
| **D4** | 구버전 레코드는 **완화 기준으로 강등**하되 §5 게이트를 함께 통과해야 kill | 두 극단(영구 정지 불가 / 방어 무력)을 모두 피한다. 모집단이 한정되고 재기동 1회로 닫힌다(§3) |
| **D5** | **상태 파일 삭제를 하트비트로 게이트**한다 | 결함의 파괴력은 오판이 아니라 삭제에서 나온다(관측 B). 하트비트는 `ps` 경로 대조와 독립적인 생존 증인이다(§5) |
| **D6** | 새 순수 함수·새 상태·새 설정 키를 **만들지 않는다** | 필요한 판정(`is_server_alive`)이 이미 순수 함수로 있고 이미 테스트돼 있다. 판정표를 `decide_stop_action` 같은 새 함수로 뽑는 안을 검토했으나 기각했다 — 이유는 D7 |
| **D7** | 판정 분기를 `stop_server` **안에** 둔다(전용 판정 함수로 뽑지 않는다) | 두 가지 이유. (i) `tests/run.sh` T25-16 은 AST 로 "`os.kill` 이 있는 **같은 함수 안에서** `is_our_server_process` 를 **맨 이름으로** 먼저 호출한다"를 강제한다 — 판정을 다른 함수로 옮기면 이 가드가 깨지고, 그러면 `tests/mutations.tsv` 의 T25-16 면제행이 "개정·수정 시 변조행으로 승급"을 요구한다. PID 재사용 방어의 회귀 가드를 이 회차에 흔들 이유가 없다. (ii) 늘어나는 분기가 2개라 함수가 50줄 아래에 머문다 — 추출의 실익이 없다(YAGNI) |
| **D8** | 진단에 `ps` 출력 원문을 싣지 않는다 | PID 가 재사용됐다면 그것은 제3자의 명령행이고 비밀이 실릴 수 있다(§5) |
| **D9** | `docs/prps/hub-server-control-skill.md` 의 「전제 2」를 **철회**로 표시한다 | 그 전제는 이 결함을 호출 규약으로 회피한 것이고, 이 설계가 그 회피를 불필요하게 만든다. 남겨 두면 다음 회차가 "이미 결정된 전제"로 읽어 같은 우회를 재생산한다 |

**D7 관련 3회차 정정.** `T25-16` 이 못박는 것은 `is_our_server_process` **호출 한 개의
위치**(같은 함수 안에서 `os.kill` 보다 먼저)뿐이다 — 완화 분기 판정(`is_path_like` 류)의
**본문**을 공용 헬퍼로 뽑는 것은 이 가드를 건드리지 않는다(3회차 검수가 합성 변형 2개로
실증했다: 판정 본문을 헬퍼로 추출하고 `is_our_server_process` 호출은 `stop_server` 에
그대로 두면 `T25-16` 은 여전히 `OK`). D7 (ii) 「추출의 실익이 없다」는 유효하지만, (i)
「판정을 다른 함수로 옮기면 가드가 깨진다」는 **`is_our_server_process` 호출 자체**에
한정해 읽어야 한다 — 이 구분이 없으면 다음 회차가 불필요하게 손발이 묶인다. 실제로 이
회차의 Major 1 수정이 그 구분 위에서 `_is_path_like_hub_py_path` 헬퍼를 뽑았다(`hub_daemon.py`).

### 검토했으나 채택하지 않은 대안

**대안 1 — 신원 판정을 없애고 `server.json` 의 PID 를 무조건 신뢰한다.** 상태 파일은 우리가
쓴 것이므로 그 PID 를 그냥 죽이면 코드가 대폭 단순해진다. 기각: 재부팅 후 낡은 상태 파일이
남았거나 서버가 비정상 종료한 뒤 PID 가 재활용되면 `SIGKILL` 이 무관한 프로세스로 간다.
`is_our_server_process` 의 존재 이유가 이것이고, `tests/run.sh` T25-16 이 그 가드의 회귀를
막고 있다. 이 저장소는 그 방어를 이미 값으로 인정했다.

**대안 2 — 레코드에 경로 대신 「설치 식별자」(예: 설치 시각·manifest 해시)를 적는다.**
사본을 구분하는 더 안정적인 키를 만드는 방향이다. 기각: `ps` 출력과 대조할 수 없다 —
`ps` 는 argv 만 보여주므로, argv 에 없는 식별자는 프로세스 쪽에서 읽을 방법이 없다.
`/proc` 이 없는 macOS 에서 그 값을 프로세스로부터 회수하려면 새 통신 경로(추가 상태 파일
또는 서버에 질의하는 엔드포인트)가 필요하고, 이는 "읽기 전용 서버 · 새 HTTP 경로 없음"
성격과 충돌한다.

**대안 3 — 두 벌 존재 자체를 없앤다**(레포의 `hub/bin` 을 설치본으로 심볼릭 링크). 기각:
`hub/install.sh` 의 소유권 모델(레포가 배포하는 파일을 복사한다)을 바꾸는 큰 변경이고,
레포를 지우거나 브랜치를 옮기면 설치본이 따라 움직이는 새 결합을 만든다. 그리고 결함의
본질(오판 시 삭제)은 사본이 한 벌이어도 다른 원인으로 재발할 수 있다(R6).

### 3회차 검수가 남긴 잔존 한계 (후속 판단 대상, 차단 아님)

**엄격 분기의 부분문자열 대조는 하트비트 게이트 밖에 있다.** 기록값이 경로 형태이면
(`/` 를 하나라도 포함하면) 게이트를 건너뛰고 곧장 kill 로 간다 — 그런데 엄격 분기의 대조는
`hub_py_path in ps_output` 이라 기록값이 짧으면 아무 명령행에나 걸린다. 실측(3회차 접지
렌즈): 기록값 `"/"` · 하트비트 없음 · `ps` 출력이 `"/sbin/launchd server-run"` 인 조건에서
`os.kill` 이 1회 발사됐다. 같은 조건에서 기록값이 `"hub.py"`·`None` 이면 완화 분기로 가서
게이트가 잡는다(0회).

**차단하지 않은 이유.** `sys.argv[0]` 은 항상 실행한 스크립트(또는 심볼릭 링크)의 경로라
`"/"` 같은 값을 만들 수 없고, `_normalize_hub_py_path` 도 비공백 문자열을 보존만 한다 —
도달 경로는 `server.json` 의 손편집이나 손상이다. 검수 판정은 Minor · 차단 아님이었다.

**후속으로 고칠 때의 두 방향.** (a) 엄격 분기 진입에도 최소 조건(기록값이
`LEGACY_RECORD_HUB_PY_TOKEN_SUFFIX` 로 끝난다)을 요구한다 · (b) 엄격 일치도 공백 토큰 단위로
대조한다. (b) 가 더 근본적이지만 공백이 든 경로에서의 토큰 분해를 먼저 확인해야 한다 —
`test_n7_legacy_record_relaxed_criteria_with_spaced_home_directory` 가 그 케이스를 고정한다.

**이것은 전수 증명이 아니다.** 위는 실측한 한 조합이고, 같은 기제(짧은 기록값 + 부분문자열
대조)에서 다른 조합이 더 있을 수 있다. 비망라 예시로 적는다.

## 12. 승인이 필요한 결정

1. **신원 기준을 (a) 로 옮기고 `ServerRecord` 에 선택 필드 `hub_py_path` 를 추가한다**
   — 데이터 모델 변경이다. 값은 `sys.argv[0]` 이며 정규화하지 않는다(관측 E).
2. **구버전 레코드는 완화 기준으로 강등한다** — 안전 성질을 그 한 경우에서만 의도적으로
   교환한다. 대안(영구 정지 불가 / 무조건 kill)은 §3 에서 기각했다.
3. **신원 확인 실패 시 상태 파일을 지우지 않는다**(하트비트가 신선할 때). `server-stop` 의
   그 분기가 `ok:true` → `ok:false` 로 바뀌므로 **사용자에게 보이는 계약 변경**이다.
4. **`tests/run.sh` 정적 가드(T25-172) 추가 여부**(§9-4) — 원장 행 1건이 함께 따라오는
   비용이 있다. 넣지 않아도 §9-2·§9-3 이 회귀를 잡는다.
