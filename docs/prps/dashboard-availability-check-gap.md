# `/dashboard` 가용성 확인 실패 — 도구 카테고리 불일치 (이슈 분석)

## 요약

`jackal-to-giraffe` 프로젝트의 Phase 6(App v1) 착수 시점, 메인 세션이 전체 경로 작업을
정확히 인지하고 `/dashboard init`을 부르려 시도했음에도 실제로는 호출하지 않고 넘어갔다.
원인은 "기능이 없었다"가 아니라 **가용성을 확인한 도구(`ListSkills`)가애초에 개인 커스텀
커맨드를 인덱싱하지 않는 도구였다**는 것 — 확인 자체가 구조적으로 항상 실패하게 되어 있었다.

## 재현 조건 / 발견 경위

`jackal-to-giraffe` 세션에서 실기기 테스트 중 사용자가 "왜 대시보드 발행을 안 했느냐"고
질문하면서 드러났다. 해당 세션의 jsonl 트랜스크립트(39MB, 세션 전체)를 직접 grep/파싱해
아래 타임라인을 재구성했다.

## 근본 원인 분석

### 기각된 최초 가설 — "그 시점엔 커맨드가 설치돼 있지 않았다"

`~/.claude/commands/dashboard.md`의 mtime이 2026-08-21 09:35로, Phase 6 착수(08-20 02:18)보다
늦다는 점에서 처음엔 "설치 전이었다"고 추정했다. **반증됨**:

- `coding-harness/.claude/dashboard.html`(실제 생성 산출물)의 mtime이 **2026-08-18 12:03** —
  Phase 6 착수보다 이틀 앞선다. 즉 그 시점에 기능은 이미 존재했고 실제로 동작했다.
- `coding-harness` git log에 `/dashboard` 관련 커밋이 수십 건 쌓여 있다(소유권 각인, PiP 플로팅,
  그룹×단계 매트릭스 등). 오래전부터 성숙한 기능이었다.
- Aug 21 09:35 mtime은 `~/.claude/commands/` 안의 다른 커맨드 파일들(`code-review.md`,
  `harness-update.md`, `hub.md`, `prp-*.md`)과 **전부 동일**하다 — 개별 파일이 그때 처음 생긴 게
  아니라, 그 시각에 일괄 재설치(`harness-update` 등)가 있었을 뿐이다.

### 실제 원인 — 확인에 쓴 도구가 카테고리 자체가 다르다

Phase 6 착수 시점, 세션에는 "이용 가능한 스킬" 목록이 시스템 리마인더로 전혀 노출돼 있지
않았다(아래 「보조 요인」 참조). 그래서 메인 세션은 능동적으로 `ListSkills(keywords:
["dashboard"])`를 불러 확인했는데, 이 도구는 이름과 달리 `SearchSkills`·`SearchPlugins`·
`ListPlugins`·`SuggestPluginInstall`과 같은 군에 속하는 **마켓플레이스/플러그인 카탈로그
검색 도구**로 보인다. `/dashboard`는 `~/.claude/commands/dashboard.md`에 있는 **개인 커스텀
슬래시 커맨드**이지 카탈로그에 등록된 배포용 플러그인이 아니다 — 그러니 이 도구로 검색하면
실제 설치 여부와 무관하게 **항상 빈 결과**가 나온다. 메인 세션은 이 빈 결과를 "가용하지
않다"로 잘못 해석하고 조용히 대시보드 없이 진행했다.

### 보조 요인 — 수동 확인 수단도 사실상 없었다

세션 전체(39MB) 중 "available for use with the Skill tool" 형태의 스킬 목록 시스템
리마인더는 **딱 두 번**만 등장했고, 둘 다 이번 조사(사용자가 질문을 던진 시점) 근처에서만
나타났다. Phase 6 착수를 포함해 세션의 절대다수 구간에서는 이 수동 목록 자체가 컨텍스트에
없었다 — 즉 `ListSkills`가 아니었다면 참고할 다른 수단도 마땅치 않았다.

## 영향 범위

- 이번 발견은 `jackal-to-giraffe` 하나에 국한되지 않는다 — **같은 도구 오사용 패턴이면
  프로젝트와 무관하게 재발한다.** `ListSkills`로 개인 커스텀 커맨드의 가용성을 확인하려는
  시도는 어느 프로젝트에서든 구조적으로 실패한다.
- CLAUDE.md의 "전체 경로 → `/dashboard`" 트리거 문구 자체는 틀리지 않았다. 문제는 그
  트리거를 실행하기 **직전의 자체 가용성 확인 절차**가 잘못된 도구를 골랐다는 데 있다.

## 제안하는 보완 방향 (미확정 — 논의 필요)

두 가지 방향이 있고 서로 배타적이지 않다:

1. **확인 절차 자체를 없앤다.** 커맨드가 없으면 `/dashboard` 호출 자체가 실행되지 않으므로
   (슬래시 커맨드 미해석 시 일반 텍스트로 처리되거나 오류가 난다), 사전 존재 확인 없이
   그냥 호출을 시도하고 실패 시에만 대응하는 편이 더 단순할 수 있다. 다만 이 경우 "실패를
   조용히 삼키지 않고 사용자에게 알린다"는 규칙이 필요하다 — 이번 사고의 핵심은 실패
   자체가 아니라 **실패를 사용자에게 알리지 않고 넘어간 것**이었다.

2. **확인 절차를 쓰되 올바른 도구로 바꾼다.** `CLAUDE.md`의 대시보드 트리거 문구 또는
   `commands/dashboard.md`에 "가용성이 의심되면 `ListSkills`가 아니라 `ls
   ~/.claude/commands/dashboard.md` 또는 파일 존재 확인으로 판정한다"를 명시한다.

어느 쪽이든 공통으로 필요한 것: **가용성 확인이 실패(또는 불확실)로 끝났을 때, 조용히
건너뛰지 않고 그 사실을 사용자 보고에 한 줄 남긴다.** 이번 사고에서 실제로 놓친 지점은
여기다 — 확인 자체는 시도했지만 결과를 사용자와 공유하지 않았다.

## 미결 사항

- [x] 위 두 방향 중 어느 쪽을(또는 둘 다) 채택할지
      → **방향 1(확인 절차 자체를 없앤다)을 채택.** `Skill` 도구는 목록에 없는 이름을
      주면 자체적으로 실패를 반환하므로, 별도 사전 확인 없이 그냥 호출을 시도해도 실패가
      조용히 삼켜지지 않는다. 방향 2(파일 존재 확인)는 매 전체 경로 작업마다 Bash 호출을
      추가하면서도 "설치 여부"와 "이번 세션 컨텍스트에서 호출 가능한지"는 별개 질문이라
      완전히 신뢰할 수 있는 것도 아니었다.
- [x] "실패를 사용자에게 알린다"는 규칙을 어디에 넣을지
      → **`CLAUDE.md`(전역 + 코딩엔브 프로젝트 소스 양쪽)의 기존 `/dashboard` 트리거
      단락에 추가.** 사고가 난 지점이 "호출할지 말지 판단하는 층"이고, 그 판단이 사는
      곳이 `CLAUDE.md` 의 공통 규칙 절이기 때문이다 — `commands/dashboard.md` 는 이미
      호출을 결정한 "이후"의 절차라 이 사고에는 해당하지 않는다.
- [ ] 이미 같은 패턴으로 대시보드가 누락됐을 다른 프로젝트가 있는지 별도 확인이 필요한지
      — 미착수. 필요 시 사용자가 대상 프로젝트를 지정하면 별도로 확인한다.

## 반영된 수정

`CLAUDE.md` 의 `/dashboard` 트리거 단락(공통 규칙 절, 오프 스위치 확인 문장 바로 뒤)에
아래 내용을 추가했다 — `/Users/dev/works/personal/coding-harness/CLAUDE.md`(리포 소스)와
`/Users/dev/.claude/CLAUDE.md`(전역 활성 파일) 양쪽 동일하게 반영:

1. `/dashboard` 호출 전에 `ListSkills` 등으로 가용성을 사전 검색하지 않는다 — 오프
   스위치 확인이 끝나면 바로 `Skill(skill: "dashboard", ...)` 을 호출한다.
2. 호출을 생략했거나 실패했으면 그 사실을 착수 보고에 한 줄로 남긴다.

**전파 필요**: 이 리포의 `CLAUDE.md` 를 프로젝트 스코프로 설치해 둔 다른 프로젝트
(`jackal-to-giraffe` 포함)는 이번 수정이 자동 반영되지 않는다. 해당 프로젝트에서
`install.sh --scope project` 를 다시 실행하거나 `harness-update` 스킬로 갱신해야 한다.
