확인하지 못했다. 복구 경로는 `refs/pull/2/head`(아래 주의).

**`git branch -vv` 의 `[origin/…]` 표시를 원격 생존의 근거로 쓰지 마라**(검수 1회차
Major — 이 절이 실제로 그 실수를 했다). 그것은 마지막 fetch 이후 정리되지 않은 **로컬
캐시**이고, 실제 원격 상태는 라이브 조회로만 알 수 있다:

```bash
git ls-remote --heads origin     # 실제 원격 브랜치 (2026-09-09: main · feature/hub-workflow-visibility · worktree-dashboard-ui-fixes)
git for-each-ref refs/remotes    # 로컬 캐시 — 위와 다를 수 있다
```

**복구 경로의 실측(2026-09-09)** — GitHub 은 PR 로 제출된 tip 을 `refs/pull/<N>/head` 로
보존한다. 브랜치가 원격에서 지워져도 그 참조는 남는다:

| 브랜치 | 원격 브랜치 | `refs/pull/*` |
|---|---|---|
| `feature/hub-dashboard` | **없다** | `refs/pull/2/head` = `3d94c229` (로컬 tip 과 같다) |
| `feature/dashboard-hub-visual-parity`(삭제됨) | 없다 | `refs/pull/3/head` = `154ce420` |
| `feature/hub-workflow-visibility`(삭제됨) | 있다 | 있다 |
| `worktree-dashboard-ui-fixes`(삭제됨) | 있다 | 없다 |
| `backup/*` 2개(삭제됨) | 없다 | 없다 — **로컬이 유일한 사본이라는 판정의 근거였다.** 그래서 유일했던 기록을 먼저 옮긴 뒤 지웠다 |

**이 회차가 로컬에서 지운 브랜치 중 2개는 원격에 그대로 남아 고아가 됐다**
(`feature/hub-workflow-visibility` · `worktree-dashboard-ui-fixes`). 내용이 `main` 에
있으므로 원격 삭제도 안전하지만, 원격을 건드리는 것은 공유 저장소에 대한 조작이라
이 회차가 하지 않았다.

**기제** — 위 삭제 3건은 `git cherry main <브랜치>` 의 출력이 전부 `-`(패치가 이미 `main` 에
있음)인 것을 삭제 전에 확인하고 지웠다.

**그 기제에서 따라오는 한계** — 브랜치가 사라진 지금은 **사후에 재현할 수 없다**(검수 1회차
Medium). 같은 기법을 남은 3개에 적용한 결과는 위 표와 일치하지만, 그것이 삭제된 3건의
판정을 증명하지는 않는다.

**아래는 비망라 예시다** — 이 절이 열거하지 않은 것: `git cherry` 의 패치 동등성 판정이
**커밋 메시지와 저자를 보지 않는다** — 내용이 같고 메시지·저자가 모두 다른 커밋을 `-` 로
낸다(임시 저장소에서 재현: 같은 diff 를 서로 다른 메시지·저자로 커밋하고 `git cherry` 를
돌리면 `-` 가 나온다) · 병합
커밋이 섞인 이력에서의 동작 · 원격에만 있고 로컬에 없는 브랜치는 이 판정의 대상에 애초에
들지 않았다 · `refs/pull/*` 조회는 이 저장소의 호스트가 그 참조를 계속 보존한다는 전제에
기댄다. **전수 증명이 아니다.**

### 설치본 갱신 — 2026-09-09 `/harness-update` 로 최신화했다

재설치가 상류 자산을 건드리지 않았음을 확인했다 — 설치 디렉토리에는 레포 관리 대상과 상류 ECC

### D. `install.sh` 가 파이썬 캐시 폴더를 배포하던 결함 — **완료 (2026-09-03)**

`commands/` 에 `.py` 가 들어온 뒤 도달 가능해진 결함이다. 배포·대장·비교 세 경로가
`__pycache__` 를 걸러내지 않아, 샌드박스 실측에서 `.pyc` 2개가 대상에 설치되고 해시 대장이
62 → 64 항목이 됐다(로그는 「12개 파일」이라고 보고). `.gitignore` 대상이므로 소유권 원칙
위반이다.

**구현↔검수 3회차(상한)를 다 썼다.** 회차별 결과:

| 회차 | 결과 | 지적 |
|---|---|---|
| 1 | FAIL | Critical 2 · Major 3 · Minor 3 |
| 2 | FAIL | Major 3 · Medium 3 · Minor 3 |
| 3 | **PASS** | 차단 0건 (Medium 2 = 이관 권고) |

**전환점은 1회차 반려 후 방향을 바꾼 것이다.** 1회차는 배제를 위해 `cp -R` 을 `find` 순회
복사로 교체했다가 결함 3개를 함께 들였다 — 프로세스 치환 안의 `find` 실패가 전파되지 않아
소스 누락 시 「0개 복사 = 성공」이 되고 사후 검증 `diff -rq` 마저 침묵했으며(karpathy 실패
사례 1번의 재발), `${source_file#$source_directory/}` 의 패턴 쪽 미인용으로 글롭 경로에서
절대경로가 미러링됐고, `find -type f` 가 심볼릭 링크·빈 디렉토리를 빠뜨렸다. 2회차에
`cp -R` 을 복원하니 세 결함이 **패치가 아니라 제거로** 닫혔고, 남은 문제는 「삭제를 이
저장소의 규율에 맞추기」로 좁혀졌다.

최종 형태: `cp -R` 유지 + 복사 직후 `remove_copied_pycache`. dry-run 계획 노출 · 실행 시
건수 보고 · 헤더·README 예외 기록 · `find` 인자와 **독립적인** 범위·이름 재검증(`pwd -P`
정규화). 회귀 검사 T35(하위 11건) 신설. 커밋 `3f42700`.

R1 이 이 하나로 5회차, 분리가 5회차를 썼다. 형태:

3. **닫힌 열거가 항목을 빠뜨린다** — 「읽고 쓰는 경로는 둘뿐이다」가 manifest 경로를 누락.

**해법은 예시를 늘리는 것이 아니라 형식을 바꾸는 것이다.** 회피 경로는 원리적으로 무한하므로

주장하지 않으면 반증될 대상이 없다.**

> **규범 형식**: 기제 진술 → 그 기제에서 곧바로 따라오는 한계 → **비망라** 예시 →
> **전수 증명이 아니다**
>
> 실례(열어서 형식을 익힐 것): `tests/run.sh` 의 **T29 주석** · **T7(h) 주석** · **T32-7 주석**

`실측으로 확인했다`를 완전성의 근거로 쓰는 형태.
