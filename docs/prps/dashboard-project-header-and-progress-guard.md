## 0. 착수 전 필수 — 미커밋 작업에 P0 결함이 있다

**이 PRP 의 어떤 결정을 고르든 먼저 고쳐야 하는 버그를 설계 조사 중 발견했다.**

직전 작업(미커밋)이 `#dz-pip-btn` 을 `#dz-top-actions` 로 **감쌌는데**, PiP 복귀 코드는 그대로다:

```js
// commands/dashboard.md:1414 (현재 워킹트리)
document.body.insertBefore(wrap, pipButton);
```

`insertBefore(newNode, referenceNode)` 는 `referenceNode` 가 **호출 대상의 자식이 아니면**
`NotFoundError` 를 던진다. HEAD(`git show HEAD:commands/dashboard.md:1184`)에서는
`<button id="dz-pip-btn">` 이 `<body>` 직계 자식이라 성립했지만, 지금은 부모가
`#dz-top-actions` 다 — **`document.body` 의 자식이 아니다.**

| | HEAD | 현재 워킹트리 |
|---|------|--------------|
| `pipButton.parentNode` | `document.body` | `#dz-top-actions` |
| `document.body.insertBefore(wrap, pipButton)` | 정상 | **NotFoundError** |

**증상**: 플로팅 창을 닫으면 `pagehide` 핸들러가 첫 줄에서 던지고, 그 뒤의
`pipButton.textContent = '플로팅'`·`setHint`·`poll()` 이 전부 실행되지 않는다. `.wrap` 은 파괴되는
PiP 문서에 남아 **opener 페이지가 영구히 빈 화면이 된다**(새로고침 전까지 복구 불가).
이 도구의 핵심 기능이 왕복 1회로 죽는다.

**테스트가 이 버그를 잡지 못한 이유**: `tests/run.sh` T22-34 가
`grep -qF 'insertBefore(wrap, pipButton)'` 로 **깨진 호출을 리터럴로 고정**하고 있다. 문자열 존재
검사라 부모-자식 관계는 볼 수 없다. 지금 `bash tests/run.sh` 는 24/24 통과한다 — 안전망이 오히려
회귀를 굳혔다.

**이 PRP 의 §5.4 가 수정과 T22-34 개정을 함께 다룬다.** 이 항목은 승인 대상이 아니라 **필수**다.

5. **프로젝트 명은 `init` 이 1회만 쓰고 그 뒤로 아무도 바꾸지 않는다** — 동적 6 셀렉터도,

## 4. 데이터 모델

### 4.1 새 셀렉터

```
#dz-project-name : Text        # 프로젝트 표시 이름. basename(cwd) 과 같다
#dz-page-head    : Container   # 프로젝트 명 + #dz-top-actions + #dz-pip-hint 를 담는 행
```

| 속성 | 값 |
|------|-----|
| 타입 | 순수 텍스트 노드(`<span>`). **헤딩이 아니다** — 문서의 유일한 `<h1>` 은 `#dz-title` 로 남는다(전제 3) |
| 값의 출처 | `basename "$PWD"` — 허브 `_display_name(path)` 과 **같은 규칙**(§5.1) |
| 치환 시점 | `init` 2단계, **1회뿐** |
| 이스케이프 | `&`→`&amp;`, `<`→`&lt;`, `>`→`&gt;` 순서(`log`·`step` 과 동일 규칙) |
| 위치 | `.wrap` **바깥**(§5.2) — PiP 로 이동하지 않고, 폴링 동기화 영역 밖이다 |

### 4.2 절차별 처리

| 절차 | `#dz-project-name` 처리 |
|------|------------------------|
| `init` | Edit 1회로 텍스트를 채운다(§5.1). **Edit 총 횟수 4→5** |
| `step` | 읽지도 쓰지도 않는다 |
| `impl` | 읽지도 쓰지도 않는다 |
| `log` | 읽지도 쓰지도 않는다 |
| 폴링(`apply()`) | **`syncText` 호출을 추가하지 않는다** — §4.3 |

### 4.3 왜 「동적(치환 대상) — 6 셀렉터」 표에 넣지 않는가

넣지 않는다. 그 표의 정의는 "`init` **이후에도** 절차가 치환하는 대상"이고, 소비자 측 대응표가
곧 폴링 동기화 계약이다. 프로젝트 명은 `init` 이 1회 쓰고 끝나므로 **파일과 라이브 DOM 이
발산할 수 없다** — 동기화할 것이 없다. 이미 같은 성격의 요소가 둘 있고(`#dz-matrix`,
`#dz-group-{g}`), 문서는 그것들을 별도 목록
(「`init` 시점에만 생성되고 이후 치환되지 않는 구조 요소」, 97-101행)에 두고 있다.
**`#dz-project-name` 을 그 목록에 추가한다.** "6 셀렉터"라는 숫자와 폴링 계약표의 행 구성은
그대로 유지된다.

폴링 계약표에는 **"치환하지 않는다" 행을 추가**한다 — 근거란에
"`.wrap` 바깥 = 동기화 영역 밖 + `init` 이 1회만 쓰고 이후 불변"을 적는다. 두 근거를 모두 적는
이유: 앞의 근거는 §11 결정 2 에서 안 B 를 고르면 무너지지만 뒤의 근거는 어떤 배치에서도 참이다.

## 5. 요청 1 — 설계

### 5.1 프로젝트 명의 값 출처

**권장: `init` 1단계의 기존 Bash 호출에 `basename "$PWD"` 를 이어 붙인다.**

```bash
mkdir -p .claude && rm -f .claude/dashboard.html && basename "$PWD"
```

| 근거 | 내용 |
|------|------|
| 호출 규약 불변 | `init "<제목>" "<단계…>"` 2-인자 규약이 그대로다. CLAUDE.md 트리거 표·`argument-hint` 프론트매터·기존 호출부를 **하나도 고치지 않는다** |
| 추가 비용 0 | `init` 1단계가 **이미 Bash 를 1회** 부른다. 같은 호출에 얹으므로 도구 호출이 늘지 않는다 |
| 허브와 일치 | `hub_model._display_name(path)` 이 경로의 마지막 세그먼트를 쓴다. 같은 프로젝트가 허브 카드·허브 모달 제목·대시보드 헤더에서 **같은 문자열**로 보인다 |
| 기억 의존 없음 | 이 문서의 관례("기억에 의존하지 않는다", `step` 2단계 참조)를 지킨다. 모델이 아는 cwd 를 옮겨 적지 않고 셸이 준 값을 쓴다 |

- `init` 2단계를 "「`#dz-title`」 텍스트를 `<제목>` 인자로, 「`#dz-project-name`」 텍스트를
  1단계가 출력한 디렉토리 이름으로 치환한다(Edit 2회)"로 개정한다.
- **이스케이프를 명시한다.** 디렉토리 이름에 `&`(`R&D` 등)가 들어갈 수 있다. `log`·`step` 과
  같은 순서(`&`→`&amp;`, `<`→`&lt;`, `>`→`&gt;`)를 적용한다.
- 이름이 길면 CSS 가 말줄임 처리한다(`text-overflow:ellipsis` + `min-width:0`).

기각한 대안은 §10 에, 선택지는 §11 결정 1 에 있다.

### 5.2 마크업 — 권장안 A (헤더 행을 `.wrap` 바깥에 신설)

```html
<body>
<div id="dz-page-head">
  <span class="project-name" id="dz-project-name">프로젝트</span>
  <div id="dz-top-actions">
    <button id="dz-pip-btn" type="button">플로팅</button>
    <button id="dz-theme-toggle" class="icon-btn" type="button"
            aria-label="다크 테마로 전환" title="다크 테마로 전환">☾</button>
  </div>
  <div id="dz-pip-hint" hidden></div>
</div>
<div class="wrap">
  <div class="card">
    <h1 id="dz-title">세션 제목</h1>
    …
```

설계 판단:

- **`#dz-top-actions` 는 여전히 `.wrap` 바깥이다.** PiP 가 `.wrap` 을 통째로 옮기는 메커니즘은
  **한 줄도 바뀌지 않는다**. 요구("프로젝트 명 옆")와 제약("PiP 로 딸려가면 안 된다")이
  **헤더 자체를 `.wrap` 밖에 두는 것**으로 동시에 만족된다 — 둘을 조정할 새 장치가 필요 없다.
- **`#dz-pip-hint` 도 헤더 안으로 들어간다.** 지금은 `position:fixed;top:54px;right:18px` 로
  클러스터 바로 아래에 떠 있다. 클러스터가 흐름으로 내려오면 이 좌표는 근거를 잃는다. 같은
  헤더의 두 번째 행(`flex-basis:100%`)으로 두면 "버튼 아래 한 줄"이라는 현재의 시각 관계가
  그대로 유지된다.
- **`<span class="project-name">` 이지 `<h1>`/`<h2>` 가 아니다.** `<h1 id="dz-title">` 이 허브
  파서의 고정 앵커라 태그를 바꿀 수 없고(전제 3), `<h1>` 이 둘이 되면 문서 개요가 망가진다.
  허브도 `.project-name` 을 `<span>`/`<button>` 으로 렌더한다(`renderProjectNameEl`) — 같은 선택이다.
- **클래스명 `.project-name` 을 허브에서 그대로 가져온다.** 직전 PRP 가 `.icon-btn` 에 쓴 것과
  같은 근거다 — 두 파일을 나란히 읽을 때 같은 이름이 같은 모양을 뜻한다.
- 헤더 컨테이너는 `id` 만 갖는다(`class` 없음). 허브의 `.project-head` 는 드래그 핸들·티어
  배지·경과 시간까지 담는 행이라 규칙이 다르다 — 이름만 빌리면 거짓말이 된다.

### 5.3 CSS

```css
  /* 페이지 헤더 — .wrap 과 같은 폭 상자를 써서 카드와 좌우가 정렬된다.
     .wrap 바깥에 두는 이유는 아래 「왜 .wrap 바깥인가」 절과 같다(PiP 이동 대상 제외). */
  #dz-page-head{max-width:860px;margin:28px auto 10px;padding:0 16px;
                display:flex;align-items:center;gap:10px;flex-wrap:wrap;row-gap:6px}
  .project-name{font-size:15px;font-weight:800;color:var(--head);
                overflow:hidden;text-overflow:ellipsis;white-space:nowrap;min-width:0;flex:1 1 auto}
  #dz-top-actions{display:flex;align-items:center;gap:8px;flex:0 0 auto}
  #dz-pip-hint{flex-basis:100%;font-size:11px;line-height:1.5;color:var(--muted);
               background:var(--surface);border:1px solid var(--line);border-radius:8px;
               padding:8px 10px;box-shadow:var(--shadow)}
```

- `.wrap` 의 위쪽 여백을 헤더가 가져간다: `.wrap{margin:32px auto}` → `margin:0 auto 32px`.
  `body.dz-pip .wrap{margin:10px auto}` 는 이미 오버라이드라 영향 없다.
- **`position:fixed`·`top`·`right`·`z-index` 4선언이 `#dz-top-actions` 와 `#dz-pip-hint` 에서
  사라진다.** 이것이 이번 변경의 시각적 본체다.
- `#dz-pip-btn`·`.icon-btn` 규칙은 **손대지 않는다**(색·hover·focus 는 직전 PRP 가 이미 정렬했다).
- `#dz-pip-hint[hidden]{display:none}` 규칙은 그대로 유지한다 — `flex-basis` 가 붙은 flex 아이템은
  `hidden` 만으로는 `display:flex` 계열 UA 스타일과 충돌할 수 있어 명시 규칙이 여전히 필요하다.

**부작용 하나를 명시한다**: 클러스터가 흐름에 들어가므로 **스크롤하면 화면에서 사라진다**(지금은
`position:fixed` 라 항상 보인다). 로그가 길어진 세션에서 테마 토글·플로팅 버튼에 닿으려면 위로
올라가야 한다. 완화 수단(`position:sticky;top:0;background:var(--bg)`)은 §11 결정 4-b 로 올린다 —
기본은 **일반 흐름**이다(가장 단순하고, 스태킹 컨텍스트·카드 그림자와의 상호작용이 없다).

## 6. 요청 2 — 진행 단계에서 커밋 배제

### 6.0 왜 관례가 지켜지지 않았는가 (조사 결과)

문서 세 곳이 이미 4단계만 세도록 적고 있다:

| 위치 | 내용 |
|------|------|
| `commands/dashboard.md:42-52` 트리거 표 | `step 1~4`(설계·승인·구현·검수)만 `step`, 「커밋·푸시」는 `log commit` |
| 루트 `CLAUDE.md:73-75` | "착수 보고 시 `init`, 단계 전환마다 `step`·`log`" |
| `docs/prps/session-dashboard.md` | 동일 |

**그런데 어느 문서에도 "단계 목록에 커밋을 넣지 마라"는 문장이 없다.** 트리거 표는 *언제 부르는가*
를 말할 뿐 *`init` 의 두 번째 인자에 무엇을 넣는가* 는 말하지 않는다. 그 인자는 자유 문자열이고,
`init` 절차 3단계의 검증은 **"모든 세그먼트에 `:` 가 있는가/없는가"** 하나뿐이다 — 단계 **이름**은
전혀 보지 않는다. 즉 `"설계|승인|구현|검수|커밋"` 은 문법적으로 완벽히 유효하며, 그 순간
분모가 5가 되어 검수 완료가 80% 로 표시된다.

**가드는 값이 만들어지는 지점(= `init` 의 인자 파싱)에 있어야 한다.** 트리거 표에 한 줄 더 적는
것으로는 같은 실패가 반복된다(그 표가 이미 있는데 어긋났다).

### 6.1 문구 ① — 「호출 규약」 절 (19-38행), `init` 설명 아래

> **진행 단계 목록에 `커밋`·`푸시`를 넣지 않는다.** 커밋은 진행 단계가 아니라 결과 기록이며
> `log commit` 으로만 남긴다. **검수 완료가 곧 100% 다** — 커밋은 분모에 들어가지 않는다.
> 전체 경로의 표준 단계 목록은 `"설계|승인|구현|검수"` 다.

- 표준 목록을 리터럴로 박아 **복사해 쓸 수 있게** 한다. 관례를 지키는 가장 값싼 수단이다.
- 「호출 규약」에 두는 이유: 이 절이 `init` 인자 문법을 정의하는 유일한 곳이고, 트리거 표(40행)
  바로 위라 두 문서 조각이 한 화면에 들어온다.

### 6.2 문구 ② — `init` 절차 3단계(392-397행), 파싱 규칙 마지막 항목

> - 세그먼트가 `커밋`·`푸시`·`commit`·`push` 중 하나면 **그 세그먼트를 목록에서 제외하고 진행**하고,
>   "커밋은 진행 단계가 아니라 `log commit` 으로 기록되므로 단계 목록에서 제외했습니다"를 한 줄
>   보고한다. **중단하지 않는다** — 착수 보고를 막을 만한 오류가 아니다.

- **중단이 아니라 제외**인 이유: 이 절차의 "보고 후 중단"은 **해석이 모호할 때**의 규칙이다
  (섞인 문법 → 어느 쪽으로 읽을지 알 수 없음). 여기는 폐쇄 어휘 4개에 대한 **결정적** 판정이라
  모호함이 없고, 추측이 아니다. 대시보드는 보조 도구이므로 착수 자체를 막지 않는다.
- 제외 후 남은 목록이 비면(전부 커밋/푸시) 그때는 인자가 통째로 잘못된 것이므로 **보고 후
  중단**한다 — 이 예외는 한 줄로 함께 적는다.

### 6.3 범위를 여기서 끊는다 (과설계 방지)

- **루트 `CLAUDE.md` 는 고치지 않는다.** 이미 4단계 워크플로우를 정의하고 있고, 실패 지점은
  워크플로우 정의가 아니라 `init` 호출이다. 배포되는 전역 지침을 이 정도 사유로 흔들지 않는다.
- **런타임 검증 코드를 템플릿 JS 에 넣지 않는다.** 진행률은 `init` 이 확정한 분모를 `step` 이
  ±1 로 옮기는 산술이며, 여기에 "커밋 단계 감지" 로직을 넣으면 분모의 출처가 둘이 된다.
- **`step` 절차·진행률 산술은 한 글자도 바꾸지 않는다.** 이미 커밋을 세지 않는다.
- 산출물은 **문구 2개 + 회귀 검사 2개**다. 그 이상은 이 요청의 무게를 넘는다.

- **대안 4 — 커밋 단계를 진행률 **분모에서만** 빼고 화면에는 남긴다.** 기각. `step` 의 ±1 전이

- **대안 5 — `init` 이 커밋 세그먼트를 발견하면 보고 후 중단한다.** 보류(=§11 결정 3 의 안 3).
