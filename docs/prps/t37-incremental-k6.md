## 요약 — 먼저 읽기

- 지금 전체 검사는 한 번에 약 54분이 걸리고, 그 90%가 「검사가 정말 문제를 잡는지 일부러 망가뜨려 확인하는 단계(K6)」다. 이 단계는 매번 218개 항목을 전부 다시 확인한다.
- 바꾸면 평소 실행은 **이번 변경이 닿은 항목만** 확인한다. 최근 59커밋에 대어 보면 중앙값 33개 · 전체 검사 약 9분, 느린 쪽(상위 10%)도 약 23분이다. 검사 도구의 공통 부분이 바뀌었거나 사용자가 원할 때만 218개를 전부 확인한다.
- 같은 묶음의 「망가뜨리기 전 확인」을 항목마다가 아니라 묶음마다 한 번만 돌린다. 그래서 전부 확인할 때도 약 54분 → 약 30분으로 준다.
- 검수 담당 지침에서 낡은 숫자(「15초」)를 빼고, 검수자는 변경이 닿은 테스트만 돌리고 전체 검사는 메인 세션이 커밋 직전에 한 번 돌리도록 바꾼다.

**승인하면 무슨 일이 일어나는지**: implementer 가 검사 하네스(`tests/run.sh`)·원장(`tests/mutations.tsv`)에 선택 장치를 넣고, 선택 계산을 맡는 파이썬 파일 하나(`tests/k6_selection.py`)를 새로 만들고, 검수 지침 3곳(`agents/code-reviewer.md`·`commands/code-review.md`·`rules/workflow/role-separation.md`)과 설계 문서를 고친다. 구현 직후 첫 실행은 하네스 자체가 바뀌었으므로 **전부 확인(약 30분)** 으로 돈다 — 그 뒤부터 기본 실행이 짧아진다. 내 컴퓨터의 `~/.claude` 에 반영하는 배포(`install.sh --scope user`)는 이 작업에 들어 있지 않다(사용자가 따로 요청한다). 대가는 **이번 변경이 직접 건드리지 않은 검사가 간접적으로 무뎌지는 일부 경우를 전부 확인하는 날까지 모른다**는 것이다(§10).

## 1. 요구사항 요약

T37-15(K6)는 원장의 변조행 218개마다 「미러 생성 → 변조 전 그룹 실행(PASS 확인) → sed 변조 → 변조 후 그룹 실행(FAIL + 토큰 확인)」을 순차로 돈다. 2026-10-01 실측으로 `--only T37` 이 2,892초(그중 중첩 실행 2,810초)이고 전체 스위트(≈54분)의 약 90%다. 메인 세션은 마일스톤마다 전체 스위트를 돌리며(커밋당 1.3회) 그동안 편집을 멈추고 기다린다. 반면 실측된 효익은 「새로 쓰거나 바꾼 행을 그 과제 안에서 검증」하는 것뿐이고, 기존 가드의 회귀를 나중 과제에서 잡은 사례는 0건이다. 그래서 **행은 줄이지 않되, 매번 판정하는 행을 이번 변경이 닿은 행으로 좁힌다.** 전체 218행 재확인은 (1) 검사 도구의 공용 부분이 바뀐 경우와 (2) 사용자가 명시적으로 원할 때만 돈다. 같은 날 추가 승인으로 (a) 변조 전 실행을 그룹당 1회로 줄이는 사전조건 캐시와 (b) 검수자 지침의 낡은 「전체 스위트는 싸다(15초)」 문구 교체를 함께 다룬다.

### 성공 기준 (검증 가능한 형태)

1. 인자 없는 `bash tests/run.sh` 가 공용 부분 변경이 없을 때 K6 를 선택된 행에만 수행하고, 모드·행 수·기준을 한 줄로 찍는다(§9).
2. 공용 부분 변경 · `CODING_HARNESS_K6_FULL=1` · 기준 계산 불능 · 선택 계산 이상 중 하나면 218행 전부를 판정한다(fail-close).
3. 선택 로직이 「항상 0행」·「항상 전부」로 고장 나면 합성 fixture 서브체크(T37-21~T37-23)가 실패한다.
4. 사전조건(변조 전 PASS)을 그룹당 1회만 돌리고, 변조 전 FAIL 은 그룹 단위로 한 번 보고된다. T37-16(자기 고정점)은 코드 무변경으로 계속 문다.
5. 검수자 지침 3곳에서 「15초」 문구와 「전체 스위트 + build」 를 빼고, 메인 세션의 커밋 직전 전체 검증 의무가 상시 규칙에 적힌다.

### 범위 밖 (이번에 하지 않는다)

변조행 병렬화 · T25 행 면제 정책 · 허브 unittest 반복 방식 · effort 설정 · `~/.claude` 배포 반영. 설계 중 꼭 필요하다고 판단한 범위 밖 항목은 없다.

## 3. K6 판정이 기대는 것과 선택 규칙 (질문 1)

### 3-1. 한 변조행의 판정이 기대는 것

행 r = (guard_id, target_path P, mutation_sed S, expect_group G, expect_token X, anchor A). r 의 판정(「변조 전 G PASS · S 적용 후 G FAIL · 출력에 X」)은 다음에 기댄다.

1. **원장 행 r 자신** (S·G·X 의 값)
2. **P 의 내용** — S 가 매치하는가, 매치해도 변조가 결함을 만드는가
3. **가드 코드** — X 를 내는 보고 줄과 그 판정 로직(대개 G 함수 안의 한 블록, 일부는 헬퍼)
4. **같은 그룹의 앞선 코드** — 앞 서브체크의 `record_failure + return 1` 이 X 보다 먼저 그룹을 끊을 수 있다(원장 헤더가 실측한 「T37-15 그룹 절단」 2건: T25-149·T25-225). 공용 변수·작업 디렉터리 같은 부수효과도 같다.
5. **공용 코드** — 러너·사전 점검·헬퍼·하네스(`assert_guard_bites` 등)·원장 파서
6. **P 밖의 파일·환경** — 가드가 여러 파일을 합쳐 읽는 경우(T22 합본), macOS 도구·로케일

### 3-2. 선택 규칙 (기본 실행에서 판정할 행)

비교 기준(§4) 대비 변경을 모아 아래 중 하나라도 맞는 변조행을 고른다. 근거 코드는 출력(§9)에 그대로 실린다.

| 코드 | 이름 | 고르는 행 | 덮는 경로(§3-1) |
|---|---|---|---|
| R1 | 원장 | 원장 diff 의 `+` 데이터 줄(추가·변경된 행) | 1 |
| R2 | 대상 파일 | target_path 가 바뀐 파일 목록(추적 diff ∪ 추적되지 않는 새 파일)에 든 행 — **파일 단위** | 2 |
| R3 | 가드 블록 | `tests/run.sh` 의 변경 줄(주석 포함)이 그 행의 **가드 블록** 안에 있는 행 | 3 |
| R4 | 변수 정의 | 바뀐 정의(최상위 단일 줄 `readonly 이름=` 상수 · 그룹 함수 안 `local 이름=`/`이름=`/`local 이름…`)의 이름을 가드 블록이 참조하는 행 | 3·4 |
| R5 | 앞선 줄 | 같은 그룹 함수에서 X 의 보고 줄보다 **앞에** 있는 변경 줄 중 ① 조기 종료 줄(`return`·`exit`·`record_failure`) 또는 ② 어느 가드 블록(그 함수에서 언급되는 **모든** 서브체크 ID — 면제행·미등록 포함 — 의 블록)에도 속하지 않는 정의 아닌 코드 줄(공용 줄) — 그 뒤에 있는 행 전부 | 4 |
| — | 블록 미상 | X 가 보고 줄에서 정확히 1건이 아니어서 블록을 정할 수 없는 행(T37-13 이 따로 실패로 보고) — 행 단위 fail-close | — |

그룹 함수 안 heredoc 줄(인라인 파이썬 등)은 **R3 에만** 쓴다 — 그 안의 `return`·대입은 bash 의 조기 종료·정의가 아니다(이것을 빼지 않으면 파이썬 `return` 하나가 그 뒤 T25 행 전부를 고른다).

**R5 의 「같은 그룹 함수」 해석(구현에서 확정 — §24-2)**: X 의 보고 줄이 든 함수가 **등록 그룹 함수**일 때만 R5 대상이다. T99-1~7·T36-11 처럼 보고 줄이 헬퍼에 있는 행은 R5 대상이 아니다. 그 행들은 target 이 전부 `tests/run.sh` 라서 이 파일이 어떻게든 바뀌면 R2 가 고르므로 빠지는 경로가 없다.

**가드 블록의 정의**(R3·R4 공용). 그룹 함수 안에서 `guard_id` 를 담은 줄 — (a) 첫 낱말이 그 ID 인 주석 머리줄(`^\s*#\s*(-+\s*)?T25-257` 뒤에 영숫자 없음) 또는 (b) 첫 메시지가 `"T25-257:`·`"T25-257 `·`"T25-257(` 로 시작하는 `note_failure`/`record_failure` 줄 — 과 X 의 보고 줄을 모아, 그 최소~최대 줄에 앞뒤 **W=10줄** 여유를 붙이고 감싼 함수 구간으로 자른다. ID 가 소스에 없는 T99 행은 X 의 보고 줄 ±W 다. 현재 소스 실측: 218행 전부 해소(블록 미상 0) · 블록 중앙값 15줄 · p90 44줄 · ID 머리줄 없는 행 37개(그 행은 첫 보고 줄부터 시작하고 위쪽 준비 코드는 W 와 R5 가 덮는다) · 떨어진 언급 때문에 넓어진 블록 3개(T25-149·T25-173·T25-256, 최대 3,394줄 — 과선택 쪽이라 안전).

**왜 앵커 「함수」 단위가 아니라 블록 단위인가** (사용자의 최소 후보 「anchor_function 함수 본문이 바뀐 행」에서 좁힌 자리 — 승인 요청 1): 변조행 132개의 앵커가 `test_hub_docs_and_constants`(T25, 약 6,000줄) 하나다. 허브 작업 커밋은 거의 매번 이 함수에 서브체크를 더하므로, 함수 단위로 고르면 T25 132행이 거의 매번 선택된다(T25 행당 ≈17.7초 → 약 39분). 블록 단위로 좁히되, 함수 단위가 덮던 「같은 함수의 다른 줄이 이 가드에 닿는 경우」는 R4(변수)·R5(앞선 조기 종료·공용 줄)가 메운다.

**왜 R2 는 파일 단위인가**: 사용자가 명시한 최소 후보이고, 대상 파일 안의 먼 변경(같은 리터럴을 다른 자리에 추가해 변조를 상쇄)까지 덮는다. 줄 근접(±15줄)으로 좁히면 최근 59커밋 기준 평균 약 −140초 · p90 약 −6분이 더 줄지만 그 경로를 잃는다 — 기각하고 §18 대안에 남긴다.

### 3-3. 공용 부분 → 전체 재확인 트리거

`tests/run.sh` 의 변경 줄 중 **주석·빈 줄이 아닌** 줄이 아래 어디에 있으면 전체 218행으로 간다(heredoc 안의 줄은 주석처럼 보여도 코드로 본다).

1. 등록 그룹 함수(`TEST_GROUPS`)가 **아닌** 함수 — 헬퍼·러너(`main`·`register_and_run_tests`·`print_test_summary`…)·사전 점검(`verify_*`)·하네스(`assert_guard_bites`·`parse_mutation_ledger`·이번에 더하는 K6 함수들)
2. **T37 그룹 함수**(`test_mutation_ledger_harness`) — 하네스 자체
3. 함수 밖 최상위 코드 중 **단일 줄 `readonly 이름=값` 상수 정의가 아닌 것** — 여러 줄 배열(`TEST_GROUPS`·`PATCH_CONTRACT_PAIRS`·`README_PROSE_DECLARATIONS`…)·트랩 설치·`main` 호출 등
4. `tests/k6_selection.py`(이번에 새로 만드는 선택 코어)의 **모든** 변경
5. **함수 정의 줄(`이름() {`)이 삭제된** 변경 — 지워진 줄은 새 파일에 없고 그 위치는 hunk 의 새 쪽 시작이라 이웃 함수나 최상위로 오인된다(등록 그룹 함수 하나가 통째로 사라져도 이웃 그룹 함수의 줄로 읽혀 전체 재확인이 열리지 않는다). 그래서 줄 텍스트로 알아보고 공용 부분 변경으로 본다. 구현에서 더한 트리거다(§24-2).

## 4. 비교 기준 (질문 2)

**기준 = `git merge-base HEAD origin/main`** 이고, 비교 대상은 **작업 트리 전체**(커밋 + 스테이지 + 미스테이지) **∪ 추적되지 않는 새 파일**이다.

```bash
GIT_OPTIONAL_LOCKS=0 git -C "$REPO_ROOT" rev-parse --show-toplevel        # REPO_ROOT 와 물리 경로 일치 확인
GIT_OPTIONAL_LOCKS=0 git -C "$REPO_ROOT" rev-parse --verify --quiet 'refs/remotes/origin/main^{commit}'
GIT_OPTIONAL_LOCKS=0 git -C "$REPO_ROOT" merge-base HEAD origin/main
GIT_OPTIONAL_LOCKS=0 git -C "$REPO_ROOT" -c core.quotepath=off diff --name-only --no-renames <base>
GIT_OPTIONAL_LOCKS=0 git -C "$REPO_ROOT" -c core.quotepath=off ls-files --others --exclude-standard
GIT_OPTIONAL_LOCKS=0 git -C "$REPO_ROOT" diff -U0 --no-color --no-ext-diff --no-textconv --no-renames <base> -- tests/run.sh
GIT_OPTIONAL_LOCKS=0 git -C "$REPO_ROOT" diff -U0 --no-color --no-ext-diff --no-textconv --no-renames <base> -- tests/mutations.tsv
GIT_OPTIONAL_LOCKS=0 git -C "$REPO_ROOT" diff --numstat --no-color --no-ext-diff --no-textconv --no-renames <base> -- tests/run.sh tests/mutations.tsv   # 단언 e 용(§8-2)
```

(구현은 위 호출을 `k6_git` 래퍼로 한다 — `GIT_OPTIONAL_LOCKS=0` 에 더해 환경의 `GIT_DIR`·`GIT_WORK_TREE`·`GIT_INDEX_FILE` 을 지운다. 훅 안에서 스위트가 돌 때 호출자 저장소의 값이 새어 들어와 기준 계산이 엉뚱한 저장소를 보는 일을 막는다. §24-2.)

| 상황 | 기준 | 포착되는 변경 |
|---|---|---|
| main 체크아웃 직접 작업(미커밋만) | origin/main = HEAD → HEAD | 미커밋 전부 ✓ |
| main 에서 커밋한 뒤 게이트를 다시 돔(미푸시) | origin/main 끝 | 미푸시 커밋 + 미커밋 ✓ (로컬 `main` 을 기준으로 쓰면 HEAD 와 같아 커밋분을 놓친다 — 그래서 `origin/main`) |
| 워크트리 브랜치(커밋 + 미커밋) | 분기점(또는 그 뒤의 공통 조상) | 브랜치 변경 전부 ✓ |
| 로컬 main 에 미푸시 커밋이 있고 그 위에서 워크트리 분기 | origin/main 끝(분기점보다 이전) | 브랜치 변경 + main 의 미푸시분(과선택, 안전) |
| 워크트리를 스쿼시 머지·푸시한 뒤 워크트리에서 다시 돔 | 분기점 | 이미 반영된 변경까지(과선택, 안전) |
| origin/main 이 오래 fetch 되지 않음(뒤처짐) | 더 오래된 조상 | 과선택(안전) — 스위트는 fetch 하지 않는다(네트워크 0) |
| git 저장소 아님(`.git` 없는 격리 사본 등) · REPO_ROOT 가 작업 트리 루트가 아님(다른 저장소 안에 놓인 사본) · origin/main 없음 · 공통 조상 없음 | — | **fail-close = 전체** (환경 사유 — 실패로 보고하지 않는다) |
| 기준은 정했는데 diff·ls-files 명령이 실패 | — | **전체 + T37-15 실패 보고**(계산 이상) |

- `GIT_OPTIONAL_LOCKS=0` — 같은 저장소의 동시 세션과 index.lock 을 다투지 않게 한다(diff 의 인덱스 갱신을 끈다).
- 스위트는 진입부에서 `HOME` 을 샌드박스로 바꾸므로 전역 gitconfig 가 없다 — 색·quotepath 같은 사용자 설정이 출력에 섞이지 않아 오히려 안정적이다. 명시 플래그(`--no-color`·`-c core.quotepath=off` 등)는 시스템 설정까지 막는 이중화다.
- 이름을 상수 `K6_DIFF_BASE_REF="origin/main"` 로 둔다(원격 이름이 다른 저장소에서 바꿀 자리).

```
    반환 = 0 → 그 그룹 행마다 ((rows_judged++)); assert_guard_bites 행…   (행마다 새 미러 — 지금과 같다)
```

- **계수 `precondition_groups_run` 은 루프가 아니라 `run_k6_group_precondition` 안에서 올린다**(구현에서 확정 — §24-2). 호출부에 두면 호출만 지워도 계수가 남아 「사전조건 호출을 지우면 단언 d 가 발화한다」(§17)가 성립하지 않는다(실측: 호출 삭제와 실행 줄 삭제 둘 다 발화). 미러 생성이 실패해 그 함수까지 못 간 그룹은 보고 함수가 한 번 올려 단언 d 의 분모(선택 행의 서로 다른 그룹 수)와 맞춘다. 이 부수효과 때문에 T37-26 은 그 함수를 서브셸 안에서 부른다.

- **어디서 도는가**: 그룹마다 **새 미러 하나**에서 돌고 지운다. 작업 트리에서 직접 돌리지 않는 이유 — 변조 전 확인의 뜻이 「변조 후와 같은 미러 환경(`.git` 없음·경로 독립)에서 PASS」라서다(작업 트리 실행은 바깥 스위트가 이미 한다). 여러 그룹이 미러 하나를 공유하지 않는 이유 — 앞 그룹 실행의 잔여물(`__pycache__` 등)이 뒤 그룹 판정에 섞이는 새 결합이 생긴다(미러 생성 0.16초 × 그룹 ≤18개 ≈ 3초라 아낄 것이 없다).
- **행별 미러는 그대로 둔다** — 변조 격리의 단위다. 한 미러에서 변조·되돌리기를 반복하면 0.16초/행을 아끼지만 되돌림 정확성이라는 새 위험을 들인다(YAGNI).
- **의미 변화 하나**: 지금은 변조 후 실행이 변조 전 실행을 마친 **같은 미러**에서 돈다. 바꾸면 변조 후 실행은 **아무것도 돌지 않은 새 미러**에서 돈다. 바깥 작업 트리 실행과 더 가깝고(잔여물 0), 판정이 그 차이에 기대는 가드는 없다고 본다 — 구현 직후 전체 재확인(§11-2 ①)이 그 가정을 실측으로 확인한다.
- **같은 실행 안에서만** 재사용한다 — 파일로 남기지 않으므로 낡은 캐시가 없다. 작업 트리를 실행 도중에 고치면 결과가 오염되는 기존 위험(프로젝트 메모리 「T37 은 행마다 작업 트리를 복사한다」)은 그대로다.

### 7-2. 보고와 판정 쌍 수 단언의 관계

- 변조 전 FAIL 은 **그룹 단위로 한 번** 보고한다: `T37-15: T25 사전조건 불성립 — 변조 전 T25 가 이미 FAIL(원장 무효 가능성) — 이 그룹의 선택 행 132개 판정 생략: T25-10 T25-11 …(앞 20개)`. 그 행들은 「판정」이 아니라 「생략」으로 센다.
- 단언(§8-2): `rows_judged + precondition_skipped_rows == k6_selected_rows` · `precondition_groups_run == 선택 행의 서로 다른 그룹 수`. 둘째 단언이 「사전조건 호출을 지워도 아무 단언도 발화하지 않는」 자리를 막는다(T37-20 의 「판정 함수는 물지만 호출부는 못 문다」 한계와 같은 모양을 여기서는 계수로 닫는다). tests-hardening §10-2-(1)의 「층 2 는 변조 전 PASS 관측을 요구한다」 논거가 행 단위에서 그룹 단위로 옮겨 그대로 성립한다.

### 7-3. T37-16(자기 고정점)이 계속 무는가

**T37-16 은 코드 무변경이다.** `assert_guard_bites` 의 시그니처(5인자)와 문구 계약 — 「가드 무력화」 · 「사전조건 실패 — sed 적용 후 바이트 변화 없음」 · 「실패 메시지에 토큰 … 없음」 · 「미러 생성 실패」 — 를 그대로 두고, 빠지는 것은 함수 안의 「변조 전 이미 FAIL」 분기 하나다.

- T37-16 이 보게 되는 것: 물지 않는 변조(`commands/hub.md` 끝 공백, 그룹 T29)를 넘기면 **변조 → 변조 후 실행 → 판정** 경로가 「가드 무력화」를 낸다. 판정이 「항상 통과」로 고장 나는 형태를 문다 — 지금과 같다. elif 의 「사전조건」 분기는 이제 「바이트 변화 없음」만 가리킨다.
- T37-16 이 보지 않게 되는 것: 변조 전 실행. 그것은 그룹 단계로 옮겼고, 그 판정의 **양방향**(통과→0, 실패→1)을 새 T37-26 이 스텁 미러로 문다. 지금은 변조 전 실행이 「항상 통과(실행 생략)」로 고장 나는 방향을 아무도 물지 않는다 — 이번에 더 엄격해진다.
- `assert_guard_bites` 의 doc 주석에 「전제: 호출자가 그룹 사전조건을 이미 확인했다(`judge_k6_selected_rows`). T37-16 은 바깥 실행에서 T29 가 통과한다는 사실 위에서 사전조건 없이 직접 부른다」를 적는다.

## 14. 파일 구조와 모듈 경계

이 저장소의 검증 레이어(`tests/run.sh` — bash 3.2 단일 파일 하네스)에 **선택 코어 하나만 파이썬 파일로 분리**한다.

```
tests/
├── run.sh                 # I/O·오케스트레이션: git 호출, 미러, 그룹 실행, 보고(기존 + K6 함수 28개)
├── k6_selection.py        # 신설 — 순수 로직: 입력 파일 → stdout 레코드. 외부 세계에 닿지 않는다(git·미러·실행 0)
└── mutations.tsv          # 원장(데이터)
```

- **경계**: `run.sh` 가 git 으로 입력 파일 다섯 개를 만들어 넘기고(§15-1), 코어는 그 파일만 읽어 레코드를 낸다. 코어는 git·파일 쓰기·하위 프로세스를 쓰지 않는다 — 합성 fixture 만으로 전 기능을 시험할 수 있다(T37-21~23).
- **왜 파이썬인가**: 판정에 필요한 것이 정규식 단어 경계(`\b`)·lookbehind(here-string `<<<` 배제)·이름별 집합이다. BSD awk 에는 `\b` 가 없어 손으로 문자 경계를 훑어야 하고, 선택이 틀리면 행이 **조용히** 빠지는 자리라 읽기 쉬운 쪽을 고른다. python3 표준 라이브러리는 이미 스위트의 의존성이다(T24·T25·T32 의 inline `python3`).
- **왜 별도 파일인가**(inline heredoc 이 아니라): 200줄 안팎의 프로그램을 bash 함수의 heredoc 에 넣으면 그 함수가 50줄 규칙을 크게 넘고(CLAUDE.md §5 예외는 T 그룹 함수뿐), heredoc 안의 열 0 `}`·`trap` 시작 줄 같은 함정이 기존 정적 검사(함수 구간·트랩 계수)와 얽힌다. 별도 파일은 그 검사들의 대상 밖이고 다른 세션과 머지 충돌도 없다. 대가는 「공용 부분」 정의에 이 파일을 넣어야 한다는 것(§3-3 의 4).
- 파이썬 쪽 관례: `rules/python` 의 순수 모듈 · 프로즌 dataclass · 이름 있는 상수 · 표준 라이브러리 전용. 실행은 `python3 -B`(바이트코드 파일을 만들지 않는다 — 프로젝트 메모리의 `__pycache__` 오염 주의).

판정 규칙의 정본 표현(구현이 그대로 옮길 것):

- 주석 줄: heredoc 밖에서 `^\s*#` 또는 빈 줄. heredoc 줄: 주석이 아닌 줄의 `(?<!<)<<(?!<)(-?)\s*(['"]?)([A-Za-z_]\w*)\2` 여는 줄 다음부터 그 낱말과 같은 줄(`<<-` 면 앞 탭 제거) 직전까지 — 닫는 줄이 없으면 heredoc 으로 보지 않는다.
- 정의 줄: 최상위 `^readonly [A-Z_][A-Z0-9_]*=` 이고 값이 `(` 로 시작하지 않음 · 그룹 함수 안 `^\s*(local\s+)?[A-Za-z_]\w*=` 또는 `^\s*local\s+[A-Za-z_][\w ]*$`.
- 이름 참조: `\$\{?[#!]?NAME\b`, NAME 이 대문자뿐이면 맨 낱말 `\bNAME\b` 도(산술 문맥).
- 조기 종료 줄: `\b(return|exit|record_failure)\b`.
- 가드 언급 줄: `^\s*#\s*(-+\s*)?<ID>(?![0-9a-z])` 또는 `^\s*(note_failure|record_failure)\s.*"<ID>[: (]`. 토큰 보고 줄: `FAILURE_REPORT_LINE_PATTERN`(기존 상수와 같은 정의)이면서 토큰을 고정 문자열로 포함.

## 19. GOTCHA (구현자가 틀리기 쉬운 함정)

1. **`set -e` 는 그룹 호출 트리에서 꺼져 있다**(기존 GOTCHA 1). git·코어 호출마다 반환값을 직접 본다 — 실패한 `git diff` 가 빈 문자열로 흘러 「바뀐 게 없다 → 0행」이 되는 것이 이 설계의 **유일한 fail-open 경로**다. `diff_text=$(…) || { 사유; return 1; }` 형태로 끊는다.
2. bash 3.2 — 연관 배열 없음, `set -u` 아래 빈 배열 `"${arr[@]}"` 전개 금지, `((x++)) || true`. 판정 루프는 파이프가 아니라 `while … done < <(…)` 로 부모 셸에서 돌려 계수가 남게 한다.
3. **새 보고 줄에 다른 행의 expect_token 을 쓰지 않는다** — T37-13 판별자 자격(보고 줄 정확히 1건)이 깨진다. 짧은 토큰 예: `dz-subtitle`·`PV9 위반`·`overflowRuns`·`트리 잔재`·`T33-1:`·`T33-2:`.
4. **T39-5**: `tests/run.sh` 새 주석·문자열에 `이름.sh:숫자` 꼴 인용을 쓰지 않는다(래칫 5). **T39-4**: 배포 문서에도 마찬가지.
5. **원장 헤더 인용 대조**(`verify_ledger_header_citations`)는 정규식이 **정확히 1회** 맞아야 한다 — 새 헤더 문단에 `LEDGER_EXEMPT_ROW_RATCHET(`·`아래 <숫자>개는`·`T37-0~T37-<숫자>(<숫자>개)` 꼴을 다시 쓰지 않는다.
6. T37-24 의 임시 저장소는 HOME 샌드박스 때문에 전역 gitconfig 가 없다 — `-c user.name … -c user.email … -c commit.gpgsign=false`, `git init -q`. `$fixture_root` 아래(레포 밖 mktemp)에 만든다.
7. 코어 출력은 ASCII 만 — 로케일이 C 여도 깨지지 않게. 한국어 이름 매핑은 bash 쪽.
8. 새 최상위 상수·전역은 **K6 함수들 옆**(하네스 구역)에 둔다 — T36 조각 추출 범위(`set -euo pipefail` ~ `trap suite_exit_guard EXIT` · `cleanup_registered_paths` 닫는 줄) 밖이어야 조각 프로브가 흔들리지 않는다. `K6_SUMMARY_LINE=""` 대입으로 상속값을 덮는다.
9. `assert_guard_bites` 의 문구(「가드 무력화」·「사전조건 실패 — sed 적용 후 바이트 변화 없음」·토큰 없음·미러 생성 실패)를 바꾸지 않는다 — T37-16 이 그 문구에 기댄다. 마지막 `return 0` 도 유지(그 주석의 「판정 반전」 함정).
10. `agents/code-reviewer.md` 에 「재검수 모드」를 새로 쓰지 않는다(T38-3 변조행 sed 가 줄마다 첫 것만 바꾼다). `role-separation.md` 는 99행 다음 독립 줄로 넣고 T31-8·T22-158b·T40-8 이 sed 로 겨누는 줄을 건드리지 않는다.
11. T26 은 **정확 일치**다 — `role-separation.md` 편집 후 `cat CLAUDE.md rules/README.md rules/common/*.md rules/workflow/*.md | wc -c` 로 재측정한 값으로 상수와 README 2곳(`실측 <n>B`, 콤마 표기)을 함께 바꾼다.
12. 원장의 T37 면제행은 기존 사전순 자리(`T37-20` 뒤, `T37-3` 앞)에 넣는다 — 다른 세션의 T25 행 추가와 줄이 겹치지 않는다.
13. 실행 도중 작업 트리를 고치면 선택(시작 시점)과 미러(나중 시점)가 어긋난다 — 기존 오염 위험과 같다. 고치지 않는다(문서화만).
14. 구현 커밋의 첫 기본 실행은 하네스 변경 때문에 **전체**로 돈다 — 정상이다. 증분 동작은 그다음 커밋부터 관측된다.

### 24-3. 정정 — 합본 `cat` 줄은 R5 가 덮지 못한다

초안 §3-4·§10 은 「T22 합본을 만드는 `cat … >` 줄이 바뀌면 R5 가 그 뒤 행을 고른다」고 적었다. 실제 소스에서는 틀렸다. 그 줄(작성 시점 `tests/run.sh` 3042행)은 변조행이 없는 면제행 서브체크 T22-2 의 머리 주석 바로 위(머리줄 −10줄 안)라 **그 블록에 덮인다.** R5 ②는 그 함수에서 언급되는 모든 서브체크 ID — 면제행 포함 — 의 블록 밖 줄만 「공용 줄」로 보므로 이 줄은 대상이 아니고, T22-2 에는 변조행이 없어 R3 도 아무 행을 고르지 않는다. 코어에 이 줄만 바뀐 diff 를 넣어 확인했다 — R3·R5 근거로 선택되는 행이 0개이고(`tests/run.sh` 가 바뀐 파일이라 target 이 그 파일인 17행만 R2 로 선택된다), 같은 함수의 블록 밖 줄(앞머리 준비 줄 · 파일 존재 확인)을 바꾼 대조에서는 T22 행이 R5 로 선택된다.

- 조치: §3-4 에서 이 줄을 「잃음」 행으로 옮기고(블록 밖 공용 줄의 R5 예시는 그룹 함수 앞머리의 준비 줄로 바꿨다) §10 에 같은 「잃음」 행을 더했다. §3-4 의 「변수의 간접 의존」 행과 §10 의 해당 행 괄호도 「서브체크 블록 밖의 공용 줄이 바뀌면」으로 좁혔다.
