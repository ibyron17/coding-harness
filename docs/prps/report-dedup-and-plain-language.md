# 보고 중복 제거와 비개발자 기준 보고 (report-dedup-and-plain-language)

## 1. 요구사항 요약

사용자 화면에 같은 작업 보고가 두 번 나오고(서브에이전트가 한 번, 메인 세션이 또 한 번),
그 보고가 개발자 언어로 쓰여 있어 사용자가 **내용을 이해하지 못한 채 승인·통과**시키는
일이 반복된다. 이 설계는 워크플로우 지침을 고쳐 (A) **사용자용 보고를 메인 세션이 단계마다
한 번만** 쓰게 하고, (B) 그 보고를 **비개발자가 읽고 판단할 수 있는 형태**로 쓰게 한다.
새 에이전트·새 스킬·새 절차 단계를 만들지 않는다 — 변경의 본질은 always-on 규칙 2줄의
치환과 에이전트 파일 3개의 수신자 명시다.

---

## 2. 원인 (확인된 사실)

중복은 두 지시가 겹쳐서 생긴다.

1. `agents/{design-architect,implementer,code-reviewer}.md` 가 각자 **사용자용 요약을
   쓰라고 지시**한다. 예: design-architect 는 "사용자 승인이 필요한 핵심 결정 사항을
   3줄 이내로 요약해 함께 보고한다". 이 보고는 데스크톱 트랜스크립트에 노출된다.
2. 그 직후 `rules/workflow/role-separation.md` 「공통 규칙」 첫 항목("각 단계의 산출물…은
   사용자에게 보고한 뒤 다음 단계로 넘어간다")에 따라 **메인 세션이 같은 내용을 다시
   쓴다.**

즉 어느 한쪽의 버그가 아니라 **두 지시가 같은 수신자(사용자)를 겨냥한 구조**가 원인이다.
고치는 방법도 대칭이다 — 수신자를 갈라준다. 서브에이전트 보고의 수신자는 오케스트레이터,
사용자용 보고의 저자는 메인 세션 하나.

> **이 설계는 하네스가 서브에이전트 출력을 화면에 보여주는지에 의존하지 않는다.**
> 보여주면 사용자는 "압축된 기술 블록 + 쉬운 요약 1개"를 본다(중복 아님). 숨기면
> "쉬운 요약 1개"만 본다. 어느 쪽이든 같은 내용이 두 번 나오지 않는다.
> (한계: 지침으로는 서브에이전트 블록을 화면에서 **없앨 수 없다**. 없애는 것은
> 하네스의 몫이고, 이 설계가 없애는 것은 *내용의 중복*이다. §9 R-1 참조.)

- **`rules/common/*.md` 는 손대지 않는다.** (a) 4-에이전트 역할 분리는 `rules/workflow/`
  개념이고, `common/` 은 이 워크플로우를 쓰지 않는 프로젝트에도 배포된다. (b)
  `common/git-workflow.md` 「Message style」이 이미 "비개발자가 이해할 수 있게 / 단답형"
  을 정의하고 있으므로 **재정의 대신 참조**한다(DRY이자 바이트 절약). (c) `common/` 의
  모든 바이트는 모든 프로젝트에서 상시 로드다.
- **`agents/explore.md` 는 손대지 않는다.** 출력이 이미 요약 전용이고 사용자용 서사를
  쓰지 않는다. 예방적 확장은 YAGNI.
- **FRIDAY output style 을 이름으로 부르지 않는다.** `~/.claude/output-styles/friday.md`
  는 사용자 로컬 설정이고 이 저장소가 배포하지 않는다. 규칙이 그 존재를 전제하면 다른
  사용자에게는 근거 없는 문장이 된다 → §6 의 충돌 해소는 **순서 규칙**으로만 쓴다.

## 4. 문안 (실제로 적용할 텍스트 전문)

### 4.1 `rules/workflow/role-separation.md` — 「공통 규칙」 첫 항목 치환

**삭제할 텍스트(현재 첫 두 줄, 145B):**

```
- 각 단계의 산출물(설계 문서, 구현 diff 요약, 검수 보고서)은
  사용자에게 보고한 뒤 다음 단계로 넘어간다.
```

**삽입할 텍스트(816B):**

```
- **사용자용 보고는 메인 세션이 단계마다 한 번만 쓴다.** 서브에이전트의 최종 보고는
  다음 단계의 입력으로 쓰는 내부 산출물이라 그대로 옮겨 붙이지 않는다 — 메인이 한 번
  정리해 보고한 뒤 다음 단계로 넘어간다.
- **보고는 비개발자 기준이다.** 무엇이 달라졌고 무엇을 정해야 하는지를 쉬운 말로 먼저
  2~3줄(말투는 `common/git-workflow.md` 「Message style」), 파일명·명령어·수치는 그 아래
  세부로 — 빼는 것이 아니라 순서다. 승인·판단을 요청하는 자리(설계 승인, 검수 미해결
  종결)에는 **승인하면 무슨 일이 일어나는지**를 그 쉬운 말에 넣는다 — 이해하지 못한 채
  통과시키는 것이 막으려는 실패다.
```

절 안의 나머지 항목(`/prp-plan` 미설치 항목, `/dashboard` 항목)은 **그대로 둔다.**
T22-158(`디스패치·결과 수령 시점마다`)·T23-7(`dashboard_enabled`) 앵커 리터럴은 그
항목들 안에 있으므로 훼손되지 않는다.

### 4.2 `agents/implementer.md` — 「완료 보고 형식」

`## 완료 보고 형식` 줄 **바로 아래**에 빈 줄 + 다음 문단을 넣는다(기존 4개 불릿은 유지):

```
**수신자는 오케스트레이터(메인 세션)다.** 이 보고는 사용자 화면용 글이 아니라 검수
단계의 입력이다 — 아래 항목만 사실대로 채우고, 사용자가 읽을 쉬운 설명은 메인이 따로
한 번 쓴다(여기서 또 쓰면 같은 내용이 화면에 두 번 나온다).
```

### 4.3 `agents/code-reviewer.md` — 「보고서 형식」

`## 보고서 형식` 줄 **바로 아래**에 빈 줄 + 다음 문단을 넣는다(`각 지적 사항:` 이하
`[심각도]/[분류]/[위치]/[문제]/[제안]` 블록과 Validation Results·Review Summary·Verdict
는 **한 글자도 바꾸지 않는다**):

```
**수신자는 오케스트레이터(메인 세션)다.** 아래 기계적 형식은 메인이 implementer 에게
넘길 재검수 입력의 원재료이므로 그대로 유지한다 — 풀어 쓰지 않는다. 사용자가 읽을 쉬운
설명은 메인이 따로 한 번 쓴다(이 보고서를 사용자 화면에 그대로 옮기지 않는다).
```

### 4.4 `agents/design-architect.md` — 「준수 사항」 마지막 항목

**치환 전:**

```
- 설계 문서 작성 후, 사용자 승인이 필요한 핵심 결정 사항을
  3줄 이내로 요약해 함께 보고한다.
```

**치환 후:**

```
- 설계 문서 작성 후, 오케스트레이터가 사용자에게 물어야 할 핵심 결정 사항을
  3줄 이내로 요약해 함께 보고한다.
- **최종 보고의 수신자는 오케스트레이터(메인 세션)다.** 사용자가 읽을 쉬운 설명은
  메인이 따로 한 번 쓰므로, 여기서는 결정·근거·파일별 변경점을 압축해 적는다 —
  사용자용 서사를 여기서 쓰지 않는다(같은 내용이 화면에 두 번 나온다).
```

## 5. 데이터 모델 — 보고의 수신자 계약

코드가 아니라 문서 변경이므로 "데이터 모델"은 **보고 산출물 3종의 수신자·형식 계약**이다.
이 계약이 모듈 경계(에이전트 ↔ 메인 ↔ 사용자)를 가른다.

| 산출물 | 저자 | 수신자 | 형식 | 사용자 화면 |
|--------|------|--------|------|-------------|
| PRP 문서 + 핵심 결정 3줄 | design-architect | 메인 | 압축(결정·근거·변경점) | 그대로 옮기지 않음 |
| 완료 보고(파일 목록·설계 차이·검증 결과·특이사항) | implementer | 메인 | 기존 4항목 유지 | 그대로 옮기지 않음 |
| 검수 보고서(`[심각도]/[분류]/[위치]/[문제]/[제안]` + 표 + Verdict) | code-reviewer | 메인 | **기존 기계적 형식 유지** | 그대로 옮기지 않음 |
| **단계 보고** | **메인 세션** | **사용자** | 쉬운 말 2~3줄 → 세부 | **여기 한 번만** |

핵심: 검수자의 기계적 형식은 **폐기 대상이 아니다.** 그것은 메인이 implementer 에게
넘길 재검수 입력의 원재료이고(`role-separation.md` 3단계가 이미 "1회차 지적 항목
(심각도·위치·문제)을 함께 넘긴다"를 요구한다), 풀어 쓰면 그 계약이 깨진다. 바뀌는 것은
**그것을 사용자 화면에 그대로 붙여넣지 않는다**는 것뿐이다.

## 6. 기존 지침과의 충돌 해소

사용자의 output style(FRIDAY)은 "파일명, 라인, 명령어, 수치를 항상 구체적으로 말한다"를
요구하고, 새 규칙은 "비개발자 기준"을 요구한다. **둘은 같은 보고의 서로 다른 부분을
지배하므로 충돌하지 않는다.**

```
[1] 쉬운 말 2~3줄   ← 비개발자 기준. 무엇이 달라졌나 / 무엇을 정해야 하나 / 승인하면 무슨 일이
[2] 세부            ← FRIDAY 기준. 파일명·명령어·수치·테스트 실패 원문
```

문안에 "**빼는 것이 아니라 순서다**"를 박아 넣은 이유가 이것이다 — 구체적 식별자를
**없애라는 규칙이 아니라 뒤로 내리라는 규칙**임을 규칙 자신이 말하게 한다. FRIDAY 의
"되돌리기 어려운 작업 전 경고" 항목은 승인 게이트를 이미 덮으므로 규칙에서 되풀이하지
않는다(중복 금지).

  # 옛 문장(각 단계 산출물을 사용자에게 보고)으로 되돌아가거나 요건 하나만 빠지는 회귀를
  # 막는다. 아래 세 토큰이 그 계약의 뼈대다 — 저자·횟수(단계마다 한 번만) · 수신자 기준
  # (비개발자) · 승인 게이트 요구(승인하면 무슨 일이 일어나는지). 하나라도 사라지면 요건
  # 하나가 삭제됐을 가능성이 있다(그룹 머리 주석의 정적 토큰 검사 한계 절이 그대로 적용된다).
  local report_contract_token
  for report_contract_token in "단계마다 한 번만" "비개발자" "승인하면 무슨 일이 일어나는지"; do
    if ! grep -qF -- "$report_contract_token" "$REPO_ROOT/rules/workflow/role-separation.md"; then

  교체만으로 위양성이 난다. 현재 0건 실측.
- `승인하면 무슨 일이 일어나는지` — 요건 (B) 중 사용자가 실제로 아프다고 말한 부분

### 7.3 `tests/mutations.tsv` — T31-8 변조행 (탭 8열)

열 순서: `guard_id → target_path → mutation_sed → expect_group → expect_token →
defect_description → exempt_reason(빈 칸) → anchor_function`

- `guard_id`: `T31-8`
- `target_path`: `rules/workflow/role-separation.md`
- `mutation_sed`: `s/비개발자 기준이다/짧게 쓴다/`
- `expect_group`: `T31`
- `expect_token`: `보고 계약 토큰`
- `defect_description`: `사용자용 보고를 비개발자 기준으로 쓰라는 요건이 문안 다듬기에
  밀려 조용히 사라져도, 신설 당시에는 그 요건의 존재를 보는 검사가 없었다(실측 0건)`
- `exempt_reason`: **빈 칸**(변조행이므로 탭 2개 연속)
- `anchor_function`: `test_rules_workflow_guardrails`

확인 사항:

- 3열 `sed` 는 `/` 구분자 · `w`/`W`/`r`/`R`/`e` 플래그 없음 → `mutation_sed_is_write_safe`
  통과.
- 5열 `보고 계약 토큰` 은 run.sh 실패 보고 호출 줄에서 1건(T31-6 의 `인용 계약 토큰`,
  T31-7 의 `프리뷰 목업 지침 토큰` 과 문자열이 다르므로 `grep -F` 충돌 없음).

이 행을 넣으면 T37 이 미러 사본에 변조를 적용해 **T31 이 실제로 빨개지는지** 자동
검증한다 — `rules/common/code-review.md` 의 "새 검사와 가드는 의도적으로 깨졌을 때
실패함을 확인한다" 항목이 이것으로 충족된다.

## 8. 설계 결정과 근거

- **D1 — 정책은 always-on 규칙에, 기제는 에이전트 파일에.** `role-separation.md` 는
  "누가·몇 번·어떤 말로"(정책)만 갖고, "네 보고의 수신자는 오케스트레이터다"(기제)는
  T26 예산 밖인 `agents/*.md` 에 둔다. 상시 컨텍스트 증가를 정책에 필요한 최소로 묶는
  배치다.
- **D2 — 추가가 아니라 치환.** 「공통 규칙」 첫 항목이 중복을 지시하던 문장이므로 새 절을
  만들지 않고 그 자리를 갈아끼운다. 새 절을 만들면 옛 문장이 남아 두 지시가 공존한다.
- **D3 — 말투 정의를 재사용.** "비개발자가 이해할 수 있게 / 단답형"은
  `common/git-workflow.md` 「Message style」에 이미 있다. 참조 한 줄로 대신한다(약 140B
  절약, DRY).
- **D4 — 검수자 기계적 형식 보존.** 폐기하면 재검수 입력 계약(3단계의 "1회차 지적
  항목을 함께 넘긴다")이 깨진다. 바꾸는 것은 **수신자 선언 한 문단**뿐이다.
- **D5 — 디자인 패턴 도입 없음.** 새 에이전트·스킬·체크리스트 단계를 만들지 않는다.
  문제는 "두 지시가 같은 수신자를 겨냥한다"이고 해법은 "수신자를 갈라 적는다"다 — 가장
  단순한 구조다(YAGNI).
- **D6 — 새 T 그룹이 아니라 T31-8.** 검사 형태(리터럴 토큰 존재)와 한계가 T31-6·T31-7 과
  같다. T31 머리 주석이 이미 "T31-7 을 얹으면서 범위를 넓혔다"고 기록했으므로 같은 관례를
  따른다.
- **D7 — 줄일 수 있는 기존 문장을 찾았으나 없다(정직한 보고).** always-on 세트에서
  후보 3곳을 검토했다. (a) 「서브에이전트 위임은 사용자가 상시 요청한 것이다」 절
  (약 1.6KB) — 문서 자신이 "compact 요약에도 보존한다"고 못박은 재발 방지 기록이라 제외.
  (b) `/dashboard` 항목(약 1.5KB) — T22-158·T23-7 앵커와 운영 사고 기록이 들어 있고 이번
  요청과 무관해 수술적 변경 원칙상 제외. (c) `common/development-workflow.md` 의
  1·3단계 — `role-separation.md` 와 겹치지만 이 워크플로우를 쓰지 않는 프로젝트에도
  배포되는 범용 규칙이라 제외. **결론: 이번 회차의 순증가는 +671B 이고 상쇄분은 없다.**
  선례와 같은 크기다 — 같은 파일군의 `common/git-workflow.md` 「Message style」 6줄
  추가가 +328B 였다(`tests/run.sh` T26 이력 주석).

## 9. 리스크와 대안

### 리스크

- **R-1 (수용) — 정적 토큰 검사는 이행을 보증하지 않는다.** T31-8 은 문구가 남아 있는지만
  본다. 세션이 그 문구를 읽고도 장황하게 보고하는 것은 잡지 못한다. T31-7 이 "목업을
  실제로 만들었는지는 검사하지 못한다"고 적은 것과 같은 한계이고, 같은 처방(검수의 몫)을
  따른다. 대안(트랜스크립트 사후 분석 훅)은 이 저장소 범위를 크게 넘는다.
- **R-2 (완화됨) — output style 의존.** 규칙이 FRIDAY 를 이름으로 부르면 그 style 이
  없는 사용자에게는 뜻이 비는 문장이 된다. §3.1·§6 대로 **순서 규칙으로만** 쓰고 이름을
  부르지 않아 완화한다.
- **R-3 (수용) — 상시 컨텍스트 +671B(55,509 → 약 56,180, +1.2%).** 이 저장소가 스스로
  정한 병목을 1.2% 악화시킨다. 근거: 이 문단이 막는 실패(사용자가 이해 못 한 채 승인)는
  잘못된 설계를 통과시켜 구현·검수 왕복 전체를 낭비하게 만든다 — 그 비용이 671B 보다
  훨씬 크다. T26 상수를 고치는 커밋 메시지에 이 근거를 남긴다.
- **R-4 (완화됨) — 화면의 블록 수는 줄지 않을 수 있다.** 하네스가 서브에이전트 출력을
  계속 보여주면 사용자는 여전히 기술 블록을 본다. 이 설계가 없애는 것은 *같은 내용의
  반복*이지 블록 자체가 아니다(§2 인용 블록). 사용자에게 이 구분을 명시해 기대를
  맞춘다.

### 검토했으나 채택하지 않은 대안

- **대안 A — 서브에이전트가 최종 메시지 대신 파일에 보고서를 쓰고 "완료" 한 줄만 반환.**
  화면 중복이 확실히 사라지는 대신, 서브에이전트의 최종 메시지는 오케스트레이터가 결과를
  받는 **유일한 경로**다(에이전트 지침이 "최종 보고가 곧 산출물"이라고 명시). 파일 경유로
  바꾸면 메인이 그 파일을 다시 읽어야 해 컨텍스트를 더 쓰고, 도구 실패 시 결과가 통째로
  유실된다. **기각.**
- **대안 B — 보고 규칙을 `rules/common/` 에 신설.** 모든 프로젝트에 적용되는 대신, 이
  4-에이전트 워크플로우를 쓰지 않는 프로젝트에도 상시 바이트를 물린다. `common/` 은
  언어·워크플로우 중립 원칙 층이라는 `rules/README.md` 의 계층 정의와도 어긋난다.
  **기각.**
- **대안 C — 테스트 없이 문서만 고친다.** T31-8·원장 행·floor 2종의 비용(약 15줄)이
  사라지는 대신, 지침 절이 조용히 사라지는 회귀를 잡을 수 없다 — T31-7 이 바로 그 이유로
  신설된 선례가 있다(2026-09-10 사고). **기각.**
