# 커밋 시 로컬 서버 자동 종료 + 플로팅 창 상태 고정 (PRP)

## 요구사항 요약

`/dashboard init` 의 자동 발행이 띄운 로컬 정적 서버는 세션이 끝나도 살아남는다. 지금은 사용자가
포트를 기억했다가 `/dashboard serve stop {포트}` 를 직접 불러야 정리된다. 이번 라운드는 **전체 경로
워크플로우의 마지막 트리거인 `/dashboard log commit` 이 그 서버를 자동으로 끄게** 한다. 동시에,
서버가 죽은 뒤에도 **이미 열려 있는 Document PiP 창은 마지막으로 동기화된 화면(진행률 100% ·
커밋 로그가 찍힌 완료 상태) 그대로 조용히 고정**되어야 한다.

핵심 난제는 하나다: **`log commit` 시점에 "어느 포트를 죽여야 하는지"를 기계적으로 알아내는 것.**
지금 이 정보는 오케스트레이터의 대화 메모리에만 있고 파일에는 없다. 이 스킬의 확립된 철학
(「별도 상태 파일(JSON)은 두지 않는다 — `.claude/dashboard.html` 의 DOM 자체가 상태다」)을
지키면서, `#dz-log` 여는 태그에 포트를 각인하는 방식으로 해결한다.

### 사용자와 합의된 확정 사항 (재논의 대상 아님)

1. **종료 트리거는 `log commit` 이다.** `step` 이 100% 가 되는 시점도, 새 `/dashboard done`
   하위 명령도 아니다. CLAUDE.md 트리거 표의 마지막 행(커밋·푸시)에 종속시킨다.
2. **PiP 는 추가 UI 없이 현재 상태로 조용히 고정한다.** 안내 배지·오버레이·"서버 종료됨" 문구를
   새로 만들지 않는다. 폴링은 계속 재시도하되 실패해도 창을 닫거나 방해하지 않는다.
3. **새 하위 명령·새 인자를 만들지 않는다.** 호출 규약은 한 글자도 바뀌지 않는다.

### 워크플로우 경로 판정

**전체 경로**다. 데이터 모델(DOM 계약)에 속성 1개가 추가되고, `log` 의 결정적 절차에 분기가
생기며, 두 파일(`commands/dashboard.md` · `tests/run.sh`)에 걸친다.

## 데이터 모델

### 개념 모델

```
ServerRecord                     # .claude/dashboard.html 의 #dz-log 여는 태그에 각인된다
  port : int(1024..65535) | ""   # "" 또는 속성 부재 = 이 프로젝트를 서빙 중인 로컬 서버가 없음
```

값이 하나뿐이므로 별도 구조를 만들지 않는다. 프로젝트당 대시보드 파일이 하나이고, 자동 발행은
`REUSE` 를 `FREE` 보다 우선해 같은 프로젝트에 서버가 쌓이는 것을 이미 막고 있다.

### DOM 상 표현

```html
<ul class="log" id="dz-log" data-current-session="1" data-server-port="8791"></ul>
```

- **반드시 `data-current-session` 뒤에 온다.** T22-11 이 `id="dz-log" data-current-session="1"` 을
  **연속 문자열**로 검사하기 때문이다. 사이에 끼워 넣으면 그 테스트가 즉시 깨진다.
- 템플릿 기본값은 빈 문자열(`data-server-port=""`)이다. `init` 이 파일을 새로 만든 직후에는
  아직 서버가 없고, 각인은 「자동 발행」 3단계가 한다.
- 이 기능 도입 이전에 만들어진 대시보드에는 속성이 **없다.** 읽는 쪽은 "부재 = 빈 문자열"로
  간주하고, 쓰는 쪽은 여는 태그의 `>` 바로 앞에 새로 삽입한다(마이그레이션 절차를 따로 두지 않는다).

### 왜 `<body>` 가 아니라 `#dz-log` 인가

이 문서는 같은 문제를 이미 한 번 풀었다 — `data-current-session` 이 새 행이 아니라 `#dz-log` 행의
하위 개념인 이유가 그것이다: **`log` 절차가 어차피 매번 grep 하는 줄에 얹혀 있어 탐색 단계를
늘리지 않는다.** 자동 종료를 수행하는 주체가 바로 그 `log` 절차이므로, 포트를 같은 줄에 두면
**커밋 경로에 Bash 호출이 하나도 늘지 않는다**(0-a 의 기존 grep 결과에 값이 이미 들어 있다).
`<body>` 에 두면 `log commit` 이 grep 을 한 번 더 해야 한다. 같은 문제에는 같은 해법을 쓴다.

### grep 유일성 검토 (기존 불변식 위반 여부)

| 기존 grep 패턴 | 새 속성이 미치는 영향 |
|---------------|---------------------|
| `grep -n 'id="dz-log"'` (`log` 0-a, `init` 1-a) | 같은 줄에 속성이 하나 늘 뿐 **매칭 줄 수는 그대로 1**. 두 절차 모두 "줄 전문을 읽어 old_string 으로 쓴다"는 방식이라 속성이 늘어도 무해하다 |
| `grep -c 'dzs-all'` (세션 탭 판정) | 무관 |
| `grep -c 'dz-cell-.*data-state="done"'` · `'dz-step-.*class="done"'` · `'dz-impl-[0-9].*class="done"'` | `data-server-port` 는 `dz-cell-`·`dz-step-`·`dz-impl-` 중 어느 것도 포함하지 않는다 |
| `grep -n 'dz-group-\|dz-cell-'` (표 지도) | 무관 |
| T22-41 (템플릿 안 `id="dz-log"` 매칭 줄 수 == 1) | 그대로 1 |
| T22-38 (`[id="dz-` 형태 금지) | `id="…"` 형태의 새 완전일치 문자열을 만들지 않는다 |

`data-server-port="{P}"` 라는 문자열 자체도 문서 내 유일하므로, 각인 해제 Edit 의 앵커로 그대로
쓸 수 있다(줄 전문을 다시 읽을 필요가 없다).

## 인터페이스

### 호출 규약 — **한 글자도 바뀌지 않는다**

```
/dashboard log <impl|pass|fail|commit> "<한 줄 요약>" ["상세"] [--round N]
/dashboard serve [포트] | serve stop
```

`argument-hint` 도 그대로다. 자동 종료는 기존 `commit` 인자에 **부수 효과로 붙는다** — 사용자가
새로 배울 것이 없다는 점이 확정 사항 1(별도 명령 금지)의 실질적 이유다.

```markdown
2. Edit 1회로 그 줄을 치환한다. `old_string` 은 1에서 읽은 전문을 그대로 쓴다.
   - `data-server-port="…"` 가 이미 있으면 **값만** `{P}` 로 바꾼다.
   - 없으면(이 기능 도입 이전에 만들어진 대시보드) 여는 태그의 `>` **바로 앞**에
     ` data-server-port="{P}"` 를 삽입한다. `data-current-session` 앞으로 끼워 넣지 않는다.
3. **이 절차의 실패는 호출자를 중단시키지 않는다.** 각인이 없으면 `log commit` 이 아무것도 하지
   않을 뿐이고, 사용자는 `/dashboard serve stop {포트}` 로 언제든 직접 끌 수 있다
   (「자동 발행」의 실패 비차단 원칙과 같다).
```

#### (7) `serve` 절차

```diff

     …
     - "Address already in use" 로 죽으면 포트 충돌이다. 다른 포트를 **추측해서 재시도하지 말고**
       보고하고 `/dashboard serve 8792` 를 제안한다.
+    - **기동에 성공했으면**(위 오류 없이 백그라운드 태스크가 살아 있으면) 위 [포트 각인] 절차로
+      `{포트}` 를 각인한다. 실패해 보고하고 끝나는 경로에서는 각인하지 않는다.

  4. `stop`: `pkill -f "http.server {포트} --bind 127.0.0.1"` 를 실행하고 결과를 보고한다.
     (0단계에서 정한 대상 포트를 쓴다. …)
+    실행 후, `#dz-log` 의 `data-server-port` 값이 **이번에 중지한 포트와 같으면** [포트 각인]
+    절차로 빈 문자열을 각인한다. **다르면 건드리지 않는다** — 다른 서버에 대한 기록이다.
+    낡은 각인이 남으면 `log commit` 의 자동 종료가 그 사이 그 포트를 차지한 **다른 프로젝트의
+    서버**를 끌 수 있다. 이 한 줄이 그 경로를 막는다.
```

```markdown
      | `{P}` | 행동 |
      |-------|------|
```

## 설계 결정과 근거

### 1. PiP 고정은 **코드를 한 줄도 바꾸지 않고** 달성한다

현재 `poll()` 의 실패 경로는 이미 요구사항 2를 정확히 충족한다:

```js
.catch(function(){
  if(++failureCount >= FAILURE_LIMIT)
    setHint('대시보드를 읽지 못했습니다. …');
})
```

- 창을 닫지 않는다. `location.reload()` 를 부르지 않는다. DOM 을 비우지 않는다.
- `apply()` 는 **성공 경로에서만** 호출되므로, `sessionTabsChanged()` 발 강제 `pipWindow.close()`
  경로도 서버가 죽은 뒤에는 절대 실행되지 않는다.
- 유일한 부작용인 `setHint(...)` 는 `#dz-pip-hint` 를 쓰는데, 이 요소는 `.wrap` **바깥**이라
  PiP 창으로 이동하지 않는다. 즉 **PiP 만 보고 있는 사용자에게는 그 문구가 애초에 보이지 않는다.**
  평소에는 이 배치가 한계지만, 이번 요구("추가 UI 없이 조용히 고정")에서는 그것이 정확히
  원하는 동작이다.

따라서 이 요구사항의 산출물은 **코드가 아니라 회귀 테스트**다. 아무도 건드리지 않아 동작하는
성질은 언젠가 조용히 깨지므로, T22-85(역방향)로 "실패 경로가 창을 닫거나 리로드하지 않는다"를
못 박는다.

### 2. 각인 지점을 **티어 확정 시점 하나**로 모은다

기동 성공(FREE) · 재사용(REUSE) · 티어 2 폴백의 세 결말이 모두 「3. URL 확정」을 지난다.
여기 하나에만 각인을 두면 **모든 경로가 자동으로 커버되고**, 특히 티어 2 로 내려앉는 모든 사유
(python3 없음 · `NONE` · 기동 실패 · 스캔 명령 자체 실패)가 **낡은 값 지우기**로 수렴한다.
기동 성공 지점(2-a)에만 각인했다면 "낡은 값이 남는" 경로가 넷 생겼을 것이다.

### 3. `sleep 6` — 서버를 죽이기 전에 **마지막 화면을 전달**한다

`log commit` 은 커밋 항목을 파일에 쓴 직후 서버를 끈다. 폴링 주기가 5초이므로 즉시 죽이면
최대 5초치의 최신 상태(=커밋 항목 그 자체)가 브라우저에 영영 닿지 않는다. 그러면 PiP 는
"커밋 직전" 화면에서 얼어붙어 이 기능의 목적을 정면으로 배신한다.

- 6초는 `POLL_INTERVAL_MS`(5000) 에서 파생된 값이다. 문서에 그 연결을 명시해 두어야
  폴링 주기를 바꾸는 사람이 여기도 함께 본다.
- 백그라운드 실행(`run_in_background`)으로 턴을 막지 않는 선택지도 검토했으나, 그러면
  보고 시점과 실제 종료 시점이 어긋나 "종료했습니다"가 사실이 아니게 된다. 커밋 턴에서
  6초는 무시할 만한 비용이므로 **전경 실행**을 택한다.

### 4. 각인을 **두 지점에서 지운다** (`log commit` c · `serve stop`)

자동 pkill 의 유일한 실질 위험은 "낡은 포트로 남의 서버를 끄는 것"이다. 각인이 남을 수 있는
경로는 정확히 둘 — (a) 자동 종료 후 그대로 둔 경우, (b) 사용자가 `serve stop` 으로 먼저 끈 경우.
두 곳에서 지우면 **각인이 남아 있다 = 그 포트에 우리 서버가 있다**가 거의 항상 참이 된다.
`serve stop` 쪽에 "중지한 포트와 같을 때만"이라는 조건을 붙이는 이유는, 사용자가 각인과 무관한
포트를 끌 수도 있기 때문이다(그때 각인을 지우면 살아 있는 서버의 기록을 잃는다).

### 5. 스크립트는 이 속성을 **읽지 않는다** (불변식 8)

`syncLog` 는 `innerHTML` 만 대입하므로 라이브 DOM 의 여는 태그 속성은 폴링으로 갱신되지 않는다.
JS 가 이 값을 읽기 시작하면 "화면이 들고 있는 값"과 "파일의 값"이 갈라지고, 불변식 7이 「지금」
카드에서 막았던 것과 똑같은 이중 출처 문제가 재발한다. 각인은 **오케스트레이터 사이의 메모**이지
화면의 입력이 아니다.

### 6. `commit` 분기는 절차의 **맨 끝**에 둔다

2단계(prepend) 앞에 두면 커밋 항목이 기록되기 전에 서버가 죽는다(설계 결정 3). 또한 종료 로직이
어떤 이유로 어긋나도 **로그 기록이라는 본래 책임은 이미 완수된 뒤**여야 한다. 이 스킬의 전반적
톤 — 부가 기능의 실패가 본체를 막지 않는다 — 과 같은 배치다.

### 7. 새 셀렉터·새 카드·새 CSS 를 만들지 않는다

추가되는 것은 기존 태그의 속성 1개뿐이다. 「동적 — 7 셀렉터」 표의 행 수는 그대로 7이고,
매트릭스·「지금」 카드·impl 카드는 한 글자도 바뀌지 않는다.

### 수동 검증 (구현 후 1회, 실제 세션에서)

| # | 시나리오 | 기대 |
|---|---------|------|
| 1 | `/dashboard init` → 티어 1 기동 | `.claude/dashboard.html` 의 `#dz-log` 에 `data-server-port="8791"` 각인 |
| 2 | 1의 상태에서 브라우저 「플로팅」 → `/dashboard log commit "…"` | 6초 뒤 서버 종료. PiP 창에 **커밋 항목이 찍힌 채로** 정지. 창이 닫히지 않는다 |
| 3 | 2 직후 `curl -sf http://127.0.0.1:8791/dashboard.html` | 실패(연결 거부). 각인은 `data-server-port=""` |
| 4 | 3 직후 `/dashboard log commit "…"` 재호출 | 아무 일도 일어나지 않고 종료 보고도 없다 |
| 5 | `/dashboard serve 9000` → `log commit` | 9000 이 각인되고 9000 이 죽는다(후보 포트 밖 커버) |
| 6 | 서버 없이(`file://` 티어 2) `log commit` | 아무 일도 없고 로그만 기록된다 |
| 7 | `/dashboard serve stop 8791` 로 먼저 끈 뒤 `log commit` | 각인이 이미 비어 조용히 넘어간다 |

## 리스크와 대안

### 검토했으나 채택하지 않은 대안

**대안 A — 각인 없이, `log commit` 시점에 「포트 스캔」을 다시 돌린다.**
「자동 발행 2단계」의 python3 스캔은 후보 포트에 붙어 **바이트 비교로 "이 프로젝트의 대시보드인가"를
확인**한다. 그 스크립트를 그대로 재사용해 `REUSE` 로 판정된 포트만 죽이면, 새 데이터 모델이
전혀 필요 없고 남의 서버를 끌 위험도 구조적으로 0이다. 상당히 매력적인 안이었다.

채택하지 않은 이유:
1. **후보 포트(8791~8793) 밖의 서버를 못 죽인다.** 사용자가 `/dashboard serve 9000` 을 부른 경우가
   그대로 누락된다 — 요구사항 3("자동 발행과 `serve` 둘 다 커버")을 만족하지 못한다.
2. **`log commit` 이 python3 에 의존하게 된다.** 지금 `log` 는 grep·Read·Edit 만으로 끝나는
   가장 값싼 명령이며, 그 성격을 커밋 경로에서 깨고 싶지 않다.
3. 커밋 시점마다 새 프로세스와 3회의 TCP 연결이 생긴다.

다만 대안 A 가 가진 장점(죽이기 전 신원 확인)을 잃는 대신, 각인을 **두 지점에서 지우는**
설계 결정 4로 그 위험 창을 좁혔다.

**대안 B — `<body data-server-port>`.** 데이터 모델상 더 "중립적인" 자리처럼 보이지만,
`log commit` 이 포트를 읽기 위해 Bash grep 을 한 번 더 해야 한다. `data-current-session` 이
같은 이유로 이미 `#dz-log` 에 얹혀 있다 — 선례를 따른다.

**대안 C — `step` 이 100% 가 되는 순간 자동 종료.** 사용자와의 합의로 배제. 구조적으로도
`step 4 done` 이후 검수 FAIL 로 되돌아가는 경로가 있어 "100% = 끝"이 참이 아니다.

**대안 D — PiP 안에 "서버가 종료되어 화면이 고정되었습니다" 안내를 띄운다.** 사용자가 명시적으로
"추가 UI 변경 없이"를 선택했고, 현재 코드가 이미 조용한 고정을 달성한다(설계 결정 1).

### 잔존 리스크

| # | 리스크 | 영향 | 완화 |
|---|-------|------|------|
| R1 | 낡은 각인으로 **다른 프로젝트의 서버**를 끈다 | 중 · 확률 낮음 | 각인 해제 2지점(설계 결정 4) + `--bind 127.0.0.1` 까지 포함한 정밀 패턴. 잔여 위험은 기존 `serve stop 8791` 과 **동일 수준**이며 그 이상으로 방어하지 않는다 |
| R2 | `sleep 6` 이 커밋 턴을 6초 지연 | 낮 | 의도된 비용. 문서에 사유를 못 박고 T22-86 이 삭제를 막는다 |
| R3 | `POLL_INTERVAL_MS` 를 늘리면 6초가 부족해진다 | 낮 | `log` 4-b 에 파생 관계를 명시. T22-86 이 두 문자열의 공존을 검사한다 |
| R4 | 종료 후 사용자가 opener 탭을 새로고침하면 오류 화면이 뜨고 PiP 도 사라진다 | 낮 | 브라우저 동작의 한계. 보고 문구에 `/dashboard serve {P}` 복구 경로를 넣어 대응 |
| R5 | 여러 세션이 한 대시보드를 공유할 때 세션 A 의 커밋이 세션 B 가 보던 서버를 끈다 | 낮 | 프로젝트당 대시보드 1개라는 기존 전제상 의도된 동작. B 는 `/dashboard serve` 로 되살린다 |
| R6 | 각인 Edit 실패로 포트가 기록되지 않는다 | 낮 | 실패 비차단. 결과는 "현재와 동일"(사용자가 직접 `serve stop`) — 이 기능은 어떤 환경에서도 기존 경험을 나쁘게 만들지 않는다 |
