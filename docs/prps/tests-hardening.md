### 0-2. 트랩 3종 — 손으로 재현했다 (§4 (b)·(c) 의 1차 증거)

세 실험 모두 별도 스크립트로 실행. 실행 로그는 세션 스크래치패드에 있고 커밋하지 않는다.

1. **EXIT 트랩은 마지막 설치만 발화한다.** 전역 EXIT 트랩을 걸고 함수 두 개에서 각각 EXIT
   트랩을 설치한 뒤 종료 → 로그에 `F2_TRAP_FIRED` 만 남았고 `GLOBAL_TRAP_FIRED` 는 없다.
   `trap -p EXIT` 도 마지막 것만 보여준다. 전역 트랩이 지우려던 디렉토리는 **살아남았다.**
2. **RETURN 트랩은 트랩을 건 함수로 범위가 한정되지 않는다.** `inner → runner → main` 3단
   중첩에서 `inner` 안에 설치한 RETURN 트랩이 **3회 발화**했다(카운터 파일 3줄).
3. **`f || true` 로 호출된 함수 내부에서는 `set -e` 가 죽는다.** 같은 함수 본문(`false` →
   `echo`)이 `probe || true` 로 부르면 `PROBE_CONTINUED` 를 찍고, 직접 부르면 그 자리에서
   스크립트가 죽는다(exit 1).

이 파일에서 실측한 트랩 설치 지점: **EXIT 28곳**(진입부 전역 1 + 테스트 함수 안 27) ·
**RETURN 1곳**(`test_pycache_excluded_from_deployment:7454`). 실행 순서상 T35 보다 먼저
설치되는 마지막 EXIT 트랩은 `test_manifest_ledger_and_removals`(`:6563`)로, HANDOFF §3-D
(b)의 범인 특정과 일치한다.

## 1. 요구사항 요약

`tests/run.sh`·`tests/hub` 는 이 저장소의 유일한 안전망인데, **검사를 추가해도 그 검사가
무는지 확인하는 절차가 없고**, **무는 힘 없는 검사가 추가돼도 스위트가 초록으로 남는** 구조다.
그 결과 커밋 `4be8f58` 가 「규범만 있고 검증 기계가 없던 자리 8곳」을 닫은 직후의 회차에서
같은 유형이 6건 재발했다. 이 PRP 는 **개별 결함 24건을 고치는 것이 아니라, 그 24건을
반복 생산하는 발생기 3종을 기계로 막는 것**을 목표로 한다. 개별 항목은 새 기계의 회귀
고객으로 배치한다.

### 성공 기준 (검증 가능한 형태)

| # | 기준 | 검증 방법 |
|---|---|---|
| K1 | 스위트가 요약을 출력하지 못한 채 종료하면 **exit 0 이 나올 수 없다** | RETURN 트랩에 재실행 실패 명령을 심어 조기 종료를 재현 → exit ≠ 0 이고 명시적 오류 문구가 나온다 |

## 3. 발생기 진단 — 왜 24건이 같은 자리에서 다시 나는가

### G1 — 보호 분기가 열거되지 않는다

「새 가드에 뮤테이션 검증을 요구한다」를 기계가 물으려면 **가드를 셀 수 있어야** 한다. 현재
유일한 열거 수단은 실패 메시지의 `T{n}-{k}` 접두인데, 실측 893 호출 중 **777만** 갖고 있고
**11/34 그룹**만 이 관습을 따른다. 열거가 안 되면 「이 가드에 뮤테이션이 붙었는가」라는 질문
자체를 던질 수 없다 — 그래서 규범이 디스패치 문면에만 남고 매번 새어 나간다.

### G2 — 계약이 주석에만 있다

`finish_group` 주석은 `passed + failed == total_tests` 를 **계약이라고 선언한다**(`:186-188`).
검사는 없다. `total_tests=34` 는 손으로 쓴 리터럴이다(`:7765`). T35 주석은 「이 트랩에 넣는
명령은 재실행돼도 안전해야 한다」를 적는다 — 검사는 없다. A1·A2·A5 도 같은 형태다: 규범이
문서에 있고 기계가 없다. **이것이 HANDOFF §4 「부차 결함」의 정확한 정의이고, 6건이 한
회차에서 나온 이유다.**

### G3 — 실패가 통과처럼 보인다 (리포팅 채널의 fail-open) — **상위 발생기**

세 경로를 실측했다.

1. 모든 그룹이 `test_x || true` 로 호출돼 **함수 내부에서 `set -e` 가 죽는다**(§0-2 실험 3).
   중간 명령이 실패해도 계속 진행하고, 오염된 상태에서 뒤 검사가 판정한다.
2. **조기 종료 시 요약이 아예 출력되지 않는데 그룹 헤더는 전부 `[OK]` 로 남는다**(A8, 실제
   사고). exit code 를 보지 않으면 전체 통과로 읽힌다.
3. **총합 무대조**(B3). 그룹이 집계에 도달하지 못해도 「실패: 0」이 찍히고 exit 0 이다.

**G3 는 G1·G2 를 은폐한다.** 무는 힘 없는 검사를 추가해도 스위트가 초록이므로 되돌아오는
신호가 없다. 그래서 **단계 순서는 이 인과에서 나온다: G3 → G1 → G2.** G3 를 먼저 닫지
않으면 G1·G2 의 수정이 실제로 작동하는지 확인할 수단이 없다.

## 4. 발생기 대응 — 「뮤테이션 검증을 통과 조건으로」를 무엇으로 강제하는가

### 4.1 결론 요약: 기계 강제와 문서의 경계

| 강제 대상 | 수단 | 기계 가능? |
|---|---|---|
| 요약 미출력·총합 불일치 시 exit 0 금지 | 전역 EXIT 트랩 + 총합 대조 | **가능** (§4.2) |
| EXIT 트랩 1곳·RETURN 0곳 | 구문 계수 검사 + 뮤테이션 | **가능** (§4.3) |
| ID 있는 가드가 원장에 전부 등록됨 | 집합 차집합 검사 | **가능** (§4.4) |
| 등록된 변조가 실제로 무는지 | 정방향 FAIL + **역방향 PASS** + 고유 토큰 | **가능** (§4.4) |
| ID 없는 호출이 늘지 않음 | 116 래칫(T26 과 동형) | **가능** (§4.4) |
| 등록된 가드 주석에 한계 표기가 있음 | 등록 블록 한정 존재 검사 | **가능** (§4.6) |
| 변조가 **의미 있는** 결함을 흉내내는가 | 원장의 `defect_description` 열 존재만 강제 | **불가 — 검수(사람)** |
| 문서 단정이 **정직한가** | — | **불가 — 검수(사람)** |
| 금지 어휘 사용 | — | **불가 — 위양성 지배**(§0-6, §11-5) |
| 부정 단언의 공허성 판정 | — | **불가 — 위양성 지배**(§0-7, §11-6) |

**경계를 한 문장으로: 기계는 「존재」와 「무는 힘」을 강제하고, 「정직함」과 「의미」는 검수가
본다.** 이 경계를 문서에 못박는 것 자체가 이 PRP 의 산출물이다 — 문서 규범만으로 이미
실패했으므로(디스패치에 규범을 명시했는데도 15번째 거짓 단정이 났다), 문서에 남길 것은
**규범이 아니라 규범의 한계**다.

### 4.2 S1 — 리포팅 채널을 fail-close 로 (G3)

1. **그룹 레지스트리 배열화.** `register_and_run_tests` 의 34줄 호출 목록을
   `TEST_GROUPS=("T1:test_scope_project_new_install" …)` 배열로 바꾸고
   `total_tests=${#TEST_GROUPS[@]}` 로 **산출**한다. 리터럴 `34` 를 제거한다(리터럴은
   `:7765` 한 곳뿐이고 README 선언이 없어 파리티 부담이 없다 — §0-1).
2. **ID↔함수 파리티 검사.** 배열의 ID 와 함수 안 `local test_name=` 값이 일치하는지 확인한다
   (레지스트리가 조용히 어긋나는 것을 막는다).
3. **총합 대조.** `print_test_summary` 에서 `passed + failed != total_tests` 면 **실패로
   종결**하고 집계에 도달하지 못한 그룹 ID 를 보고한다(B3·K2).
4. **요약 미출력 검출.** 요약 출력 성공 시 플래그를 세우고, **전역 EXIT 트랩**이 플래그
   부재를 보면 `[ERROR] 스위트가 요약 전에 종료됨` 을 찍고 종료 코드를 보존한다(A8·K1).
   → 이 검출은 **전역 EXIT 트랩이 실제로 발화해야** 성립하므로 **S2 와 짝**이다.
5. **`--only` 선택자와 미지 인자 거부.** `main` 이 인자를 파싱한다: `--only T22,T35` ·
   `--list`(원장 완비 검사가 소비) · 그 외 인자는 **exit 2**. 선택 실행에서는
   `total_tests` 를 선택 그룹 수로 산출해 총합 계약을 유지한다(K7).
   정량 근거: 원장 N행에 정·역방향 2N회 그룹 실행이 필요하고, 선택자가 없으면 회당 37.3초다
   (N=10 → 12분). 선택자가 있으면 대상 그룹만 돈다(§0-8).

### 4.3 S2 — 트랩 운용의 관용구 교체 (A4·A8)

**27곳을 개별로 고치지 않는다. 관용구 하나를 바꾸고 그 관용구를 검사한다.**

- 테스트 함수는 `trap … EXIT` 를 걸지 않고 자기 샌드박스 경로를 전역 배열에 등록한다:
  `register_cleanup_path "$sandbox"`.
- 그룹 정리는 **트랩이 아니라 명시 호출**로 한다 — `finish_group` 이 반환 직전에
  `cleanup_registered_paths` 를 부른다. 조기 `return 1` 경로에서 빠뜨려도 **전역 EXIT
  트랩이 받는다**(fail-safe).
- RETURN 트랩은 **0곳**이 된다. T35 가 RETURN 을 쓴 목적(레포의 `commands/__pycache__` 를
  스위트 끝까지 남기지 않기)은 등록 + `finish_group` 정리로 그대로 달성된다 — 그래서 A8 의
  「재발화 때 멱등이어야 한다」는 제약 자체가 **소멸**한다.
- **기계 강제**: `tests/run.sh` 안에서 `trap … EXIT` 설치가 정확히 1곳, `trap … RETURN` 이
  0곳임을 검사한다. 함수 안에 EXIT 트랩을 심는 변조가 이 검사를 물어야 한다(K3).
- **K4 로 결과를 직접 관측한다**: `CODING_HARNESS_TEST_HOME` 을 지정해 돌린 뒤 그 디렉토리가
  사라졌는지 본다. 삼중 증거의 첫 증거를 그대로 회귀 검사로 승격하는 것이다.

### 4.4 S3 — 뮤테이션 원장과 완비 검사 (G1·G2 의 핵심)

이 절이 「새 보호 분기를 추가할 때 뮤테이션 검증을 통과 조건으로 만드는 절차」의 답이다.

**(1) 원장 파일** — `tests/mutations.tsv`. 탭 구분, `#` 주석 허용. 7열:

| 열 | 의미 |
|---|---|
| `guard_id` | 서브체크 ID (`T28-3`) |
| `target_path` | 변조 대상(레포 상대경로) |
| `mutation_sed` | 사본에 적용할 `sed` 스크립트. 면제행은 `-` |
| `expect_group` | 변조 후 실패해야 하는 그룹 ID (`T28`) |
| `expect_token` | 실패 메시지에 반드시 나타나야 하는 고유 토큰(보통 `guard_id`) |
| `defect_description` | **이 변조가 흉내내는 실제 결함** 한 줄. 비어 있으면 파싱 실패 |
| `exempt_reason` | 면제 사유. `mutation_sed == -` 일 때만 허용, 비면제행에서는 비어야 한다 |

**(2) 하네스** — 새 그룹 `T36`(현재 최댓값 T35 의 다음, T11 결번 유지). 각 행마다:

1. 레포 사본(mirror)을 만든다 — `rules/`·`agents/`·`commands/`·`install.sh`·`tests/`.
2. **역방향 먼저** (개정 2026-10-01 → §28) — 행마다가 아니라 **그룹마다 1회**: 변조하지 않은 사본에서 `expect_group` 을 실행해 **PASS** 를 확인한다.
   PASS 가 아니면 「사전조건 불성립」으로 그 행을 실패 처리한다.
   → **이것이 A9 의 해법이다.** 「변조로 넓어졌다」와 「이미 넓게 출하됐다」는 단독 grep 으로
   구분되지 않지만, **변조 전 PASS · 변조 후 FAIL 의 쌍**은 두 경우를 갈라낸다. 프로덕션이
   이미 넓게 출하됐으면 역방향이 FAIL 하고 진단이 정확해진다.
3. `sed` 를 적용하고 **적용됐는지** 확인한다(파일 바이트 변화 — 기존 T35-8 의 grep 사전조건
   보다 강하다).
4. `expect_group` 만 실행해 **FAIL** 을 확인하고, **실패 메시지에 `expect_token` 이
   있는지** 단언한다 (개정 2026-10-01 → §28 — 변조 후 실행은 이제 새 미러에서 돈다). → exit 코드만 보는 검사는 무관한 이유로 실패해도 통과한다(HANDOFF §4).
5. 사본을 지운다(전역 정리 배열에 등록).

**(3) 원장 완비 검사** — 같은 그룹 안에서:

- `tests/run.sh` 소스에서 `T{n}-{k}` 집합을 추출(§0-4 의 방법)하고 원장의 `guard_id` 집합과
  비교한다. **차집합이 비어야 통과**한다(K5).
- 면제는 원장에 `-` + 사유로 **등록해야** 하므로 **침묵 면제가 불가능**하다. 이것이
  「통과 조건으로 만든다」의 실체다: 새 서브체크에 ID 를 붙이는 순간 완비 검사가 그 ID 를
  요구하고, 원장에 넣으려면 변조식 또는 사유를 써야 한다.
- **ID 접두 부재 래칫**: ID 없는 `note_failure`/`record_failure` 호출 수의 상한을 **116**
  으로 고정한다(§0-4 실측). 내리는 것은 자유, 올리려면 상수를 고치는 커밋에 이유가 필요하다
  — T26 과 동형의 이 저장소 확립 관용구다. **116건을 일괄 개조하지 않는다**(YAGNI).
- **공허 통과 방지**: 원장 행 수와 판정 쌍 수가 0 이면 실패한다(T28-1 의 `BLOCKS_CHECKED > 0`
  선례).

**(4) 초기 원장의 크기** — 완비 검사를 켜는 순간 364 ID 전부에 변조식을 요구하면 착지가
불가능하다. 그래서 **면제행을 1차 시민으로 둔다**: S3 착지 시점의 원장은
`실측 변조행(소수) + 면제행(나머지)` 이고, 면제행의 사유는 「S3 이전에 존재한 가드 —
개정·수정 시 변조행으로 승급」이라는 **한 가지 사유 문자열**을 공유한다. 이후 회차에서 그
가드를 건드리면 사유가 성립하지 않으므로 변조행으로 올려야 한다. **래칫이지 소급 개조가
아니다.**

### 4.5 S3 — 파이썬 층 (B8)

경계가 2개뿐이므로(§0-7) 개별 판정 대신 **테스트 하네스 1곳**을 고친다.

- `tests/hub` 의 훅·statusline 시나리오 베이스 클래스가 진입점을 호출할 때 내부 `_run` 을
  **래핑해 예외를 기록**하고, 케이스가 명시적으로 옵트인하지 않았으면 **삼킨 예외가 있으면
  테스트를 실패**시킨다. 프로덕션 코드는 건드리지 않는다(§11-4).
- 효과: `test_fresh_hub_html_does_not_spawn` 류의 부재 단언이 **대상 코드가 결정 지점까지
  실제로 도달했음**을 전제로만 통과한다. 그 모듈의 모든 케이스가 한 번에 면역된다.
- 남는 한계(정직하게): 이 래퍼는 **예외로 인한 공허성**만 닫는다. 예외 없이 분기 판정이
  틀려 부재가 관측되는 경우는 잡지 못한다. 아래는 비망라 예시다 — 상태 준비가 잘못돼
  애초에 그 분기에 들어가지 않는 경우, 모킹 대상이 실제 호출 경로가 아닌 경우. 전수 증명이
  아니다.

### 4.6 S3 — 문서 단정에 대해 기계로 할 수 있는 것

**할 수 없는 것**(§0-6·§11-5): 금지 어휘 denylist. `tests/run.sh` 안에서만 정당한 기제 서술
7건에 걸리고, 그러면 HANDOFF §4 가 경고한 그대로 「정비자가 상수를 올리거나 검사를 지워
이빨이 영구히 빠진다」.

**할 수 있는 것**: **등록된 블록에 한정한 존재 검사.** 원장에 등록된 가드의 주석 블록에
한계 표기(`실측한 범위` / `비망라` / `전수 증명이 아니`) 중 최소 하나가 있는지 확인한다.
대상이 등록 집합이라 위양성이 구조적으로 없다. 현재 그 표기의 총 사용량은 22건(§0-6)이므로
**초기 적용 범위는 원장의 변조행에 한정**하고, 면제행에는 요구하지 않는다.

이것이 잡는 것: 새 가드에 한계 서술이 **아예 없는** 경우. 잡지 못하는 것: 있지만 **거짓인**
경우. 후자는 검수의 몫이며, 이 경계를 §4.1 표에 못박는다.

## 6. 데이터 모델

레이어 간 통신에 쓰이는 명시적 타입. bash 에는 타입이 없으므로 **행 포맷과 불변식**으로
정의하고, 파서가 위반을 즉시 실패로 만든다.

### 6-1. `MutationRecord` (`tests/mutations.tsv` 한 행)

```
guard_id \t target_path \t mutation_sed \t expect_group \t expect_token \t defect_description \t exempt_reason
```

불변식:
1. `guard_id` 는 `T[0-9]+-[0-9a-z]+` 를 만족하고 원장 안에서 유일하다.
2. `target_path` 는 레포 상대경로이고 실재한다.
3. **면제행**: `mutation_sed == "-"` ∧ `exempt_reason != ""` ∧ 나머지 실행 관련 열은 `-`.
4. **변조행**: `mutation_sed != "-"` ∧ `exempt_reason == ""` ∧ `expect_group` 이 레지스트리에
   있는 ID ∧ `expect_token != ""`.
5. `defect_description` 은 면제·변조 무관하게 비어 있을 수 없다.
6. 열 수가 7 이 아닌 행은 파싱 실패(조용히 건너뛰지 않는다).

### 6-2. `TestGroupEntry` (레지스트리 배열 원소)

```
"<group_id>:<function_name>"
```

불변식: `group_id` 는 유일하고, `function_name` 은 정의된 함수이며, 그 함수 안의
`local test_name=` 값이 `group_id` 와 같다.

### 6-3. `GuardIdSet` (파생 — 검사만 소비)

`tests/run.sh` 소스에서 `note_failure`/`record_failure` 인자의 `"T{n}-{k}` 접두를 추출한
집합. **파생 데이터이므로 파일로 저장하지 않는다**(중복 원장 금지 — 드리프트 원천).

# (개정 2026-10-01 → §28): 역방향 PASS 는 그룹 단위 사전조건으로 옮겼다 — 시그니처는 그대로다.
assert_guard_bites <guard_id> <target_path> <sed> <group_id> <token> → void (note_failure 로 보고)

## 8. 단계 분할 — 4단계, 각 단계 독립 커밋·독립 착지

**24건을 한 회차에 다 하는 것은 옳지 않다.** 근거 셋:

1. **인과 순서가 있다.** G3(리포팅 fail-open)을 닫기 전에는 G1·G2 의 수정이 실제로 작동하는지
   확인할 수단이 없다(§3). 한 회차에 섞으면 「고쳤다」의 근거가 서로를 순환 참조한다.
2. **검수 왕복 상한이 3회다.** 직전 회차는 파일 3개 규모의 작업에서 3회차를 다 썼다
   (HANDOFF §3-D). 24건을 한 커밋에 넣으면 1회차 지적이 수십 건이 되고, 상한 안에 수렴할
   가능성이 낮다. 3회 FAIL 은 재설계 신호이므로(role-separation §3) 분할이 비용이 아니라
   보험이다.
3. **S3 은 되돌릴 결정을 포함한다.** 원장 포맷·면제 정책은 실제로 몇 행을 써 본 뒤에야
   판정이 되는 종류다. S1·S2 를 먼저 착지시켜 두면 S3 이 반려돼도 얻은 것이 남는다.

| 단계 | 내용 | 해소 항목 | 선행 | 단독 착지 가능성 | 검증 |
|---|---|---|---|---|---|
| **S1** | 레지스트리 배열화 · `total_tests` 산출 · 총합 대조 · 요약 미출력 검출 · `--only`/`--list` · 미지 인자 거부 | B3, A8(절반) | 없음 | **완전** — 새 검출력만 늘고 34/34 유지. 이후 단계 없이도 가치가 있다 | K1·K2·K7·K9 |
| **S2** | 트랩 관용구 교체(EXIT 1곳·RETURN 0곳) + 그 규범의 검사 | A4, A8 | S1 권장(요약 미출력 검출이 전역 EXIT 트랩에 얹힌다) | **높음** — S1 없이도 27곳 교체와 검사 추가는 성립한다. 순서 교환 가능 | K3·K4·K9 |
| **S3** | 원장 + T36 하네스 + 완비 검사 + ID 래칫 + 한계 표기 검사 + 파이썬 삼킴 래퍼 + A1·A2·A5·A3 이빨 | A1, A2, A3, A5, A9, B8 | **S1 필수**(선택자 없으면 2N×37.3초) | **중간** — S1 에 강하게 의존한다. 원장이 소수 행만 담아도 완비 검사는 성립한다 | K5·K6·K9 |

**착지 판정 규칙**: 각 단계 끝에서 §10 의 4개 정본 명령을 완주하고, 그 단계의 K 기준을

## 9. 개별 항목의 배치와 처리 방향

발생기 대응이 만든 기계의 **첫 고객**으로 배치한다 — 고치는 것으로 끝내지 않고 원장 행을

### A6 — `install.sh` 미인용 3곳 (S4, 우선순위 최상)

- 수정: `${absolute_path#"$REPO_ROOT"/}` · `${target_file_path#"$target_base_dir"/.claude/}`
  로 패턴 쪽을 인용한다. `list_missing_managed_files` 의 `grep -E "^Only in $source_directory"`
  는 ERE 해석을 피하도록 바꾼다(`grep -F` 로는 앵커 `^` 를 잃으므로, 접두 비교를 셸 문자열
  연산으로 옮기는 쪽이 자연스럽다 — 구현 시 판단).
- 회귀: §0-3 의 재현 절차(`re[po]` 경로 사본 + 대장 키·해시 검사)를 새 서브체크로 고정하고,
  **인용을 되돌리는 변조**를 원장에 등록한다(K8).
- **우선순위 근거**: 매니페스트는 이 저장소의 유일한 레이어 간 통신 채널(project CLAUDE.md
  §2)이다. 조용히 무의미해지면 은퇴 판정(규칙 5)·stale/modified 분류·멱등성 비교가 전부
  근거를 잃는다. fail-closed 방향이라 차단 사유는 아니었지만 **파급 범위가 24건 중 가장
  넓다.**
- **이관 중복 주의**: `shell-hardening` 에 이미 `install.sh:121`(grep 미이스케이프)이 있다.
  같은 계열이다 → §14 승인 항목 2.

## 10. 테스트 계획 — 「검사를 검사하는」 층과 후퇴 정지점

### 10-1. 층 구조

| 층 | 대상 | 이 PRP 의 산출물 |
|---|---|---|
| 0 | 프로덕션 (`install.sh`·`hub/bin`) | A6·A10~A16 수정 |
| 1 | 검사 (`tests/run.sh` 34그룹 · `tests/hub` 617) | B1·B2·B4·B7·B9 보강 |
| 2 | **층 1 이 무는지 검증** (`tests/mutations.tsv` + T36) | 신설 |
| 3 | 층 2 를 검증하는 층 | **만들지 않는다** |

### 10-2. 층 3 을 만들지 않는 근거 (후퇴 정지점)

1. **층 2 는 자기 자신에 대한 양성 대조를 내장한다** (개정 2026-10-01 → §28). 하네스는 각 행에서(지금은 각 그룹에서) **변조 전 PASS** 를
   먼저 요구한다. 하네스가 「그룹을 실행하지 않고 통과 판정」하는 방향으로 고장나면 역방향
   PASS 관측도 만들 수 없다 — 실행하지 않으면 PASS 도 관측되지 않는다. 즉 이 고장 형태는
   **층 2 자신의 요구를 깨뜨린다.**
2. **그 논리로 닫히지 않는 고장 형태를 원장 1행으로 접는다.** 원장의 첫 행은 **하네스 자신을
   변조 대상으로 삼는 행**이다 — 「판정 로직이 항상 통과를 반환하게 만드는 변조」에 대해
   T36 이 **FAIL 을 보고해야 한다.** 층 3 을 별도 파일·별도 그룹으로 만들지 않고 층 2 안의
   한 행으로 접는 것이므로, 이것은 후퇴가 아니라 **고정점**이다.
3. **층 2 의 고장은 층 1 의 고장과 달리 조용하지 않다.** T36 은 원장 행 수와 판정 쌍 수를
   출력하고 **0 이면 실패한다**(T28-1 의 `BLOCKS_CHECKED > 0` 선례). 층 1 의 무는 힘 부재는
   초록으로 위장되지만, 층 2 의 부재는 카운터 0 으로 드러난다. **은폐 가능성의 비대칭이
   정지 근거다** — 층 3 을 두면 층 4 의 논거가 똑같이 성립하므로 어딘가에서 멈춰야 하고,
   멈출 자리는 은폐가 어려워지는 첫 지점이다.

### 10-4. 뮤테이션 검증 (구현 중 필수 — 되돌리지 않고 원장에 남긴다)

이전 PRP 들은 뮤테이션을 「구현 중 1회 확인 후 되돌린다」로 운영했다(audit-remediation §8-5).
**그것이 재발의 원천이다** — 확인이 커밋되지 않으면 다음 회차가 같은 확인을 다시 해야 하고,

## 11. 기각 목록 — 검토했으나 하지 않기로 한 것

1. **B6 거대 함수 2개 분할 — 기각.** project CLAUDE.md §5 가 T 그룹 함수에 대한 50줄 예외를
   명문화했고(user rules 보다 project 가 우선), 「시나리오 나열이 본질이라 분할이 오히려
   가독성을 해친다」는 근거가 그대로 유효하다. 재실측으로 두 함수가 3,206줄·1,532줄로
   **커졌음**을 기록해 둔다(§0-5) — 커진 것 자체가 문제가 아니라 **개발 루프 비용**이
   문제이고, 그 비용은 §4.2 의 그룹 선택자가 낮춘다. 분할은 그 뒤에도 필요하면 별건으로 판단.
2. **B10 산문 어서션 99건 일괄 심사 — 기각(흡수).** 근거 둘. (i) 「99」가 내 계수 기준으로
   재현되지 않는다 — `grep -q` 계열 615줄, 그 중 패턴에 한글 139(§0-6·§2-2). 분류 자체가
   미완인 대상을 일괄 심사하는 것은 기준 없는 작업이다. (ii) **원장 등록이 심사를 대신한다** —
   가드를 원장에 올리려면 「변조 전 PASS·변조 후 FAIL」을 통과해야 하고, 무는 힘 없는 앵커는
   그 자리에서 드러난다. 별도 심사 회차를 만들지 않고 **가드를 건드릴 때마다 심사되게**
   한다. 대안(일괄 심사)은 615건에 대한 사람 판정이라 3회 왕복 상한 안에 수렴할 근거가 없다.
3. **`|| true` 폐지 / 그룹당 서브프로세스 격리 — 기각(이번 범위 밖).** `set -e` 억제는
   실측된 사실이지만(§0-2 실험 3), 서브셸에서 카운터를 갱신하면 부모에 반영되지 않아
   **34그룹 전부의 집계 접근을 파일 기반으로 바꾸는 개조**가 된다. 이 PRP 규모의 3배다.
   대신 **은폐를 닫는다**(총합 대조 + 요약 미출력 검출). 남는 위험은 §12 에 적는다.
4. **`hub/bin` 의 예외 삼킴 경로를 명명 함수로 분리 — 기각.** 테스트 편의를 위해 프로덕션을

## 13. GOTCHA (구현자가 틀리기 쉬운 함정)

1. **`set -e` 는 `f || true` 로 호출된 함수 내부에서 죽는다.** 새 헬퍼가 실패를 반환해도
   호출자가 그룹 함수 안이면 스크립트가 멈추지 않는다. 실패는 **반환값으로 전파**하고
   `note_failure` 로 보고한다. `((counter++))` 는 값이 0 이면 상태 1 을 반환한다 —
   `|| true` 를 붙이는 기존 관행을 유지한다.
2. **RETURN 트랩을 새로 쓰지 마라.** 범위가 한정되지 않아 이후 모든 함수 반환에서 재발화한다
   (실측 3회). S2 이후 이 파일의 RETURN 트랩은 0곳이고 검사가 그것을 강제한다.
3. **`bash` 는 3.2.57 이다.** 연관 배열(`declare -A`)이 없다. 원장을 메모리에 담을 때
   `ID:값` 문자열 배열 + 선형 탐색으로 쓴다(364행 규모에서 성능 문제는 없다).
4. **`sed -i` 는 BSD 다.** `-i.bak` 형태를 쓰고 `.bak` 를 지운다(T35-8 의 기존 관행).
5. **`find` 를 스크립트에서 부를 때와 대화형 셸에서 부를 때가 다르다.** 대화형 셸의 `find` 는
   스냅샷 함수로 `bfs` 를 가리킨다. 재현은 반드시 별도 파일을 `bash script.sh` 로 실행하거나
   `/usr/bin/find` 를 절대경로로 부른다.
6. **`total_tests` 리터럴 제거 시 `--only` 와의 상호작용.** 선택 실행에서 총합 계약을
   그대로 두면 항상 실패한다. 선택 그룹 수로 산출한다.
7. **미러 사본에 `tests/` 를 포함해야 한다.** T36 이 사본에서 그룹을 실행하려면 사본 안에
   `tests/run.sh` 가 있어야 하고, 그 사본이 다시 T36 을 실행하면 무한 재귀가 된다 →
   **미러 실행은 반드시 `--only <expect_group>` 으로 한정하고, `expect_group == T36` 인
   행은 원장 파서가 거부한다**(§10-2-(2)의 자기 고정점 행은 하네스 판정 함수를 변조하되
   실행 대상 그룹은 다른 그룹으로 둔다).
8. **`install.sh` 에 `hub` 문자열을 넣지 마라** — T25-21 이 0건을 강제한다(실측 확인).
9. **원장 파일은 배포 대상이 아니다.** `install.sh` 가 배포하는 것은 `rules/`·`agents/`·
   `commands/` 3종이다. `tests/mutations.tsv` 는 `removals.txt`·파일 수 상수와 무관하다.
10. **T35-9 는 `chmod 555` 를 쓴다.** 트랩 관용구를 교체할 때 이 경로의 권한 복구
    (`chmod -R u+w`)가 정리보다 **먼저** 일어나야 한다. 기존 코드가 그 순서를 지키는 이유가
    주석에 있다 — 옮길 때 함께 옮긴다.

## 17. S2 착지 기록과 이관 목록 (2026-09-04)

### 결정 5 — K4 를 K4a·K4b 로 분할한다 (S2 구현 중 승인)

§5 의 K4 원문은 「`CODING_HARNESS_TEST_HOME` 으로 지정한 디렉토리가 스위트 종료 후 **삭제된다**」이고

경위: S1 검수 1회차에서 `suite_exit_guard` 가 호출자가 준 경로를 삭제하는 것이 Critical 회귀로

`SANDBOX_IS_OURS` 소유권 게이트가 들어갔고, T36-1·T36-2 가 「호출자가 준 디렉토리는 살아남는다」를
회귀 검사로 고정했다. 즉 원문 K4 를 구현하면 그 Critical 수정을 되돌리고 T36-1·T36-2 를 깨뜨린다.

- **K4a** — `CODING_HARNESS_TEST_HOME` 미지정 시 스위트가 `mktemp -d` 로 만든 `$GLOBAL_HOME_SANDBOX`
  가 종료 후 삭제된다. **T36-3 이 이미 검사한다**(S1 에서 착지).
- **K4b** — 지정 시 **그 디렉토리 자체는 보존**되고 그 안에 그룹 샌드박스가 남지 않는다.

  1회성 실측으로 남긴다 — 이 환경의 `mktemp` 이 `TMPDIR` 재지정을 반영하지 않아 그 항목 수
  비교가 비결정적이기 때문이다(실측 확인).

### S2 착지 요약

커밋이 필요하다. 그 경계는 T37-5 의 fixture 가 고정한다.

**정규화의 순서가 규약이다.** 검수 3회차가 `\\/`(이스케이프된 백슬래시 + 진짜 구분자) 우회를

순서를 바꾸면 우회가 살아나고, T37-5 의 `\\/` fixture 가 그것을 잡는다.

| SIGKILL | 137 | 실행되지 않음(원리적) |

처음 보고는 「TERM·INT·HUP·QUIT 4종 모두 실행」이었고, 그 SIGQUIT 관측은 **백그라운드 잡 구성**에서 나온 것으로 보인다 — 그 구성에서는 시그널이 애초에 전달되지 않으므로 트랩이 「깨끗해 보인다」.

따라서 `register_cleanup_path` + `suite_exit_guard` 의 fail-safe 가 덮는 것은 **TERM·INT·HUP 세 계열**이고, **SIGQUIT 과 SIGKILL 은 덮지 못한다.** 555·`chflags uchg` 처럼 평범한 `rm -rf` 를 이기는 잔여를 만드는 프로브는 그 두 시그널에서 잔여를 남긴다 — 회수 절차는 `chmod -R u+w <경로> && rm -rf <경로>` 다. 이 결론은 bash 버전에 의존하므로 위 환경 밖에서는 다시 재야 한다. **실측한 범위는 위 5종이고 비망라다** — 다른 치명 시그널(SIGABRT·SIGSEGV 등)은 재지 않았다. 전수 증명이 아니다.

#### 이 회차의 방법론 소득

- **「가드가 있다」와 「가드가 불린다」는 다르다**(§18 의 교훈이 다시 확인됐다). 봉쇄 함수를 살려둔 채 **호출부 한 줄만** 지우면 함수 단언은 통과한다 — S3a 의 `T37-18` 이 그래서 함수 단언과 호출부 단언을 따로 두고, 미러 밖 파일이 실제로 변조됐는지를 표식으로 확인한다.
- **산문이 상수를 인용하면 그 인용이 표류한다.** 2회차 수정이 상수 3개를 움직였고, 그 값을 인용한 두 곳(원장 헤더 · 이 문서의 §19-3 착지 요약)이 모두 낡았다. 기계는 그 숫자를 읽지 않으므로 검수만이 잡는다 — 이 문서를 쓴 메인 세션도 같은 실수를 했고 같은 렌즈에 잡혔다.
- **한계 표기가 검증 가능한 예측으로 쓰였다.** `T36-11` 의 한계 절이 「호출부는 T36-3·T36-8·T36-5 까지 함께 발화하고 그중 한 줄만 원인을 말한다」고 적었고, 두 렌즈의 재현에서 글자 그대로 재현됐다(6건 발화, 원인을 말한 것은 `T36-11` 뿐).

**두 렌즈의 검출은 두 번 겹쳤고, 겹친 자리가 값이 컸다.** 1회차에 T36-12 의 전처리 인과 주장을

**이 회차가 그 자체로 증명한 것 둘.**

  래퍼를 떼어도 622건이 전부 통과했다(구현자 실측). 진입점 베이스에 래퍼가 실제로 얹혀 있는지를
  묻는 대조 2건을 더해 닫았다.
- **T36-12 의 「줄 전체 앵커」 결정이 다음 회차에 값을 냈다.** 2회차의 진단 문구 리워딩이 같은

  (재검수 렌즈 A 실측). 엄격 패턴이 load-bearing 임이 사후에 확인됐다.

**차단 판정 4건의 성격.** 전부 「적어 놓은 것이 참인가」였고 가드 동작을 바꿀 지적은 하나도
없었다. 그중 하나는 **거짓 인과**다 — 「`main` 호출 뒤에 두면 정상 종료 경로가 `main` 의 `exit`
를 통과해 이 줄에 도달하지 못한다」고 적었으나 `main()` 은 `exit` 를 부르지 않고 `return` 한다.
검수자가 사본 끝에 표식 출력을 붙여 **실제로 도달하는 것**을 확인했다. 배치가 옳은 진짜 이유는
반대쪽이었다: 사전 점검의 직접 `exit 1` 과 실패 시 `print_test_summary` 의 `return 1` → `set -e`
가 그 줄을 건너뛰므로, **뒤에 두면 정상적인 테스트 실패마다 트랩이 파싱 오류로 오진한다.**

### 20-5. 오케스트레이터가 심은 과대 진술 (정정 기록)

「파이썬 층 가드는 원장에 **구조적으로 등록할 수 없다**」는 진술은 **디스패치 프롬프트에 내가
써서 심은 것**이고, 구현자는 그것을 세 파일에 옮겨 적었다. 검수자가 파서를 읽어 반증했다:
앵커 유일성 제약은 **변조행에만** 걸리고, 면제행 분기는 `validate_exempt_row_structure` 만
통과하면 되며 `validate_mutation_target_path` 는 확장자를 보지 않는다 — `T36-9` 와 같은 형태로
**등록 가능하다.** 실제 대가는 `LEDGER_EXEMPT_ROW_RATCHET`(394, 헤드룸 0)을 올리는 커밋이고,
그것은 관용구가 의도한 마찰이지 불가능성이 아니다.

세 곳을 「**변조행으로는** 등록할 수 없다 / 면제행 등록은 파서가 허용하지만 이번 회차에는 하지

실제로 추가하지는 않았다.

### 21-6. 이 회차가 스스로 만든 결함 (기록)

문면 회차인데 **차단 판정 10건 중 6건이 이 회차가 새로 만든 것**이었다.

- **금지 어휘가 같은 문단에서 형태만 갈아탔다.** 직전 회차가 「3개뿐이다」를 지운 그 문단에
  `~뿐이다`가 다시 들어왔고, 더 나쁜 것은 **같은 문장 안에서 증거 기준이 역전**된 것이다 —
  `grep` 0 을 근거로 쓰는 것을 스스로 거부하고서 곧바로 트리 스캔 결과를 계수 기준 없이 단정했다.
- **분류가 닫히지 않았다** — 13 + 11 = 24 인데 분모는 25. 남은 1행이 문서 어디에도 이름이 없었고,
  그 행을 언급한 표현은 오히려 정반대로 읽혔다. **25행 표로 재구성해 구조적으로 닫았다** —
  모든 행이 정확히 한 번 등장하므로 독자가 할 산수가 남지 않는다.
- **승격한 절차가 실행 불가였다** — 두 번 그랬다. 1회차에는 필수 입력을 문서가 세운 조회 방법으로
  얻을 수 없었고(부모 sha 해석 단계 누락), 2회차에는 **레시피가 목표 판본을 산출하지 않았다**:
  「최종 커밋의 부모」는 벤더링 이후 그 경로의 상류 커밋이 **정확히 1개일 때만** 벤더링 시점
  판본과 같다. 1회차까지 그 레시피가 정확했던 것은 실제로 수행된 3파일이 모두 단일-후속-커밋
  사례였기 때문이다 — **「수행 기록」이 「장래 규칙」이 되면서 전제가 깨졌다.** 3회차에 조회를
  벤더링 경계(`until=<벤더링 시각>` 의 `[0].sha`)로 바꾸고 지름길에 확인 단계를 붙였다.
- **승격문이 기존 방법론 문단을 실질 중복하고 두 사본의 표기가 이미 갈렸다.** 같은 절차가 한 절에
  두 벌 있으면 한쪽만 고쳐진다 — 이미 그렇게 됐다. 절차를 한 곳으로 모았다.
- **근거로 든 계수가 5행 중 1행에서 성립하지 않았다** — 재동기화 담당자가 문서에 적힌 명령을
  그대로 돌리면 다른 값을 보는데, 그 차이가 「검사가 추가됐다」인지 「픽스처다」인지 문서로
  구분할 수 없었다. 픽스처 제외 열거에 두 ID 를 넣어 닫았다.
- **성립하지 않는 한계는 새로 없었다** — 구현 2·3회차의 자기 점검이고, 검수 3회차가 신규
  Critical·HIGH 0 으로 확인했다(§20 회차의 같은 결함이 재발하지 않았다).

**밀도와 정확성이 충돌했다.** 검수가 「문서가 너무 길어 정작 필요한 규칙이 묻힌다」를 지적했는데,
그것을 고치라고 요구한 항목들(25행 표 · 실행 가능한 절차 · 증거 등급)이 전부 새 내용이라 결과가
**더 길어졌다**(8,479B → 10,847B). 검수 2회차가 「요구 충돌이 아니라 미완」으로 판정하고 줄일
세 곳을 지목해 9,018B 로 내렸다 — 지목된 세 곳은 지정 형태로 전부 감축했고(−2,659B) 잔여는
절차 수정의 필수 증가분이다. 검수 3회차 후 사용 불가한 지름길 불릿을 지우고(−504B) 경계 규칙을

### 22-2. 결정 12 — 서브체크 1개를 3개로 늘린다 (구현 중, 실측 근거)

§9 는 서브체크 1개를 지시했다. 구현자가 3개로 확장하고 근거로 「§0-3 의 문자 그대로 재현

있어야, `:253` 은 **설치 대상 경로**(레포 경로가 아니다)에 메타문자가 있어야 발화한다.

확장의 유일한 근거가 이 주장이므로 검수 접지 렌즈에 독립 검증을 맡겼고, 단일 fresh install

### 22-3. §0-3 의 인과 서술 정정 (검수 렌즈 B Major)

§0-3 은 매니페스트 해시가 빈 문자열이 되는 이유를 「`compute_sha256` 는 `shasum | awk`
파이프라인이라 대상 부재 시 awk 가 0 을 반환하고」로 적었다. **틀렸다.** `install.sh` 는
`set -euo pipefail` 이고 `pipefail` 은 파이프의 종료 코드를 가장 오른쪽의 비정상 종료
명령에서 취하므로, awk 가 0 을 반환해도 `sha256sum` 이 실패하면 파이프라인 전체가 비정상
종료로 잡힌다.

실제 기제는 **호출 문맥**이다 — `save_manifest_file || return 1` 이 그 함수 트리 전체에서
`set -e` 를 끄고, 그래서 실패한 명령 치환이 중단 없이 빈 문자열로 흐른다. 최소 재현으로
갈렸다: 조건문 밖에서 같은 파이프라인을 돌리면 스크립트가 그 줄에서 rc 1 로 죽고,
`|| return 1` 체인 안에서는 rc 0 으로 빈 값이 흐른다. **오케스트레이터와 검수 렌즈 B 가
독립적으로 같은 재현에 도달했다.**

이 결함류의 계보가 이 저장소에 이미 있었다 — `install.sh` 의 「`set -e` 는 조건문에서
호출된 함수 내부에 적용되지 않으므로 직접 검사해야 한다」 주석과
`rules/common/karpathy-guidelines.md` 의 실패 사례가 같은 것을 적고 있다. **구현자가 새로
쓴 주석이 정확한 쪽**이었고, 설계 문서를 인용하면서 조용히 바로잡은 형태라 검수가 Major 로
올렸다. 이 절과 §0-3 의 취소선이 그 정정이다.

### 22-8. 이 절의 한계

§22-4 의 수치는 **이 회차 착지 시점의 실측**이다(§19-6·§20-6·§21-8 과 같은 핀). 이 문서는

않았다」도 그 4시나리오와 코드 독해에 근거한다.

아래는 비망라 예시다 — 이 절이 열거하지 않은 것: 다른 OS·셸에서 `case` 패턴의 인용 규칙 ·

**전수 증명이 아니다.**

| **A** 후보 자신이 쓰기 금지 + 중첩 (= T35-9 확장) | 실패 2건 · 집계 없음 | **동일** | 확장으로는 변조를 못 잡는다 |

이유: 후보 자신이 쓰기 금지면 중첩 자식도 함께 못 지워 **양쪽 다 실패**로 끝나고 부풀림이 없다.
부풀림은 후보의 **조상**이 쓰기 금지라 `rm -rf` 가 부분 성공(안의 자식은 지우고 자신은 못 지움)할
때 생긴다. 그리고 `cp -R src/. dst/` 는 `dst` 의 모드를 옮기지 않고 `install.sh` 에 `chmod` 호출이
없어, 최초 설치 한 번으로는 그 상태를 만들 수 없다 — 2단계 픽스처(정상 설치 → 대상 권한 조정 +
중첩 생성 → 재설치)가 필요하다.

**설계의 지시를 그대로 따르면 이빨 없는 검사가 됐을 자리다.** §9 의 그 문장에 취소선과 정정을
넣었다. 이 PRP 의 발생기 목록(§4.4)에 「설계가 지목한 기존 가드가 그 시나리오에 도달하지
못한다」는 형태를 더할 후보다.

### 23-6. 정정이 반대 방향으로 과교정됐다 (2회차 접지 Minor)

1회차 차단을 고치면서 발화 조건을 **「대상 자체가 쓰기 금지인 혼합 상황에서만」**으로 좁혀
적었다. 실제 조건은 「후보의 **조상 중 하나**가 쓰기 금지」다 — 접지 렌즈가 대상은 정상이고 그
안의 중간 디렉토리만 쓰기 금지인 픽스처로 발화를 실증했다. 게다가 같은 회차가 쓴 T35-12 한계
문단은 이미 그 변형을 알고 있어 **두 주석이 서로 어긋났다.**

**한 번의 정정이 반대 방향의 과소 진술을 만들었다.** 이 계열은 「단정이 실측보다 넓다」의
거울상이고, S4-1 에서도 한계 표기가 과소 진술로 나왔다(그때는 무해한 방향 — 실측이 표기보다
넓었다). 여기서는 유해하다: `install.sh` 에 `chmod` 호출이 없으므로 「대상 자체」를 믿은 독자는
이 가드를 **실환경 도달 불가로 오판해 지울 수 있다.** 실제로는 사용자가 `.claude/` 안 어느
디렉토리 권한을 조인 상태에서 발화한다.

### 23-7. 오케스트레이터가 심은 오류 2건 (정정 기록)

**(a) 틀린 전제.** 검수 디스패치에 「이전 판에서 터미널로 나갔던 `rm` 에러가 이제 나가지
않는다 — 진단을 잃는 방향인가」를 전제로 적었다. 옛 판은 `rm -rf … 2> /dev/null` 로 표준에러를
**이미 버리고 있었다.** 신규 판은 그것을 캡처해 경고에 담으므로 **순수한 진단 획득**이고 잃는
것이 없다. 접지 렌즈가 `git show HEAD:install.sh` 로 확인해 전제를 반박했다.

**(b) 잘못 센 수치.** 재접기 대상을 「`install.sh` 2줄 · `tests/run.sh` 6줄」로 넘겼는데 실제는
**5줄**이었다 — 표시폭 초과 목록에서 주석이 아닌 코드 줄 둘을 함께 센 것이 원인이다. 산문 렌즈가
두 방식(줄 단위 재측정 · 전후 컨텐츠 집합 대조)으로 재측정해 잡았다.

(b)는 **「움직이는 값의 인용」계열이 아니다**(§20-8 의 결론이 덮지 않는다). 낡은 인용이 아니라
**방금 만든 측정이 틀린 형태**다. 넘기는 측정에는 **세는 대상**을 함께 적어야 검수자가 재현할 수
있고, 이번에 그렇게 적었기 때문에 잡혔다 — 그것이 이 회차가 이 계열에 더하는 것이다.

### 23-8. A15 근거의 인과 정정 (2회차 접지 Minor)

「`cd ""` 가 성공해 범위 가드의 기준이 호출부 cwd 로 잡히므로 거부한다」 — 앞 절은 사실이지만
**인과가 접지되지 않는다.** 그 앵커는 루프 안 `case` 에서만 읽히고, `find ""` 가 후보를 0개 내므로
루프 본문이 한 번도 돌지 않아 **앵커가 읽히는 지점에 도달하지 않는다**(접지 렌즈 실측:
`find "" -type d -name '__pycache__'` → stdout 비어 있음, rc 1). 가드의 실제 값은 앵커 보호가
아니라 **조용한 무작동 대신 경고를 남기는 것**(fail-loud)이다.

**오케스트레이터의 사전 측정도 같은 오류를 담고 있었다** — 「실제 삭제는 일어나지 않지만 앵커
오염 자체가 결함이다」로 적었고, 그 「오염」이 관측되는 지점이 없다는 것까지 확인하지 않았다.
A15 의 **코드는 수정하지 않았다** — 두 회차 모두 검수자가 수정을 권하지 않았다(인자 누락은
가드보다 위의 `local target_directory="$1"` 에서 `set -u` 가 먼저 막고, 호출부가 한 곳이라
도달 불가다).

1. **T35-12 의 픽스처는 한 변형만 겨냥한다** — 더 깊은 중간 디렉토리만 쓰기 금지인 변형은 같은

2. **이름 재확인 경로에 커밋된 검증이 없다** — 그 `continue` 에 로그가 없어 **관측 가능한 신호가

3. **`log_info` 가 경로를 이스케이프 없이 인쇄한다** — 개행이 든 경로는 한 레코드가 물리적으로
   여러 줄로 보인다. 주석은 그 사실을 적었고 `%q` 인쇄는 이번 범위 밖으로 뒀다.
4. **A15 는 빈 문자열만 막는다** — `"${1:-}"` 가 인자 누락까지 함께 덮는다. 도달 불가라 손대지
   않았다(23-8).
5. **신규 `mktemp -d` 2줄의 결과 미검사**(접지 렌즈 미제출 의심). 같은 함수의 기존 9줄과 같은
   관례이고, 빈 값이 흘러도 사전조건 분기가 fail-close 한다는 것이 코드로 확인됐다.
6. **`install.sh` 가 800줄 상한을 더 넘었다** — 접지 렌즈 관찰. 상한 초과는 이 회차 이전부터이고
   증분의 대부분이 주석이다.
7. **§4.4 발생기 목록에 새 형태 후보** — 「설계가 지목한 기존 가드가 그 시나리오에 도달하지
   못한다」(23-3).

### 23-10. 이 절의 한계

§23-4 의 수치는 **이 회차 착지 시점의 실측**이다(§19-6·§20-6·§21-8·§22-8 과 같은 핀).

검수 회차별 건수는 그 회차 보고서의 집계이고 산출물이 저장소에 남지 않아 사후 재현이
불가능하다. 접지 렌즈의 픽스처 A~D·심볼릭 링크 4형태·권한 3형태는 **표본**이다 — 권한 조합과
디렉토리 형태의 전수가 아니다. 「대상 밖 삭제 0건」도 그 표본에 대한 관측이다.

「가드 없음 판에서 부풀림이 재현된다」는 두 픽스처(A·B)와 D 에서 확인됐고, 그 셋이 발화 조건의
전수라는 뜻은 아니다. 「`cp -R` 가 대상 모드를 옮기지 않는다」는 이 플랫폼(macOS)의 `cp` 에 대한
관측이다.

아래는 비망라 예시다 — 이 절이 열거하지 않은 것: 다른 OS·`find` 구현에서의 후보 순서 ·
동시 실행 중 외부 행위자가 후보를 지우는 경합의 전수 · `rm -rf` 부분 성공의 다른 형태 ·
재접기가 문단의 **가독성**에 미친 영향(텍스트 동일성만 기계로 단언했다). **전수 증명이 아니다.**

### 24-2. 정직한 부정 결과 — 함수 앵커 분리는 구조적으로 불가하다

§18 이관 13 은 「두 행의 토큰이 같아 한계 표기 검사가 같은 함수를 두 번 본다」를 지적했다.
토큰은 교체했다(`총합 불일치` → `집계에 도달하지 못한 그룹:`) — T99-2 가 범용 메시지 대신
**자기 결함에 더 특정한 조건**을 검사하게 되어 정밀도는 올랐다. 그러나 **함수 앵커 분리는
성립하지 않는다**: 두 토큰이 `print_test_summary()` 안의 인접한 두 줄에 있고 그 사이에 함수
경계가 없다. 근본 원인은 **두 결함이 물리적으로 그 함수 한 곳에서만 관측된다**는 것이다 —
코드를 그 함수 밖으로 재구성하지 않는 한 어떤 토큰을 골라도 결과가 같다.

오케스트레이터와 두 검수 렌즈가 각각 독립으로 확인했다. 구현자가 이것을 「해결됨」으로
포장하지 않고 **부분 해결로 남기고 그 사실을 원장 행에 적었다** — 산문 렌즈가 그 문면을
「과대도 과소도 아니다」로 판정했다. 진짜 해법은 §18 이관 10(8번째 열 `anchor_function` 분리)
이고 이번 범위 밖이다.

### 24-3. 「추가하지 않았다」 결정 — B1 의 두 번째 공허 경로

부재로 읽힘. **(b) 에는 단정을 추가하지 않았다** — T22-2 의 필수 셀렉터 하드 게이트(6종,

비어 있지 않다는 뜻이다(오케스트레이터·산문 렌즈가 각각 확인).

**그 근거를 코드 옆 주석에 남겼다.** 남기지 않으면 다음 회차가 같은 판단을 다시 해야 하고,

검사를 새로 만들지 않는다」의 실행이다.

### 24-4. 접지 렌즈의 커버리지 판정 — 삭제형 변조가 더 강하지 않다

`T3-2`·`T3-3` 의 변조는 **검사 자신의 코드**를 바꿔 방어 분기를 강제 발화시키는 형태다.
「그 분기를 통째로 지우는 변조로 바꾸면 더 강한가」를 실측으로 갈랐다:

### 25-2. §18 이관 12 의 원인 — 의도된 프로덕션 동작과 픽스처 가정의 충돌

허브의 기본 `ignore_globs` 에 `/tmp/**`·`/private/tmp/**` 가 있다. 파이썬 `tempfile` 은
`TMPDIR` 를 따르므로, 격리 `TMPDIR` 을 그 아래 두면 **픽스처가 만든 가짜 repo 경로 자체가 무시
대상**이 되어 세션이 통째로 사라진다. `snapshot.projects` 가 빈 튜플로 돌아온다.

**그 무시 패턴은 결함이 아니라 의도된 동작이다** — 검수 산문 렌즈가 `docs/prps/hub-dashboard.md`
의 노이즈 필터 논거(실측 35개 중 20개가 scratchpad·worktree)에서 그 의도가 **명문화돼 있음**을
확인했다. 즉 「테스트 결함이고 프로덕션 결함이 아니다」는 판정에 근거가 있다.

**결정적 증거는 같은 파일 안에 있었다.** 자매 클래스가 정확히 같은 문제를 이미 겪고 고쳐 두고
그 이유를 주석으로 남겼다(`hub-worktree-fold.md` 의 U-11 결정). 이 클래스만 그 선례를 놓쳤다.
접지 렌즈가 `collect_snapshot` 호출부를 전수 훑어 **결함 범위가 이 클래스 하나**임을 좁혔다.

### 25-3. 오케스트레이터의 사전 측정이 틀렸다 — 그러나 범위를 적어 두어 잡혔다

디스패치에 「배제한 가설 셋」을 실었고 그중 **무시 글롭이 정답이었다.** `load_config()` 의 반환
튜플에서 필드를 잘못 꺼내 「빈 튜플」로 읽었다.

**S4 에서 내 브리핑이 네 번째로 틀렸다**(앞의 셋은 §23-7·§24-8). 그런데 이번 건은 앞의 셋과
갈린다: **내 확인의 근거 범위를 함께 적었다** — 「내 확인은 실제 설정 파일 기준이었으니 그
테스트는 `CONFIG_PATH` 를 치환하므로 **기본값 경로를 다시 확인해 봐라**」. 구현자가 그쪽을 봐서
찾았다. §24-8 이 세운 처방(「확인하지 않은 것은 미확인으로 표시한다」)이 실제로 작동한 첫
사례다 — 틀린 측정을 넘겼는데도 그 표시 때문에 재확인 대상이 됐다.

### 25-4. 접지 렌즈가 자기 신고보다 넓은 위험을 찾았다 — 그리고 그것을 닫았다

구현자가 트레이드오프를 스스로 신고했다: SIGKILL 테스트가 `time.monotonic` 의 side_effect 를
**정확히 3회 호출**에 맞춰 고정했고 「호출 횟수가 바뀌면 `StopIteration` 으로 실패한다」.
접지 렌즈가 실측으로 **그 서술이 한 방향만 맞음**을 보였다:

| 회귀 형태 | 결과 |
|---|---|
| 루프 **본문 안**에서 호출이 늘어남 | side_effect 가 바닥나 `StopIteration` — 요란하게 죽는다 |
| 루프 **진입 전** 호출 추가(진입 시각 기록 등) | 폴링 반복이 1회 → **0회**로 바뀌는데 **조용히 통과** |
| deadline 값을 첫 조건 검사에 재사용하는 리팩터 | 폴링 반복이 1회 → **2회**로 바뀌는데 **조용히 통과** |

즉 「SIGKILL 전에 몇 번 폴링하는가」가 드러나지 않은 채 바뀔 수 있었다. 렌즈는 「지금 깨진 것은
없으니 한계로 적어 두거나 폴링 횟수를 따로 단언하라」고 권했다 — **후자를 택했다.**
`_ps_args_for_pid` 목을 이름에 묶어 `call_count == 1` 을 단언했고, **오케스트레이터가 위 두
조용한 형태를 각각 주입해 새 단언이 발화하는 것을 확인했다**(`0 != 1` · `2 != 1` — 실패
메시지가 실제 폴링 횟수를 지목한다). docstring 에 그 비대칭을 적었다.

### 25-5. 두 렌즈가 같은 중복을 서로 다른 각도에서 잡았다

`ignore_globs` override 블록이 두 클래스에 토씨 하나 안 틀리고 복제됐다.
- **산문 렌즈**: DRY 위반이고, 새 회귀 테스트가 같은 클래스 30줄 안의 기존 헬퍼(`_write_events`)를
  재사용하지 않고 네 줄을 복제했다(그 헬퍼가 cwd 를 파라미터화하지 않아서다).
- **접지 렌즈**: 그 중복 때문에 **자기 검증이 엉뚱한 클래스를 건드렸다** — 문자열 치환 되돌리기가
  자매 클래스에 먼저 걸려 「수정을 되돌렸는데 테스트가 통과한다」는 혼란을 겪고 줄 번호로 정밀
  타겟팅해 다시 했다.

이 회차에 **헬퍼 파라미터화만** 했다(`_write_events(session_id, cwd=None)`) — 새 테스트가 한 줄로
줄었다. **클래스 간 공용 헬퍼 추출은 하지 않았고 그 근거를 코드 옆에 남겼다**: 자매 쪽은 워크트리

### 26-3. 차단 사유 — 공허를 닫는 수정 자신이 검증되지 않았다

1회차에 **두 렌즈가 엇갈렸다**(접지 PASS · 산문 FAIL). 모순이 아니라 **서로 다른 질문에 답한**
것이다:

- **접지 렌즈**: 「수정이 **작동한다**」를 실물로 증명. `chflags uchg` 로 `rm -rf` 를 실제로
  실패시켜 기준 판/현재 판을 나란히 돌렸다 — 기준 판은 캡처가 `"[ERROR] …\nNOT_DELETED"` 가 되어
  **네 분기 어느 것과도 안 맞고**(공허 통과), 현재 판은 `"NOT_DELETED"` 로 정확히 매치했다.
- **산문 렌즈**: 「그 수정을 지키는 **살아있는 검사가 없다**」를 증명. `>&2` 를 되돌리고
  `--only T36` → **rc 0**. **오케스트레이터가 독립 재현했다** — 되돌리면 전체 스위트도 36/36 이다.

둘이 같이 참인 이유: **T36-7 의 프로브는 정상 실행에서 `log_error` 에 도달하지 않는다**(쓰기
가능한 `mktemp -d` 를 대상으로 하므로 정리가 실패할 일이 없다). 접지 렌즈는 그 실패를 **손으로
주입**해 정확성을 봤고 스위트는 그 주입을 하지 않는다. 정리 실패를 **실제로 만드는** T36-10 은
이미 `2>&1` 로 캡처하므로 **애초에 이 수정의 수혜자가 아니었다.**

**즉 「검증이 커밋되지 않아 재발을 막지 못하는 형태」가, 공허를 닫는 수정 자신에게 일어났다.**

### 26-4. 2회차 — 구현자가 오케스트레이터의 제안보다 나은 근거를 냈다

위험**이다. `SIGINT`/`SIGTERM` 경로는 이 샌드박스에서 신호 전달이 의도대로 되지 않아 접지 렌즈가
직접 재현하지 못했다(bash 문서화 동작에 근거한 추론, 그 렌즈 확신 ~60%).

26-5 의 bash 함정은 이 셸 버전(3.2.57)에서의 관측이다. 「39곳 전수 점검」은 1회차 구현 보고의
집계이고 이 절이 재검산하지 않았다. `T36-13` 이 보는 것은 `log_error` 한 함수의 스트림이며 다른
캡처 자리의 `2>&1` 유무는 그 자리 각각의 판정 로직에 달려 있다.

아래는 비망라 예시다 — 이 절이 열거하지 않은 것: 다른 셸·플랫폼에서 리다이렉션 적용 순서 ·
`command -v` 가 성공을 보고하는 다른 「깨진 실행 파일」 형태 · 완료 플래그를 사전 점검 밖에서
세우는 형태의 전수 · 여섯 조건별 메시지가 조건 추가 시 유지되는지. **전수 증명이 아니다.**

## 27. S4-6 착지 기록 — 승인 4 · §15-2, 그리고 S4 결산 (2026-09-08)

### 27-1. 무엇이 들어왔나

**§16 승인 4**(배포 규칙에 체크리스트 1줄 + T26 3중 갱신)와 **§16 §15-2**(`HANDOFF.md` 「LOW 9건」
→ 8). **S4 에서 배포 자산을 건드리는 유일한 회차**다 — `rules/common/code-review.md` 는
`install.sh` 가 다른 프로젝트에 설치하는 파일이고, 추가한 줄은 그 프로젝트들의 검수 체크리스트가
된다.

채택 문구: `- [ ] New checks and guards are confirmed to fail when deliberately broken`
(개행 포함 **75바이트**). 구현자가 후보 4개를 비교해 버린 이유를 남겼고, 산문 렌즈가 취지 정합·
문체·영어로서의 자연스러움을 각각 판정해 통과시켰다.

### 27-2. 배포 경로를 끝까지 돌려 확인했다

접지 렌즈가 **구버전 설치 → 신버전 업그레이드 → 재설치**를 샌드박스 `HOME` 으로 재현했다:
새 줄이 든 파일이 **「사용자 수정」이 아니라 「낡은 사본」으로 올바르게 분류**되고, 대장 해시가 새
값으로 갱신되고(옛 해시 잔존 없음), 재설치가 멱등이다. 대장 해시가 갱신되지 않으면 다음 설치가
그 파일을 사용자 수정으로 오분류해 `--force` 없이 막히는데, 그 자리가 정상이다.

**T26 3중 갱신이 견고함도 실증됐다** — 상수·`README.md` 2곳·실측 네 값 중 어느 하나가 단독으로
어긋나거나 선언 하나가 문구째 사라지는 **다섯 가지 변조 전부** 발화했다.

### 27-3. 오케스트레이터의 사전 측정이 폐기됐다 — 지시가 작동한 사례

오케스트레이터는 후보 문구 기준 「82바이트 → 예산 55,464」를 넘기면서 **「내 숫자를 그대로 쓰지
말고 문구를 정한 뒤 직접 재라」**고 지시했다. 구현자가 자기 문구가 75바이트임을 직접 재
**55,457** 로 맞췄다. §24-8 의 처방(「넘겨받은 주장을 넘기기 전에 확인한다」)이 **넘기는 쪽에서도
작동한** 사례다 — 값을 주면서 그 값의 근거와 재현 방법을 함께 주면 받는 쪽이 검증한다.

### 27-4. 구현자가 「범위 밖」으로 올린 판단 하나는 의무였다

구현자는 `NOTICE.md` §5 갱신을 요청 범위 밖으로 보고 하지 않았고 판단을 요청했다. **§5 자신이
규칙을 적어 뒀다** — 「**새 로컬 패치가 추가되거나** 상류가 더 바뀌면 갱신이 필요하다」.

형식 문제가 아니다. §5 는 **상류 재동기화가 로컬 패치를 조용히 되돌리는 것**을 막기 위한 대장이고
(S3b 후반부-2 가 그 표를 실측으로 재구성한 것이 §21 이다), 새 체크리스트 줄은 상류에 없는 로컬
패치다. 대장에 없으면 **다음 재동기화가 그 줄을 지워도 아무도 모른다.** 오케스트레이터가 두 표
(로컬 패치 표 · 커버리지 표)를 직접 갱신하고 검수에 그것을 명시적으로 맡겼다 — 산문 렌즈가 근거의
실재와 표 계수 기준 정합을 확인했고, 접지 렌즈가 **그 줄만 지운 사본으로 36그룹을 돌려 T26 하나만
발화함**을 실증해 커버리지 표의 서술을 접지했다.

### 27-5. 두 렌즈가 한 지점에서 엇갈렸고 둘 다 부분적으로 맞았다

1회차 구현이 `HANDOFF.md` 의 「8건」에 각주를 붙였다 — 「「정리 실패 시 원인 삼킴·건수 과대 보고」
내부의 · 는 구분자가 아님, 재계수 주의」.

- **산문 렌즈(Major)**: 그 각주가 「8건」과 **반대 논리**라고 판정했다 — 지시대로 합치면 7이 되어
  모순이고, 원장에 A11·A12 가 별개 행으로 있다.
- **접지 렌즈(미제출 의심, 확신 낮음)**: **공백 있는 `" · "`** 로 나누면 7묶음이고 세 번째가 두
  결함을 압축한 것이면 「6단일 + 1이중 = 8」로 산수가 맞아 각주가 일관적일 수 있다고 봤다.

**오케스트레이터가 타이포그래피를 직접 세어 접지 렌즈의 관찰이 맞음을 확인했다** — 상위 구분자는
공백 있는 `" · "` 이고 문제의 하나만 공백이 없다. 그리고 §9 대조로 그 묶음이 A11+A12 압축임이,
나머지 6묶음이 A9·A10·A13~A16 에 1:1 대응함이 확정됐다.

**결론: 각주는 「반대」가 아니라 「불완전」했다.** 「구분자가 아니다」까지만 적어 독자가 **7에
멈추고**, 「그 묶음이 두 항목을 압축했다」는 나머지 절반이 없었다. 재작성으로 7 → 8 의 길을 문면
안에서 재현 가능하게 만들었고, 재검수가 원장 대조로 1:1 대응 전부를 확인해 해소로 판정했다.

**미제출 의심이 결론을 뒤집은 두 번째 사례다**(첫 번째는 §20-8 의 `:-0` 인과). 확신 80% 미달을
버리지 않고 근거와 함께 남기게 한 규약이 두 번 값을 냈다.

### 27-6. 오케스트레이터의 다섯 번째 브리핑 오류 — 처방이 하나 늘었다

사전 측정을 이렇게 넘겼다: 「`·` 로 구분된 **7개 그룹**인데 그중 하나가 **내부에 `·` 를 품어**
실제 항목은 8개다」. **결론(8)은 맞았고 설명이 틀렸다** — 「내부에 품었다」가 그 `·` 를 구분자가
아닌 것으로 만들고, 구현자가 그 설명을 각주로 옮겼다. 그리고 산문 렌즈에 그것을 「반대 방향」으로
전달할 때 **오케스트레이터 자신의 계수도 틀렸다**(공백 없는 `·` 까지 구분자로 세어 8묶음으로 봤다).

**S4 에서 오케스트레이터 브리핑 오류가 다섯 건이고**(§23-7 둘 · §24-8 하나 · §25-3 하나 · 이 건)
형태가 같다 — **결론은 맞는데 그 결론에 이르는 설명·인과·이력을 검증하지 않고 실었다.** §24-8 이
세운 처방(「넘겨받은 주장을 넘기기 전에 확인한다」)에 하나가 붙는다:

> **넘기는 측정에는 결론만이 아니라 그 결론을 재현하는 방법을 적는다.** 그러면 받는 쪽이 설명
> 자체를 검증할 수 있다. §25-3 은 근거 범위를 적어 두어 틀린 측정이 재확인 대상이 됐고(작동),
> 이 건은 적지 않아 틀린 설명이 문서까지 갔다(실패).

배포 경로 확인은 **한 시나리오**(구버전 설치 → 업그레이드 → 재설치, 샌드박스 `HOME`, `--scope
user`)에 대한 관측이다 — `--scope project` 경로, 다른 스코프 조합, 대장이 없는 v1 설치본에서의
업그레이드는 이 회차가 돌리지 않았다. T26 변조 5종도 **단일 지점 변조**이고 두 값이 동시에
어긋나는 조합은 시험하지 않았다.

「그 줄의 존재를 직접 보는 검사가 없다」는 **그 줄만 지운 사본으로 36그룹을 돌린 실측 범위**의
결론이다. 채택 문구의 영어 자연스러움은 **한 렌즈의 판단**이고 원어민 검토가 아니다 — 그 줄은
다른 프로젝트로 나가므로 이 한계가 실제 무게를 갖는다.

아래는 비망라 예시다 — 이 절이 열거하지 않은 것: 그 체크리스트 항목이 다른 프로젝트에서 실제로
지켜지는지(기계로 강제되지 않는다 — §16 승인 4 가 이미 그 범위 한계를 적었다) · 예산 상수가

24행이 이번 회차에도 여전히 참인지. **전수 증명이 아니다.**
