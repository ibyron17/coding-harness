# 대시보드 옵션의 대화형 설치·사후 전환 (PRP)

## 요구사항 요약

coding-harness 를 실제 개발 프로젝트에 설치하는 경로가 "사용자가 셸에서 `install.sh` 를 직접
실행" 하나뿐이다. 실제 사용 시나리오는 **대상 프로젝트의 Claude Code 세션에 이 레포 URL 을
붙여넣고 "설치해줘" 라고 말하는 것**이다. 이 대화형 경로를 정식 절차로 문서화하고, 그 안에서
`/dashboard` 기능을 **켤지 끌지 사용자에게 묻고 즉시 반영**한다. 설치 이후에도 JSON 을 손으로
편집하지 않고 옵션을 바꿀 수 있게 `/dashboard` 에 `on`/`off` 하위 명령을 추가한다.

옵션의 저장 위치와 판정 규칙(`.claude/settings.local.json` 의 `dashboard_enabled`, 부재 시 켜짐)은
[직전 라운드](./session-dashboard.md)에서 이미 정해져 배포된 계약이다. **이번 라운드는 그 계약을
바꾸지 않고, 값을 설정하는 경로만 사람 손에서 에이전트 절차로 옮긴다.**

### 닭과 달걀 문제 — 이 설계의 출발점

"설치해줘" 는 슬래시 커맨드가 아니고, 그 시점의 대상 프로젝트에는 **coding-harness 의 CLAUDE.md 도
커맨드도 아직 없다.** 즉 이 절차를 안내할 문서는 대상 프로젝트가 아니라 **coding-harness 레포 자체
안에, 에이전트가 clone(또는 WebFetch) 직후 자연스럽게 읽는 위치**에 있어야 한다.
이 제약이 「설계 결정 1」의 배치를 강제한다.

## 파일 구조와 모듈 경계

이 기능에도 **실행 코드가 없다.** 이 레포의 일관된 패턴대로 지시문 + 상태 파일로만 구성한다
(`install.sh` 만이 유일한 실제 스크립트라는 사실은 이번에도 유지된다 — 「설계 결정 4」).

| 층 | 실체 | 책임 | 로드 시점 |
|----|------|------|----------|
| 진입 지시문 | `README.md` 「AI 에이전트로 설치」 | 아직 아무것도 설치되지 않은 대상 프로젝트에서 에이전트가 읽는 **유일한** 문서. 절차의 **순서**와 **질문 시점**을 소유 | clone/WebFetch 직후 1회 |
| 절차 지시문 | `commands/dashboard.md` 「`on`/`off`」 | 설정 파일 갱신 절차의 **단일 출처**. 값 병합 규칙을 소유 | 호출 시 또는 설치 절차가 직접 Read 할 때 |
| 소비 지시문 | `CLAUDE.md` 「공통 규칙」 | 메인 세션이 전체 경로 착수 시 값을 **읽고** `/dashboard` 호출 여부를 판정 | 항상 |
| 상태 | `.claude/settings.local.json` | 값의 유일한 보관처. 커밋되지 않음 | — |

### DRY 경계 — 병합 절차는 한 곳에만 쓴다

설치 시점과 사후 변경은 **같은 파일에 같은 필드를 쓰는 동일 작업**이다. 절차를 README 와
`dashboard.md` 양쪽에 적으면 반드시 표류한다. 따라서:

- 실제 절차 서술은 **`commands/dashboard.md` 에만** 둔다.
- README 의 설치 5단계는 "`.claude/commands/dashboard.md` 의 「`on`/`off`」 절을 읽고 그대로
  수행한다"로 **참조만** 한다.

> **왜 `/dashboard off` 를 호출하라고 쓰지 않는가**: 커맨드 파일은 방금(설치 3단계) 대상
> 프로젝트에 복사됐다. 실행 중인 세션이 새로 생긴 슬래시 커맨드를 즉시 인식한다는 보장이 없다.
> 파일을 직접 Read 해 절차를 따르면 이 가정에 의존하지 않으면서도 단일 출처는 유지된다.

## 데이터 모델 — `.claude/settings.local.json` 계약

```json
{
  "dashboard_enabled": false,
  "permissions": { "allow": ["..."] }
}
```

| 항목 | 규격 |
|------|------|
| 키 | `dashboard_enabled` (최상위, 고정 표기) |
| 타입 | boolean |
| 기본값 | **파일 부재 또는 필드 부재 = `true`(켜짐)** |
| 소유권 | 이 필드 하나만 coding-harness 소유. **다른 필드(`permissions` 등)는 절대 건드리지 않는다** |
| 파싱 실패 | 켜짐으로 간주하고 경고만. **파일을 덮어쓰지 않는다** |

`install.sh` 의 소유권 원칙(`install.sh:5-7` — "레포가 배포하는 파일만 관리한다")을 설정 파일
수준으로 그대로 옮긴 것이다. 이 파일은 배포 대상이 아니라 **대상 프로젝트 소유**이며, 우리는
필드 하나만 빌려 쓴다.

### 상태 전이

| 현재 상태 | `on` 결과 | `off` 결과 |
|----------|----------|-----------|
| 파일 없음 | **아무것도 하지 않는다** (기본값이 이미 켜짐) | `{ "dashboard_enabled": false }` 로 생성 |
| 파일 있음, 필드 없음 | **아무것도 하지 않는다** | 첫 필드 자리에 `"dashboard_enabled": false,` 삽입 |
| 파일 있음, 필드 `false` | 값을 `true` 로 치환 | 변경 없음 (이미 꺼짐) |
| 파일 있음, 필드 `true` | 변경 없음 (이미 켜짐) | 값을 `false` 로 치환 |

**키를 삭제하는 경로가 없다.** JSON 에서 키를 지우려면 앞뒤 쉼표를 함께 다뤄야 해서 LLM 이
파일을 깨뜨릴 여지가 가장 큰 연산이다. `on` 은 "값을 `true` 로 치환"만 하므로 순수 값 교체로
끝난다.

## 인터페이스

### A. `README.md` — 「AI 에이전트로 설치 (대화형)」

`README.md:5` 의 `## 설치` **바로 아래**, 기존 `### 기본 사용법` **앞**에 삽입한다.
아래는 그대로 옮겨적을 내용의 규격이다(문장은 다듬어도 되나 **굵게 표시된 지시는 문구를 유지**한다
— T23 이 grep 으로 검증한다).

> **이 절은 에이전트에게 주는 지시문이다.** 사람이 셸에서 직접 설치하려면 아래 「기본 사용법」으로.
> 사용자가 이 레포 URL 을 붙여넣고 "설치해줘"라고 하면 아래 순서대로 수행한다.

1. **레포 확보** — 이미 로컬에 clone 돼 있으면 그 경로를 쓴다. 없으면 **설치 대상 프로젝트
   바깥에 clone 한다**(예: `~/works/coding-harness`). 대상 프로젝트 안에 clone 하면 남의 레포가
   프로젝트 트리에 그대로 남는다.
2. **계획 확인** — 대상 프로젝트 루트에서 `<repo>/install.sh --scope project --dry-run` 을 실행하고
   출력을 사용자에게 보고한다. `--scope` 는 생략할 수 없다.
3. **설치** — `--dry-run` 없이 재실행한다. exit 0 이면 4단계로.
   - **exit 1 이고 CLAUDE.md 충돌인 경우**: 대상 프로젝트에 이미 CLAUDE.md 가 있다는 뜻이다.
     **자동으로 `--force` 를 붙이지 않는다.** 배포본은 범용 지침이고 기존 파일에는 프로젝트
     고유 내용(아키텍처·병목·빌드 명령)이 들어 있어, 덮어쓰면 그 내용이 본문에서 사라진다.
     차이를 요약해 보여주고 선택을 받는다:
     (a) `--force` 로 덮어쓰기 — 기존 파일은 `CLAUDE.md.bak-<타임스탬프>` 로 자동 백업되므로,
         **덮어쓴 뒤 백업본에서 프로젝트 고유 섹션을 되살려 병합한다**.
     (b) 중단 — 사용자가 직접 병합한 뒤 다시 요청한다.
   - **exit 1 이고 rules/agents/commands 차이인 경우**: 이전에 설치한 파일이 수정됐다는 뜻이다.
     차이 파일 목록을 그대로 보여주고 `--force` 여부를 확인받는다.
4. **대시보드 옵션 질문** — 설치가 **성공한 직후, 최종 보고 전에** 묻는다. 안내는 3줄을 넘기지 않는다:
   - 전체 경로(설계→구현→검수) 작업의 진행 상황을 `.claude/dashboard.html` 로 기록하는 기능이다.
   - 브라우저로 열어 보며, 커밋되지 않는 로컬 파일이다.
   - 지금 정하지 않아도 되고, 나중에 `/dashboard on` · `/dashboard off` 로 언제든 바꿀 수 있다.

   `AskUserQuestion` 도구가 있으면 선택지 2개(**켜기(기본)** / **끄기**)로 묻고, 없으면 평문으로
   같은 내용을 묻는다. 사용자가 답하지 않고 다른 지시로 넘어가면 **기본값(켜짐)을 유지**하고
   최종 보고에 그 사실과 전환 방법을 한 줄 남긴다.
5. **선택 반영** — `.claude/commands/dashboard.md` 의 「`on`/`off`」 절을 **읽고 그대로 수행한다.**
   (방금 설치된 슬래시 커맨드가 이번 세션에서 인식되지 않을 수 있으므로 파일을 직접 읽는다.)
   *켜기*를 골랐고 파일에 필드가 없다면 **할 일이 없다** — 기본값이 켜짐이다.
6. **최종 보고** — 반영된 파일 수, 대시보드 옵션의 최종 상태, 전환 방법(`/dashboard on|off`)을
   각 한 줄로 보고한다. 3단계에서 install.sh 가 **전역 커맨드 불일치 경고**를 냈다면, 이 머신에서는
   전역 사본이 우선하므로 `install.sh --scope user` 로 전역도 갱신하라고 함께 안내한다.

### B. `commands/dashboard.md` — `on` / `off`

#### frontmatter 갱신

```yaml
description: "세션 진행 상황을 프로젝트 로컬 HTML 대시보드로 기록 — init/step/log + on/off 스위치"
argument-hint: "init \"<제목>\" \"<단계1|단계2|...>\" | step <n> <done|active|wait> | log <impl|pass|fail|commit> \"<요약>\" [...] | on | off"
```

#### 호출 규약

```
/dashboard on      # 이 프로젝트에서 대시보드 기록을 켠다 (기본값)
/dashboard off     # 이 프로젝트에서, 나만, 대시보드 기록을 끈다
```

**대상 파일은 `.claude/settings.local.json` 뿐이다.** `on`/`off` 는 `.claude/dashboard.html` 을
만들지도 지우지도 않는다 — 생성은 `init` 의 책임이다. `off` 이후에도 기존 대시보드 파일은
그대로 남으며, 지울지는 사용자가 정한다(안내만 한다).

#### 절차 (Read 1회 + Edit 또는 Write 1회 + Read-back 1회)

1. **읽기** — `.claude/settings.local.json` 이 있으면 Read 한다.
   - 파일이 없다 → 요청이 `off` 면 3-a 로, `on` 이면 3-b 로(아무것도 하지 않는다).
   - **JSON 으로 파싱되지 않는다 → 절차를 중단하고 그 사실만 보고한다.** 깨진 파일을
     덮어쓰면 사용자의 권한 허용 목록이 사라진다.
2. **현재 값 판정** — `dashboard_enabled` 필드의 유무와 값을 확인한다. 필드가 없으면 켜짐이다.
   요청한 상태와 현재 상태가 같으면 **아무것도 하지 않고** 그 사실을 보고한다.
3. **쓰기**
   - **a. 파일 없음 + `off`**: `.claude/` 를 만든 뒤 아래를 Write 한다.
     ```json
     {
       "dashboard_enabled": false
     }
     ```
   - **b. 파일 없음 + `on`**: 아무것도 하지 않는다. 기본값이 켜짐이다.
   - **c. 필드 있음**: 값만 Edit 로 치환한다 (`"dashboard_enabled": false` ↔ `"dashboard_enabled": true`).
   - **d. 필드 없음 + `off`**: **여는 `{` 바로 뒤 첫 필드 자리**에 삽입한다.
     ```
     {
       "dashboard_enabled": false,
     ```
     빈 객체(`{}` 또는 `{ }`)이면 뒤따르는 필드가 없으므로 **쉼표 없이** 넣는다.

     > **왜 첫 자리인가**: 마지막 필드 뒤에 넣으려면 직전 줄에 쉼표를 붙이는 Edit 이 하나 더
     > 필요하고, 그 줄의 내용은 프로젝트마다 다르다. 첫 자리는 앵커가 항상 `{` 하나로 고정된다.
   - **기존 필드는 어떤 경우에도 건드리지 않는다.**
4. **검증** — 쓴 파일을 다시 Read 해 **유효한 JSON 인지 눈으로 확인한다**(파일은 보통 20줄 미만).
   `python3` 이 있으면 `python3 -m json.tool .claude/settings.local.json > /dev/null` 로 확인해도 된다
   (없어도 되는 선택지다 — 새 의존성을 만들지 않는다).
5. **보고** — 최종 상태 한 줄. `off` 인 경우 "이번 프로젝트에서 나에게만 적용되며 커밋되지 않는다"를
   덧붙인다. `.claude/settings.local.json` 이 대상 프로젝트의 `.gitignore` 에 없으면 그 사실을 알린다.

### C. `CLAUDE.md` — 문구 1구절 삽입

`CLAUDE.md:78` 의 다음 부분에 괄호 하나를 더한다(상시 로드 문서이므로 이 이상 늘리지 않는다):

```
`.claude/settings.local.json` 에 `"dashboard_enabled": false` 를 추가한다(`/dashboard off` 가 대신 해준다) — 메인 세션은
```

판정 규칙(파일 확인 → false 면 호출 생략 → 부재 시 기본값) 서술은 **그대로 둔다.**

## 설계 결정과 근거

### 1. 대화형 설치 안내는 `README.md` 안에 둔다 (별도 파일 아님)

에이전트가 URL 만 받은 시점에 접근하는 것은 레포 그 자체뿐이고, 그중 관례적으로 먼저 읽는
파일은 README 다. 별도 파일(`INSTALL-AGENT.md` 등)로 빼면 **"README 를 읽고 → 링크를 따라간다"**
는 한 단계가 더 붙는데, 이 한 단계는 특히 WebFetch 로 렌더된 페이지를 요약해 읽는 경로에서
탈락하기 쉽다. 절 제목에 "AI 에이전트"를 넣어 검색성도 확보한다.

**기각한 대안 — `AGENTS.md`**: 여러 도구가 관례적으로 읽는 파일명이라는 장점이 있으나,
그 관례는 *이미 그 레포에서 작업 중인* 에이전트에게 적용된다. 여기서는 대상 프로젝트에서
작업하는 에이전트가 **남의 레포를 참조**하는 상황이라 자동 로드가 성립하지 않는다.
결국 사람이든 에이전트든 README 를 먼저 읽으므로 이점이 없고 파일만 하나 는다.

### 2. 옵션은 설치 성공 **직후** 묻는다

- `install.sh` 는 사전 조건 실패 시 **파일을 하나도 건드리지 않고 중단**한다(`install.sh:216-224`).
  대상 프로젝트에 CLAUDE.md 가 이미 있는 경우는 흔하므로 중단 확률이 낮지 않고, 먼저 물으면
  사용자의 답을 버리게 된다.
- 더 나쁜 경우: 먼저 묻고 `settings.local.json` 을 써 놓았는데 설치가 실패하면, 설치되지도
  않은 기능의 설정만 남는 **부분 상태**가 생긴다. `install.sh` 의 all-or-nothing 성질과 어긋난다.
- 대시보드 기능 자체가 CLAUDE.md 배포 이후에야 존재한다. 존재하지 않는 기능을 먼저 설명하는
  순서는 사용자 입장에서도 어색하다.

**기각한 대안 — 설치 전 일괄 질문**(scope·force·dashboard 를 한 번에): 중단이 잦다는 문제 외에,
`--force` 판단은 `--dry-run` 출력을 봐야만 가능하므로 애초에 앞당길 수 없다. 질문 시점을 하나로
모으는 이득이 성립하지 않는다.

### 3. 사후 전환은 `/dashboard` 의 하위 명령으로 넣는다 (새 커맨드 아님)

요구사항 3("이후에도 옵션을 변경할 수 있으면 좋겠다")을 만족시키는 세 안을 비교했다.

| 안 | 사용자 동작 | 변경 규모 | 결정 |
|----|------------|----------|------|
| **A. `/dashboard on\|off`** | `/dashboard off` | `dashboard.md` 1개 수정. 파일 수·`COMMANDS_FILE_COUNT`·테스트 구조 불변 | **채택** |
| B. 문서 안내만 | "대시보드 꺼줘"(자연어) 또는 손으로 JSON 편집 | 변경 거의 없음 | 기각 |
| C. 새 커맨드 `/dashboard-config` | `/dashboard-config off` | 파일 9개 → `install.sh` 상수·README 표·T22-5 전부 변경 | 기각 |

- **B 를 기각한 이유**: 자연어 요청 시 에이전트가 매번 절차를 즉석에서 지어낸다. 이 작업에는
  깨지면 아픈 규칙이 셋 있다 — 기존 필드 보존, 빈 객체 처리, 파싱 불가 파일에 손대지 않기.
  실패 시 대가가 **사용자의 권한 허용 목록 소실**이라 자유 서술에 맡길 수 없다.
  A 는 이 규칙들을 결정적으로 고정하면서도 B 를 배제하지 않는다(자연어로 말해도 에이전트가
  같은 절을 읽게 된다).
- **C 를 기각한 이유**: 커맨드 하나를 늘릴 만한 독립성이 없다. 대시보드 기능의 표면이 둘로 갈린다.
- **A 의 대가**: `/dashboard` 가 "HTML 갱신"과 "설정 전환" 두 책임을 갖는다. 다만 둘 다 *대시보드
  기능의 표면*이고, `on`/`off` 는 `init`/`step`/`log` 와 상태를 공유하지 않는 독립 절이라
  응집도 훼손이 작다고 판단했다.

#### `status` 는 만들지 않는다 (YAGNI)

`on`/`off` 가 실행 후 최종 상태를 보고하고, "지금 켜져 있나?" 는 파일 한 줄 읽으면 답이 나온다.
현재 상태만 보는 전용 명령을 위해 절차를 하나 더 쓰지 않는다.

### 4. `install.sh` 는 대화형으로 만들지 않는다

`install.sh` 는 이 레포에서 유일한 실제 실행 파일이며 "순수 bash, 외부 의존 없음"(`README.md:257`)이
명시된 계약이다. `read` 프롬프트를 넣으면 (a) 비대화형 실행(테스트 스위트 21종 전부, CI, `/harness-update`
의 재실행)이 즉시 깨지고, (b) JSON 병합을 bash 로 해야 해 `jq` 의존성이 따라온다.
**대화는 스크립트 바깥의 에이전트 레이어가 감싼다.** 이 레포의 다른 모든 기능이 쓰는 패턴
("셸 스크립트 없이 LLM 이 문서화된 절차를 수행")과도 일치하므로, 일관성을 깨는 지점이 없다.

### 5. 저장 위치와 판정 규칙은 그대로 둔다

`.claude/settings.local.json` + `dashboard_enabled` + "부재 시 켜짐"은 직전 라운드에서 승인·배포된
계약이다. 이번 요구는 "값을 어떻게 설정하는가"이지 "값을 어디에 두는가"가 아니다.
바꾸면 `CLAUDE.md`(상시 로드)와 이미 설치된 프로젝트의 설정이 함께 흔들린다.
단, 리스크 1(미검증 사항)이 실측에서 현실이 되면 그때 재검토한다.

### 6. 켜기는 "아무것도 쓰지 않는다"

파일이 없거나 필드가 없는 상태에서 `on` 을 골랐을 때 `"dashboard_enabled": true` 를 굳이 기록하지
않는다. 기본값이 이미 켜짐이라 동작이 같고, 대상 프로젝트 소유 파일에 우리 흔적을 남기지 않는
편이 「데이터 모델」의 소유권 원칙에 맞다.

**대가**: "물어본 적 없음"과 "묻고 켜기를 골랐음"을 구분하지 못해, 재설치 시 다시 묻는다.
설치는 드문 이벤트이고 질문 비용은 한 줄이라 수용한다.
**단, 이미 `false` 가 기록돼 있을 때는 `true` 로 치환한다** — 키 삭제 연산을 만들지 않기 위해서다
(「데이터 모델 · 상태 전이」).

### 7. 병합 절차는 `commands/dashboard.md` 한 곳에만 쓴다

설치 시점과 사후 변경은 동일 작업이다. README 에 절차를 복사하면 한쪽만 고쳐지는 표류가
확정적으로 발생한다. README 는 참조만 하고, 슬래시 커맨드 호출 대신 **파일 Read** 를 지시해
"방금 설치된 커맨드가 즉시 인식되는가"라는 검증 불가능한 가정을 제거한다.

## 리스크와 대안

### 1. `dashboard_enabled` 는 Claude Code 공식 설정 키가 아니다 — **미검증**

`settings.local.json` 은 Claude Code 소유 파일이다. 알 수 없는 최상위 키가 있을 때 조용히
무시되는지, 매 세션 경고를 내는지 **확인하지 못했다**(로컬에 스키마 파일이 없어 문서만으로는
단정할 수 없다). 지금까지는 사용자가 손으로 넣는 방식이라 노출이 적었지만, 이번 변경으로
**설치할 때마다 기록되므로** 경고가 난다면 전 사용자에게 반복 노출된다.

- **대응**: 위 수동 확인의 마지막 항목을 **구현 완료 판정 조건**으로 삼는다. 추측으로 넘기지 않는다.
- **경고가 확인될 경우의 대안**: 마커 파일 방식으로 전환한다 — `.claude/dashboard-off` 파일의
  **존재 여부**만으로 판정. JSON 병합이 통째로 사라져 「리스크 2」도 함께 소멸하고, 절차가
  `touch`/`rm` 수준으로 단순해진다. 대가는 `CLAUDE.md`(상시 로드) 문구 수정과, 이미 `false` 를
  기록해 둔 사용자를 위한 이행 안내 한 줄이다.
- 이 전환은 **승인 없이 임의로 하지 않는다.** 실측 결과를 보고한 뒤 결정한다.

### 2. LLM 이 JSON 병합에서 파일을 깨뜨릴 수 있다

실패 시 대가가 크다 — `settings.local.json` 이 무효화되면 사용자의 권한 허용 목록이 함께 죽는다.
완화책 4겹:

1. 삽입 위치를 **첫 필드 자리**로 고정해 앵커를 `{` 하나로 만든다(가변 문자열 앵커 제거).
2. **키 삭제 연산을 만들지 않는다**(`on` 은 값 치환뿐).
3. 파싱 불가 파일은 **아예 건드리지 않는다**.
4. 쓰기 후 **Read-back 검증을 필수**로 한다.

**기각한 대안**: `jq` 로 병합. 이 레포가 지금까지 지켜 온 "외부 의존 없음"을 깨고, 설치 절차가
사용자 머신의 `jq` 유무에 의존하게 된다.

### 3. 전역 커맨드가 프로젝트 사본을 이긴다

사용자의 `~/.claude/commands/dashboard.md` 가 `on`/`off` 없는 구버전이면, 프로젝트에 새 버전을
설치해도 **전역 구버전이 실행된다**(`README.md:117-129`). `install.sh` 가 이미 이 상황을 감지해
경고하므로, 설치 절차 6단계에서 **그 경고를 삼키지 말고 그대로 전달**하고
`install.sh --scope user` 재실행을 권하도록 명시했다.

### 4. README 가 길어 에이전트가 해당 절을 놓칠 수 있다

현재 298줄이고 여기에 약 45줄이 더해진다. `## 설치` 의 **첫 서브섹션**에 배치하고 제목에
"AI 에이전트"를 넣어 위치와 검색성을 모두 확보했다. 다만 **WebFetch 로 요약본만 읽는 경로에서
절이 통째로 탈락할 가능성은 남는다** — 이 경우 에이전트는 기존 「기본 사용법」대로 설치를
진행하게 되고, 대시보드 질문만 누락된다. 기본값(켜짐)으로 동작하므로 **열화이지 고장은 아니다.**

### 5. 자동 테스트가 문자열 존재 확인에 그친다

절차의 *실제 수행 품질*은 검증되지 않는다. 이 레포의 모든 LLM 지시문 자산이 공유하는 한계이며
(T22 도 동일), 그래서 수동 확인 항목을 실제 실패 모드(권한 블록 보존, 빈 객체, 깨진 JSON)에
맞춰 구체적으로 뽑았다.

### 6. 대상 프로젝트의 `.gitignore` (승인 항목 4와 연동)

대시보드를 켜면 `.claude/dashboard.html` 이 생기는데, 대상 프로젝트가 이를 무시하지 않으면
생성물이 커밋된다. **자동으로 `.gitignore` 를 수정하지는 않는다** — 대상 프로젝트 소유 파일이고,
`install.sh` 의 소유권 원칙과도 어긋난다. 설치 절차 6단계에서 **알리기만** 한다.

## 워크플로우 경로 판정

**전체 경로(설계 → 구현 → 검수) 대상이 맞다.** 근거:

- **공개 인터페이스 변경**: `/dashboard` 의 호출 규약에 `on`/`off` 두 하위 명령이 추가되고
  frontmatter 가 바뀐다.
- **3개 이상 파일 변경**: `README.md`, `commands/dashboard.md`, `CLAUDE.md`, `tests/run.sh` = 4개.
- **상시 로드 문서(`CLAUDE.md`) 수정**: 설치된 모든 프로젝트의 매 세션에 영향을 준다.

---

## 사용자 승인이 필요한 핵심 결정

1. **대화형 설치 절차를 `README.md` 의 `## 설치` 첫 서브섹션에 둔다** — 별도 파일(`AGENTS.md`
   등)로 빼지 않는다. 링크를 한 번 더 따라가는 단계가 WebFetch 요약 경로에서 탈락하기 쉽다는
   판단이다. 대가: README 가 약 45줄 길어진다.
2. **대시보드 옵션은 `install.sh` 성공 직후(exit 0) 최종 보고 직전에 묻는다** — 설치 전 일괄
   질문은 하지 않는다. `install.sh` 가 사전 조건 실패 시 전량 중단하므로 답을 버리거나, 설치되지
   않은 기능의 설정만 남는 부분 상태가 생긴다.
3. **사후 전환은 `/dashboard on|off` 하위 명령으로 제공한다** — 새 커맨드를 만들지 않고
   (파일 수·`COMMANDS_FILE_COUNT` 불변), `status` 는 만들지 않는다(YAGNI).
   병합 절차의 단일 출처는 `commands/dashboard.md` 이며, 설치 절차는 이 파일을 **Read 해서**
   따른다(방금 설치된 슬래시 커맨드의 즉시 인식을 가정하지 않는다).
4. **대상 프로젝트의 `.gitignore` 는 자동 수정하지 않고 안내만 한다** — 대시보드를 켰는데
   `.claude/dashboard.html` 이 무시 목록에 없으면 알리기만 하고, 추가는 사용자가 결정한다.
   *이 안내 자체를 빼는 선택지도 있다*(요청 범위 밖이라고 보면).
5. **저장 위치·판정 규칙은 직전 라운드 계약을 그대로 유지한다** — 다만 리스크 1(미지의 설정
   키에 대한 Claude Code 의 경고 여부)은 **미검증**이며, 구현 중 실측해 경고가 확인되면
   마커 파일 방식으로의 전환을 **별도 승인 대상**으로 다시 올린다.
