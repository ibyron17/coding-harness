# 대시보드 「구현」 단계 전용 서브태스크 패널 (PRP)

## 요구사항 요약

`/dashboard` 에 **「구현」 매크로 단계 하나에만 붙는 고정 서브태스크 패널**을 추가한다. 전체 경로
워크플로우에서 「구현」은 유일하게 여러 서브에이전트가 **병렬로** 뛰는 단계인데, 현재 대시보드는 그
구간을 `#dz-step-3` 이라는 칸 하나(`진행중`)로만 표현한다. 실제로는 그 안에서 10~15개의 세부 작업이
돌고 그중 둘 이상이 동시에 활성인데, 곁눈질 화면에는 몇 시간 동안 같은 화면이 떠 있다. 이 패널은
그 구간을 **번호가 붙은 세부 작업 목록 + 항목별 상태(done/active/wait)** 로 펼쳐 보여준다.

계기는 사용자가 보여준 외부 샘플(`~/Desktop/m7-progress-dashboard.html`)의 두 번째 패널
(`#impl-stages`, 14개 항목 중 2개가 동시에 `active`)이다. **그 파일은 우리 `/dashboard` 가 만든 것이
아니고 셀렉터 명명 체계도 완전히 다르다** — 형태만 참고하고 마크업·CSS·절차는 전부 이 저장소의
기존 관례로 다시 짓는다.

### 사용자와 합의된 확정 사항 (재논의 대상 아님)

이 PRP 는 아래 5가지를 **전제**로 그 위의 구체 설계만 담는다.

1. **스코프를 「구현」 단계 하나로 고정한다.** 임의의 단계에 하위 목록을 붙이는 범용 메커니즘을
   만들지 않는다. 설계(design-architect 1회)·사용자 승인(1회)·검수(code-reviewer 1회)는 원자적
   단일 행위라 쪼갤 것이 없다. 병렬 지점은 「구현」뿐이다(YAGNI).
2. **데이터 출처의 한계를 설계·문서에 명시한다.** 갱신 주체는 여전히 메인 세션뿐이며
   (`session-dashboard.md` 「4. 메인 세션만 갱신한다」), 서브태스크 상태는 오케스트레이터가 **직접
   아는 두 시점**에만 바뀐다: 디스패치(→`active`), 결과 보고 수령(→`done`).
   "서브에이전트 내부의 실시간 진행률"로 오인되지 않게 문서와 화면 양쪽에 적는다.
3. **비어 있으면 CSS 만으로 카드 전체가 자동으로 숨는다.** `init` 이 조건부로 마크업을 빼는 방식이
   아니라 `.step-detail:empty{display:none}` 과 같은 계열의 "내용이 비면 CSS 가 알아서 숨긴다"
   패턴을 재사용한다. 이 프로젝트는 Document PiP 때문에 이미 Chromium 만 지원 대상이므로
   `:has()` 를 안전하게 쓸 수 있다.
4. **갱신 메커니즘을 새로 만들지 않는다.** `step` 이 쓰는 grep-앵커 + Edit 방식(파일 전체를 읽지 않고
   대상 줄만 grep 해 그 전문을 `old_string` 으로 삼는다)을 그대로 적용한다. 토큰·복잡도 예산이 실제
   관심사다.
5. **기존 불변식·셀렉터 계약을 깨지 않는다.** 불변식 1(선형/매트릭스 비공존)과 충돌하지 않아야 하고,
   기존 「동적(치환 대상) — 7 셀렉터」 표는 **한 글자도 바꾸지 않는다**(새 셀렉터만 추가).
   회귀 테스트는 `tests/run.sh` 의 `test_dashboard_template_integrity`(T22) 에 T22-48 부터 이어 붙이고
   `total_tests=22` 는 유지한다.

### 사용자 스토리

> 전체 경로 작업을 돌리는 개발자로서, 「구현」 단계에 들어가 서브에이전트 두셋을 병렬로 붙여 놓은 뒤
> 화면 구석의 플로팅 창만 흘깃 보고 **"지금 어떤 세부 작업 둘이 돌고 있고, 남은 게 몇 개인지"**를
> 알고 싶다. 지금은 `3 구현 [진행중]` 한 줄이 두 시간 동안 그대로 떠 있어 곁눈질의 정보량이 0이다.

### 복잡도

**Medium** — 3파일. 신규 자산은 **CSS 1줄 추가 + 기존 CSS 1줄에 셀렉터 1개 추가 + 마크업 5줄 +
JS 함수 1개(5줄) + 절차 1개 절 신설 + 테스트 11개.** 새 모듈·새 레이어·새 의존성·새 색 토큰 없음.
레이아웃 CSS 는 **한 줄도 새로 쓰지 않는다**(설계 결정 2).

## 스코프와 비목표

### 스코프 안

- 「구현」 단계 전용 고정 슬롯 1개. 카드 1장, 세부 작업 목록 1개, 세부 진행 카운터 1개.
- 항목 상태 3종(`done`|`active`|`wait`)과 **동시 다중 `active`**.
- 항목별 한 줄 상세(기존 `.step-detail` 재사용). 담당 서브에이전트 표기는 이 상세 문자열 안에 넣는다.
- 목록이 비면 카드 자동 숨김(CSS `:has()`).
- 폴링 동기화 대상에 카드 추가(안 하면 브라우저에서 영구히 stale).

### 비목표 (명시적으로 만들지 않는 것)

| 제외 항목 | 사유 |
|-----------|------|
| **임의 단계에 하위 목록을 붙이는 범용 메커니즘** | 확정 사항 1. `step <n>` ↔ 슬롯 매핑, 슬롯 개수 관리, 슬롯별 셀렉터 네임스페이스가 전부 따라온다. 병렬 지점은 「구현」뿐이다 |
| **서브에이전트가 대시보드를 직접 갱신** | 확정 사항 2. `session-dashboard.md` 설계 결정 4를 정면으로 위반한다(별도 컨텍스트·파일 경합) |
| **서브에이전트 내부 실시간 진행률(%)** | 오케스트레이터가 알 수 없는 값이다. 알 수 없는 값을 그려내면 대시보드 전체의 신뢰가 깨진다 |
| **세부 작업 간 의존 관계·DAG 시각화** | 목록은 평면이다. 의존 관계는 항목 이름·상세 문자열로 충분하다(샘플도 "2·3과 병렬 가능"을 텍스트로 적었다) |
| **세부 작업이 매크로 진행률에 반영되는 것** | 불변식 6. 분모가 두 체계로 갈라지면 `step` 2단계의 전이(±1) 산술이 무너진다 |
| **세부 작업별 소요 시간·경과 타이머** | 새 스크립트가 필요하고, 이 커맨드는 "기계적 치환만" 이 대전제다 |
| **담당 에이전트를 위한 별도 필드(`data-agent`)** | 소비자(CSS·JS·절차)가 하나도 없다. 상세 문자열에 "에이전트 C" 를 적으면 끝난다(YAGNI) |
| **`impl clear` / 목록 재정의** | 아래 리스크 3. `init` 가드와 같은 철학으로 "파일을 지우고 다시 시작" 안내로 처리한다 |
| **매트릭스 모드에서 그룹별 서브태스크** | 목록은 세션당 하나다. 그룹 귀속은 항목 이름에 적는다(설계 결정 7) |

## 설계 결정과 근거

### 1. 셀렉터 접두어를 `dz-impl-` 로 한다 — `dz-sub-` 는 기존 셀렉터와 충돌한다

| 후보 | 판정 |
|------|------|
| `dz-sub-{k}` | **기각.** `#dz-subtitle` 이 이미 있다. `grep 'id="dz-sub'` 같은 느슨한 패턴이 제목 줄에 걸려 "결과는 항상 N줄" 전제가 조용히 깨진다. 이 저장소의 grep 앵커 방식과 최악의 궁합이다 |
| `dz-task-{k}` | **기각.** 이름이 스코프를 말하지 않는다. 확정 사항 1(「구현」 전용 고정 슬롯)이 이름에서 사라져, 다음 라운드에서 범용화 유혹이 생긴다 |
| `dz-impl-{k}` | **채택.** 기존 어떤 셀렉터와도 접두어가 겹치지 않고(`dzf-impl` 은 `dz-impl` 을 포함하지 않는다), 하위 명령 이름(`impl`)·카드 제목과 이름이 일치한다 |

이름이 스코프를 고정한다는 점이 중요하다. `#dz-impl-*` 라는 이름은 "이건 구현 단계의 것"이라고
마크업 자체가 말하므로, 별도의 `data-owner-step="3"` 같은 **소비자 없는 속성을 만들 필요가 없다**.

### 2. 세부 작업 목록에 `class="steps"` 를 그대로 준다 — 레이아웃 CSS 를 새로 쓰지 않는다

이번 설계에서 가장 큰 절약이다. `<ol class="steps" id="dz-impl-tasks">` 하나로 아래가 **전부 공짜**가 된다.

| 재사용 자산 | 얻는 것 |
|------------|--------|
| `ol.steps li` (flex + `flex-wrap` + `row-gap`) | 항목 한 줄 레이아웃과 상세 줄바꿈 |
| `.num` | 번호 배지. **인덱스가 화면에 보이는 것은 기능 요구다** — 호출자가 `impl <k>` 로 항목을 지정하려면 k 를 눈으로 알아야 한다 |
| `.chip`, `li.done .chip`, `li.active .chip`, `li.done`, `li.active` | 상태 색·굵기. 이 규칙들이 `ol.steps` 로 스코프되지 않은 **기존 사실** 덕분에 그대로 적용된다 |
| `.step-detail`, `.step-detail:empty` | 항목별 한 줄 상세와 빈 값 숨김 |
| `body.dz-pip ol.steps li…` 4줄 | PiP 압축 레이아웃 + active 배경 강조 + 비활성 상세 숨김 |

**중복 정의(`ol.impl-tasks{…}`)를 만들지 않는다.** 두 벌이 되면 한쪽만 고쳐 화면이 갈라진다.
T22-50 이 역방향 assertion 으로 `ol.impl-tasks` 규칙의 신설을 막는다.

**부작용 점검**: `class="steps"` 를 두 번 쓰면 `syncVisualization` 의
`querySelector('#dz-steps,#dz-matrix')` 가 헷갈릴까? **아니다 — 그 셀렉터는 id 기반이다.**
`#dz-impl-tasks` 는 매칭되지 않는다. 불변식 1(선형/매트릭스 비공존)도 id `dz-step-`/`dz-cell-`
에 관한 것이라 무관하다.

### 3. 자동 숨김은 `:has(li)` 로 한다 — `:empty` 는 이 자리에서 **작동하지 않는다**

확정 사항 3은 "`.step-detail:empty` 같은 관례를 재사용하라"였다. 관례(=내용이 비면 CSS 가 숨긴다)는
그대로 따르되, **의사 클래스는 `:empty` 를 쓸 수 없다.**

| 후보 | 판정 |
|------|------|
| `#dz-impl-tasks:empty{display:none}` | **기각.** 두 가지가 동시에 틀린다. (a) 템플릿의 빈 목록은 `<ol …>` 과 `</ol>` 이 두 줄이라 **내부에 개행 텍스트 노드가 있고**, `:empty` 는 공백 하나에도 매칭이 풀린다. (b) 목록만 숨어도 **카드 제목과 카운터는 남는다** — "카드 전체가 안 보여야 한다"는 요구를 못 맞춘다 |
| `init` 이 조건부로 카드 마크업을 뺀다 | **기각.** 확정 사항 3이 명시적으로 배제. `init` 에 분기가 생기고, `impl set` 시점에 카드를 통째로 삽입하는 별도 Edit 경로가 필요해진다 |
| 스크립트가 항목 수를 세어 `style.display` 를 대입 | **기각.** JS 상태가 늘고 폴링마다 재실행해야 한다. 이 커맨드는 "CSS 로 되는 건 CSS 로"가 원칙이다(`session-dashboard.md` 설계 결정 5) |
| `#dz-impl-card:not(:has(#dz-impl-tasks li)){display:none}` | **채택.** 규칙 1줄. 개행에 영향받지 않고, 숨기는 대상이 **카드 전체**다 |

`:has()` 를 쓸 수 있는 근거는 이 프로젝트가 이미 Chromium 만 지원 대상으로 못 박았다는 점이다
(`documentPictureInPicture in window` 로 전체 게이팅). **그리고 실패 모드가 가볍다** —
`:has()` 미지원 브라우저에서도 깨지는 게 아니라 **빈 카드가 하나 보일 뿐**이다.

### 4. 하위 명령을 새로 만든다 — `step` 을 확장하지 않는다

`step 3.1` 로 "3번 단계의 1번 세부 작업"을 표현하고 싶은 유혹이 있지만 **`<g>.<p>` 는 이미
매트릭스 칸 좌표다.** 같은 문법에 두 의미를 얹으면 `step` 0단계가 "지금 이 파일이 매트릭스인가"를
먼저 판단해야 하고, 판정 실패가 곧 엉뚱한 칸 갱신이 된다. 확정 방향 4("결정성 유지")를 정면으로 깬다.

| 후보 | 판정 |
|------|------|
| `step 3.1 active` | **기각.** 매트릭스 좌표와 문법 충돌. 판정 분기가 생긴다 |
| `substeps "…"` + `substep <k> …` | **기각.** 한 글자 차이 이름 두 개는 LLM 지시문에서 최악이다 |
| `impl set "…"` + `impl <k> …` | **채택.** 첫 토큰이 `set` 이냐 정수냐로 갈리는 단일 토큰 판정. 셀렉터 접두어·카드 제목과 이름이 일치한다 |

`init` 에 세 번째 인자로 목록을 받는 안도 **불가능하다** — 세부 작업 목록은 **PRP 가 승인된 뒤에야**
확정된다. `init` 은 그보다 앞선 착수 보고 시점에 불린다. 별도 호출 시점이 필연이다.

### 5. 폴링 동기화에 **행을 하나 추가한다** (이번 라운드에서 유일하게 스크립트를 건드린다)

직전 라운드는 "스크립트는 한 줄도 바뀌지 않는다"가 자랑거리였다. 이번엔 바뀐다. **안 바꾸면
기능이 조용히 반쯤 죽기 때문이다** — `apply()` 는 6개 대상만 동기화하므로, impl 카드는
`http://` 로 열린 브라우저와 PiP 창에서 **영원히 초기 상태로 남는다**(파일은 정상, 화면만 거짓).
`file://` 경로는 전체 리로드라 우연히 동작해서, **가장 알아채기 어려운 형태의 버그**가 된다.

| 후보 | 판정 |
|------|------|
| `syncVisualization` 의 셀렉터에 `#dz-impl-tasks` 추가 | **기각.** `querySelector` 는 **첫 매칭 하나**만 준다. 둘을 다루려면 함수 구조를 바꿔야 하고, 이미 T22-29~34 로 고정된 검증된 코드를 건드리게 된다 |
| `#dz-impl-tasks` 와 `#dz-impl-count` 를 각각 동기화 | **기각.** 함수가 둘로 늘고 계약 표에 행이 둘 는다. 얻는 게 없다 |
| `#dz-impl-card` 를 `outerHTML` 로 통째 교체 | **채택.** 함수 1개(5줄), 계약 1행. 카드 안에 **사용자 상태가 하나도 없다**(라디오 없음, `<details>` 없음) — `syncVisualization` 이 `#dz-steps` 를 통째 교체하는 것과 정확히 같은 근거다 |

기존 sync 함수 4개와 **문체가 같은 5번째 함수**를 추가하는 것이므로 새 메커니즘이 아니다
(확정 사항 4의 정신 유지). T22-51 이 함수와 호출의 존재를, T22-53 이 기존 `syncVisualization`
셀렉터의 비퇴화를 각각 고정한다.

### 6. PiP 압축 뷰에서 impl 카드를 **숨기지 않는다**

로그 카드는 숨기는데 이건 왜 안 숨기나 — **곁눈질 화면이 원하는 정보가 정확히 이것**이기 때문이다.
직전 라운드는 "PiP 에 남길 것 = 세션 제목 · 전체 진행 단계 · 현재 진행중인 단계"로 정리했고,
「구현」 구간에서 "현재 진행중인 것"의 실체가 바로 이 세부 작업 둘이다. 로그는 이력이고
이건 현재 상태다.

그리고 `class="steps"` 재사용 덕분에 **PiP 전용 CSS 를 한 줄도 안 써도** 원하는 동작이 나온다:
active 항목은 배경 강조가 들어가고, 비활성 항목의 상세는 숨는다
(`body.dz-pip ol.steps li:not(.active) .step-detail{display:none}`).

| 후보 | 판정 |
|------|------|
| `body.dz-pip #dz-impl-card{display:none}` | **기각.** 압축 뷰에서 가장 값진 정보를 버린다 |
| PiP 에서 `done` 항목만 숨겨 목록을 줄인다 | **기각(이번엔).** 규칙 1줄이면 되지만, 항목이 사라졌다 나타나며 목록이 위아래로 움직여 곁눈질에 오히려 방해다. 세로 공간 문제는 `resizePipToFit` 의 클램프와 스크롤로 이미 처리된다(리스크 4). 실사용에서 아쉬우면 그때 1줄 추가한다 |
| 그대로 보여준다 | **채택.** 새 CSS 0줄 |

T22-58 이 역방향 assertion 으로 "숨김 규칙이 몰래 들어오는 것"을 막는다.

### 7. 목록은 **평면**이다 — 매트릭스 모드에서도 하나뿐이다

매트릭스 세션(그룹 2개 이상)에는 「구현」 열이 그룹 수만큼 있다. 그룹별 서브태스크 목록을
만들면 슬롯이 N개가 되고 확정 사항 1(고정 슬롯 하나)이 즉시 깨진다.

**세션당 목록 하나로 두고, 그룹 귀속은 항목 이름에 적는다**(예: `"worktree — 파일 I/O"`).
절차에 분기가 생기지 않고(선형·매트릭스 어느 쪽에서도 같은 코드 경로), 참고 샘플도 정확히
이 방식이었다(항목 이름에 `0b ·`, `2·3과 병렬 가능` 같은 맥락을 텍스트로 넣었다).

### 8. `impl set` 은 항목을 **전부 `wait` 으로** 만든다

`init` 은 1번 단계를 `active` 로 만든다. `impl set` 은 그러지 않는다. 목록 정의와 디스패치는
**다른 시점**이고, 아직 부르지도 않은 서브에이전트를 진행중으로 그리는 순간 이 패널의 유일한
신뢰 근거(확정 사항 2 — 관측된 두 시점만 기록)가 무너진다. 디스패치할 때 `impl <k> active` 를
부르면 된다. 호출 1회를 아끼려고 정직성을 파는 거래는 하지 않는다.

### 9. 세부 진행률 텍스트를 매크로와 **같은 형식**(`M/K · P%`)으로 둔다

바가 없으니 `%` 를 뺄 수도 있지만, `impl <k>` 2단계는 `step` 2단계의 파싱·전이 산술을
**문장째 재사용**한다. 형식이 갈리면 절차가 두 벌이 된다. 형식을 맞추는 대가는 P 를 한 번
더 계산하는 것뿐이다. (`dashboard-group-matrix.md` 설계 결정 7이 이미 같은 판단을 했다.)

## 리스크와 대안

### 1. "실시간 진행률"로 오인될 수 있다 — 이번 라운드의 최대 리스크

**가능성 상 / 영향 중.** 항목이 `진행중` 으로 20분째 떠 있으면 보는 사람은 "지금 그 작업이
돌고 있다"고 읽는다. 실제로는 "디스패치했고 아직 보고가 안 왔다"뿐이며, 서브에이전트가
실패해 멈춰 있어도 화면은 동일하다.
**완화**: (a) 카드 제목에 `· 디스패치와 결과 보고 시점에만 갱신` 을 **상시 노출**,
(b) `impl` 절 서두의 한계 문단을 T22-55 가 문구째 고정, (c) `#dz-updated` 가 계속 보여
"언제 마지막으로 갱신됐는지"가 함께 읽힌다.
**기각한 대안**: 항목에 경과 시간 타이머를 붙인다 → 새 스크립트가 필요하고, "오래 걸림"과
"멈춤"을 구분해 주지도 못한다.

### 2. `impl` 호출을 빠뜨려 목록이 화석이 된다

**가능성 상 / 영향 하.** 서브에이전트를 셋 붙여 놓고 `impl <k> active` 를 안 부르면 목록이
전부 `대기` 인 채 남는다. `step` 도 같은 성격의 리스크를 이미 안고 있다(지시문 방식의 근본 한계).
**완화**: 트리거 표에 **디스패치 직전 / 결과 수령 직후**라는 구체적 시점을 못 박았다.
자동화(hook)는 `session-dashboard.md` 설계 결정 4에서 이미 기각된 방향이라 다시 꺼내지 않는다.

### 3. 세션 2에서 이전 세션의 목록이 남고, 재정의가 막힌다

**가능성 중 / 영향 중.** `init` 가드가 기존 대시보드를 재렌더하지 않으므로, 같은 프로젝트에서
새 전체 경로 작업을 시작하면 지난 세션의 세부 작업 목록이 그대로 보인다. 그 상태에서
`impl set` 을 부르면 가드에 걸려 중단된다.
**완화**: 가드 메시지가 "`.claude/dashboard.html` 을 지우고 `init` 부터 다시 하라"를 안내한다.
이는 `init` 가드의 알려진 한계(현행 문서 L307~311)와 **정확히 같은 성질·같은 해법**이다.
**기각한 대안**: `impl clear` 하위 명령 추가 → 문법이 하나 늘고, 오호출이 진행 상태를 날리는
경로를 새로 만든다. 파일 삭제 한 번이 더 싸다(YAGNI).

### 4. 항목이 많으면 PiP 창이 스크롤된다

**가능성 중 / 영향 하.** 14항목이면 `.wrap` 실제 높이가 `PIP_MAX_HEIGHT`(720px)를 넘어
클램프되고 아래쪽이 스크롤된다.
**완화**: 클램프·스크롤은 이미 구현돼 있고(`resizePipToFit`), active 항목은 배경 강조가 있어
찾기 쉽다. 수동 확인 17이 이 상태를 직접 본다.
**기각한 대안**: PiP 에서 `done` 항목 숨기기 → 목록이 위아래로 움직여 곁눈질에 오히려 방해다
(설계 결정 6). 실사용에서 아쉬우면 CSS 1줄로 나중에 켠다.

### 5. `:has()` 미지원 환경

**가능성 하 / 영향 하.** 이 프로젝트는 이미 Chromium 만 지원 대상이지만, `file://` + 구형
브라우저 조합이면 `:has()` 가 무시된다.
**완화**: 실패 모드가 **"빈 카드가 하나 보인다"** 뿐이다. 데이터도 절차도 깨지지 않는다.
**기각한 대안**: `:has()` 없이 JS 로 개수를 세어 숨기기 → 폴링마다 재실행해야 하고 CSS 원칙을 깬다.

### 6. 스크립트를 건드리는 첫 라운드라 폴링 계약이 퇴화할 수 있다

**가능성 중 / 영향 상.** `apply()` 를 편집하면서 `resizePipToFit()` 호출 순서를 바꾸거나
`syncLog` 를 밀어내면 직전 두 라운드의 성과가 조용히 죽는다.
**완화**: T22-43(`syncLog`)·T22-47(`resizePipToFit`)·T22-53(`syncVisualization`)이 세 방향에서
고정한다. 구현 순서 Task 4의 GOTCHA 에도 명시했다. **검수자는 이 지점을 중점 항목으로 본다.**

### 7. 세부 카운터와 실제 상태가 어긋난다

**가능성 중 / 영향 하.** 전이(±1) 산술은 "이전 상태를 정확히 읽었다"에 의존한다. `step` 이
이미 같은 구조를 쓰고 있고, 이전 상태는 0단계 grep 결과 줄에 그대로 적혀 있어 기억에
의존하지 않는다.
**완화**: 감사용 재계수 명령(`grep -c 'dz-impl-[0-9].*class="done"'`)을 절차에 명시.
수동 확인 7이 이를 직접 돌린다.
